§3 — attachment integrity, batch versioning, and version ordering (2026-07-27)

The RC was deliberately NOT cut this session. The plan's course correction said to stop treating the naming residual as blocking and cut the RC. Then a pre-flight check of the batch found 11 accepted WEST names whose unit contradicts their own DD source (354 graph-wide), including a divertor strike-point coordinate attached to a camera up-vector. The lead's direction was explicit: "this is CRITICAL. the backing graph data needs to be correct … all such occurrences should be properly root caused and fixed."

So the sequencing was inverted: correctness first, RC after. PR'ing a batch with known-faulty names would spend the stage-3 reviewer's attention on defects we already knew about — the opposite of what the rehearsal is for.

The root cause: a guard at the caller, not at the boundary

_is_attachment_consistent already rejected the worst live case. Asked directly, it refuses summary/boundary/strike_point_inner_z/value → z_image_up_unit_vector_of_camera with "locus/source device mismatch". Yet that attachment was in the graph, on an accepted name. The guard was reachable from exactly one module — compose, in workers.py — so an audit of every write path that can create a source→name edge found 13 of 15 ungated:

  • persist_refined_name is an active laundering channel. A refine migrates every source from the predecessor onto the successor wholesale, with no re-validation against the new name. That is how the strike-point source reached a camera name after compose had correctly refused it.
  • retarget_standard_name_sources (three call sites) and bind_sources_exclusively (the catalog-import path) move bindings the same way; the first also deletes competing historical edges, so an ungated rename both mis-attaches and destroys the evidence.
  • The guard had no dimensionality rule, so physically distinct quantities collapsed onto one name.

Healing the data alone would not have held: the bad edges return on the next refine rotation. Both halves were needed — write-time gates plus a retroactive re-validation of every existing edge.

Version ordering (imas-standard-names)

The catalog site's version dropdown read rc64, rc9, rc8, rc7, rc63, rc62 …. The cause was NOT the SPA: versions.json is written by ISN's own catalog/gh_pages.py, whose _SEMVER_RE requires a prerelease to start with - or +. rc64 starts with r, so no version matched at all and every entry fell through to a plain string sort. Two further defects in the same key: the rc number compared as a string, and the final-vs-prerelease rule was inverted — with the docstring and the very next comment contradicting each other. Fixed at the source (8b45a46) and defensively in the SPA (b27c5fb, so the already-deployed site renders correctly without a redeploy), plus build-metadata support (c960740): matched, displayed, and excluded from precedence, with a stable sort so equal-precedence entries keep their order. Verified against the real 65-entry deployed list.

Open, with the mechanism established

  • The DD pin guard aborted every unscoped run. 8741 sources are pinned at 4.1.0 against a configured 4.1.1. The lead's rule settles the design: "we should not re-extract on a DD bump, we should track provenance … in-work items should take the DD version and metadata from that version." A pin is immutable; a pin behind the current DD is ordinary state, not staleness. The seeder was stamping the current version onto every source and merging without the batch default, so a re-seed collided with its own stored pin — while the correct mechanism (default_dd_version, which pins only genuinely-new sources) already existed and every other caller used it.
  • sn edit --hint reaches only 24 of 86 sources for the names under repair, so 62 would regenerate unsteered. Paid review is deliberately held until this is fixed: reviewing candidates that never saw the hint spends budget twice. Every hint-steered edit made before this fix was weaker than it appeared.
  • The gm1–gm7 collapse. Seven distinct flux-surface metric coefficients across four dimensionalities were collapsed onto three names. radial_flux_surface_averaged_metric carries two HAS_UNIT edges — the only such node in the graph, and a schema-cardinality symptom of the collapse. Verified from DD text at the configured version: gm1=<1/R²>, gm2=<|∇ρ|²/R²>, gm3=<|∇ρ|²>, gm4=<1/B²>, gm5=<B²>, gm6=<|∇ρ|²/B²>, gm7=<|∇ρ|>.
  • The line-of-sight split. ~40 /r paths on one name while the matching /z paths are split across two names on no principle, one of which has also swallowed pure-geometry thick_line paths that are not beam tracing at all. No unit contradiction, so it never appeared in the 354 — a same-name/different- quantity fault spanning ~110 attachments. One of the two names is human-edited and protected; repairing it needs the lead's explicit authorization.
  • Dead code: build_unapproved_cleanup_manifest has no callers and no tests (the one-off whose stale output was deleted this session). find_semantic_source_invariant_violations likewise — but it encodes a real invariant, so it should be wired in as a graph-quality test rather than deleted; an unwired checker carries no signal.
