Where a wrong attachment comes from (2026-07-28)

The headline: applying the guard at more call sites would not have caught the line-of-sight fault. Called directly, post-fix, with units and populated siblings, the guard accepts every one of the offending pairs. Both sides are metres, so the dimensionality rule is silent; the locus tokens (beam_tracing_point, sight) are not hardware words, so the locus rule never fires. This fault class sits outside the rule set entirely.

Two separate things were therefore conflated in the earlier framing: WHERE the guard is called (a coverage question, four real gaps below) and WHAT the guard can judge (a rule question — it needs a new rule).

The line-of-sight split, root-caused

185 live attachments across 15 names, with 10 DD leaves carrying two names at once. The axis asymmetry is stark: /r resolves to one name (64 attachments, clean), /z splits across two (43 + 23), and /phi splits across two (41 + 3).

It was not a refine, and not an edit cascade

The boundary is provably arbitrary. Bucketing every /z object by its ordinal-stripped stem: 17 objects keep all ordinals on one name; 13 are split with no rule at all. soft_x_rays puts first-point on the beam name and second-point on the sightline name; interferometer does the exact opposite; bolometer puts first-point on BOTH. No ordinal rule, no device rule, no consistent direction — which also rules out the ordinality bug as the boundary-drawer, since that would have partitioned by ordinal.

What actually froze it: a dedup invariant that exempts human edits

supersede_prior_source_names enforces "one source, at most one non-superseded name". Its selector carries AND coalesce(old.origin, 'pipeline') = 'pipeline' — the dedup exempts catalog_edit by design, as catalog-authoritative.

So the July-22 recompose retired every competing pipeline name and left the catalog one standing. /r had two pipeline lineages — both foldable, one clean name. /phi had three, and the catalog name was the fold target, so it converged. /z had one foldable pipeline lineage and one unfoldable catalog rival, so it stayed split. The whole axis asymmetry falls out of which side of that one predicate each lineage landed on.

The catalog name's 43 sources were replayed from a July-3 snapshot (catalog_commit_sha a2f8831c…, the documented recovery reference) via bind_recovery_sources — reinstating the attachment set as it stood before the July-22 recompose, thick_line included. Zero inbound REFINED_FROM and no matching change record confirm no refine or edit ever touched it. Both /z names then took new sources in the same hour: with two accepted names live, auto-attach picked whichever scored closer.

Why the thick_line paths do not belong, per the DD

The DD defines the parent as: "The element is approximated by a rectangle defined by a central segment and a thickness in the direction perpendicular to the segment." So thick_line/first_point/z is an endpoint of the central segment of a rectangle approximating a solid conductor's poloidal cross-section — one of five interchangeable conductor-geometry representations selected per element by geometry_type. Every affected IDS is structural hardware: pf_active, pf_passive, pf_plasma, iron_core, ferritic, ic_antennas/…/strap. No beam, no sightline, no optics.

They must not simply be rebound to the *_outline_of_* family — that is the DD's separate polygon representation, and it is already damaged: vertical_outline_of_antenna_strap has swallowed 15 unrelated paths (cryostat, vessel, contour-tree, iron-core outlines), and radial_outline_of_coil_conductor_element is sourced from an arcs_of_circle path — different IDS and different representation. A separate defect, not yet sized.

Write-path verdicts

Two corrections to the earlier framing: derivation.py has no graph writes at all, and parents.py has none either (three read queries only). The derived-parent writes live in graph_ops.py.

The plan's stated tension — "gating a faithful reconstruction with a newer rule would destroy history rather than protect it" — is valid but was applied too broadly. It holds for a path that re-establishes an edge against the same name, or that builds scaffolding the guard was never calibrated for. It does not hold for a path that migrates a source set onto a different name: the set is historical, but the pairing is brand new, and a brand-new pairing is exactly what the guard exists to judge. Filing those under "history" is what left the biggest hole.

Needs a write-time guard

  • persist_refined_name steps 4/5 — migrates the predecessor's entire PRODUCED_NAME and HAS_STANDARD_NAME set onto the successor with no guard call. Consistent-with-radial_line_of_sight is not consistent-with-radial_coordinate_of_line_of_sight. This is how conductor vertices rode onto sightline names as passengers of a lineage fold.
  • write_standard_names — the bulk persist writes the DD-side projection with no guard at all, so an import-shaped batch bypasses the compose gates entirely.
  • bind_sources_exclusively / retarget_standard_name_sources — exclusive rebind onto a different name is a fresh claim about every source moved, and it deletes the prior edges, so an ungated rename both mis-attaches and destroys the evidence. Being exclusive makes it more consequential, not less.
  • reconcile_standard_name_dd_edges — already applies the unit rule and routes disagreements to triage, the closest to correct; it should call the full guard rather than the unit rule alone. Cheap and purely additive.

Must NOT be gated

  • The derived-parent materializer — a deterministic grammar peel producing structural scaffolding, not a physics claim. The guard's lexical rules are leaf-calibrated and would systematically reject legitimate abstractions, the same construction bias that makes parent enrichment skip the name quorum. Admission is the parent gate's job.
  • The orphan-parent reconcile — repairs scaffolding for an already-admitted parent; gating a repair with a rule that never governed the creation would orphan the parent.
  • The provenance edge reattach — a pure desync heal that invents nothing. Gating it turns silent loss into permanent loss. If the pair really is bad, the retroactive pass detaches it with an audit record — the correct order.
  • The recovery-snapshot replay — faithful replay; gating against today's rules would silently narrow a recovery. But it is a non-exclusive MERGE, so it left the July-3 set coexisting with the July-22 recompose. The fix is not a write-time guard but a mandatory consistency reconcile immediately after any rebuild, in the same operation.

Two gaps in the guard itself

  1. A geometry-representation rule is missing. A path under …/geometry/{thick_line,outline,rectangle,oblique,arcs_of_circle}/… must not realize an optical-locus name, and vice versa. Without it population A stays invisible to both gates.
  2. The compose gate is WEAKER than the retroactive pass. _process_attachments_core calls the guard without dd_unit/sn_unit, so the dimensionality rule is skipped at write time and only ever applied retroactively. Pass the units.

Correction to an earlier record
