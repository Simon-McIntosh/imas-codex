§8 — Jev rerank in DD-path search

The candidate stage already reranks DD paths with Jev for each source. The search_dd_paths tool, which a person uses to check or correct a binding, does not. discovery-judgments-through-jev §9 is building a search-time Jev rerank for code and wiki search; its prototype raised nDCG@10 from 0.25 to 0.51. The DD-path tool reuses that rerank owner and does not build a second one. Its own measure uses mapping questions: the plasma current's homes, where flux-loop positions live, which IDS holds a coil current.

§9 — Enrichment context through the Jev rerank

Signal enrichment grounds each description on code and wiki context fetched by embedding order alone. _fetch_code_chunks (imas_codex/discovery/signals/parallel.py:216) keeps the vector top 3 above a 0.45 floor. fetch_semantic_wiki_context (imas_codex/discovery/signals/scanners/wiki.py:266) keeps the top 3 to 5 above a 0.35 to 0.4 floor. discovery-judgments-through-jev §9 measured embedding order at nDCG@10 0.246 against 0.509 after a Jev relevance rerank on JT-60SA code and wiki questions, and its node search-rerank builds the rerank owner. This section is that owner's consumer for enrichment, as §8 is for DD-path search. It adds no second rerank.

Each fetch retrieves wide: the 30 nearest chunks above its existing floor. It passes them, with the enrichment query text it already builds (the source's group key and member names), to the generic retrieve-wide-then-rerank core in imas_codex/discovery/base/judgment.py. It keeps the Jev-ranked top 3 for code and the existing count for wiki. When the rerank returns no ordering, through a failed call, a spent budget or an unreachable decision service, the fetch keeps embedding order and logs why. That is the owner's own fallback, so enrichment never stops for want of a ranking. The decision spend is added to the enrichment run's cost total, so the §2 cap covers it.

Write paths: imas_codex/discovery/signals/parallel.py, imas_codex/discovery/signals/scanners/wiki.py and tests/discovery/test_enrichment_context_rerank.py. Done when uv run --no-sync pytest tests/discovery -p no:cacheprovider passes, with tests showing:

  • each fetch requests 30 candidates and calls the rerank owner with the enrichment query and each candidate's text;
  • it keeps the reranked top k in Jev order;
  • it falls back to embedding order when the owner returns no ordering;

The recommendation is after the audit, per IDS. Validation checks that a binding executes, not that it chose the right home.
