§2 — Enrich the JT-60SA signals

Run imas-codex discover signals jt-60sa --enrich-only from the ITER host. Enrichment claims only standalone signals and the representatives of SignalSources (build_enrich_claimable_predicate, imas_codex/discovery/signals/parallel.py:317). That is 267 representatives, whose enrichment propagate_source_enrichment copies to the 3,565 members and to each source, plus the 1,969 standalone signals: 2,236 claims. It reads only the graph and the LLM, and needs no facility access. The census categories cost about USD 1 for 764 signals, so this run is estimated at USD 3, under a USD 5 cap. discovery-judgments-through-jev later moves signal-enrichment judgments to Jev and re-judges stored rows from the graph. This run does not wait for it.

§3 — Every signal reaches the map

Every stage of the mapping pipeline keys on SignalSource: the candidate claim, the MAPPING_CANDIDATE edges and the MAPS_TO_IMAS bindings. A signal that grouping left alone has no source, so the 1,969 standalone JT-60SA signals can never be mapped. The recommended repair, under the decision below, gives each standalone enriched signal a singleton SignalSource. The signal is its only member and its representative. The source is made by the existing owner of SignalSource creation, create_signal_source (imas_codex/discovery/base/grouping.py:26), so the mapping pipeline keeps one unit and needs no change. The repair is facility-independent, and JT-60SA is where it is measured.

Node singleton-signal-sources, role implement, 1.5 h. Write paths: imas_codex/discovery/base/grouping.py, imas_codex/discovery/signals/parallel.py and tests/discovery/. Done when uv run --no-sync pytest tests/discovery tests/ids -p no:cacheprovider passes with tests showing that an enriched standalone signal gains a singleton source carrying its enrichment; that re-running creates none twice; and that claim_sources_for_candidates claims the singleton. A live run then leaves no enriched JT-60SA signal outside a source.

§4 — EDDB units reach Unit nodes

The map stage writes unit conversions, and it reads each source's unit to do so. EDDB stores units as free text. 1,482 JT-60SA signals carry a unit normalize_unit_symbol (imas_codex/units/__init__.py:96) cannot parse, among them uST (480), n/day (371), MPaG (187), KA, DEG, DegC, oC, KV and the Pa*m3/s family. No JT-60SA signal is linked to a Unit node. jt60sa-discovery-completion parked this as followup f-jdc-004 because it belongs to DD binding, and this plan adopts it.

Facility spellings join the pint definitions the normaliser already loads, in a facility-unit alias file beside data_dictionary_unit_aliases.txt. That keeps one parser and one definition mechanism. A spelling that names no physical unit is listed as unresolved with its count, never guessed. Unit is one such spelling; gauge pressure (MPaG) is another, because it is not an absolute pressure. EDAS signals are then linked to Unit nodes the way the MDSplus path links its signals.

Node eddb-unit-normalisation, role implement, 2 h. Write paths: imas_codex/units/, imas_codex/discovery/signals/ and tests/units/. Done when uv run --no-sync pytest tests/units tests/discovery -p no:cacheprovider passes, and a live census shows each of the 76 JT-60SA unit strings either normalised or listed as unresolved with its count and reason. Every signal with a normalised unit has a HAS_UNIT edge.

§5 — Candidates for every JT-60SA source

Each source gets the Jev IDS routing, the DD shortlist from hybrid_dd_search reranked by Jev's same_quantity judgment, and the cross-IDS cluster siblings from mapping-candidate-selection §11. It records the measured seconds per source, so the decision about adding workers rests on a number.

§6 — Every home, audited

Draw 40 JT-60SA sources across the EDAS categories. Label each for every DD home it has, in any IDS, without seeing its candidates. Unlike the mapping-candidate-selection §3 labels, the IDS is not fixed first, so a second home such as the plasma current's measured constraint in equilibrium is scored. Under the recommended defaults every source routes escalated, so the measures read the stored candidate edges:

  • the share of labelled homes whose section is in the source's escalated list (its top five and their cluster siblings), and the same share at node level;
  • how many sources have homes in two or more IDSs, and how many of those homes the list carries;
  • section-level precision of a Jev-alone selection at the §3 thresholds, computed from the stored probabilities;
  • the share of sources with no DD home that a floor of 0.1 would have caught.

Node jt60sa-candidate-audit, role implement, 2 h. Write path: docs/evidence/fragments/jt60sa-imas-maps/jt60sa-candidate-audit.html. Done when the fragment states each measure above, and lists the 40 sources with their labelled homes and their escalated lists.

§7 — Map JT-60SA

Run imas-codex imas map run jt-60sa once for each IDS that holds a candidate, with --no-activate and under a USD 10 cap on the reasoning seat. After mapping-candidate-selection §8, the assign stage asks the reasoning model to pick every listed home for each escalated source. The map stage then maps each source into every IDS of its picks, checking each mapped field against the picked node's section. Validation runs per IDS. Activation is a separate decision, made after the audit.

Node jt60sa-map-run, role implement, 2.5 h over resumes. Write path: docs/evidence/fragments/jt60sa-imas-maps/jt60sa-map-run.html. Done when the fragment states, per IDS, the bindings written, the validation outcome and the spend. 30 bindings drawn across IDSs are audited by hand for target, units and sign convention, and the fragment reports their section-level precision with every disagreement listed.

§8 — Jev rerank in DD-path search

The candidate stage already reranks DD paths with Jev for each source. The search_dd_paths tool, which a person uses to check or correct a binding, does not. discovery-judgments-through-jev §9 is building a search-time Jev rerank for code and wiki search; its prototype raised nDCG@10 from 0.25 to 0.51. The DD-path tool reuses that rerank owner and does not build a second one. Its own measure uses mapping questions: the plasma current's homes, where flux-loop positions live, which IDS holds a coil current.

Node dd-path-search-rerank, role implement, 2.5 h, after the gate below. Write paths: the DD search tool module and its tests, named at dispatch from the rerank owner that section lands. Done when nDCG@10 on 15 hand-labelled mapping questions is reported before and after the rerank, and the rerank is one call into the shared owner.

§ Decisions

How does a signal in no SignalSource reach the mapping pipeline?

The recommendation is a singleton source. Every mapping stage, edge and claim keys on SignalSource. A singleton keeps one unit of mapping, while claiming signals directly would need two units through every stage.

When are JT-60SA mappings activated?

The recommendation is after the audit, per IDS. Validation checks that a binding executes, not that it chose the right home.
