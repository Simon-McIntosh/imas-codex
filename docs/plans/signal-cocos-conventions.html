§1 — The convention is a property of the signal, settled before the map

The map stage writes a binding's sign and 2π factor from two facts: the target field's COCOS transformation class, which the Data Dictionary (DD) declares on 553 IMASNodes, and the source's own convention, which nothing in the graph declares today. Enrichment writes a free-text sign_convention (86 of 46,872 JET signals and 18 of 15,018 JT-60SA signals carry one) and FacilitySignal.cocos is set on 12 JT-60SA signals and no JET signal. mapping-decision-chain §4 settles a slot in code only when the source's convention is known, so without this plan every COCOS-labelled binding becomes an open slot that a model guesses.

This plan adds a conventions stage between signal enrichment and the candidate stage. It runs a branching network of bounded decisions over each enriched SignalSource. Jev first answers whether the quantity's sign or 2π normalisation depends on the coordinate convention at all. A convention-independent source is recorded as none, and its binding later needs at most a unit translation. For a dependent source, Jev chooses its transformation class among the DD's labels, from options templated with real DD exemplars of each class, and chooses its writer: a raw diagnostic, a named reconstruction code, or unknown. Code then validates the convention against facility data and persists the class, the COCOS survivors, the COCOS when it is unique, a confidence and the evidence. The signal's values are never transformed here; the map applies one transform, once. A result below the acceptance threshold is marked for followup, which signal-evidence-followups turns into a triage loop.

What data can and cannot settle. imas-ambix measured this on MAST in imas-ambix:machine-map-cocos-transform, and the result bounds what this stage may claim. The sign of σBp is measurable from raw magnetics: on 56 of 56 channel-shot relations a flux loop's response opposed the measured plasma current. The 2π exponent eBp needs an external declaration such as the units of ψ, because array values cannot establish it. The handedness σRφZ is not determinable from data at all: it is how the facility defines positive φ, so it must be declared. A first verdict there picked COCOS 4 over 3 from the point ordering of a reconstructed boundary, which is a serialisation choice, and was overturned; COCOS 3 and 4 both survive the MAST data. Outputs of a reconstruction code carry the code's convention, not the machine's. A single current polarity cannot separate a convention error from a current-sign error, so both polarities are required.

The map does not need the COCOS number, only the factor of the target's class. ψ's factor depends on σBp and eBp alone, so a psi_like binding is settled when the survivors are {3, 4}, while an ip_like binding is not. This stage therefore persists the survivor set, and the map settles a slot in code exactly when every survivor gives the same factor for that slot's class.

Oriented sensors carry their convention in their geometry. The DD labels a pickup coil's magnetics/b_field_pol_probe/field one_like and its poloidal_angle pol_angle_like, so a convention change rotates the probe's orientation rather than flipping the field. A flux loop's ψ sign also depends on its orientation. imas-ambix's JT-60SA machine map settles such per-channel signs (its channel_factor) from SELENE-deck geometry, loop-reference fits and vacuum-field predictions from coil currents. §6 puts that geometry in the graph so these judgments and the map can read it.

The facility-level prior, the predominant COCOS and the declared machine orientation, comes from the conventions block jt60sa-discovery-completion §56 adds to facility_config.yaml. This stage reads it when present and never treats it as proof: every run checks it against data, and a source whose data disagrees with the prior keeps its own convention.

§3 — Convention properties on the signal source

The SignalSource is the mapping unit, so it carries the convention. It gains convention_dependent with its Jev probability p_convention_dependent; cocos_class, from a new enum holding none, the seven non-trivial DD labels (psi_like, dodpsi_like, ip_like, b0_like, q_like, tor_angle_like, pol_angle_like) and compound; cocos_class_distribution, the Jev choice distribution as JSON; convention_writer; cocos_survivors, an integer list; cocos, set only when the survivors are one convention; cocos_confidence; convention_status from a new enum (judged, probed, settled, needs_followup); convention_question, the open question a followup carries; timestamps; and claim fields for the stage's claim loop. An absolute and a differential measurement are different quantities in different sources (§9), so a difference's order is a property of its source, not a per-member exception. A member whose installation reverses its sign within an otherwise identical group, such as a pickup coil mounted the other way round, keeps that on FacilitySignal.channel_sign.

A new ConventionObservation node records one sign read from facility data: facility, shot, quantity, observed sign, the plasma-current sign of that shot, the DataAccess used and when. It links OBSERVED_FOR to the source, so a later reader can recompute every verdict.

§4 — Jev judges dependence, class and writer

One decisions request per source carries four questions, which Jev answers in parallel: a noul on whether the quantity's sign or 2π normalisation depends on the coordinate convention; a choice of transformation class, whose premise is stated as "if it depends"; a noul on whether a reconstruction or analysis code wrote the value rather than a diagnostic measuring it; and a choice of writer among the facility's codes, a raw diagnostic, and unknown. Code consumes the class and writer answers only when the dependence answer applies.

Each class option is templated from the DD, not written by hand. Its criteria hold the label's definition from the COCOSLabelTransformation enum and up to five exemplar DD fields of that class, with their documentation and units. The exemplars come from the same graph query the imas-cx get_dd_cocos_fields tool serves, run in process, preferring fields in the source's physics domain and resolving a label carried on a structure to its data leaves. The state holds the source's description, unit, members and free-text sign convention, its reranked code and wiki context through rerank_pool, its geometry from §6 when present, and the facility prior. The answers go to the §3 properties through the shared judge_rows core in imas_codex/discovery/base/judgment.py, on a new signal-conventions seat.

§5 — Facility data validates the convention

A convention is accepted only after facility data has been read against it. For each convention-dependent source, code reads signs at reference shots of both plasma-current polarities through the source's DataAccess template: the flat-top sign of an ip_like or b0_like source against the facility's declared Ip and Bt directions, the sign of a raw flux loop's ramp-up response against Ip for σBp, and the sign of q against Ip·Bt. Angle classes read the §6 geometry instead of a time trace. Each read is a ConventionObservation.

The observations score the sixteen canonical conventions (1 to 8 and 11 to 18) through cocos_to_parameters. Each coefficient is classified as measured, measurable only as a product, or requiring a declaration; a declared handedness from the facility prior narrows the survivors, and an undeclared one leaves them split. A set of observations no convention fits is recorded as not COCOS-expressible, never rounded to the nearest. The class factor is unanimous or split across the survivors, and the confidence falls when a polarity is missing.

§9 — Absolute and differential measurements are separate sources

The lead ruled on 2026-10-09 that an absolute and a differential measurement are different signals and belong to different sources. A differential flux loop measures ψL − ψref: still psi_like, but a different quantity, whose DD home is a magnetics/flux_loop entry whose type names it differential and whose indices_differential names the two loops. Its sign includes the order of the difference, which is a property of the source. On JT-60SA flux loop 7 is the only absolute loop and the other 26 are differential entries [7, L], per the SELENE deck's type-6 entries and imas-ambix's loop-reference study.

The graph does not group them that way. detect_signal_sources keys groups on digit runs in the accessor, so loops 1 to 9 are one-member sources and loops 10 to 27 share one 25-member source; loop 7 stands alone only by accident. The measurement kind comes from the sensor geometry §6 ingests: each SensorGeometry records whether its sensor is absolute or differential and, when differential, its reference sensor. A regroup in imas_codex/discovery/base/grouping.py then makes each source hold one kind: it moves members, links each differential source REFERENCES its reference sensor's source, records SPLIT_FROM or MERGED_INTO with the reason and time so the change is traceable like a rename, and clears the convention and candidate state of every source it changed so they are judged again.

§ Decisions

Do sensor positions and orientations live in the graph, so every judgment and map prompt can read them?

Lead ruling 2026-10-09, accepting the recommendation: geometry is small, static per operation phase, and read by the convention judgment, the probe for angle classes and the map for geometry targets and index consistency; fetching it from facility files at judgment time would make the map depend on facility access.

Where does the convention live: on the SignalSource, or on each FacilitySignal?

Lead ruling 2026-10-09: the SignalSource carries the convention because it is the unit one binding maps. The lead amended the channel-sign example: absolute and differential measurements are different signals in different sources (§9), so a difference's order is a source property; channel_sign stays only for a member whose installation reverses its sign within an otherwise identical group.
