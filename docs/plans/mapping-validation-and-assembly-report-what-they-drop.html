§2 — A transform result must fit its target's dimensionality

validate_mapping (imas_codex/ids/validation.py) proves a transform executes by running it through _probe_transform. That tries a scalar first, then a length-4 array when the expression indexes its input. Nothing compares the result with the target node's data_type, although check_dd_paths already returns it with the target's existence check. So a slice such as value[0:2] bound to a scalar field passes validation, and the wrong-shaped value reaches assembly.

The repair returns the probe's result and compares it only where the comparison is decidable from synthetic inputs:

  • A target whose data_type ends in _0D needs a scalar result: a Python number or a zero-dimensional numpy value.
  • An array result records the check error transform returns an array for a scalar target.
  • Targets of higher dimension get no new refusal, because the probe cannot know the real source's shape.

§3 — Assembly reports every mapping it did not place

IDSAssembler._apply_mappings (imas_codex/ids/assembler.py) skips three kinds of active mapping:

  • one whose target lies outside the section, with a bare continue and no log at all;
  • one outside the configured nested path, now logged as a warning;
  • one whose final set fails, now logged as a warning.

A warning in a log still leaves the built IDS silently missing those fields, and the first kind leaves no trace. The extraction path reports success, and the commands that call the assembler (imas_codex/cli/imas_dd.py, the IDS show and export commands) print nothing about it.

The repair makes every skip part of the result. The assembler collects one entry per unplaced item and exposes the list after assemble(). Each entry carries the reason (outside_section, outside_nested_path, set_failed with the error text, or §4's missing_member) and the target path. A mapping's entry also carries the mapping id; a gap carries the member number instead, because no mapping exists for it. The CLI commands print the count and the entries, and how a non-empty list ends an export is the decision below.

§4 — Array members keep their facility number

For an array_per_node section the assembler resizes the struct array to the number of nodes it read and fills element i from the i-th node. The node query (select_nodes in imas_codex/ids/graph_ops.py) orders by the numeric suffix of the node path. So members 1, 2 and 3 land at elements 0, 1 and 2, as they should. A gap breaks it: with members 1, 2 and 4, member 4 lands at element 2, where a consumer reading coil(3) by position expects member 3. Its current is then bound to the wrong coil's geometry, silently.

The repair places member n at element n − 1. It sizes the array to the largest member number, leaves an empty element at each gap, and lists each gap in §3's skip report with reason missing_member. Members whose path carries no number keep today's rank order, and the report says so.

§5 — No writer creates an active mapping

create_imas_mapping (imas_codex/ids/graph_ops.py) writes m.status = 'active' when it creates a mapping. That is the one path that would skip generated and validated altogether. Only tests/ids/test_graph_ops.py calls it today. The project has no backwards-compatibility obligation, and activation already has its own guarded owner (imas map activate). So the function and its test go, rather than being changed to write generated.

§ Decisions

Does an IDS export that skipped an active mapping succeed?

An IDS built without an active mapping's field is wrong output, not degraded output. But a facility may carry an active mapping for a section the recipe does not build yet, and an operator may want the rest of the IDS anyway.

Recommended: exit non-zero unless --allow-skipped is given. A script calling export then cannot mistake an incomplete IDS for a complete one, and the flag records that the operator accepted the gap.
