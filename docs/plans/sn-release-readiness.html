§1 — Why this plan exists

No Standard Name has ever been published. Every superseded name in the graph carries a null catalog_approved_at, which means none of the release machinery has run against real published state even once. That is the good news and the whole problem: every release gate in imas_codex/standard_names/export.py is latent, and the first release is when each one is tested for the first time, in public, against the live catalog.

The export path does not fail loudly when something is wrong with a name. It filters. _fetch_candidates selects on name_stage, validation_status and docs_stage; Gate C then filters again on score. A name that fails any of these is not reported as a defect — it simply is not in the output. The release ships whatever survives, and nothing in the pipeline asserts that the number that survived is the number anyone intended to ship.

This plan is not a cleanup list. Its spine is a single structural claim: exclusion must become visible before the first release, and the classes that exclusion is currently hiding must be dispositioned rather than discovered afterwards. Every figure below is a live measurement taken on 2026-08-23, not carried forward.

§2 — Every unscored name is a defect, not a design category

Applying the export predicates in order to the live graph gives the shape of what a release would contain today.

1,469 of the 2,296 export-eligible names carry no reviewer_score_name at all, while only 14 are genuinely scored below the 0.85 bar. Reading those 1,483 together as "failures" is wrong — unscored and low-scoring are different conditions with different fixes — but so is the opposite reading, which this plan originally took.

One of the five is legitimately unscored; the other four are not. The complete partition has no residual, and the discriminator that matters is not origin but the reviewer marker.

A derived parent is genuinely an exception, and scoring it would be theatre. The structural accept in graph_ops.py says so in terms, and the reasoning holds: the name is a deterministic grammar peel of children that are already reviewed, it is never reviewed or refined, so a score would grade a mechanical consequence rather than a choice. The quorum is worse than useless here — it marks an abstraction down for being less specific than its own children, measured at roughly two thirds below 0.85 — so routing these 221 through it would spend budget to manufacture exhausted parents. Quality is gated on the docs axis instead, which is where the writing actually happens.

What is wrong is not that they lack a score but that a missing score is indistinguishable from never having been assessed. The fix is to make the exemption legible rather than to abolish it. The invariant is therefore every accepted name carries either its own reviewer score or a recorded structural-accept marker, and the exclusion ledger reports the structural population as a named category rather than a silent null. That admits the 221 and still catches all 1,248 rows that are genuinely unassessed.

Two of those populations were not traced until this partition was taken, which is worth stating plainly rather than presenting the analysis as complete: the 92 are the structural population wearing a different origin after a catalog round trip, so origin='derived' is not a safe discriminator anywhere in this plan; and the 65 — 84 across the whole graph, every one of them with live children and none carrying parent_enriched_at — never went through enrich_parents at all. Those 84 are a real hole, and the right repair is the sanctioned structural path rather than the name quorum, which also means they cost description synthesis rather than review budget.

The documentation side is nearly the same rows seen from the other axis: of the 129 export-eligible names with no reviewer_score_docs, 128 are also name-unscored. Fixing the names carries almost all of it.

§3 — An exclusion ledger, so a release cannot be quietly short

The deliverable that makes the rest of this plan durable is a gate that counts what did not ship. Gates A, B and C already exist: _run_gate_a runs the graph suites, _run_gate_b checks cross-field consistency including COCOS and the grammar version, and _run_gate_c applies the score thresholds and returns excluded_below_score and excluded_unreviewed counts. Gate C therefore already knows two of its own exclusions. Nothing aggregates them, nothing accounts for the exclusions that happen earlier in _fetch_candidates, and nothing asserts a total.

The work is to make every drop between the accepted population and the emitted catalog attributable to exactly one named reason, and to fail the release when the arithmetic does not close. Concretely: for a run over N accepted names, the ledger must satisfy emitted + sum(exclusions by reason) = N, with a row per reason and the identities recoverable for each. A release that drops a name for an unnamed reason is a bug in the ledger, which is the point — the ledger is what converts a silent filter into a reviewable statement.

This extends the existing gate structure rather than adding a parallel preflight. A second command that "checks readiness" beside a release path that filters independently would drift within one sprint.

§4 — Supersede lineage is an internal record, and it is incomplete

Successors are never released. Supersede lineage is a documented internal record of how the catalog reached its current state, not an external reference a consumer resolves. That settles the disposition question and removes the urgency this plan first attached to it: the 509 successorless retirements cannot break a published contract, because there is no published contract to break.

It does not make the record worthless. Provenance is what lets a future session answer "where did this name go" without re-deriving it, and the record is currently thin: of 1,643 superseded names only 17 carry superseded_by, 1,117 keep their lineage only in a REFINED_FROM edge, and 509 record no successor anywhere — no edge, no scalar, no receipt.

So the work here is small and forward-looking rather than archaeological: keep the record complete from now on. The operator fix at 1854c6d4 writes superseded_by for a supersede-into-a-different-identity, which is the shape that leaves no REFINED_FROM edge, so the class stops growing.

One consequence needs checking against this decision rather than assumed. _fetch_deprecation_stubs and _build_stub_entry in export.py emit status: deprecated catalog entries that point at a successor — that is, they publish supersede lineage into the released catalog. If successors are never released, that machinery is emitting something the release should not contain, and it also resolves successors only along REFINED_FROM while never reading superseded_by. Confirm the intended behaviour before the first release rather than discovering it in the output.

§4a — Close the holes, then drain; not the other way round

A drain that runs before the entry paths are closed refills behind itself. The first deliverable is therefore to find every code path that can land a name or a documentation string in an accepted state without a score of its own, and shut it. The known entrant is old sn edit output — 1,181 rows — and the structural-inheritance accept accounts for a further 221, but neither should be assumed to be the complete list until the paths are enumerated rather than inferred from the populations they produced.

The closure is a graph invariant, not a convention: an accepted name must carry a reviewer_score_name and an accepted documentation string must carry a reviewer_score_docs, both from a real reviewer, and the pipeline must refuse a transition that would violate it. A schema-driven test in tests/graph/ asserting zero unscored accepted rows is what stops this class regrowing after the drain, and it is what the drain is measured against.

Only then the drain: 1,469 names and the documentation strings that accompany them, through the ordinary generate/review path, under the authorized budget. Order the work so the sample that sizes the derived-parent failure rate runs first, before the bulk spend commits to an approach the quorum will reject.

§5 — The docs and validity backlog behind the upper two drops

197 of the 2,535 accepted names do not have accepted documentation: 82 pending, 56 drafted, 47 reviewed, and 12 exhausted. Because the export gate is docs_stage = 'accepted', all of them are excluded from a full release without appearing anywhere as a problem. The 12 exhausted are the sharp end: an accepted name whose documentation reached the refine cap and gave up, so it will never clear the gate on its own and needs either a rescore or an explicit disposition.

Separately, 47 accepted names are validation_status='quarantined' and 4 live names carry a null validation status. Quarantine is a working state that the compose worker sets; carrying it on an accepted name is a contradiction worth resolving before a release rather than after.

The boundary with the documentation-quality programme matters here. sn-quality-parity owns the bar — the holdout benchmark, the content-gated template, richer DD and COCOS context into compose, and the link-resolution lifecycle. This plan owns only the drain: getting the existing backlog to a terminal state under whatever bar that plan sets, and refusing to let a release quietly omit what has not drained. If the two are worked in the wrong order the drain is done twice, so the drain node must cite the bar in force when it runs.

§6 — Sources whose physics never reaches a published name

145 live names never reached accepted — 119 reviewed, 21 drafted, 5 pending — and a further 72 are exhausted, between them holding 121 producing sources. Every one of those sources represents a Data Dictionary path or facility signal whose physics has no name a consumer can cite.

These are not all recoverable and this plan should not pretend otherwise. exhausted is explicitly a recoverable state — sn rescore reverts a name to drafted and resubmits the same name for a fresh quorum draw, and a structurally sound name whose siblings accept at 0.96 typically clears on a redraw. But repeated exhaustion of sound names is a signal to fix the pipeline, not something to grind through by rescoring in a loop. The node here is a census that partitions the 217 into redraw-eligible, needs steering, and correctly abandoned, with the count for each, before any budget is spent.

The 119 reviewed names overlap the below-threshold class handed to sn-quality-parity in the closure that preceded this plan. The split is by question, not by row: how do we make this name good is that plan's; what does a release do with a name that never became good is this one's.

§7 — Metadata gaps that would ship into the catalog

Small, cheap, and embarrassing in public. Among the 2,535 accepted names: 21 carry no physics_domain, and 1 has no documentation string at all. Every accepted name has a unit, a description and an embedding, so those axes are already clean and need no work.

Two further items. 855 accepted names carry a null catalog status while 1,680 read draft; since the exporter writes status: active at publish time this may be harmless, but a null where a vocabulary value is expected should be confirmed harmless rather than assumed so. And 2 accepted documentation strings still contain a bare [name] bracket despite the accept path normalising links at source — a small leak, but it means the normalisation has a hole worth finding while only two rows show it.

§8 — Residue carried in from the integrity closure

sn-integrity-residual-closure shipped with four identities holding no producing source and three dual-bound semantic sources, each refused for a recorded reason rather than left unexamined. Two of those refusals are owned elsewhere and stay there: the fast-ion power identity waits on Data Dictionary issue 294 and PR 295, and the field-map grid locus waits on an imas-standard-names vocabulary decision.

The rest need an authority this plan can carry, because each is a question about what a release does with an identity that cannot be given a producer: neutron_flux_due_to_fusion, whose retarget would strip its predecessor's last producing source; tendency_of_total_thermal_plasma_internal_energy, whose only unit-agreeing path is held by the quarantined plasma_internal_energy; the three dual-bound sources, where every cut strips a last producer; voltage_of_diagnostic_antenna, which needs a sanctioned source-less rename transition; and reflector/centre/phi, which needs a reviewed centre-of-curvature identity of its own. A name with no source is not automatically unpublishable — but shipping one should be a decision on the record, not an accident of which filter it happened to survive.

Two further coordination facts. Both plans will drive sn run: the pool workers are claim-token safe so concurrent execution will not corrupt state, but two campaigns with separate cost caps interleave and make spend unattributable, so the drains should run under one campaign at a time even where the work itself is independent. And the file scopes are close enough to need stating explicitly before dispatch — this plan works in export.py and the review-admission paths, the quality plan in the docs prompts and compose context.

A defect the quality plan's own reconnaissance surfaced is worth carrying across, because it will bite either plan: the docs COCOS lookup queries :COCOS where the schema owns :HAS_COCOS. Whichever plan reaches it first should fix it rather than route around it.

§ Decisions

What happens to the 1,469 export-eligible names that carry no reviewer score — 1,181 old sn edit rows and 221 structural-inheritance accepts?

REVISED from all-reviewed on the lead's challenge, and the code settles it. A derived parent's name is a deterministic grammar peel of already-reviewed children, never reviewed or refined, so graph_ops.py deliberately writes no reviewer_score_name - scoring a name we never change grades a mechanical consequence, not a choice. The quorum actively penalises the abstraction for being less specific than its own children, roughly two thirds below 0.85, so routing the 221 through it would spend budget manufacturing exhausted parents. Quality stays gated on the docs axis. The discriminator is the reviewer marker, NOT origin: the structural population is 129 derived plus 92 catalog_edit that flipped origin in an export/import round trip, so origin='derived' is unsafe anywhere in this plan. Invariant: every accepted name carries either its own reviewer score or a recorded structural-accept marker, and the ledger reports the structural population as a named category rather than a silent null. Drain scope is therefore 1,181 catalog_edit rows plus 2 score-write defects, not 1,469. Separately untraced until this partition: 65 in-pool (84 graph-wide) derived names with live children, no reviewer and no parent_enriched_at, which reached accepted through neither review nor the sanctioned structural accept - repair through enrich_parents, which costs description synthesis rather than review budget. USD 200 authorised.

What does a release do with the 509 superseded names that record no successor anywhere?

Successors are never released. Supersede lineage is a documented internal record of how the catalog reached its state, not an external reference a consumer resolves, so the 509 successorless retirements cannot break a published contract and do not gate the release. The record still matters internally and stops growing now that the operator writes superseded_by for an identity supersede. Open consequence to confirm: export.py currently emits status:deprecated catalog entries carrying a successor pointer, which publishes lineage this decision says is internal.

Does the first release wait for a quality graph and pipeline, or publish the subset that already clears the gates?

The first release awaits a quality graph and pipeline. It is not rushed and not split into a partial publication followed by an increment.

§ Followups

Build the exclusion ledger before draining anything

Start at section 3, not at the largest number. The ledger is what makes every other section verifiable: until a release can state emitted + sum(exclusions by reason) = N with the identities recoverable per reason, every drain below it is unmeasurable and every count in this plan has to be re-derived by hand. Gate C already returns excluded_below_score and excluded_unreviewed, so two reasons exist and are unaggregated; the earlier exclusions in _fetch_candidates have none. Two of the three open decisions (unreviewed-in-first-release, docs-backlog-blocks-release) change what the ledger must report, so lock those with the lead before the drain nodes in sections 5 and 6 are authored. The section 4 scalar fallback is independent of all three and can land first if a quick win is wanted.
