§1 — Why a chain of bounded decisions

The map stage writes the IMAS bindings, so it is the step whose errors reach a user's data. Today map_signals in imas_codex/ids/mapping.py makes one open-ended reasoning call per target section. That call returns a SignalMappingBatch whose entries carry a free-form Python transform_expression, a cocos_label, units and a confidence. The model therefore settles every part of a binding at once: which field, the sign, any 2π factor, the unit conversion and the index layout. Its prompt carries the source's representative COCOS, the DD's COCOS and the paths that need a flip, but nothing makes the sign it writes agree with them.

Most of those parts are not open questions. imas_codex/ids/transforms.py already computes a COCOS sign or factor deterministically, as cocos_sign(label, cocos_in=..., cocos_out=...), from a DD field's cocos_transformation_type and the two conventions. convert_units converts units through pint. What is missing is the source's own convention, which jt60sa-discovery-completion §56 now establishes per source and per quantity with evidence. Once that is known, the sign and factor of a COCOS-labelled field follow in code. What is left is genuinely uncertain, and each such slot is a bounded choice that Jev answers well: a sign of 1 or −1, a factor of 1, 2π or 1/2π, one of the unit readings pint offers, or one of a few index layouts. A local-lane model handles a slot only when it is not Jev-shaped, and anything still uncertain is escalated rather than guessed.

Candidate selection, which picks the target field, already works this way: Jev judges each candidate and the assign stage chooses among the shortlist. This plan extends the same discipline to the transform. Mapping stays opt-in in imas-codex discover FACILITY until this plan's proof lands, under the mapping-stage-default decision in facility-discovery-sequence.

§3 — Typed slots replace the free-form transform

A binding's transform becomes a set of typed slots, each with a value, the way it was settled (code, jev, local or escalated) and its evidence: sign, scale_factor, unit_conversion, cocos_label and an index layout. One composer in imas_codex/ids/transforms.py builds the transform_expression from the settled slots, so the expression stored on MAPS_TO_IMAS is always produced by code and always uses names that execute_transform accepts. A binding with any slot still open is not written; it is escalated with the open slots named. The slot set and its kinds come from the §2 census, so the model covers what bindings actually need, not a guess.

§4 — Conventions settle what code can settle

A resolver runs before any model. It reads the source's conventions through the loader jt60sa-discovery-completion §56 adds, planned as get_conventions(facility, source) -> {cocos, psi_factor, quantities: {name: {sign, reference, evidence, confidence}}}. It reads the DD field's cocos_transformation_type and the DD's own COCOS. A COCOS-labelled field whose source COCOS is known gets its sign and factor from cocos_sign. A quantity with a recorded per-quantity sign, such as Ip or Bt direction relative to φ, a flux-loop or pickup-coil normal, or a loop-voltage sign, gets that sign. Units come from pint when the source unit is known. An absent convention leaves its slot open: the loader never defaults a value, and neither does the resolver. Each settled slot records the convention's evidence and confidence beside its value, and the persisted conventions are injected into every later decision's state next to the DD COCOS label, so a Jev decision starts from what is known.

§5 — One Jev decision per open slot

Each slot still open becomes one bounded Jev question. The options are the slot's own: 1 or −1 for a sign; 1, 2π or 1/2π for a factor; the readings pint offers for an ambiguous unit; the candidate layouts for an index. The state is the source's detail, the target field's documentation and COCOS label, the injected conventions and the §6 context. Independent slots of one binding go in one request, as Jev runs them in parallel. A slot is accepted when its answer clears an acceptance threshold set from the §2 census. Below it, the slot goes to escalation with Jev's distribution as evidence. A slot that is not a bounded choice, such as an unusual index expression, goes to the local-lane model with the same state, and its answer must still name one of the composer's slot kinds. When the OpenRouter key is absent, the chain skips Jev and sends open slots to the local model, as the candidate stage already does.

§6 — Reranked context from every source kind

The map stage's context today is a fixed set of wiki and code snippets gathered per IDS. The decision state instead takes, per source, what the hybrid search finds across code, wiki pages, documents and signals, reranked by Jev against the binding being decided through the shared core in imas_codex/discovery/base/judgment.py. The top items by relevance go into the state, each labelled with its kind and origin, so a sign decision can read the code that writes the signal and the wiki page that defines its direction.
