§1 — Why this exists

uv run pytest — the command this repository’s own guidance names as the default — exited 2 having run zero tests, every time, from 2026-08-25 to 2026-09-01. One undeclared import in tests/docs/test_documentation_layout.py raised at collection, and a collection error aborts the whole run.

That was repaired in commit 1d4fb8be while shipping graph-operational-safety, whose verification node found it. The repair is not what this plan is about. The suite now collects, and 49 tests failed. Twenty were repaired at 8ee947b0 the same day (§2b); this plan owns the remaining twenty-nine and the recurrence guard.

The shape is worth naming because it is not a test-maintenance backlog. An exit code of 2 with no failure list does not read as “the suite is broken”; it reads as something odd with the runner, and it gets stepped past. A guard that reports its own malfunction in a register nobody parses is indistinguishable from a guard that passes — and for a week every change landed against a suite that verified nothing while appearing to be present.

§2a — The twenty are claimed, and the author’s diagnosis inverts the obvious fix

The author of 9c4403db claimed the SN twenty within minutes of being notified, reproduced them at 20 failed / 77 passed across the three files, and reached a conclusion worth recording here because it is the opposite of what this plan would have guessed. The fixtures should not gain a source cohort and the guard should not tolerate the legacy shape — the guard is aimed at the wrong path.

Their decisive evidence is a rename inside their own commit: a test called test_source_less_rename_still_records_human_edit was flipped to test_source_less_rename_refuses_without_recording_human_edit, on the reading that it codified a defect. It did not; it encoded a distinction the flip erased. An automated refine minting a successor from an ungrounded predecessor is what needed refusing; a human sn edit --rename on an ungrounded name is a deliberate correction and the only sanctioned path for correcting a standard name. The guard therefore broke the correction path for exactly the names that most need correcting. The repair scopes the refusal to the automated refine path and restores the original assertion.

Their independent measurement also makes the blast radius larger than §1 states. testpaths = ["tests"], so a bare uv run pytest collects tests/docs/, hits the missing import, and interrupts collection for the whole tree — they measured exit 2 with Interrupted: 1 error during collection. The consequence is the part to carry: every green figure quoted in that week came from a targeted invocation that happened to avoid one directory. They had been reporting a 6,818-passed standard-names run as general health, and a node gate reporting 255 passed is what let this regression through. A narrow green is not evidence about a tree.

Neither option in §2a was the fix, and the author says so explicitly. The fixtures did not need sources and the guard did not need to tolerate the legacy shape — the guard was aimed at the wrong path. The atomic preflight's effective_edit_mode now separates the two cases: a non-empty effective mode permits the source-less no-op and records human_edit, while an empty effective mode refuses an observed empty authoritative cohort. The check that matters is what the fix did NOT touch. Making these twenty green by deleting the guard would have been trivial and would have reopened the stranding path it closed. Verified independently here rather than taken on the author’s word: 8ee947b0 changes graph_ops.py and two test files, and test_refine_source_cohort_gate.py is not among them, so test_empty_authoritative_source_cohort_refuses_successor still asserts the refusal it always did. The guard was narrowed, not removed.

One correction to §1, and it is the kind worth making loudly. This plan and its opening commit called all 49 “pre-existing”. That is wrong for at least one of them: the SN twenty were introduced by 9c4403db at 19:13 on 2026-09-01, inside the outage window rather than before it. So the accurate statement is not that the collection error hid an old backlog — it is that the outage window was itself a period in which new breakage could land and be invisible, and at least one did. That is a strictly worse property than a stale backlog, and it raises the priority of the recurrence guard in §4 above the repairs.

§2c — One commit produced both the damage and the blindness to it

§1 treats the broken import as an accident that happened to a working suite. It was not. Commit 651d2367 performed a 34-file documentation migration, wrote the guard that would have verified it, and shipped that guard with the import already broken. Verified from the commit itself rather than inferred: 60 files changed, 34 renames, tests/docs/test_documentation_layout.py added with from reckon.resources import TYPE_ROOTS on line 4 of the added file.

So the guard never ran once — not degraded over time, dead on arrival — and because a collection error aborts the tree, it took the entire suite with it from the same instant. One commit therefore produced the half-migrated corpus, the check that would have caught it, and the blindness that stopped the check ever reporting. The check’s own subject was the thing it failed to see.

The corpus damage is measured, from a fresh before-state captured at 55db4635 by the layout migration now in flight: 214 HTML resources, 346 internal links, 299 resolving, 46 missing targets and 1 missing anchor. The 46 is up from 45 at an older revision, so the class is still growing. These are broken links that predate any current migration; they are what a half-completed rename looks like when nothing has validated it for a week.

§2d — The repair fixed the instance, not the class

Proven by controlled probe, not by reading the code. A deliberately broken import was written into a collectable test file and the tree run: 

EXIT=2
ERROR tests/docs/test_zzz_tmp_probe_abort.py
!!! Interrupted: 1 error during collection !!!

The probe was then removed and tests/ confirmed clean. pytest.importorskip is file-local — line 5 of one file — and addopts carries no --continue-on-collection-errors. So one undeclared import in any collectable file still silences the whole suite exactly as before, and today’s green is a property of nobody having broken it again yet rather than of anything preventing it. Per-file protection would require predicting which file breaks next, which is a guess rather than a guard. The guard belongs at the runner.

Recommendation against the collection-failure-visibility decision, offered rather than locked, because it changes how everyone in this repository runs tests. Two shapes were proposed; one of them is ruled out by this plan’s own argument.

  • --continue-on-collection-errors alone recreates the defect at file granularity. A bad import would stop zeroing the suite and instead report 1 error, 12021 passed. That file’s tests still never ran, and nothing loud says so — the blast radius shrinks from the tree to one file and the signal shrinks with it. “1 error” in a summary line is precisely the register that was misread for a week.
  • An explicit collection check is NOT the missing half, and asking for one was this plan’s own aiming error. See §2e: it already exists, it has been failing on every push for a week, and nobody read it. A second emitter would duplicate a signal that is already produced and already ignored.

§2e — The guard exists, it is CI, and it has been red on every push

Verified independently over 120 workflow runs, because a claim this alarming deserves its own check rather than acceptance. .github/workflows/test.yml runs uv run pytest --cov=imas_codex --cov-report=xml --cov-report=term-missing --timeout=120 — the bare whole-tree invocation, no path restriction — on every push to main and every pull request, with no continue-on-error, so a collection error is fatal to the job.

Zero successes across every run on record. So exit 2 was not merely visible in principle — it was a red job on every push for a week, and the outage persisted regardless. The failure mode is delivery, not detection, and no pytest flag addresses it. That reframes this plan’s recurrence deliverable: the problem was never that nothing said the suite was broken, it is that saying so had no consequence.

And 65 of the 120 runs were destroyed rather than failed. The workflow sets concurrency: cancel-in-progress: true with group ${{ github.workflow }}-${{ github.ref }}, so every push to main cancels the one before it. A cancelled run has no conclusion at all — neither pass nor fail. With several agent sessions pushing in quick succession, rapid pushing does not delay the signal, it erases it. That policy is right for pull requests, where a superseded commit’s result is genuinely uninteresting, and wrong for main, where each commit’s result is the record.

The consequence gate must judge by delta, not by absolute redness — and this plan is its own proof. A gate refusing to promote work while the tree’s suite is red would have blocked every node of the session that discovered this problem, including the one that made the redness visible at all. The repository already holds the correct form of this rule for lint (judge your own change by delta against a baseline, since a file may carry findings that are not yours to fix in passing); the same shape applies here. What a promotion must demonstrate is that it added no failure, not that the tree is clean.

§3 — What each cluster needs, and from whom

These are four different kinds of work and should not be treated as one queue. Two of them need a decision before any repair, and one is not this plan’s to make at all.

  • The SN twenty are the author’s. The guard added by 9c4403db is plausibly correct and the fixtures plausibly predate it; deciding whether the fixtures gain a source cohort or the guard tolerates the legacy shape needs whoever made the change. This plan tracks them and does not repair them.
  • The torch eighteen need a policy, not a patch. A test that fails because an optional extra is absent is either a test that should skip or an extra that is not really optional. Both are defensible; picking one silently is how the situation recurs.
  • The integration nine need triage before estimation. Nothing is known about them yet beyond the count, and pretending otherwise would repeat the error that produced this plan.
  • The two singletons need a verdict on whether they are defects at all. A timeout and an environment-dependent message may both be artifacts of where the suite ran rather than of what it tested.

§4 — Deliverables

  • A triage pass that assigns every one of the 49 to a cluster with a verdict: a defect to fix here, a defect owned elsewhere, an environmental artifact, or a test whose premise is wrong.
  • A decision on the optional-dependency policy, applied consistently, so a test never again fails merely because an extra is absent.
  • Whatever repairs the triage assigns to this plan, each with a named test moving from failing to passing.
  • A guard against the recurrence itself: the failure here was not the broken import but that an exit-2 collection error was indistinguishable from an environment quirk for a week. Something must make a suite that collects nothing loud rather than quiet.
  • A final full-suite figure recorded against the census above, so the count that closes this plan is comparable to the count that opened it.
