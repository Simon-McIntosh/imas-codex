§1 — Why this exists

uv run pytest — the command this repository’s own guidance names as the default — exited 2 having run zero tests, every time, from 2026-08-25 to 2026-09-01. One undeclared import in tests/docs/test_documentation_layout.py raised at collection, and a collection error aborts the whole run.

That was repaired in commit 1d4fb8be while shipping graph-operational-safety, whose verification node found it. The repair is not what this plan is about. The suite now collects, and 49 tests failed. Twenty were repaired at 8ee947b0 the same day (§2b); this plan owns the remaining twenty-nine and the recurrence guard.

The shape is worth naming because it is not a test-maintenance backlog. An exit code of 2 with no failure list does not read as “the suite is broken”; it reads as something odd with the runner, and it gets stepped past. A guard that reports its own malfunction in a register nobody parses is indistinguishable from a guard that passes — and for a week every change landed against a suite that verified nothing while appearing to be present.

§2a — The twenty are claimed, and the author’s diagnosis inverts the obvious fix

The author of 9c4403db claimed the SN twenty within minutes of being notified, reproduced them at 20 failed / 77 passed across the three files, and reached a conclusion worth recording here because it is the opposite of what this plan would have guessed. The fixtures should not gain a source cohort and the guard should not tolerate the legacy shape — the guard is aimed at the wrong path.

Their decisive evidence is a rename inside their own commit: a test called test_source_less_rename_still_records_human_edit was flipped to test_source_less_rename_refuses_without_recording_human_edit, on the reading that it codified a defect. It did not; it encoded a distinction the flip erased. An automated refine minting a successor from an ungrounded predecessor is what needed refusing; a human sn edit --rename on an ungrounded name is a deliberate correction and the only sanctioned path for correcting a standard name. The guard therefore broke the correction path for exactly the names that most need correcting. The repair scopes the refusal to the automated refine path and restores the original assertion.

Their independent measurement also makes the blast radius larger than §1 states. testpaths = ["tests"], so a bare uv run pytest collects tests/docs/, hits the missing import, and interrupts collection for the whole tree — they measured exit 2 with Interrupted: 1 error during collection. The consequence is the part to carry: every green figure quoted in that week came from a targeted invocation that happened to avoid one directory. They had been reporting a 6,818-passed standard-names run as general health, and a node gate reporting 255 passed is what let this regression through. A narrow green is not evidence about a tree.

§2d — The repair fixed the instance, not the class

Proven by controlled probe, not by reading the code. A deliberately broken import was written into a collectable test file and the tree run: 

EXIT=2
ERROR tests/docs/test_zzz_tmp_probe_abort.py
!!! Interrupted: 1 error during collection !!!

The probe was then removed and tests/ confirmed clean. pytest.importorskip is file-local — line 5 of one file — and addopts carries no --continue-on-collection-errors. So one undeclared import in any collectable file still silences the whole suite exactly as before, and today’s green is a property of nobody having broken it again yet rather than of anything preventing it. Per-file protection would require predicting which file breaks next, which is a guess rather than a guard. The guard belongs at the runner.

Recommendation against the collection-failure-visibility decision, offered rather than locked, because it changes how everyone in this repository runs tests. Two shapes were proposed; one of them is ruled out by this plan’s own argument.

  • --continue-on-collection-errors alone recreates the defect at file granularity. A bad import would stop zeroing the suite and instead report 1 error, 12021 passed. That file’s tests still never ran, and nothing loud says so — the blast radius shrinks from the tree to one file and the signal shrinks with it. “1 error” in a summary line is precisely the register that was misread for a week.
  • An explicit collection check is NOT the missing half, and asking for one was this plan’s own aiming error. See §2e: it already exists, it has been failing on every push for a week, and nobody read it. A second emitter would duplicate a signal that is already produced and already ignored.

Zero successes across every run on record. So exit 2 was not merely visible in principle — it was a red job on every push for a week, and the outage persisted regardless. The failure mode is delivery, not detection, and no pytest flag addresses it. That reframes this plan’s recurrence deliverable: the problem was never that nothing said the suite was broken, it is that saying so had no consequence.

And 65 of the 120 runs were destroyed rather than failed. The workflow sets concurrency: cancel-in-progress: true with group ${{ github.workflow }}-${{ github.ref }}, so every push to main cancels the one before it. A cancelled run has no conclusion at all — neither pass nor fail. With several agent sessions pushing in quick succession, rapid pushing does not delay the signal, it erases it. That policy is right for pull requests, where a superseded commit’s result is genuinely uninteresting, and wrong for main, where each commit’s result is the record.

The consequence gate must judge by delta, not by absolute redness — and this plan is its own proof. A gate refusing to promote work while the tree’s suite is red would have blocked every node of the session that discovered this problem, including the one that made the redness visible at all. The repository already holds the correct form of this rule for lint (judge your own change by delta against a baseline, since a file may carry findings that are not yours to fix in passing); the same shape applies here. What a promotion must demonstrate is that it added no failure, not that the tree is clean.

§2f — Who owns which half, so neither is built twice nor dropped

The recurrence work split across two repositories once it was clear the gap was consequence rather than detection. Recording the split here because the dangerous outcome is not duplication — it is a half that each side believes the other holds.

  • The promotion gate is reckon’s, at promotion-consequence-gate (commit 28b789d, reckon S9), so every project benefits rather than this one. It carries the delta constraint as its §2 and, usefully, a deliverable proving the gate would not have blocked the fifteen nodes of the session that found this — the counter-example promoted to an acceptance test so the constraint cannot be quietly dropped during implementation. Three decisions are open there: the delta baseline, who executes the suite, and whether it defaults on. This plan must not build a second one.
  • The concurrency policy is THIS repository’s and this plan claims it. The file is .github/workflows/test.yml — imas-codex config, not reckon’s — so a plan in another repository can note it but cannot fix it. Left merely “tracked to be handed on”, it is precisely the work that falls between two plans and is never done.

The two halves touch at exactly one point, and it is a correctness constraint on the gate rather than a coincidence. A promotion gate that reads a CI conclusion must treat cancelled as absence of evidence, never as a pass. With 65 of 120 runs cancelled, the naive reading — “not failed” — would let the majority of pushes through a gate that had measured nothing. That is the same absence-as-permission shape this repository has now named repeatedly, and it would arrive inside the very mechanism built to prevent it.

Scope note on the concurrency change: it is a real behavioural change to CI — more runs reaching a conclusion means more consumed minutes — and it is a policy decision rather than a defect repair, since cancel-in-progress is the correct setting for pull requests. It is therefore recorded as claimed, not as done, and wants the lead’s agreement before it lands.

§2g — The repair turned a loud failure into a silent no-op

The importorskip fix recorded in §1 is a real improvement and also introduced a defect of exactly the class this plan exists to name. Re-measured in this repository’s own environment: 

uv run --no-sync python -c "import reckon"              ->  ModuleNotFoundError: No module named 'reckon'
grep -c reckon pyproject.toml                           ->  0
uv run pytest tests/docs/test_documentation_layout.py   ->  EXIT=5, no tests collected
SKIPPED [1] tests/docs/test_documentation_layout.py:5: reckon is not installed

reckon is neither declared nor installed here, so the guard is skipped whole, every time. Before the fix: exit 2, the tree aborted — catastrophic and impossible to miss. After it: 12,020 tests collect, which was the point and is a genuine improvement, and the typed-layout invariant still never executes, with nothing saying so. That is precisely the zero-signal state this repository’s own testing guidance names for a disabled test: not run, invisible, nobody knows it exists.

The reasoning that produced it is worth recording as wrong, because it was plausible. The shipped analysis argued that declaring the dependency was the wrong repair — reckon is a local checkout, not a published package — and that the import should therefore become conditional, keeping the check “wherever reckon is available”. The unexamined half of that sentence is the load-bearing one: in this repository reckon is never available, so “wherever available” evaluates to nowhere. A conditional guard is only a guard if its condition is sometimes true where it runs.

The arc completes badly. 651d2367 added a guard that could not run and aborted everything; the repair made everything run and left the guard unable to run; and the typed layout migration has now landed while the check that would confirm it has not executed once in the repository it guards.

The decision, which is the lead’s. Two shapes, and importorskip as a resting state is not one of them — it is the option that resembles both and is neither.

  • Declare reckon as a test dependency so the invariant actually runs. Cost: a declared dependency from an operational repository onto its planning tooling. A dev-group or extra scopes it, but the coupling is real and may be deliberate policy to avoid.
  • Remove the check. If the dependency is unwanted, deleting is more honest than skipping: a check with zero signal is worth less than nothing, because it occupies the space where enforcement appears to exist.

And a third constraint on the recurrence gate, from the same seam: collecting is not executing. A gate reading “the suite collected” passes here today while the layout check runs zero tests. Any measure the gate reads must distinguish ran-and-passed from was-skipped. That makes three instances of absence-as-permission appearing inside the mechanism built to prevent it — exit 2 read as configuration noise, cancelled read as not-failure, and now skipped read as satisfied.

§ Decisions

When a test needs an optional extra that is absent, what should happen?

Locked by the lead 2026-09-01: the extra is provisioned for test runs and its absence is a real failure, reported once and loudly. torch is already declared in the [test] extra, and pyproject's own comment states that a silently-skipped contract test carries no signal, so the eighteen torch failures were an unprovisioned environment rather than a missing declaration. Deliverables: verify CI and the documented test recipe install the test extra (with the cpu torch index) and repair if not; replace the scatter of eighteen import errors with one conftest-level check that fails collection of the dependent suites with an install instruction naming the extra. importorskip is not adopted for torch because the search and scoring suites would then never run on a machine lacking it.

What should make a zero-collection suite impossible to mistake for a passing one?

Locked by the lead 2026-09-01. The plan's own probe (§2d, §2e) showed the detection already exists: CI ran the bare whole-tree suite and was red on all 55 concluded runs, while 65 of 120 runs were cancelled with no conclusion at all. So the repair is delivery, not a pytest flag. Two parts: (1) THIS repository changes .github/workflows/test.yml so cancel-in-progress applies only to pull requests and every commit on main reaches a conclusion, accepting the extra CI minutes; (2) the consequence is reckon's promotion gate (promotion-consequence-gate), which judges by delta against a baseline and treats a cancelled run as absence of evidence, never as a pass. --continue-on-collection-errors is rejected because it shrinks the blast radius and the signal together, and a second collection emitter is rejected because the existing one was already produced and ignored.

Where should the typed-layout check live, given it has never run in imas-codex?

Locked by the lead 2026-09-01. The check moves to reckon. Grounds measured rather than preferred: in imas-codex reckon is not importable, pyproject.toml names it zero times, and the module skips whole at EXIT=5 with no tests collected - so the guard has never executed once in the repository it guards, and the conditional import made a loud failure silent rather than making the check portable. Reckon already holds both halves the check needs: TYPE_ROOTS is a local import there, and reckon reads imas-codex's docs corpus through the registered project mount - not theoretically, since the layout migration's own link checker ran across that corpus from reckon this evening. So enforcement becomes real with no declared dependency from an operational repository onto its planning tooling. Rejected alternatives and why: declaring a dev dependency puts enforcement where the files are, but couples imas-codex to a local checkout that is not a published package, so the declaration cannot be expressed portably and fails in every environment lacking that checkout; deleting the check is honest about today's zero signal but removes the typed-path invariant entirely, immediately after a 149-file migration that depended on it. The cost accepted is DISTANCE: the check will live one repository away from the corpus it guards, so a contributor working only in imas-codex will not see it fail - which makes it reckon's responsibility to surface a violation somewhere a codex reader encounters it, or the same invisibility returns in a new place. Sequencing: the check produces zero signal today, so removing it from imas-codex reduces no enforcement, but it should follow reckon's implementation rather than precede it so the invariant is never orphaned in the record as well as in fact.
