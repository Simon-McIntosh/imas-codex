§1 — Sessions start without their tools

On 2026-11-12 a Claude Code session on the fleet node started with both the imas-cx and reckon MCP servers reported as failed: connection timed out after 30000ms. Neither server was broken. Both processes were alive 24 minutes later, and both connected on a later retry.

Measured the same hour, at a load average of 73, by spawning each server exactly as its configuration does and timing the answer to the protocol's initialize request:

ServerTime to first answerClient limit
imas-codex serve35.1 s30 s
reckon mcp11.5 s warm; over 30 s at session start30 s

For imas-codex serve the time is spent before the server exists. imas-codex serve --help, which starts nothing, took 27.5 s, and an import profile of the command-line package accounts for 19.9 s of it: 18.6 s arrives through the discovery commands, of which the language-model client library is 11.5 s, the schema runtime 4.6 s and the facility configuration 3.9 s. Those three are cumulative import times that include what each imports in turn, so they overlap and do not sum to the 18.6 s. The server command pays for every other command's imports. The remaining 7.6 s of the 27.5 s is not attributed by that profile, and process spawn does not explain it. Nothing here attributes the further 7.6 s between the 27.5 s help reading and the 35.1 s first answer; §2's attribution is of the whole 35.1 s.

The client's connect limit was raised to 180 s in the user's Claude Code settings on 2026-11-12 as a stopgap. That hides the delay and does not remove it: every session still waits half a minute for its tools, and any client without that setting still fails. The reckon mcp half belongs to the reckon repository and is not in this plan.

§2 — First answer in under ten seconds

Starting the server costs what the server needs and nothing else. The other commands keep working and keep their own import cost. Every timing, the load it was taken at, the base-revision readings and the control's failure at the base revision are committed under docs/evidence/fragments/serve-answers-inside-the-connect-limit/.

Done when:

  • imas-codex serve, spawned as .mcp.json spawns it, answers initialize in under 10 s as the median of five cold starts on a debug-partition node, with the five timings and the node's load recorded, against the same measurement taken at the base revision;
  • five starts on the fleet node, where sessions run, each answer in under 15 s, with the node's load average recorded beside each and the base revision timed in the same sitting;
  • the record attributes at least 90 % of the base revision's wall time to first answer to named parts, so the 7.6 s §1 leaves unexplained is accounted for;
  • imas-codex serve --help returns in under 10 s on the debug-partition node by the same measure;
  • a test fails when any of the discovery commands, the language-model client library or the schema runtime is imported on the path that answers initialize, or by the time imas-codex --help exits, and that test is shown failing at the base revision; the server's deferred background warm-up is outside that path, and the test gives the same verdict on ten consecutive runs whether or not the warm-up has started;
  • the tool list the server answers with is identical, by name, to the list at the base revision in each of its three serve modes;
  • imas-codex --help still lists every command it lists at the base revision, and the command-line test files pass with no added failure.
