Plan · standard names · S18, ahead of the WEST release

The integrity backlog, fixed before the release

From August to late September the standard-name work was mostly about the machinery that manages names: lifecycle axes, provenance, scalar mirrors, deletion guards and repair receipts. Sixteen plans carried that work, and between them they held 53 open followups while the WEST batch waited. The guards that mattered most landed. What remains is gathered here, one row per item. The lead ruled on 2026-10-12 that it is worked before the WEST release, not after it.

§1 — Why it comes before the release

The portfolio review of 2026-10-12 first parked this residue behind the WEST release, to keep a one-week release in reach. The lead reversed that the same day. Several rows sit on the path the release itself takes. WEST's name repairs and the grouping plan's synonym rulings go through sn edit and sn supersede. The fold guard reads history where it means the present, and when this plan was written four sanctioned paths refused an orphaned identity's state (§4, §2); three remain (§7). The restore command's refusal of a re-armed origin is now pinned (§9), and 412 live names (334 when recorded) are labelled scaffolding while carrying reviewed documentation (§2). A catalog built on machinery with those holes would be released on trust rather than on evidence.

Every row below was read against its source plan and kept only if it described a defect or decision that still existed. Each row names the plan and followup it came from, so the full measurement is one click away in that plan's frozen text. The measurements are weeks old, and adjacent work has fixed recorded defects before, so no row is dispatched as written: §6 re-confirms every row on the live graph first.

A row needed by the WEST release has already moved to sn-west-prototype-release and is not repeated here: the export gate chain, the two recovered names, the two vocabulary admissions, the half-width base, rehearsal accounting and roster identity.

§6 — First: re-confirm every row on the live graph

Before any repair is dispatched, re-measure every item named in §2 to §4 against the live graph and the current tree. This is read-only: no graph write, no code change. It needs Neo4j, so it runs as an execution-capable node on a compute partition, never as a review or investigate node. Each item gets one verdict:

  • still true, with the live count or the failing command that shows it;
  • fixed, naming the commit or the measurement that shows it gone;
  • changed, with both the recorded and the live figure;
  • needs a ruling, for an item that is a decision or waits on something outside this repository rather than a measurable defect (the questions recorded for the lead, the strain-gauge names waiting on an ISN token, whether one DD path may hold several source nodes, domain routes and terminal stages). It names who rules and what the ruling unblocks, and gets no repair section.

Reuse the census conventions that already exist rather than inventing a parallel shape. The row format and its anchor-resolution count follow docs/evidence/reuse-map-residual-closure.md, and each census header records the invocation commit and the row-set predicate, as the censuses under docs/evidence/sn-integrity-residual-closure/ do. Where a row's cohort already has a read-only reader, the census calls it and cites it rather than writing a fresh query: find_provenance_orphans and find_edge_scalar_desyncs in imas_codex/standard_names/ledger.py, find_semantic_source_invariant_violations in imas_codex/standard_names/provenance_lifecycle.py, and the thresholds pinned in tests/graph/test_sn_integrity_ratchets.py, which the census reads and never recomputes. A row with no owning reader is marked as such, since that is where new code would be needed.

Each item that survives is assigned to one proposed repair section with its write paths, its gate and an effort estimate. Items that touch a path the release takes come first: anything reached through sn edit, sn supersede, the restore command, the fold guard or the export. An item that is new coverage rather than a correctness defect (the MAST source manifest, the 1,268-source composition pass, upstream Data Dictionary filings) is marked as such and listed for the lead's ruling. The worker does not defer it.

Done when: docs/evidence/fragments/sn-integrity-backlog/row-census.html holds one row per separately stateable item: every followup id and every separately named defect or figure inside a table row of §2 to §4 is its own row, so the seven footguns of the lifecycle row are seven rows and the restore row's three items are three. §20 — The successor edge comes from the supersede operation

The operation that marks a name superseded is the signed supersede mutation in imas_codex/standard_names/signed_manifest.py (near line 4712). It sets name_stage, status and superseded_by and mints no edge, so HAS_SUCCESSOR exists today only because a derivation in the imas_codex.standard_names.graph_ops module rebuilds it from the scalar. Make the mutation write the HAS_SUCCESSOR edge to the successor it is signed with, stamped with the mutation's receipt so a signed edge is distinguishable from one the derivation built, and extend its postcondition (near line 4090) to require that edge, so a receipt proves the edge landed. The mutation is part of a signed, program-validated manifest: the edge write stays inside the existing mutation and its validation, never a side write. Removing the scalar-reading derivation is §16's, with the other readers.

Done when: applying a signed supersede in a test writes the HAS_SUCCESSOR edge to its signed successor, and the test fails when the edge write is removed; the postcondition refuses a supersede whose edge is absent (test); and the signed-manifest tests add no failure against their base.
