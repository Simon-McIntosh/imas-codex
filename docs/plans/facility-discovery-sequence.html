§1 — Why one command

Taking a facility from nothing to IMAS mappings takes seven commands today: discover paths, code, documents, wiki, signals and map, then imas map run. The operator has to know their order: code and documents read the paths that paths scored, and signal enrichment reads the wiki and code context those stages leave in the graph. The operator also has to know which stages can reach the facility at all. For JT-60SA run from the ITER host, the wiki and document sources sit behind tunnels through a laptop reverse tunnel. Every SSH stage fails whenever that hop is down. The graph-only stages, signal enrichment, discover map and imas map run, can always run.

One command, given a facility, runs every stage whose prerequisites hold, in dependency order. It skips the stages it cannot run, and says why for each one. Re-running it continues where it stopped, because every stage's claim loop is already idempotent.

§2 — Stage registry and access probes

A stage registry in imas_codex/cli/discover/sequence.py lists the stages in order. Its domains are the existing DISCOVERY_DOMAINS (imas_codex/cli/discover/common.py:30), which already gives the domain set one owner. For each stage it records the command that runs it, what the stage needs, the stages whose output it reads, and the existing pending-work predicate that says whether it has work. Each stage keeps exactly one owner. The registry points at the existing click command and adds no second implementation.

Documents has its two checks only as private helpers, _has_pending_image_documents and _has_pending_image_scores (imas_codex/discovery/documents/pipeline.py:58, 74). The node makes them one public has_pending_work in that module, which the pipeline and the registry both call. That is one added public definition, which replaces two private ones.

Every stage ends in one of four outcomes, each with a reason: ran (counts done and remaining), skipped: not configured (for example no wiki_sites), skipped: unreachable (the probe's own result), and skipped: nothing to do (its pending-work predicate is false). A stage whose input stage was skipped still runs if the graph already holds that input from an earlier run. A first run of code needs scored paths, and a later run can reuse them.

§3 — The runner and its report

The runner invokes each runnable stage's existing click command with ctx.invoke. Every discover domain builds its engine inside its own command function and then calls run_discovery (imas_codex/cli/discover/common.py:212), so invoking the command is the only path that reuses each stage whole, without refactoring seven commands or starting subprocesses. The runner passes the shared options through: --time per stage, and a total --cost-limit shared across the paid stages in proportion to their pending work, with each stage's own cap never exceeded.

A stage that raises is recorded as failed with its error. The runner then continues with the stages that do not read its output, so one broken stage does not stop an independent one. --only and --skip take stage names. The run ends with one table, one row per stage, giving outcome, reason, counts done and remaining, cost and wall-clock time. The same table goes to the CLI log at ~/.local/share/imas-codex/logs/.

The command adds one CLI entry and retires none. The per-domain commands stay the way to run one stage with its stage-specific options, for example discover signals --category.

  • a failing stage is reported as failed, a stage that reads its output is skipped with that reason, and an independent stage still runs;
  • the total cost cap is split across the paid stages and no stage exceeds its own cap;
  • --only and --skip select stages by name;
  • the final table lists every stage with outcome, reason, counts, cost and time.

§4 — The mapping stages join the sequence

The last two stages run the mapping pipeline. candidates runs discover map. mapping runs imas map run FACILITY once, and its own target enumeration, discover_mappable_ids (imas_codex/ids/tools.py:376, called at imas_codex/cli/map.py:211), decides the IDSs. The sequence keeps no second list. That enumeration picks IDSs by physics-domain overlap today, so it could miss an IDS that holds a source's cross-IDS sibling home. This node extends it: an IDS holding a selected or escalated candidate edge for the facility is a target even when the domain overlap misses it. With the per-IDS map claim from mapping-candidate-selection §8, the one invocation then maps each source into every home it has. The mapping stage runs only when the decision below allows it, because it spends on the reasoning seat.

§5 — JT-60SA proof

From the ITER host, run imas-codex discover run jt-60sa --dry-run. Then run it for real with --only signals-enrich under a small cap. The dry run must name every stage, with wiki and documents skipped and their probe results as reasons. The real run must enrich without touching the facility. § Decisions

What is the sequence command called?

The recommendation is discover run . It reads as an action beside discover status and discover clear , and it does not promise that every stage runs, which a skipped stage would contradict.

Does the sequence run imas map run by default?

The recommendation is opt-in. The mapping stage spends on the reasoning seat and writes bindings a person validates. Discovery up to candidates is cheap and safe to repeat.
