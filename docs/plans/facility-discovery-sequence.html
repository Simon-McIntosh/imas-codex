§1 — Why one command

Taking a facility from nothing to IMAS mappings takes seven commands today: discover paths, code, documents, wiki, signals and map, then imas map run. The operator has to know their order: code and documents read the paths that paths scored, and signal enrichment reads the wiki and code context those stages leave in the graph. The operator also has to know which stages can reach the facility at all. For JT-60SA run from the ITER host, the wiki and document sources sit behind tunnels through a laptop reverse tunnel. Every SSH stage fails whenever that hop is down. The graph-only stages, signal enrichment, discover map and imas map run, can always run.

One command, given a facility, runs every stage whose prerequisites hold, in dependency order. It skips the stages it cannot run, and says why for each one. Re-running it continues where it stopped, because every stage's claim loop is already idempotent.

§2 — Stage registry and access probes

A stage registry in imas_codex/cli/discover/sequence.py lists the stages in order. Its stages are finer than the six domains of DISCOVERY_DOMAINS (imas_codex/cli/discover/common.py:30): signals splits into scan, enrich and check, and mapping is not a discover domain. Each stage that runs a discover command therefore records its domain, drawn from that tuple. The mapping stage, which runs imas map run, records none. A test fails when a domain has no stage, so adding a domain cannot leave the registry stale. For each stage it records the command that runs it, what the stage needs, the stages whose output it reads, and the existing pending-work predicate that says whether it has work. Each stage keeps exactly one owner. The registry points at the domain's stage function, which §3 folds out of the domain's former click command, and adds no second implementation.

  • candidates: has_pending_candidate_work (imas_codex/ids/workers.py:404);
  • mapping: has_pending_mapping_work and has_pending_validation_work (imas_codex/ids/workers.py:386–395).

Documents has its checks only as private helpers in imas_codex/discovery/documents/pipeline.py, and both stay as they are. Its image-score check, _has_pending_image_scores (:74), is not a copy of has_pending_image_work (imas_codex/discovery/base/image.py:354). The pipeline's check counts ingested images that no worker has claimed, which is what its workers can take next. The image module's check counts ingested images with no description, including those a worker holds. The image module's check also returns False when the query fails. Replacing one with the other would change which images the document pipeline treats as pending. The module instead gains one public has_pending_work(facility) for the registry. It is true when either private check is true. The private checks raise on a failed query, so a graph fault reaches the runner as unreachable and never as nothing to do. That is one public definition added and nothing removed. The registry's documents stage calls only has_pending_work, never has_pending_image_work.

Every stage ends in one of four outcomes, each with a reason: ran (counts done and remaining), skipped: not configured (for example no wiki_sites), skipped: unreachable (the probe's own result), and skipped: nothing to do (its pending-work predicate is false). A stage whose input stage was skipped still runs if the graph already holds that input from an earlier run. A first run of code needs scored paths, and a later run can reuse them.

§ Decisions

What is the sequence command called?

The lead chose the bare group, imas-codex discover FACILITY, without a run subcommand, as other groups do: host.py's _HostGroup routes an unknown first argument to a hidden subcommand, so imas-codex discover jt-60sa runs the sequence while imas-codex discover signals jt-60sa still reaches its subcommand.

Does the sequence run imas map run by default?

On 2026-10-08 the lead reversed the earlier choice: the mapping stage runs only when named, as --only mapping, because mapping writes IMAS bindings, it is the critical step and needs more work, and JT-60SA's native COCOS is not yet established. Candidates stays in the default run, because it writes candidate routes rather than IMAS mappings and mapping reads them.
