§1 — Why this exists

A read-only audit on 2026-09-01, commissioned only to decide whether a review rehearsal could run on an isolated graph, found two defects that have nothing to do with that rehearsal and outlive it. Both share one shape: a safeguard that is named and documented, and does not hold. Neither was found by reading the documentation, which asserts the opposite; both were found by walking the code.

The audit is recorded at graph-substrate-audit. It returned a no-go, and the rehearsal it was serving is a separate plan's problem. What belongs here is the reason the answer was no.

§2 — The function named for backing up data does not back up data

backup_existing_data() writes zero-byte graph_data_existed.marker files. It records that data was present, not the data. So the recovery directory looks populated to anyone who lists it, the call site reads as protective, and there is nothing to restore from.

Measured state at the time of the audit: the backups directory contained no dump at all. The newest archive anywhere was 2,457,088,786 bytes dated 2026-08-27 12:49, while live database files had been written the same afternoon as the audit — data/transactions/neo4j/checkpoint.0 at 2026-09-01 14:16:59. The live directory was 15,058,189,845 bytes. A five-day-old archive against a 15 GB live store is not a backup, and the thing that was supposed to make one produces a placeholder.

This is the more dangerous of the two defects, because it is silent in the direction that flatters: a marker file present in a recovery directory reads as evidence of safety. The fix is that a function claiming to back up data either produces a restorable artifact or fails loudly, and that a caller can ask “is there a current backup?” and get an answer derived from the artifact's own modification time against the live store's, not from a marker's existence.

§3 — The environment variable does not select the target; the symlink does

User-facing documentation describes IMAS_CODEX_GRAPH as selecting the graph. In resolve_neo4j() (imas_codex/graph/profiles.py:389) the location chooses the host and ports, while data identity comes from a single active neo4j symlink. There is no per-command destination profile for load or clear. Both therefore act on whatever that one symlink currently resolves to.

The practical consequence is that isolating a destructive operation by setting an environment variable — which is what the documentation invites — does not isolate anything. An operator who believes they are clearing a scratch graph clears the live one, and per §2 there is nothing to restore.

§3b — Where the target check belongs, and where it must not spread

Measured before dispatch so the fix does not widen unnecessarily. graph_load and graph_clear both live in imas_codex/cli/graph/data.py (lines 496 and 1231), so the check has one natural home. resolve_neo4j has twelve callers — settings, graph/__init__, neo4j_ops, client, profiles, health, cli/graph/registry, cli/tunnel, cli/graph/data, cli/release, cli/compute, cli/services — and most are read-only consumers that connect rather than destroy.

So the destination requirement belongs at the destructive command boundary, not threaded through the selector. Adding a destination parameter to resolve_neo4j would put a twelve-file blast radius behind a two-command problem, and would oblige every read-only caller to name a target it has no opinion about. The check the locked decision requires — the command names its destination and refuses when the resolved symlink disagrees — is expressible where the symlink is already resolved for a destructive purpose. Four test files reference the load or clear surface (test_graph_cli_package, test_dd_resolutions, test_docker_embedded, graph_mcp/conftest) and must be in scope from the start, because a rename or signature change whose references are left unscoped is exactly what stopped the backup node at its fence.

§4 — Deliverables

  • A backup routine that produces a restorable artifact or fails loudly, with the marker-only path removed rather than left beside it.
  • A currency check answering “is there a current backup?” from the archive's modification time against the newest live database file, so the answer cannot be satisfied by a stale archive or a marker.
  • An explicit destination on every destructive graph command, so load and clear name what they act on instead of inheriting it, and refuse when the resolved target does not match the name given.
  • Documentation corrected to describe the symlink as the data selector, with the environment variable's real scope stated, so the safe procedure and the documented procedure are the same procedure.
  • A regression proving a destructive command aimed at a scratch target cannot touch the live directory, failing against the current code.
  • An archive naming contract carrying the code revision and a UTC timestamp, so no filename asserts a property that decays. The 2026-09-01 dump landed as codex-current-20260901T125005Z.tar.gz while its own internal manifest already recorded git_commit 6fc745cf, version 5.3.0rc7.dev2213 and its timestamp, and its inner directory already followed the established imas-codex-graph-dev-<sha> convention — so the producer discarded identity it was holding and stamped a mutable claim in its place. “Current” is not a name, it is a computed comparison between archive and live modification times, which is the check above; a filename that asserts it will be wrong within days and cannot be corrected without breaking every receipt that cites the path. Note the existing exports/ convention omits a timestamp, so two dumps at one revision collide — the contract must carry both.
  • An offsite currency figure, measured rather than assumed. Every local restore point shares one GPFS filesystem, so a filesystem loss is bounded by the newest offsite copy, not the newest local one. The local graph manifest records its last push as 5.3.0rc6.dev91-g2479801d7.d20260706-r1, indicating roughly two months of exposure — but that is the local record of what was pushed, not a registry query, so the first task is to confirm it against the registry and only then decide whether release-pinned offsite copies are an adequate floor.
  • The graph service submitted to the partition its compute_locations entry declares, so partition: titan stops being dead config, with the correlated-failure trade recorded where an operator will read it.
  • Node and label counts recorded in the archive manifest, so a backup can state what it contains without a trial restore. The current manifest carries the code revision and format only, which identifies compatibility but not scope.

§ Decisions

How should a destructive graph command establish its target?

Locked by the lead 2026-09-01. load and clear must NAME their destination and refuse when the resolved symlink disagrees. The grounds are measured on this workstation rather than preferred: resolve_neo4j() at graph/profiles.py:389 takes the host and ports from the location, while DATA IDENTITY comes from a single active neo4j symlink, and neither load nor clear accepts a destination. So IMAS_CODEX_GRAPH - which user-facing documentation describes as selecting the graph - does not isolate a destructive command at all, and an operator following the documentation would have been clearing the live store while believing they were clearing a scratch one. That gap ran alongside a second: backup_existing_data() writes zero-byte markers, so the recovery directory looked populated with nothing in it. Together they put a 15,058,189,845-byte live graph one wrong symlink from unrecoverable destruction on the day this was locked. Rejected alternatives and why: printing the resolved path with an interactive confirmation protects only interactive use, and the invocation that actually took the graph down was a scripted service restart, not a human at a prompt; a protected-name denylist blocks the worst case but leaves every newly created production graph unprotected until somebody remembers to add it, which is the same absence-as-permission shape the audit was commissioned to find. The cost accepted is a required argument on every invocation.

When a backup cannot be produced, what should the caller experience?

Locked by the lead 2026-09-01 as the full posture rather than the narrow one: point both destructive call sites at a REAL dump, ABORT the operation if that dump fails, and RENAME the marker function to say what it does. The context that made this decidable was enumerated rather than assumed, and it removed the coordinator's own stated caveat. backup_existing_data has EXACTLY TWO CALLERS, both destructive - cli/graph/data.py:582 as pre-load and cli/graph/registry.py:808 as pre-pull - so there is no hot path and the blast radius of aborting is precisely graph load and graph pull, the same two commands the destructive-target decision governs. THE DEFECT IS IN THE NAME, NOT THE DOCSTRING: the function is documented as 'Create a marker for pre-operation recovery (lightweight)' and does exactly that, touching a zero-byte graph_data_existed.marker. Its own docstring never claimed a backup; the NAME does, which is why the defect survived - anyone who opened the function would have seen the truth, and nobody needed to. AND A REAL BACKUP ALREADY EXISTS UNUSED IN THE SAME FILE: backup_graph_dump() produces a genuine neo4j-admin dump. So this was never a trade between protection and speed - two destructive commands were calling a marker-writer while the real thing sat beside it. The cost objection also largely dissolves because load and pull already stop the service to replace the data, so a dump adds time to an operation that is already stop-the-world. Rejected: fail-closed alone would harden a function that still produces nothing recoverable, so the operation would proceed with no way back, merely more reliably; warn-and-proceed on a failed dump reproduces exactly the silent-exposure shape that left a 15 GB live graph with no current backup; rename-only fixes the misleading name while leaving both destructive commands genuinely unprotected.

§ Followups

Make graph recovery real, then make destructive commands name their target

Two decisions are open and both change the shape of the work, so lock them before dispatching: what establishes a destructive command's target, and whether a failed backup aborts the operation that asked for protection. The measured starting state is in §2 and §3 and does not need re-deriving. Order matters: recovery before restriction, because the currency check is what makes every later change verifiable.
