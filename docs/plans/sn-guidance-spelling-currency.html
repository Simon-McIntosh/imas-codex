§1 — A pointer is not a spelling, and only one of them was measured

The foreign-key migration 23c4b55a left two kinds of residue behind, and they are easy to conflate. One is a spelling — a name the schema no longer declares. The other is a pointer — a reference to a location that has since moved. They rot for different reasons and no single check finds both.

The spellings are clean, and this plan does not claim otherwise. sn-graph-identity-convention shipped with the clause no file under AGENTS.md, agents/, or imas_codex/**/AGENTS.md names a spelling the schema no longer declares, and that clause holds: those files are free of sn_id, sn_ids, docs_review_resolution_method and the plural axis token. Where they name produced_sn_id and terminal_sn_id they are correct, because both are still declared.

What rotted is three line-number anchors, and a spelling grep cannot see a line number by construction. That is a coverage boundary, not a false claim and not a failed detector. The defect is that the measure was narrower than the standing rule it served: guidance already requires that whenever a doc cites an anchor you open it and confirm it exists, because a pointer to something moved is worse than no pointer — the reader cannot grep for it and cannot tell whether they are missing context or chasing a ghost. The measure tested spellings and never tested anchors.

One further item sits outside that plan's scanned set entirely: the schema's own prose. standard_name.yaml is neither an AGENTS.md nor under agents/, so nothing scanned it — and it is the authority every other file cites.

The most valuable thing to record here is what must NOT be touched, because a careless sweep would be far more damaging than the defect. The rule applies to declared generic foreign keys only. Semantically specific slots keep their names and are correct: StandardNameSource.produced_sn_id is the scalar mirror of PRODUCED_NAME, and StandardNameSourceRetry.terminal_sn_id names a terminal identity. Both remain declared in the schema.

Separately, graph_ops.py alone contains 318 occurrences of a bare sn_id or sn_ids token, and workers.py another 190. These are Python parameter names, local variables, dataclass fields and UNWIND row keys — a different namespace from graph properties, and not in scope. Renaming them would be a large diff that changes no graph behaviour while risking the writers this programme depends on.

§4 — Fix the pointer style, not just the numbers

Re-pinning three line numbers into a 3,600-line schema would restore the pointers and guarantee they rot again on the next slot insertion — this migration moved them by roughly twenty lines. The durable repair is to cite class and slot name, which a reader can grep and which survives any edit that does not rename the slot itself. That is also the form the surrounding guidance already uses for every other reference.

§ Decisions

How should guidance reference a schema slot?

Class and slot. The line anchors rotted within hours of a single rename that shifted them about twenty lines, and a pointer a reader cannot grep is worse than no pointer because they cannot tell whether they are missing context or chasing a ghost. Re-pinning restores the pointers and schedules the same failure.
