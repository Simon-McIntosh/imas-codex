§1 — Why this outlives any one batch

A review batch is a conversation with a physicist conducted entirely through a catalog file and a generated site. That surface has to be honest about three things, and none of them is specific to WEST: what the reviewer is invited to change, what is machine-owned and would silently break provenance if edited, and what happens to an edit after it is merged. Every future batch inherits whatever this plan settles, which is why it is tracked apart from the batch that first needed it.

The prompt for it was a real reviewer's feedback on the first upstream attempt: the YAML was painful to review, it carried far more Data Dictionary content than a reader needed, entries ran together with no separation, and a declared scalar was being rendered as a vector. Those particular defects are fixed. What is not yet built is the part that keeps the surface honest once a reviewer starts typing into it.

§2 — What a reviewer may change

The reviewer is invited to change the standard name itself and its description and documentation prose, because those carry the physics judgement the review exists to capture. Machine-owned and not to be edited by hand: the unit, which comes from the Data Dictionary and never from an author; the entry kind; the status; every source binding field; the generated identity roles; and the file's structure, meaning entry ordering, blank-line separation and key order. That distinction is now written into the catalog's REVIEWING.md in plain sentences, framed as protecting a reviewer from silently breaking provenance rather than as restricting their judgement.

§3 — Enforcement, not just guidance

A guideline nobody checks is a guideline that decays. A continuous-integration job compares the base and head of every changed entry in a review pull request and fails when a machine-owned field differs, naming the identity, the field and both values so the reviewer can see exactly what to revert. A change confined to the name or the prose passes. The job reports and never rewrites the reviewer's branch, because silently correcting someone's edit is worse than refusing it.

The same discipline has a second half whose fold-back is built but has not yet been exercised live: after a review merges, the fold-back has to carry each edit back into the graph so that an accepted human change is traceable to the reviewer and the pull request that made it, and a change that fails the naming grammar is marked contested rather than absorbed. Proving that end to end, including that a trial run leaves no lasting change, is the work this plan still owes.

§4 — Deliverables

  • The editable-versus-machine-owned distinction stated in the reviewer guide.
  • A continuous-integration check that fails a review pull request touching a machine-owned field, proven live against one forbidden edit and one permitted prose edit.
  • An exercised approval fold-back carrying an accepted edit and a pipeline-refused edit, with the refusal visible to the reviewer rather than silent.
  • Evidence that the exercise can be unwound with no lasting change to the graph or the catalog, so a rehearsal never costs real state.
  • A traceability check: for an accepted edit, the graph records who changed it and which pull request carried it.

§ Decisions

When a reviewer edits a machine-owned field, does the check correct it or refuse it?

Locked: the job reports and never rewrites the reviewer's branch. Silently correcting someone's edit hides the disagreement and teaches nothing, while a named failure shows exactly what to revert and why the value is machine-owned.
