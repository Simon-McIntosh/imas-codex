Plan · ITER plant data

CODAC UDA signals in the graph, and the rename to iter-codex

An agent or a person finds an ITER plant signal by description, loads it over a bounded window, and plots it. The scanner and loader are built under the current project name; the rename follows in stages once the live standard-names work is at rest.

§1 — Where this starts: what the prototype and the live coordinator established

The graph is being extended from IMAS science data to ITER plant data, and the project is to be renamed from imas-codex to iter-codex. The first plant source is the CODAC UDA archive. A throwaway prototype (scripts/codac_uda_prototype/, report at docs/evidence/fragments/codac-uda-signals/prototype-report.md) measured the following on 2026-11-14.

§2 — A reader runs under the archive client's module environment from one call

Delivers. Project code running in the Python 3.12 environment can run a script under a facility data system's declared setup commands and interpreter on the local host, in one invocation, and receive its structured result, identically through the synchronous and the asynchronous entry point. Resolving a facility's data system to its setup and interpreter stays in the one facility-aware layer that already performs it. The CODAC UDA reader lives with the project's other facility-side scripts and is reachable this way.

Done when. A focused test shows a local run with a declared setup command observes the environment that command sets, and that a local run with no setup command behaves exactly as before, each shown on both the synchronous and the asynchronous entry point; the executor resolves no data system's setup or interpreter itself and receives them from its caller. A live control lists one variable through the same call from a compute partition, supplying the archive client's setup commands and endpoint itself from private configuration, and records count and elapsed time in the landing record. Negative control: with the setup step removed, the same test fails on both entry points because the client is not importable.

§3 — The schema can hold an archive, a pulse and a pulse category

Delivers. The LinkML schemas and facility configuration represent: a CODAC UDA data system for ITER with its setup, interpreter, named archive roles and read limits; an archive endpoint that is not an MDSplus server; a pulse with a string identity, absolute start and end in nanoseconds and its archive; and a pulse category with pulse membership. Operator-reserved endpoints are representable as excluded and are refused before any connection.

Done when. The generated models build; schema-driven tests pass; a fixture pulse with a non-numeric identity round-trips; and the ITER facility configuration validates with the new data system while every other facility's configuration validates unchanged. Negative control: a configuration naming an operator-reserved endpoint as a readable role is rejected by validation.

§4 — The variable catalogue for a named cohort is in the graph

Delivers. A registered CODAC UDA scanner. For a cohort of variable patterns declared in the private ITER configuration, each archive variable is a facility signal owned by the ITER facility, carrying its exact archive selector, its unit and description as the archive reports them, and the data-access record that reads it. Each signal records two archive roles separately: the archive whose listing supplied its metadata, and the archive verified to serve its data, which is unset until a read has returned samples from it. Each signal also records whether it is sampled continuously or archived on change, where the archive or a read establishes it. The scan is resumable and reports how many variables it enumerated, wrote and skipped, with reasons.

Done when. For one declared cohort, the number of signals in the graph equals the number the archive lists for the same patterns, counted independently in the landing record; a second run writes no duplicates; a sample of ten cohort signals has its data-serving archive confirmed by a bounded read that returns samples, with the counts confirmed and unconfirmed in the landing record; and the scan ran on a compute partition (rigel or all_debug). Modified graph statements pass under the graph marker. Negative control: a scan interrupted part-way reports itself incomplete and is not counted as a finished cohort; and a signal listed on an archive that returns no samples for it keeps its data-serving archive unset.

§5 — A signal is loaded by identity over a bounded window, with honest sampling

Delivers. A loader that takes a graph signal identity and either an absolute time window or a pulse, plus a sampling mode (raw, envelope or binned) and explicit sample and byte limits, and returns time and value arrays with the signal's name, unit, description, time base, the query issued and the sampling evidence. Whether the result is decimated is reported as true, false or unknown, and is never taken from the client's own flag alone. Structured-record fields and string-valued signals are loadable. Results are cached by archive, selector, bounds and sampling settings.

Done when. One live two-second interval of one signal loads in raw and in envelope mode from a compute partition, with sample count, time span and elapsed time in the landing record; a repeat load is served from the cache; a request beyond the limits is refused before any fetch; for one identical request the scanner's validity check and the loader return the same samples, and for one failing request the same error classification. Negative control: a paged raw read issued without the explicit no-decimation setting fails the cadence test, as it does in the prototype.

Negative control: a name that does not follow the convention is recorded as not conforming and gets no component.

§12 — Every readable archive variable is catalogued with all the metadata the archive holds

Delivers. A private catalogue store, outside the repository and outside the graph, covers every variable the two readable archives list. Only the pilot set already written to the graph stays there; the remaining variables enter the graph later, through the discovery pipeline's own command, once their node shape is designed in the plan iter-signal-context-and-enrichment. In the store, each variable carries every metadata field the archive reports for it: unit, description, data type, structure fields, and sampling kind and first and last sample time where the archive supplies them. A field the archive does not supply is recorded as absent, never as an empty value. A variable the archive lists but refuses metadata for is still catalogued, with a metadata state of unavailable and the archive's error code, so the store holds every listed variable and says which ones the archive would not describe. Each variable records every archive that lists it. A census records how many distinct variable selectors each archive lists, how many both list, and the count of their union. The scan runs in resumable batches.

Done when. The landing record gives each archive's census count, the number of selectors listed by both, the count of the union, and the store's count, which equals the union; the graph's count of ITER signals before and after, which are equal; the number of variables carrying each metadata field; the number in each metadata state, available and unavailable, with the unavailable ones broken down by archive error code; and the elapsed time. A second run adds no rows to the store, and a scan interrupted part-way resumes without refetching completed batches. The scan ran on rigel, and where it cannot finish inside one job the landing record gives the measured rate and the completed fraction of each job. The code that catalogued the pilot set passes its tests, with modified graph statements passing under the graph marker. Negative control: a variable whose metadata request fails is stored with the unavailable state and its error code, never as available with empty metadata; and a run of the scan changes no graph count.

§ Decisions

Are the fork and the iterorganization upstream repository renamed, and who does it?

A repository rename is outward-facing and needs the organisation's agreement. GitHub redirects the old address, but release automation, registry ownership and badges move with it.

Both the fork and the organisation repository are renamed; the lead reports that agreement with the organisation has been reached. Container images do not move with a repository rename and are migrated separately.

Does the Python import package become iter_codex , or does only the user-facing name change?

The package name is in 138,394 places and in every in-flight worktree. Changing only the distribution, command and MCP key is far smaller, and leaves an import name that no longer matches the product.

The import package becomes iter_codex, in the last stage of the rename at a quiet window, so the import name matches the product. The stored graph templates that import the old name migrate with it.

What do the two servers advertise after the rename?

Today the client key is imas-cx and the data-dictionary server is imas-dd . The data-dictionary server is about IMAS and both sessions consulted say it keeps its name.

The full server advertises iter-cx. The data-dictionary server keeps imas-dd because it serves the IMAS data model.
