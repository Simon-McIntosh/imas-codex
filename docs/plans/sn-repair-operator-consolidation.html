§1 — Why this plan exists

Standard Name integrity repair works. It is also the slowest thing in the project, and the cost is structural rather than incidental: every defect class gets its own bespoke signed operator. On 2026-08-20 a single execution session against sn-graph-wide-integrity added 2,102 lines of production code and 1,006 lines of tests to repair roughly 194 graph relationships and retire 16 names — about eleven lines of production code per repaired edge. A further 5,236 lines were prose describing the work, so 63% of the session's output was documentation rather than mechanism.

The result of repeating that pattern is visible in one file. graph_ops.py runs to 25,912 lines and holds 22 apply_* / repair_* / retire_* / reconcile_* functions, of which ten consume a signed authority artifact and are this plan's target: apply_adjudicated_source_dispositions, repair_scalar_projection_mismatches, repair_normalization_peel_parent_units, retire_signed_provenance_orphans, retire_signed_dual_authority_targets, retire_ineligible_standard_name_sources, reconcile_error_siblings, reconcile_lifecycleless_standard_name_stubs, reconcile_structural_edges_for_standard_names, and detach_signed_stale_source_bindings in provenance_lifecycle.py. Three were added in one session — against a plan whose own §7 states "no new manifest machinery". The machinery grows by accretion because there is no generic path, so every new defect class, and every new mutation kind, is a new function.

This plan does not question the safety discipline. That discipline is earning its keep: in the same programme the guards refused a proposed bulk retirement of 85 accepted names justified by identical boilerplate reasoning, refused a manifest whose admitted set had drifted outside its signed authority, refused a retirement that would have stripped live producers, and refused a geometry fold that would have collapsed a reflecting surface's centre onto a sphere's centre of curvature. Each refusal prevented real damage. The argument here is that one operator can enforce all of it, and twenty-two need not.

§2 — What every one of the twenty-two already shares

The operators differ in which rows they select and what they mutate. They are near-identical in everything that makes them safe, and that shared part is the whole of the ceremony:

  1. verify a committed authority artifact by file digest and by canonical signed-payload digest;
  2. derive the executable row set from that artifact rather than from any caller-supplied list;
  3. capture a preview closure over sources, bindings, projections, targets and structural children, and emit a would_apply manifest;
  4. compare-and-set lock every participating node and relationship, then re-hash after locking;
  5. enforce guards — last-producing-source, structural legitimacy, out-of-allowlist immutability;
  6. write one receipt row per logical change;
  7. replay the exact manifest and require already_applied with changed=0;
  8. prove collateral immutability by per-row digests over the untouched closure.

Steps 1 and 3–8 carry no class-specific content whatsoever. Only step 2, the selection predicate, and the specific mutation in step 6 are genuinely per-class — and both are expressible as data in the authority artifact that already exists for every class.

§3 — A second cost: the authorities staleness-break each other

Because each operator signs a closure computed at its own preview time, any committed transaction invalidates every other operator's pending manifest and ledger baseline. This is not hypothetical: in one session it produced two separate fail-closed refusals. A signed manifest was refused because an intervening authorized detach moved its parent_manifest_sha256 even though the drift lay entirely outside its selected rows, and a second node refused because its StandardNameChange baseline was stale by 53 rows written by an authorized reconcile.

Both refusals were correct, and both were pure friction: the underlying repairs were sound and were applied unchanged once re-authorized. A single operator that regenerates its preview and re-reads its counters inside the applying invocation removes this class of stall entirely, because there is no cross-operator authority to go stale.

§4 — Scope

  1. Characterise the twenty-two. For each operator record its authority artifact shape, selection predicate, mutation set, guards, receipt operation name, and test location. The output is a table, and it is also the specification for the generic operator: anything it cannot express is a genuine extension point rather than an accident.
  2. Define one authority schema. A LinkML-declared artifact carrying the row set, per-row signatures, the selection predicate, the mutation kind, and the guard set each row must satisfy. Existing committed artifacts must be readable under it or convertible without re-signing, since re-signing would discard adjudication provenance.
  3. Implement apply_signed_manifest. One operator implementing the eight-step envelope, parameterised by mutation kind and guard set, with the preview and the counter baselines both read inside the applying invocation.
  4. Migrate class by class, newest first. Each migration must reproduce its predecessor's behaviour on a disposable graph before the bespoke function is deleted — including its refusal cases, which are the part that matters.
  5. Delete each bespoke operator as its own migration lands, not at the end. A parallel generic-plus-bespoke surface is worse than either alone, so no operator counts as migrated until its bespoke function is gone — but that is a per-operator gate, never a plan-wide one. Ten operators behind one all-or-nothing switch would be a big-bang refactor of the safety layer, which is exactly the risk profile this plan exists to reduce. Each migration is independently landable, revertible, and valuable.

§5 — Test strategy

The migration is only safe if the guards are proven equivalent, so behavioural equivalence is the gate, not code coverage. For each migrated class, the existing disposable-Neo4j suite runs unchanged against the generic operator and must produce identical admitted sets, identical refusal sets with identical reasons, identical receipt-row counts, and identical replay outcomes. A migration that changes which rows are refused has changed physics semantics and must be rejected regardless of how much code it removes.

One extra property is worth proving that no current operator proves: that two generic invocations over disjoint row sets cannot corrupt each other's collateral proof. That would retire the plan-wide serialization constraint which currently caps repair throughput at one transaction at a time.

§6 — Non-goals

  • Not a relaxation of any guard. The last-producing-source rule, structural-legitimacy authority, and out-of-allowlist immutability proof all survive verbatim. If consolidation requires weakening one, the consolidation is wrong.
  • Not the CLI surface. The archived 33-cli-harmonization proposes one manifest/apply/receipt contract across eight typed CLI intents. That is the same idea one layer up and is complementary; this plan is strictly about the operator layer beneath it.
  • Not the reconcile_* self-heal family, initially. Those run automatically post-drain rather than from a signed artifact, so they share only part of the envelope. Characterise them in §4 item 1, but migrate the signed-artifact operators first.
  • Not a rewrite of graph_ops.py. Shrinking a 25,908-line module is a welcome side effect, not the objective.

§7 — Sequencing and why this is backlog

This work is deliberately not scheduled into a sprint yet. It is not on the WEST release path: it makes future integrity classes cheaper without repairing any current defect, so scheduling it ahead of the catalog release would delay the release to speed up work that follows it. The natural trigger is the next SN integrity class that would otherwise need a twenty-third operator, or the WEST catalog release landing — whichever comes first.

One caution on timing. §4 item 4 requires reproducing each operator's refusal behaviour exactly, and those refusal cases are best understood while the repair programme that produced them is still fresh. Waiting until the knowledge has decayed raises the cost of the safest part of the work.

§8 — Three operators have no suite for the equivalence gate to compare against

The 2026-08-21 census found this, and it is a prerequisite rather than an exception. §5 makes behavioural equivalence the gate: a migrated operator must reproduce identical admitted sets, identical refusal sets with identical reasons, identical receipt counts and identical replay outcomes on its existing disposable-Neo4j suite. Seven of the ten have such a suite. Three do not — reconcile_structural_edges_for_standard_names, repair_normalization_peel_parent_units and reconcile_error_siblings carry only mocked or source-inspection coverage. For those three the gate has nothing to compare against, so migrating them under the §5 rule is not currently possible.

These are also exactly the three deterministic self-heal operators the census identified: no committed authority artifact and no durable receipt. That is not a coincidence — the absent suite and the absent artifact are the same gap seen twice, which is why §6 already defers this family. The consequence is a sequencing rule, not a scope cut: build the disposable-graph suite first, characterising each one's current refusal behaviour from its live code, then migrate. A suite written after the migration would be written against the generic operator and would prove nothing.

The seven covered operators are unaffected, including the retirement operator this sprint migrates first, so this does not gate the current wave.

§ Decisions

May the generic operator require re-signed authority artifacts, or must it read the existing committed ones as they stand?

Committed artifacts such as refused-target-orphan-adjudication.json and owner-geometry-rc66-partition.json carry adjudication provenance and per-row signatures produced by independent review. Re-signing them under a new schema would produce identical rows with new digests and no review lineage.

Recorded from the plan's own constraint rather than chosen afresh: §4 item 2 already requires that existing committed artifacts be readable under the new schema or convertible without re-signing, because re-signing would produce identical rows with new digests and no review lineage. Adjudication provenance is the expensive part of every one of these artifacts, so the generic operator adapts to their shapes. Lossless conversion with retained original digests stays available as a fallback for a specific artifact that cannot be read in place; re-signing is rejected.

Should the generic operator aim to retire the one-mutator-at-a-time constraint?

Repair throughput is currently capped by the rule that concurrent mutators invalidate each other's out-of-allowlist immutability proofs. A per-row-scoped collateral proof could permit disjoint concurrent applies, but it weakens the strongest evidence the programme relies on.

§ Followups

Characterise the twenty-two signed repair operators before writing any generic one

Start at section 4 item 1, because it is both the cheapest step and the specification for everything after it. For each of the 22 apply_*, repair_*, retire_* and reconcile_* operators in graph_ops.py, record its authority artifact shape, selection predicate, mutation set, guard set, receipt operation name and test location. Anything the emerging schema cannot express is a real extension point rather than an oversight, so record those explicitly instead of smoothing them over. Do not write the generic operator in this pass and do not delete anything: the characterisation is what makes the migration safe, and it is worth doing while the refusal cases from the 2026-08-20 repair wave are still fresh.

Adjudicate the peel-unit child predicate before migrating that operator

The behavioural suite for repair_normalization_peel_parent_units pins the live predicate, which examines every child, so a normalization child carrying a null unit is refused.
