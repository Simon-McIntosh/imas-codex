What imas-codex Actually Is, Measured Before The Handover

Successor sessions receive this repository entirely through the planning layer. Anything that exists only in a retiring session's conversation is lost. This plan holds the measurements a successor needs and cannot re-derive cheaply: which features are reachable from real call sites, where a plan's impl overstates its code, and which couplings to shared machinery should be reduced to thin interfaces.

The standing hazard this plan exists against. A plan figure is an assertion by its author, not a measurement of the code. Four open sprints, 47 plans and an aggregate implementation_pct of 69.1 are the state as declared. Every number a successor acts on should carry the path and line that establishes it, because this repository has repeatedly found features that were documented, tested, and reached from nothing.

§1 · Implementation depth, per feature

For each pending plan, is the feature deep — implemented, covered by a test that would fail if it broke, and reachable from a call site production code takes — or shallow: a module nothing imports, a function no call site reaches, a flag nothing reads, or documentation describing behaviour the code does not have? The discriminator that earns this section its keep is whether a symbol's only references are its own definition and its own tests.

§2 · Where plan status disagrees with the code

Plans whose declared status or impl is not what the code supports, in either direction. Both directions matter: an overstated plan sends a successor to work that is done, and an understated one hides landed capability.

§3 · Thin interfaces to shared machinery

Where this repository reimplements or couples tightly to machinery it does not own — the reckon crew and plan layer, the local lane and router, fleet and SLURM placement, imas-python data access, and GPFS paths and state files. For each, the refactor that would reduce it to a thin interface, and what that refactor would let a successor stop maintaining.

§4 · Critical next steps

What a successor should do first, in order, with what gates what. Distinguishes work that is blocked on a ruling from work that is merely unstarted.

Store minted_from repo-relative and repair the twelve dangling values

Twelve released catalog manifests carry provenance that resolves to nothing. catalog_release.py mints minted_from as an absolute reckon-worktree path. Of the fourteen committed manifests, twelve carry such a path and all twelve already dangle — the worktrees they name are gone. They span ship-s10-20260901 (6), ship-sli-20260904 (2), ship-wcr-20260903, ship-s10-20260908, ship-s10-20260907 and one unattributable, so the oldest have been dead for about three weeks, in released artifacts, with nothing reporting it.

No worktree reaped on 2026-09-24 appears among them, so that cleanup neither caused this nor is implicated. It is recorded here because the first framing of this finding was conditional and implied otherwise; the unconditional version is the worse one.

Why it matters more than its size suggests. Provenance is exactly the field an auditor trusts to trace a released standard name back to the tree it was minted from. A well-formed absolute path looks authoritative and is never re-resolved, so the failure is silent by construction — the same shape as a stale configuration read as current, or a guard that reports safety it does not provide.

The repair is small. Mint minted_from repo-relative, and rewrite the twelve existing values by prefix: the files they name still exist at the same relative paths inside the repository, so the rewrite is mechanical and loses nothing. A released manifest is an artifact, so treat the rewrite as a correction with its reason recorded rather than a silent edit.

Done when a fresh cut mints a repo-relative minted_from that resolves from a clean clone; the twelve existing manifests resolve from a clean clone too; and a test asserts that a minted value contains no absolute path, so the next mint cannot reintroduce it. The last clause is the load-bearing one: without it the repair is a correct implementation with nothing keeping it correct.
