§2 — Every selected home is answered or retried

The candidate stage can select several homes for one source, and two of them can sit in different sections of one IDS, for example magnetics/ip and magnetics/flux_loop. build_target_assignments (imas_codex/ids/mapping.py) builds one assignment per section, so the map stage asks once for each. Mapping state, though, is tracked per IDS:

  • claim_sources_for_mapping (imas_codex/ids/workers.py) refuses a source once any MAPS_TO_IMAS binding into the IDS exists;
  • refresh_mapping_status collects the selected edges' IDS names, so one binding marks the whole IDS bound.

Suppose the second section's answer comes back empty, or omits the source. A SignalMappingBatch need not account for every source it was asked about. Then the source reads validated, the empty home is never claimed again, and the run's partial report does not name it, because it counts only sources with no binding at all.

The repair records an outcome on each selected home: the selected MAPPING_CANDIDATE edge itself. home_outcome takes one of three values:

  • bound, once a binding into that edge's section persists;
  • declined, when the answer lists the source in unmapped for that section, with the reason stored as home_evidence;
  • unanswered, after a second answer that still does not account for the assignment; home_attempts counts the answers so far.

The rules that follow from it:

  • Claim: a source is claimable for an IDS while it has a selected edge into a section that is neither bound nor carries an outcome.
  • Status: refresh_mapping_status writes validated only when every selected section is bound or declined. An unanswered home leaves the source short of validated, and the validate stage's partial report names each one.
  • Coverage: the map stage judges whether an answer covers an assignment. A mapping whose target lies in the section counts, and so does an unmapped entry naming the source. The model's output schema does not change.

The new edge properties go wherever the MAPPING_CANDIDATE edge's properties are declared: the relationship description in imas_codex/schemas/facility.yaml, and imas_codex/graph/cypher_property_check.py if it adjudicates edge properties. That way the property checker passes the new Cypher.

§3 — An error bound attaches to one determined parent or none

match_error_signals_to_imas (imas_codex/ids/mapping.py) derives an error field from the binding of the signal the error belongs to. When the error signal's group key, with its error suffix stripped, misses an exact match, a fallback loop takes the first known key that contains it or is contained in it, then breaks. Take parents gasc_valve1 and gasc_main and an error key that strips to gasc: whichever parent the data mappings list first wins. The binding then carries mapping_type="error_derived" and evidence naming that parent, so the guess reads as a direct match, and changing the read order can silently move it.

The repair makes the fallback determined:

  • An exact key match keeps today's behaviour.
  • Otherwise the fallback collects every known key that shares a whole _- or :-delimited token sequence with the stripped key.
  • Exactly one such key gives that parent.
  • None gives no derivation.
  • Several give no derivation. The stage reports the error signal as ambiguous, naming the candidate parent keys, in its log and in the count it returns.

§4 — A filtered candidate run stays inside its filter

With --ids set, the candidate worker narrows each source's routed IDS list to the filter and stores the result unconditionally. A source routed only outside the filter therefore carries an empty list. retrieve_candidates and _merge_arms (imas_codex/ids/candidates.py) read an empty sequence exactly like "no routing information": list(routed_ids) or [UNSCOPED_ARM] searches the whole Data Dictionary. The consequences:

  • A run told to look only at magnetics judges a gas source against every IDS.
  • It can write a selected route for an IDS the operator excluded.
  • It drops that source from its own coverage without naming it.
  • It spends model calls on the exclusion.

The repair separates the two meanings. None means no routing information and searches unscoped, as it does now. An empty list means nothing is in scope, so the source is skipped for this run:

  • its claim is released untouched;
  • no candidate edge and no candidate_route are written;
  • the run summary counts it as filtered out.

_merge_arms refuses an empty list with a ValueError, so no caller can turn "nothing in scope" back into "everything". §2 also edits imas_codex/ids/workers.py, so this node dispatches after §2's node has released that path.

§ Decisions

What happens to a selected home whose answer does not account for it?

An explicit unmapped entry with a reason is an answer: it records the home as declined and is never asked again. Silence is different. It may be a dropped batch, a truncated answer or a model that skipped the item. Retrying for ever spends calls on a home the model will not answer; never retrying turns one bad batch into a permanent gap.

Recommended: retry once, then record unanswered. One retry absorbs a dropped or truncated batch. The recorded outcome keeps the home visible in the partial report and out of the claim set until imas map clear resets it.
