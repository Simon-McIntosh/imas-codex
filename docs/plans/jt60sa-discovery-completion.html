JT-60SA Discovery Completion

Paths and wiki discovery for JT-60SA are complete; signals and code have never run, half the documents failed, and the handbook's signal tables entered the graph as empty forms. This plan closes those four gaps so the ambix machine map can join every EDDB channel to its handbook entry, PID and access template, and so search_signals and search_code answer for jt-60sa.

§2 — Signals and code: run the repaired EDAS scanner and discover the equilibrium sources

Every call the EDAS scanner makes was tested against nakasvr26 on 2026-10-05 and three defects were found and repaired in a prototype commit on this branch. Reference shot: the config carried reference_shot: 1000 with a TODO; EDDB returns nothing for E001000, and valid data starts at E080000. It is now 101173, the newest E-shot the catalogue listed. Enumeration: enumerate_edas.py read the catalogue without a shot and kept only name, alias, unit and description; it now reads the table for the reference shot and keeps the data class (T time series, O one-point, P parameter), the shot validity range and the UDP id. The prototype parks them in keywords (class:T, shots:E080000-) and aliases; the decision below is that typed slots come first, so the first node of this section extends schemas/facility.yaml with data_class, shot_range and pid on FacilitySignal, regenerates the models (a graph-touching implement node, never review), moves the scanner onto the slots and only then runs the scan. Access: eddbreadTime takes its time bounds as strings; the generated DataAccess template passed integers and raised. Check: the check script tested catalogue presence rather than data; it now reads a short window with eddbreadTime for class T and eddbreadOne for class O. The scanner unit tests (55) pass; the live scan has not been run.

Done-when: imas-codex discover signals jt-60sa -s edas --scan-only lands one FacilitySignal per (category, data name) for E101173 with class, shot range and alias carried, at least 741 signals across MAG, MDAC, PSRC, FAME and MMSYS (the census in jt60sa-eddb-census is the floor), the check stage passes for the flux loops, probes and coil currents it names, and enrichment runs under a cost cap with the Japanese descriptions translated. §3 — The handbook tables are CGI forms: ingest them from EDDB, and mark dynamic pages

The JT-60SA Data Handbook page links seven per-database tables (CategoryInformation?db=EDDB, DataInformation?db=EQDB, FAME, LCDB, MBDB, PMDB, UDDB). Each is a TWiki topic whose body is a search form and an empty table that a CGI plugin fills from the database at render time. The twiki_raw adapter reads the topic source over ssh, so each landed as a one-chunk page containing only column headers (Category, DataName, PID No., Unit, Description, Shot, State) and a form. The rendered page cannot be fetched either: the TWiki host 157.111.10.188 is on the nakasvr23 segment, unreachable from nakasvr26 (HTTP 000 through the tunnel and from the server itself on 2026-10-05), and the topic files are not present on nakasvr26.

The content those tables render is the EDDB catalogue itself, which the §2 scanner reads directly with the same columns, so the fix is structural rather than a scrape: (a) the §2 scan is the ingestion of the handbook tables, and the handbook page reaches its rows through the graph's existing signal-documentation linkage: the page's single chunk carries a DOCUMENTS edge (WikiChunk.documents_signals) to every FacilitySignal of the database it fronts, so search_signals and search_docs walk the one linkage the MCP tools already follow rather than a second edge with a second owner; (b) the wiki scorer gains a dynamic-page rule — a page whose rendered text is only table headers and form labels is marked with the database it fronts (a fronts_database property on WikiPage) rather than treated as content; WikiPageStatus stays a closed enum, the page keeps ingested so its chunk can anchor the edges, and the chunk's text becomes a one-line stub naming the database instead of the empty form. Interface accounting: fronts_database is the one new graph property this section adds and it retires nothing, because no existing WikiPage property records the database a rendered page is backed by; (c) the one-point and condition data keyed by PID No. (a nine-character key, four digits then five characters, read through eddbreadOne and eddbreadPara with an empty PID to enumerate) is enumerated as its own FacilitySignal group so the PID column is present in the graph.

Done-when: the seven handbook table pages carry a fronts_database value; every FacilitySignal from §2 is reached from its database's handbook page through a DOCUMENTS edge from that page's chunk; a PID-keyed one-point enumeration for E101173 is in the graph with its PIDs; and the MCP tools follow the edges in both directions — search_docs and fetch_content on a dynamic page return the signals it fronts (name, class, unit, PID, access template) instead of the empty form, and search_signals cites the handbook page — proved by search_docs("flux loop", facility="jt-60sa") returning the PSRC flux-loop signals beside the EDDB manual chunks and by fetch_content of the EDDB Category Information page listing its categories.

§5 — Handoff notes for the ITER host

Why ITER. This work was scoped from the WSL workstation and is picked up on the ITER host for the local-lane GPU compute (embedding and LLM enrichment) and because the graph and embedding server already run there as SLURM jobs (codex-neo4j 1278157 and codex-embed 1276248 on 98dci4-gpu-0002 on 2026-10-05). On ITER, GraphClient() resolves the SLURM node directly; no tunnel is involved.

Network policy, binding. No direct connection between JT-60SA and ITER is permitted in either direction. The permitted path is through the workstation: ITER's ssh config carries Host jt-60sa with ProxyJump laptop, and the laptop's reverse ssh forward is bound on the login nodes (port 2222, measured 2026-10-05), so ssh jt-60sa from ITER reaches nakasvr26 via the laptop. Every node of this plan therefore runs from the ITER host, the EDAS scan and the code scan included, provided the workstation's codex tunnel unit is up; enrichment, embedding and document ingest need nothing beyond ITER. The facility config comments were corrected to say so (commit c84a855fc). The TWiki host on the nakasvr23 segment is unreachable from nakasvr26; the wiki content in the graph predates the server migration.

Remote execution facts. The login shell on nakasvr26 pre-loads python/3.5.6, which cannot run the remote scripts (f-strings). The working recipe, measured 2026-10-05 and now in data_systems.edas, is module unload python/3.5.6; module load python/3.12 and then the module's own python (3.12.9, numpy 2.4.2, EDDB wrapper returns arrays). python3 stays the system 3.9 without numpy, /usr/bin/python3.12 has no numpy, and module purge drops the module path so the load silently fails. The scanner passes python_command and setup_commands to the remote executor; §6 is where this becomes a contract rather than a per-facility comment. The wrapper is /analysis/src/eddb/eddb_pwrapper.py with /analysis/lib/libeddb.so; set NUMPY = True for arrays. Run under nice -n 19. Measured call shapes, sizes and the full channel listing are in jt60sa-eddb-census.

What is committed and what is not. Committed on this branch: pypdf dependency; enumerate_edas.py, check_edas.py and the scanner repairs; reference_shot: 101173; the census research doc. Not run: the live EDAS scan, the code scan, the document re-ingest, the dynamic-page rule, the handbook-page DOCUMENTS linkage and the PID enumeration. The scanner stores class, shot range and UDP id in keywords as a stopgap; the locked decision is typed slots before the scan, so §2 begins with the schema extension and a build-models regeneration, which is a graph-touching node and must be dispatched as test or implement, never review or investigate.

Consumer. The ambix plan imas-ambix:jt60sa-machine-map gates its §5 census on §2 here and reads the census doc; its own handoff notes name the same facts from the map's side.

Order of execution. The interactive census is already done and recorded in jt60sa-eddb-census; it is the floor the scan is checked against, not a step to repeat. Run §2 first as scan-only, compare counts per category with the census, then the check stage, then enrichment under a cost cap; run the code scan before enrichment so enrichment has code context. §4 is independent of §2 and runs in parallel on ITER. §3 follows §2 because it links the scanned signals to the handbook pages. §6 is independent and may land first if the remote interpreter recipe needs generalising before §2 is dispatched. The ambix map's extractor and mirror (imas-ambix:jt60sa-machine-map §3) do not wait on this plan; its §5 census is gated on §2 here.

§6 — A remote environment contract per facility

Every remote step codex runs at a facility — signal enumeration, data checks, code scans, path scans — depends on an interpreter and a shell environment that the facility sets up differently: module loads on nakasvr26 and ITER, a project virtualenv on some hosts, an environment file of credentials or library paths on others. Today that knowledge has two homes, both per data system or unread: the DataSystemBase mixin (imas_codex/schemas/facility_config.yaml) gives every data system python_command and setup_commands, which the signal scanners read and the signals pipeline merges; and data_access_patterns.setup_commands, a facility-wide key that no code consumes (tcv.yaml sets it). A code scan, a path scan and the facility tool probe belong to no data system, so they fall back to a bare python3 with no setup, the same host's code scan and signal scan can disagree, and a wrong default fails as a syntax error inside a worker rather than as a configuration finding.

This section gives the host-wide recipe one home, a facility-level remote_environment block: ordered setup_commands (module unloads and loads, source of an env file, virtualenv activation), the python_command that is valid after them, the minimum interpreter version the remote scripts require, and the modules each scanner must import. Interface accounting: the block retires data_access_patterns.setup_commands (removed from the schema and migrated out of tcv.yaml), and the DataSystemBase keys are kept with one role only, the per-data-system override of the block (TCV's MDSplus system sources a profile a plain Python call does not need), so there is one default and one override rather than two unrelated surfaces. One resolver in the facility-aware layer (imas_codex/remote/tools.py, which already resolves ssh_host and the nice level from facility config) merges the block with a data system's own keys and passes the result down to the executor as parameters; the executor itself stays facility-agnostic, as its contract states. The facility probe that already exists is extended, not duplicated: imas_codex/remote/python.py owns remote interpreter detection (get_python_status) and the version floor (PythonVersion.meets_minimum, MIN_PYTHON), and imas-codex tools status <facility> already prints that status beside check_all_tools (min_version floors, missing_required / version_too_old). The one gap is that get_python_status probes the login shell's interpreter and cannot see a module-loaded one, so it learns to run under the facility block's setup commands and to report the block's floor through meets_minimum, and check_all_tools gains only the importability of the libraries each scanner needs (numpy and the EDDB wrapper here; MDSplus or UDA elsewhere). One probe owns the facility-environment truth and no new CLI command is added; discover signals and discover code run that check before a remote scan and refuse when the floor is not met, so an unmet environment is a finding with the fix command, not a traceback. Done-when: the block exists in the facility schema and in jt-60sa.yaml, iter.yaml and tcv.yaml; data_access_patterns.setup_commands is gone from the schema and the facility files; every remote script launched through the facility-aware layer carries the block; and imas-codex tools status jt-60sa passes on nakasvr26 with the 3.12 recipe and fails, naming the floor, with the recipe removed.

§ Decisions

Do data class, shot range and PID become typed FacilitySignal slots now, or stay in keywords for this plan?

Typed slots need a schema change and model regeneration across the fleet; keywords work today but are not queryable by type.

Lead's choice 2026-10-05: data class, shot range and PID are the keys the ambix census and the handbook linkage query on, so they are typed FacilitySignal slots before the first scan rather than parsed out of keywords later. Accepted cost: the scan waits on a schema extension and a build-models regeneration, dispatched as a graph-touching implement node. Rejected: keywords-then-migrate, which would have scanned a day earlier but written 741 signals in a shape that must be rewritten.

How are CGI-rendered handbook tables represented?

Lead's choice 2026-10-05, with a condition: the handbook table pages are marked dynamic with the database they front and every scanned FacilitySignal links to its page through DOCUMENTED_IN, and the MCP tools must follow those links so search_docs and fetch_content on a dynamic page return the signals it fronts and search_signals cites the page. Rejected: synthesising table chunks from EDDB into the page, which duplicates FacilitySignal content as prose and drifts when the catalogue changes. Edge resolved at build (design review, 2026-10-05): DOCUMENTED_IN named the intent, not an existing relationship; the link is the graph's existing WikiChunk DOCUMENTS relationship (documents_signals) from the dynamic page's chunk, and the mark is a fronts_database property, so the decision's substance stands and no second edge or enum value is added.
