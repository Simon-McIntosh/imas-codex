JT-60SA Discovery Completion

Paths and wiki discovery for JT-60SA are complete; signals and code have never run, half the documents failed, and the handbook's signal tables entered the graph as empty forms. This plan closes those four gaps so the ambix machine map can join every EDDB channel to its handbook entry, PID and access template, and so search_signals and search_code answer for jt-60sa.

§2 — Signals and code: run the repaired EDAS scanner and discover the equilibrium sources

Every call the EDAS scanner makes was tested against nakasvr26 on 2026-10-05 and three defects were found and repaired in a prototype commit on this branch. Reference shot: the config carried reference_shot: 1000 with a TODO; EDDB returns nothing for E001000, and valid data starts at E080000. It is now 101173, the newest E-shot the catalogue listed. Enumeration: enumerate_edas.py read the catalogue without a shot and kept only name, alias, unit and description; it now reads the table for the reference shot and keeps the data class (T time series, O one-point, P parameter), the shot validity range and the UDP id, which the scanner stores as keywords (class:T, shots:E080000-) and aliases until the FacilitySignal schema gains typed slots for them. Access: eddbreadTime takes its time bounds as strings; the generated DataAccess template passed integers and raised. Check: the check script tested catalogue presence rather than data; it now reads a short window with eddbreadTime for class T and eddbreadOne for class O. The scanner unit tests (55) pass; the live scan has not been run.

Done-when: imas-codex discover signals jt-60sa -s edas --scan-only lands one FacilitySignal per (category, data name) for E101173 with class, shot range and alias carried, at least 741 signals across MAG, MDAC, PSRC, FAME and MMSYS (the census in jt60sa-eddb-census is the floor), the check stage passes for the flux loops, probes and coil currents it names, and enrichment runs under a cost cap with the Japanese descriptions translated. Then discover code jt-60sa scoped to /analysis/src/SAselene*, SAeqread, client_eqdbms*, SAeqfame and edas2 chunks the equilibrium sources so enrichment has code context and search_code answers for SELENE and the EQDBMS record layout. Both runs are heavy and run from the ITER host on the local lane, never on a login node.

§3 — The handbook tables are CGI forms: ingest them from EDDB, and mark dynamic pages

The JT-60SA Data Handbook page links seven per-database tables (CategoryInformation?db=EDDB, DataInformation?db=EQDB, FAME, LCDB, MBDB, PMDB, UDDB). Each is a TWiki topic whose body is a search form and an empty table that a CGI plugin fills from the database at render time. The twiki_raw adapter reads the topic source over ssh, so each landed as a one-chunk page containing only column headers (Category, DataName, PID No., Unit, Description, Shot, State) and a form. The rendered page cannot be fetched either: the TWiki host 157.111.10.188 is on the nakasvr23 segment, unreachable from nakasvr26 (HTTP 000 through the tunnel and from the server itself on 2026-10-05), and the topic files are not present on nakasvr26.

The content those tables render is the EDDB catalogue itself, which the §2 scanner reads directly with the same columns, so the fix is structural rather than a scrape: (a) the §2 scan is the ingestion of the handbook tables, and each FacilitySignal links to the handbook page for its database through a DOCUMENTED_IN edge so a reader of the page reaches the rows; (b) the wiki scorer gains a dynamic-page rule — a page whose rendered text is only table headers and form labels is marked dynamic with the database it fronts, rather than ingested as content; (c) the one-point and condition data keyed by PID No. (a nine-character key, four digits then five characters, read through eddbreadOne and eddbreadPara with an empty PID to enumerate) is enumerated as its own FacilitySignal group so the PID column is present in the graph.

Done-when: the seven handbook table pages carry status: dynamic and a fronts_database value; every FacilitySignal from §2 has a DOCUMENTED_IN edge to its database's handbook page; a PID-keyed one-point enumeration for E101173 is in the graph with its PIDs; and search_docs("flux loop", facility="jt-60sa") returns the PSRC flux-loop signals beside the EDDB manual chunks.

§4 — Document ingest: a missing dependency, then the queue

Of the 530 failed documents, 516 failed with No module named 'pypdf': the PDF extractor in discovery/wiki/pipeline.py imports pypdf, which was never declared in pyproject.toml, so every PDF on every host failed. It is now a declared dependency (prototype commit on this branch; pypdf 6.19.0). Seven WMF images fail because Pillow has no WMF loader; one PPTX was mis-typed; six MISSING RESOURCE links on the Code web are dead. The remaining 348 discovered documents and 447 pending ingests simply never ran.

Done-when: after uv sync on the ITER checkout, the 516 pypdf failures are reset and re-ingested with at least 90% succeeding; WMF files and dead links are marked unsupported with the reason rather than retried; the 447 pending ingests drain under a stated cost cap; and the eDAS quick reference, the EDDB manuals and the MECS and SELENE documentation PDFs are searchable through search_docs.

§5 — Handoff notes for the ITER host

Why ITER. This work was scoped from the WSL workstation and is picked up on the ITER host for the local-lane GPU compute (embedding and LLM enrichment) and because the graph and embedding server already run there as SLURM jobs (codex-neo4j 1278157 and codex-embed 1276248 on 98dci4-gpu-0002 on 2026-10-05). On ITER, GraphClient() resolves the SLURM node directly; no tunnel is involved.

Network policy, binding. No connection between JT-60SA and ITER is permitted in either direction. The EDAS scan, the check stage and the code scan reach nakasvr26 over ssh jt-60sa from the workstation only, so the remote halves of §2 and §3 run from the workstation and write to the ITER graph through the codex tunnel, while enrichment, embedding and document ingest run on ITER. The facility config comments were corrected to say so (commit c84a855fc). The TWiki host on the nakasvr23 segment is unreachable from nakasvr26; the wiki content in the graph predates the server migration.

Remote execution facts. The login shell on nakasvr26 pre-loads python/3.5.6, which cannot run the remote scripts (f-strings). The working recipe, measured 2026-10-05 and now in data_systems.edas, is module unload python/3.5.6; module load python/3.12 and then the module's own python (3.12.9, numpy 2.4.2, EDDB wrapper returns arrays). python3 stays the system 3.9 without numpy, /usr/bin/python3.12 has no numpy, and module purge drops the module path so the load silently fails. The scanner passes python_command and setup_commands to the remote executor; §6 is where this becomes a contract rather than a per-facility comment. The wrapper is /analysis/src/eddb/eddb_pwrapper.py with /analysis/lib/libeddb.so; set NUMPY = True for arrays. Run under nice -n 19. Measured call shapes, sizes and the full channel listing are in jt60sa-eddb-census.

What is committed and what is not. Committed on this branch: pypdf dependency; enumerate_edas.py, check_edas.py and the scanner repairs; reference_shot: 101173; the census research doc. Not run: the live EDAS scan, the code scan, the document re-ingest, the dynamic-page rule, the DOCUMENTED_IN linkage and the PID enumeration. The scanner stores class, shot range and UDP id in keywords as a stopgap; the typed slots belong in schemas/facility.yaml with a build-models regeneration, which is a graph-touching node and must be dispatched as test or implement, never review or investigate.

Consumer. The ambix plan imas-ambix:jt60sa-machine-map gates its §5 census on §2 here and reads the census doc; its own handoff notes name the same facts from the map's side.

§6 — A remote environment contract per facility

Every remote step codex runs at a facility — signal enumeration, data checks, code scans, path scans — depends on an interpreter and a shell environment that the facility sets up differently: module loads on nakasvr26 and ITER, a project virtualenv on some hosts, an environment file of credentials or library paths on others. Today that knowledge lives in two loosely typed keys under one data system (python_command, setup_commands) and in prose comments, so the same host's code scan and signal scan can disagree, and a wrong default fails as a syntax error inside a worker rather than as a configuration finding.

This section lifts it to one facility-level remote_environment block that every remote executor applies before any script: ordered setup_commands (module unloads and loads, source of an env file, virtualenv activation), the python_command that is valid after them, the minimum interpreter version the remote scripts require, and an optional per-data-system override. A discover preflight <facility> probe runs the block once, prints the resolved interpreter, version and importability of the libraries each scanner needs (numpy and the EDDB wrapper here; MDSplus or UDA elsewhere), and refuses the scan when the floor is not met, so an unmet environment is a finding with the fix command, not a traceback. Done-when: the block exists in the facility schema and in jt-60sa.yaml, iter.yaml and tcv.yaml; the executor reads it for every script; and the preflight passes on nakasvr26 with the 3.12 recipe and fails, naming the floor, with the recipe removed.
