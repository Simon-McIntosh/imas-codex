§5 — Handoff notes for the ITER host

Why ITER. This work was scoped from the WSL workstation and is picked up on the ITER host for the local-lane GPU compute (embedding and LLM enrichment) and because the graph and embedding server already run there as SLURM jobs (codex-neo4j 1278157 and codex-embed 1276248 on 98dci4-gpu-0002 on 2026-10-05). On ITER, GraphClient() resolves the SLURM node directly; no tunnel is involved.

Network policy, binding. No direct connection between JT-60SA and ITER is permitted in either direction. The permitted path is through the workstation: ITER's ssh config carries Host jt-60sa with ProxyJump laptop, and the laptop's reverse ssh forward is bound on the login nodes (port 2222, measured 2026-10-05), so ssh jt-60sa from ITER reaches nakasvr26 via the laptop. Every node of this plan therefore runs from the ITER host, the EDAS scan and the code scan included, provided the workstation's codex tunnel unit is up; enrichment, embedding and document ingest need nothing beyond ITER. The facility config comments were corrected to say so (commit c84a855fc). The TWiki host on the nakasvr23 segment is unreachable from nakasvr26; the wiki content in the graph predates the server migration.

Remote execution facts. The login shell on nakasvr26 pre-loads python/3.5.6, which cannot run the remote scripts (f-strings). The working recipe, measured 2026-10-05 and now in data_systems.edas, is module unload python/3.5.6; module load python/3.12 and then the module's own python (3.12.9, numpy 2.4.2, EDDB wrapper returns arrays). python3 stays the system 3.9 without numpy, /usr/bin/python3.12 has no numpy, and module purge drops the module path so the load silently fails. The scanner passes python_command and setup_commands to the remote executor; §6 is where this becomes a contract rather than a per-facility comment. The wrapper is /analysis/src/eddb/eddb_pwrapper.py with /analysis/lib/libeddb.so; set NUMPY = True for arrays. Run under nice -n 19. Measured call shapes, sizes and the full channel listing are in jt60sa-eddb-census.

What is committed and what is not. Committed on this branch: pypdf dependency; enumerate_edas.py, check_edas.py and the scanner repairs; reference_shot: 101173; the census research doc. Not run: the live EDAS scan, the code scan, the document re-ingest, the dynamic-page rule, the handbook-page DOCUMENTS linkage and the PID enumeration. The scanner stores class, shot range and UDP id in keywords as a stopgap; the locked decision is typed slots before the scan, so §2 begins with the schema extension and a build-models regeneration, which is a graph-touching node and must be dispatched as test or implement, never review or investigate.

Consumer. The ambix plan imas-ambix:jt60sa-machine-map gates its §5 census on §2 here and reads the census doc; its own handoff notes name the same facts from the map's side.

Order of execution. The interactive census is already done and recorded in jt60sa-eddb-census; it is the floor the scan is checked against, not a step to repeat. Run §2 first as scan-only, compare counts per category with the census, then the check stage, then enrichment under a cost cap; run the code scan before enrichment so enrichment has code context. §4 is independent of §2 and runs in parallel on ITER. §3 follows §2 because it links the scanned signals to the handbook pages. §6 is independent and may land first if the remote interpreter recipe needs generalising before §2 is dispatched. The ambix map's extractor and mirror (imas-ambix:jt60sa-machine-map §3) do not wait on this plan; its §5 census is gated on §2 here.

§9 — One probe per status call and one DataAccess writer

Two design notes from the §6 and §7 reviews, both small and both in files this plan already touched. (a) imas-codex tools status opens the remote environment probe twice: once inside check_all_tools, whose results["environment"] nothing renders, and once inside get_python_status, whose result cli/tools.py renders. probe_remote_environment has three callers: check_all_tools and get_python_status inside one tools status invocation, and ensure_remote_environment in imas_codex/cli/discover/common.py, the discover preflight called from discover/signals.py and discover/code.py, which is its own invocation and keeps its one probe. Within tools status, check_all_tools keeps the probe; get_python_status loses its own and takes the probed environment as an argument (environment=, already-resolved, optional only for the one call path that has no facility), so the interpreter floor is judged from the single probe and cli/tools.py renders the one result. The invariant is one probe per CLI invocation, and the test counts calls to probe_remote_environment across a tools status run and across a discover preflight separately. (b) The DataAccess node write now sits in three places in imas_codex/discovery/signals/parallel.py: the MDSplus branch constructs its node inline, the non-MDSplus branch in seed_worker merges it before signal ingest (the §7 ordering fix, deliberately placed so a scanner that returns access metadata with zero signals still writes it), and the phase-2 edge merge in ingest_discovered_signals depends on it. The one writer is therefore a function of its own, persist_data_access(data_access), that seed_worker calls as soon as a ScanResult carries data_access, before and independently of if result.signals, and that ingest_discovered_signals relies on rather than repeats. The MDSplus path in seed_worker is a bespoke branch that never calls scanner.scan() and builds no ScanResult; it keeps constructing its DataAccess object inline but hands it to persist_data_access instead of running its own MERGE, so the single writer has two callers and no second statement. Moving the write inside ingest_discovered_signals is rejected: that function returns early on an empty signal list and its only caller gates on result.signals, which would silently lose the thin-client write §7 landed.

Done-when: one probe per tools status invocation (a test counts calls to probe_remote_environment); rg 'MERGE \(.*:DataAccess' imas_codex/discovery/signals/parallel.py finds exactly one statement, inside persist_data_access; a test passes a ScanResult with data_access and no signals through seed_worker and asserts the DataAccess node is written; a test asserts the MDSplus branch produces ScanResult.data_access; the §7 ordering test still passes; pytest tests/remote tests/cli/test_tools_status_environment.py tests/discovery/test_signals_pipeline.py exits 0.

§17 — A retry path for embed-failed rows

The re-embed pass found that _fetch_unembedded in imas_codex/discovery/signals/parallel.py requires embed_failed_at IS NULL and that no reset clears it: SIGNAL_RESET_SPECS['discovered'] omits the field and would destroy enrichment. A row that failed to embed once is therefore never retried by the pipeline, and an operator must hand-write a property removal. Give the embed phase the claim shape the other phases have: retry a failed row after a cutoff (the claimed_at pattern), and add a documented reset that clears embed_failed_at alone. Done when a test shows a row with an old embed_failed_at is reclaimed by the embed phase and a fresh one is not, the reset spec clears only that field, pytest tests/discovery/test_signals_pipeline.py exits 0, and the same shape is applied to the code-chunk embed phase.

§ Decisions

Do data class, shot range and PID become typed FacilitySignal slots now, or stay in keywords for this plan?

Typed slots need a schema change and model regeneration across the fleet; keywords work today but are not queryable by type.

Lead's choice 2026-10-05: data class, shot range and PID are the keys the ambix census and the handbook linkage query on, so they are typed FacilitySignal slots before the first scan rather than parsed out of keywords later. Accepted cost: the scan waits on a schema extension and a build-models regeneration, dispatched as a graph-touching implement node. Rejected: keywords-then-migrate, which would have scanned a day earlier but written 741 signals in a shape that must be rewritten.

How are CGI-rendered handbook tables represented?

Lead's choice 2026-10-05, with a condition: the handbook table pages are marked dynamic with the database they front and every scanned FacilitySignal links to its page through DOCUMENTED_IN, and the MCP tools must follow those links so search_docs and fetch_content on a dynamic page return the signals it fronts and search_signals cites the page. Rejected: synthesising table chunks from EDDB into the page, which duplicates FacilitySignal content as prose and drifts when the catalogue changes. Edge resolved at build (design review, 2026-10-05): DOCUMENTED_IN named the intent, not an existing relationship; the link is the graph's existing WikiChunk DOCUMENTS relationship (documents_signals) from the dynamic page's chunk, and the mark is a fronts_database property, so the decision's substance stands and no second edge or enum value is added.
