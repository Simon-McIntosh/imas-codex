JT-60SA Mapping Study Expansion

The generated-map hand-off now works end to end for two JT-60SA systems, the pickup probes and the PF coil currents. This plan widens the study to six systems spread across different IDSs and turns each system into a measurement. It does so by scoring every generated row against imas-ambix's hand-built tokamap, which serves as the answer key.

Why the study is gated on a defect wave

The JT-60SA graph holds thousands of signal sources at enriched or checked, but only about 180 have reached the candidate stage, and almost none has a selected target. So candidates and target selection are the bottleneck, not discovery. Two hand-off iterations exposed defects that would corrupt a wider cohort silently:

  • enrichment pairs model results with the wrong signals;
  • a grouped source's members all read as their representative;
  • value signals are mapped onto their own error fields;
  • the map worker skips the selected sources it should take.

Running more systems before these are fixed would turn defects into confident wrong rows. Sections §1 to §7 are that defect wave. Sections §8 to §13 each run one system through the same fixed loop, and §14 writes the study up.

The per-system loop and its scorecard

Every system section runs the same six steps against the live graph, in this order:

  1. the cohort's signals read enriched_at after commit 5406bc598. The discovery coordinator, imas-codex-90, is regenerating JT-60SA facility-wide once §3 merges, and has already regenerated MMSYS. A cohort that regeneration has not yet reached is re-enriched with discover jt-60sa --only signals --focus <sources> --reset-to discovered, which needs §2;
  2. discover jt-60sa --only map --focus <sources> runs the candidate stage on the same sources;
  3. imas map clear jt-60sa <ids> followed by imas map run jt-60sa -i <ids> generates the mapping, on the local ids-mapping seat;
  4. imas map export jt-60sa -i <ids> --out /work/projects/imas_gpu/jt60sa/handoff/jt-60sa-<system>-handoff.json writes the hand-off document;
  5. the coordinator relays that path to the imas-ambix session, which imports it and drafts the tokamap;
  6. the coordinator records the agreement row that imas-ambix returns.

Each system reports the same five numbers:

Where imas-ambix holds no hand-built reference for a system, the row reports agreeing as "no reference" rather than zero. The other four numbers still stand.

§3 — Every member of a grouped source keeps its own identity

propagate_source_enrichment copies a representative's description to every member, and individualize_source_descriptions is meant to replace that copy with one description per member, built from its SignalNode description and member identifier. On JT-60SA the replacement never happened for the TC probe group: magPbTC11 to magPbTC23 all read "probe TC-10". The machine description therefore cannot place them, and imas-ambix reported magPbTC18 to magPbTC23 as unplaced. Find out why individualization left these members as copies, and fix the cause in imas_codex/discovery/signals/parallel.py. That may mean an ordering gap, a filter that skips grouped members, or a template that falls back to the representative. Do not add a second individualization path.

Done when: after a --focus re-run of the TC probe source, no two members of that source share a description, and each description names its own probe number. The receipt lists all fourteen. A unit test shows that a grouped source with two members whose node descriptions differ yields two different member descriptions. A second test shows that a singleton source is left untouched.

§4 — Error mappings come only from error signals

derive_error_mappings in imas_codex/ids/mapping.py runs two passes. The first walks every direct data mapping's target to its HAS_ERROR children and writes an error_derived binding from the same value source onto each error field. That claims a measured value is also its own uncertainty. The hand-off export already drops these rows, but the stage still writes them, and every consumer of the graph sees them. The second pass, match_error_signals_to_imas, maps sources that really are uncertainties, and it stays. Remove the first pass and its deduplication against it. An error field with no error signal is then simply unmapped.

Done when: a unit test shows that a direct value mapping with HAS_ERROR children produces no error binding. A second test shows that a source classified as an error signal still produces one (the positive control). The exclusion branch in imas_codex/ids/handoff.py is left in place as a guard, and its test still passes.

§7 — Every hand-off row carries its target's COCOS label

Every row of the current hand-off document carries cocos_label: null, although the graph holds the label. DD 4.x dropped some _like labels, and the graph build already repairs that: _backfill_cocos_labels in imas_codex/graph/build_dd.py carries labels forward from the versions that had them. It stores the label in IMASNode.cocos_transformation_type on the parent structure and its provenance in cocos_label_source. The graph shows 553 labelled nodes, for example magnetics/b_field_pol_probe/field as one_like from xml, magnetics/flux_loop/flux as psi_like from inferred_forward, and pf_active/coil/current as ip_like from xml. The export only reads that repaired label and never infers one itself. The lead decided on 2026-10-09 to follow the DD convention, with none where a path has no _like label.

In build_mapping_handoff in imas_codex/ids/handoff.py, fill cocos_label from the nearest ancestor of the target that carries cocos_transformation_type. Add cocos_label_source beside it, copied from that node's cocos_label_source, and write none for both when no ancestor carries a label. Both are additive keys, so format_version stays 1, and check_handoff_document and tests/fixtures/mapping_handoff_example.json learn them. If a mapped target in §8 to §13 turns out to need a label the graph lacks, that is a defect in the graph build, recorded as a followup on this plan. It is not patched in the export.

Done when: unit tests show two things. A target under a labelled parent carries that label and its source. A target with no labelled ancestor carries none for both (the negative control). A fresh live export of magnetics for jt-60sa gives its pickup-probe rows one_like from xml, and the receipt quotes one such row.

§18 — A plain pytest run resolves the tests package

About twenty test modules import shared helpers from other test modules, for example from tests.discovery.test_code_relevance import … in tests/discovery/test_code_facet_admission.py. tests/ has no __init__.py, and [tool.pytest.ini_options] in pyproject.toml sets no pythonpath. So pytest puts tests/ rather than the repository root on sys.path, and a plain uv run pytest tests/discovery/ from the root fails at collection with No module named 'tests.discovery'. Runs pass only when something else puts the root on the path: python -m pytest, or the worktree recipe's PYTHONPATH. The §3 merge gate hit this on 2026-10-09. Set pythonpath = ["."] in the pytest options so the path comes from the project configuration, not the caller's environment.

Done when: with no PYTHONPATH set, uv run --no-sync pytest -p no:cacheprovider tests/discovery/test_code_facet_admission.py collects and passes from the main checkout, and so does the same command over tests/standard_names/test_edit_parity.py. §20 — A bounded map run keeps what it mapped

§8's coil iteration ran imas map run jt-60sa -i pf_active -i tf twice under a time budget. Its map stage selected 18 sources and wrote rows for 12 pf_active/circuit, 8 pf_active/coil, 2 pf_active/supply and 1 tf/coil. Both runs persisted no MAPS_TO_IMAS edges. map_worker in imas_codex/ids/workers.py keeps every mapped batch in memory in state.mapping_batches, and validate_worker validates and persists an IDS only after the whole map phase is done. A run that stops on its time or cost limit therefore discards everything it mapped. A worker cannot hold one process for the full run, because its tool calls end at 10 minutes, so this blocks every larger cohort in the study. The coordinator ran the §8 map run unbounded in its own session as a stopgap.

Fix: when the engine stops on its deadline or cost limit, validate_worker still validates and persists the batches mapped so far for each IDS. The persisted mapping stays at status generated and records that it is partial: the sources still unmapped and the stop reason. A later run maps only those remaining sources and leaves the persisted ones in place.

Done when: a unit test stops the engine on its deadline after one of two sources is mapped. It finds that source's bindings persisted, the mapping marked partial with the other source named, and a second run mapping only the remaining source. The negative control restores persist-only-after-the-map-phase, and the first assertion then fails.

§21 — The assign phase ends when only handled sources remain

The coordinator's unbounded §8 run, imas map run jt-60sa -i pf_active -i tf, hung for at least eight minutes after its last mapping. At that point it held 35 mapped sources in memory and had persisted none. The cause is in assign_worker in imas_codex/ids/workers.py. At 09:39 the choice for ppEFCC3FB failed because the model named a path outside its shortlist. The worker released the source and added it to its handled set, but the assign phase's own pending-work check still counts that escalated source. So the assign phase never reports done. The map loop then waits on it forever, and validation never runs. A source that has no candidate to choose from is released the same way and hangs the run the same way. Commit 19dd9128c fixed this defect for the map phase, and §5 brought that fix onto main. §20 now persists what a bounded run mapped, so a deadline ends the hang without loss, but an unbounded run still never ends.

Fix: the assign phase's done check excludes the sources this run has already handled, as the map phase's does. A choice that fails or finds no shortlist ends that source's turn in this run.

Done when: a unit test drives the engine with one escalated source whose choice raises. The assign phase reaches done, the map phase completes, and validation runs and persists the other sources' bindings within the test's timeout. The negative control drops the handled exclusion from the assign phase's done check, and the test then times out.

§23 — Coil arrays carry their member identifier

The coils export left member_identifier null on 49 of its 50 rows. _member_identifier in imas_codex/ids/handoff.py takes a singleton array's identifier from a trailing number. The pickup probes end in theirs (magPbTC10), but JT-60SA's coil currents carry the member in the middle of the name, followed by the acquisition chain: curEF5LKAT, curCS1HiTe, curUFPLKAT, cur1TFLKAT. Which part of the name is the member is facility knowledge, so it belongs in facility configuration, not in a guess inside the exporter.

Fix: add a per-source-group member pattern to the facility configuration schema in imas_codex/schemas/facility_config.yaml. It is a regular expression with a named group member, keyed by source group. Declare the MMSYS pattern in imas_codex/config/facilities/jt-60sa.yaml, so that curEF5LKAT gives EF5, curCS1HiTe gives CS1, curUFPLKAT gives UFP and cur1TFLKAT gives 1. _member_identifier reads the facility's pattern for the row's group first and falls back to the trailing number. A group with no pattern behaves as it does today. Re-export the coils hand-off.

Done when: unit tests show the MMSYS pattern giving those four identifiers. A group without a pattern still uses the trailing number, and an array the pattern does not match keeps null, which is the negative control. Exporting pf_active and tf again gives a non-null member_identifier on every MMSYS row, quoted in the evidence.

§24 — A binding targets a data field, never a structure

Seven coils bindings target a structure node, such as pf_active/coil/current, pf_active/circuit/current or pf_active/supply/current, instead of its /data leaf. imas-ambix refuses them as "target is not a data field". validate_mappings in imas_codex/ids/mapping.py checks that a target exists but not that it holds values.

Fix: when a binding's target is a structure whose data child exists, validation retargets it to that child and records the rewrite in the binding's evidence. A structure with no data child is refused as an escalation. A source_property of time retargets to the structure's time child in the same way.

Done when: unit tests show pf_active/coil/current rewritten to pf_active/coil/current/data for a value binding and to .../time for a time binding, and a structure without data refused. The negative control removes the retarget, and the first test then fails.

§ Decisions

Which lane serves the ids-mapping seat during the study?

The lead ruled on 2026-10-09 that map requests use the local lane, configured in pyproject.toml , and never OpenRouter.

How many system sections may run against the graph at once?

The lead ruled on 2026-10-09 to run at maximum graph width. All six system sections dispatch together once the defect wave lands, each on its own IDS and its own focused sources, so their claims do not overlap. The picker routes every node; no lane is named.
