JT-60SA Mapping Study Expansion

The generated-map hand-off now works end to end for two JT-60SA systems, the pickup probes and the PF coil currents. This plan widens the study to six systems spread across different IDSs and turns each system into a measurement. It does so by scoring every generated row against imas-ambix's hand-built tokamap, which serves as the answer key.

Why the study is gated on a defect wave

The JT-60SA graph holds thousands of signal sources at enriched or checked, but only about 180 have reached the candidate stage, and almost none has a selected target. So candidates and target selection are the bottleneck, not discovery. Two hand-off iterations exposed defects that would corrupt a wider cohort silently:

  • enrichment pairs model results with the wrong signals;
  • a grouped source's members all read as their representative;
  • value signals are mapped onto their own error fields;
  • the map worker skips the selected sources it should take.

Running more systems before these are fixed would turn defects into confident wrong rows. Sections §1 to §7 are that defect wave. Sections §8 to §13 each run one system through the same fixed loop, and §14 writes the study up.

The per-system loop and its scorecard

Every system section runs the same six steps against the live graph, in this order:

  1. the cohort's signals read enriched_at after commit 5406bc598. The discovery coordinator, imas-codex-90, is regenerating JT-60SA facility-wide once §3 merges, and has already regenerated MMSYS. A cohort that regeneration has not yet reached is re-enriched with discover jt-60sa --only signals --focus <sources> --reset-to discovered, which needs §2;
  2. discover jt-60sa --only map --focus <sources> runs the candidate stage on the same sources;
  3. imas map clear jt-60sa <ids> followed by imas map run jt-60sa -i <ids> generates the mapping, on the local ids-mapping seat;
  4. imas map export jt-60sa -i <ids> --out /work/projects/imas_gpu/jt60sa/handoff/jt-60sa-<system>-handoff.json writes the hand-off document;
  5. the coordinator relays that path to the imas-ambix session, which imports it and drafts the tokamap;
  6. the coordinator records the agreement row that imas-ambix returns.

Each system reports the same five numbers:

§1 — Land discover signals --focus

The candidate stage already takes --focus, a list of SignalSource identities or a manifest naming them, through resolve_focus_items in imas_codex/cli/discover/common.py. The signals stage does not, so a system cohort cannot enrich only its own sources. Two files are saved from an earlier worktree: ~/.cache/imas-codex-signals-focus/signals-focus.diff, a 281-line diff touching imas_codex/cli/discover/signals.py and imas_codex/discovery/signals/parallel.py, and ~/.cache/imas-codex-signals-focus/test_signals_focus.py. Apply them to current main, reuse resolve_focus_items rather than a new parser, and finish whatever the diff left incomplete.

Done when: discover jt-60sa --only signals --focus magPbTC10 claims only the signals whose SignalSource is named. A unit test proves that an unnamed source in the same facility is left unclaimed (the negative control). An unknown focus identity fails with a usage error that names it. §2 — A focused reset touches only the focused sources

The swapped descriptions on curEF1LKAT, curEF4LKAT, magPbTC8 and magPbTC9 came from a matcher that paired results by prompt number against a batch in claim order. Commit 5406bc598, "match enrichment results to the signal they describe", fixed that on main with a test that reproduces the production symptom. The rows it wrote are still in the graph: a census on 2026-10-09 found all 4,632 enriched JT-60SA signals have enriched_at before the fix, 1,268 of them direct model results. The re-enrichment of the whole facility belongs to the discovery coordinator, who has been told. This study only re-enriches its own cohorts, which needs a reset scoped to them.

The --reset-to branch in imas_codex/cli/discover/signals.py scopes its reset by scanner and category, so that a scoped run never resets rows it will not then process. It ignores --focus. As written, discover jt-60sa --only signals --focus X --reset-to discovered would reset every JT-60SA signal and then enrich only X. The reset must take the same focus filter as the claims §1 adds.

Done when: a unit test shows that a focused reset passes the focused SignalSource identities into reset_to_status, and that a signal of an unnamed source keeps its status (the negative control). A live run of discover jt-60sa --only signals --focus magPbTC10 --reset-to discovered reports a reset count equal to that source's member count. Afterwards magPbTC8 and magPbTC9 are re-enriched through the same path, each describing its own probe, and the receipt records their before and after descriptions.

§3 — Every member of a grouped source keeps its own identity

propagate_source_enrichment copies a representative's description to every member, and individualize_source_descriptions is meant to replace that copy with one description per member, built from its SignalNode description and member identifier. On JT-60SA the replacement never happened for the TC probe group: magPbTC11 to magPbTC23 all read "probe TC-10". The machine description therefore cannot place them, and imas-ambix reported magPbTC18 to magPbTC23 as unplaced. Find out why individualization left these members as copies, and fix the cause in imas_codex/discovery/signals/parallel.py. That may mean an ordering gap, a filter that skips grouped members, or a template that falls back to the representative. Do not add a second individualization path.

Done when: after a --focus re-run of the TC probe source, no two members of that source share a description, and each description names its own probe number. The receipt lists all fourteen. A unit test shows that a grouped source with two members whose node descriptions differ yields two different member descriptions. A second test shows that a singleton source is left untouched.

§4 — Error mappings come only from error signals

derive_error_mappings in imas_codex/ids/mapping.py runs two passes. The first walks every direct data mapping's target to its HAS_ERROR children and writes an error_derived binding from the same value source onto each error field. That claims a measured value is also its own uncertainty. The hand-off export already drops these rows, but the stage still writes them, and every consumer of the graph sees them. The second pass, match_error_signals_to_imas, maps sources that really are uncertainties, and it stays. Remove the first pass and its deduplication against it. An error field with no error signal is then simply unmapped.

Done when: a unit test shows that a direct value mapping with HAS_ERROR children produces no error binding. A second test shows that a source classified as an error signal still produces one (the positive control). The exclusion branch in imas_codex/ids/handoff.py is left in place as a guard, and its test still passes.

§6 — map run --clear removes what map clear removes

In the second hand-off iteration, map run --clear left the previous bindings in place, and only a separate map clear followed by map run regenerated cleanly. The clear branch of the engine is in imas_codex/ids/workers.py (the state.clear path). It must route through the same owner as the map clear command, clear_mapping_bindings in imas_codex/ids/graph_ops.py, and not keep its own partial delete. This section follows §5 because both write workers.py.

Done when: a unit test shows that the engine's clear path calls the same owner as map clear. On the live graph, map run --clear for an IDS with existing bindings leaves no binding whose evidence predates the run.

§7 — Every hand-off row carries its target's COCOS label

Every row of the current hand-off document carries cocos_label: null, although the graph holds the label. DD 4.x dropped some _like labels, and the graph build already repairs that: _backfill_cocos_labels in imas_codex/graph/build_dd.py carries labels forward from the versions that had them. It stores the label in IMASNode.cocos_transformation_type on the parent structure and its provenance in cocos_label_source. The graph shows 553 labelled nodes, for example magnetics/b_field_pol_probe/field as one_like from xml, magnetics/flux_loop/flux as psi_like from inferred_forward, and pf_active/coil/current as ip_like from xml. The export only reads that repaired label and never infers one itself. The lead decided on 2026-10-09 to follow the DD convention, with none where a path has no _like label.

In build_mapping_handoff in imas_codex/ids/handoff.py, fill cocos_label from the nearest ancestor of the target that carries cocos_transformation_type. Add cocos_label_source beside it, copied from that node's cocos_label_source, and write none for both when no ancestor carries a label. Both are additive keys, so format_version stays 1, and check_handoff_document and tests/fixtures/mapping_handoff_example.json learn them. If a mapped target in §8 to §13 turns out to need a label the graph lacks, that is a defect in the graph build, recorded as a followup on this plan. It is not patched in the export.

Done when: unit tests show two things. A target under a labelled parent carries that label and its source. A target with no labelled ancestor carries none for both (the negative control). A fresh live export of magnetics for jt-60sa gives its pickup-probe rows one_like from xml, and the receipt quotes one such row.

§8 — PF and TF coil currents

The MMSYS group carries the coil currents. Twelve of its 26 coil signals were unenriched at the second iteration, and curEF1LKAT and curEF4LKAT carried other signals' descriptions until §2. Run the loop for pf_active and tf over the MMSYS coil-current sources. imas-ambix holds hand-built rules for these coils, so this is the first system with a full answer key. Export to jt-60sa-coils-handoff.json.

The cohort does not need §3 or §6. MMSYS sources are singletons, and the loop clears with map clear. imas-codex-90 regenerated MMSYS at 07:28 local and checked all 26 coil-current descriptions against their coils (CS1–4, EF1–6, TF1–2, UFP, LFP). curEF1LKAT and curEF4LKAT are corrected. It reported two caveats, and the candidate and mapping judgments must not take them as fact. First, several descriptions invent a meaning for the acquisition-chain suffix, for example "HiTe = high-temperature conductor circuit". HiTe and LKAT are two acquisition chains for one coil current. Second, some expand UFP and LFP as "field-parallel"; they are the upper and lower fast plasma position control coils. Coil identity, unit (A) and quantity are right in all 26.

Done when: the export passes check_handoff_document, and every MMSYS coil current is either a signal row or an unexpanded row with a reason. The receipt records the exported and refused counts and the seat's model, and the coordinator records imas-ambix's agreement row on the landing.

§15 — Error-signal matching reads the run's own data mappings

The independent review of §4 found three follow-ons in imas_codex/ids/mapping.py. First, match_error_signals_to_imas cross-references error signals against persisted direct MAPS_TO_IMAS edges. The pipeline calls derive_error_mappings from imas_codex/ids/workers.py (around line 1019) before persist_mapping_result runs, so on a first pass after map clear no error signal is ever mapped. Second, the data_mappings argument that carries the run's in-memory bindings is ignored. Third, include_direct_error_signals now gates the whole function, so its name misstates its role. Also, the no-binding test in tests/ids/test_error_derivation.py passes that flag as false and so never exercises the path it claims to test.

Fix: the matcher takes its data-mapping cross-reference from the data_mappings the caller passes. The flag is removed, since error-signal matching is now the only pass. The callers in workers.py and run_error_derivation_only pass what they hold. This section follows §6 because both write workers.py.

Done when: a unit test drives derive_error_mappings with an in-memory direct mapping and an error signal whose parent matches it, against a graph holding no persisted bindings, and gets one error binding. A second test, with the graph mocked to return HAS_ERROR children, still gets no value-derived binding. The negative control reads persisted edges only, and the first test then fails.

§16 — One absence token, and a graph test for the nearest-label query

The independent review of §7 found two follow-ons, and §7's time-row rule had already settled its third. First, imas_codex/ids/handoff.py defines COCOS_ABSENT = "none", which duplicates CocosLabel.NONE in imas_codex/ids/models.py, also read by imas_codex/ids/transforms.py. That gives the absence token two sources that can drift, so the export should read CocosLabel.NONE. Second, the traversal tests in tests/ids/test_mapping_handoff.py drive a mock that reimplements the hop selection. A query that kept *0.. but broke the ORDER BY hops and collect(label)[0] nearest-label idiom would leave them green.

Done when: handoff.py imports CocosLabel.NONE and defines no token of its own. A test marked graph runs _nearest_cocos_labels against the live graph for magnetics/b_field_pol_probe/field/data, which reads one_like from xml, and for magnetics/flux_loop/flux/data, which reads psi_like from inferred_forward. It also checks that a .../time target reads none. That test passes with -m graph on the fleet node. Its negative control drops the ORDER BY, and the test then fails or is shown to be order-insensitive with a recorded reason.
