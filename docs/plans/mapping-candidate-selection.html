Signals · IMAS mapping

Mapping Candidate Selection

imas-codex imas map asks a reasoning model to write IMAS target paths as free text for every signal source of an IDS in a single call. On JET, that left 146 sources marked validated and no mapping edge in the graph. This plan rebuilds the target-selection step in three parts. Code retrieves a shortlist of real Data Dictionary (DD) nodes for each source. Jev answers narrow yes/no questions about each pair of source and candidate. Code routes each source to selected, escalated or no candidate. The reasoning model then only sees the sources that stay ambiguous, and only the paths on their shortlist. The selection stage runs as imas-codex discover map FACILITY, so it fits the discovery workflow; imas map run keeps the field-level transforms, validation and activation.

§1 — What the map pipeline does today, measured

Pipeline. imas_codex/cli/map.py drives run_mapping_engine in imas_codex/ids/workers.py. It runs four workers over SignalSource.mapping_status: context, assign, map and validate.

  • Context (gather_shared_context, imas_codex/ids/mapping.py:565) embeds every enriched source description once. It then runs compute_semantic_matches (imas_codex/ids/tools.py:769) at 20 hits per source over the imas_node_embedding index, plus wiki and code chunks. So a per-source shortlist of DD nodes already exists, as source_candidates. Today it is only pasted into prompts as text.
  • Assign (aassign_targets, mapping.py:954) sends every domain-matched source of one IDS to the reasoning seat in one call, together with the IDS subtree. The model writes imas_target_path as a string, with a self-reported 0–1 confidence and a free-text disposition for sources it leaves unassigned.
  • Map (map_worker, workers.py:594) calls the ids-mapping seat once per source. The call writes SignalMappingEntry.target_id, also as a string.
  • Persist (imas_codex/ids/models.py:574–603) writes MAPS_TO_IMAS through MATCH (ip:IMASNode {id: $target_id}). A target id that names no node writes nothing and reports nothing.

The assembler loads bindings through USES_SIGNAL_SOURCE → MAPS_TO_IMAS (imas_codex/ids/graph_ops.py:130–144). It would therefore find nothing for any of the 53 active JET mappings. Other edges into IMASNode are intact: 94,928 IMASNodeChange FOR_IMAS_PATH and 9,076 StandardNameSource FROM_DD_PATH. §2 establishes what removed the mapping edges.

Wrong dispositions that a pair judgment should catch. jet:device_xml:magprobes/NNN/r is described as "static radial position of magnetic probe 10" and is recorded no_imas_equivalent, yet magnetics/b_field_pol_probe/position/r (unit m) exists and is embedded. jet:device_xml:pfpassive/NNN/r is recorded no_imas_equivalent and its z sibling facility_specific, yet pf_passive/loop/element/geometry/rectangle/r, /z and /width exist and are embedded. A single call that judges two hundred sources against a whole IDS subtree loses exactly these. Each one is a clear yes when the source and the path are put side by side.

What a candidate is. A signal's DD home is a quantity node: magnetics/b_field_pol_probe/field (T), pf_active/coil/current (A) or nbi/unit/power_launched (W). Its /data and /time children are structural and are not embedded. Static geometry lands on geometry leaves. Candidates are therefore the embedded quantity, geometry and identifier nodes. The data/time child is resolved by code in the field-mapping step, never by a model. IMASNode's unit property is unit, not units.

§2 — Find what removed the mapping edges

Every MAPS_TO_IMAS and POPULATES edge is gone, while the 53 IMASMapping nodes and their USES_SIGNAL_SOURCE edges remain. Edges that the SN pipeline and DD build write into IMASNode are present. The candidate edges in §6 also point at IMASNode, so whatever removed the mapping edges would remove those too. Two readings fit the facts:

  • A DD rebuild deleted and re-created IMASNode, and only pipelines that re-run wrote their edges back.
  • The JET run wrote no edges, because each MATCH on a free-text target_id found no node.

Node mapping-edge-loss, role investigate, read-only. It reads the DD build and graph-management code under imas_codex/graph/, imas_codex/cli/ and the DD build modules, with git log over them and over imas_codex/ids/models.py. It reads the map CLI logs under ~/.local/share/imas-codex/logs/ (map_jet*.log) when present. It writes only its report.

Done when the report reaches one of two outcomes. Either it names the operation that removed the edges, citing file:line and dated evidence from git history or logs. Or it states that the operation cannot be determined from code and logs, and names the record that would settle it. In both cases it states whether the same operation would remove a SignalSource → IMASNode edge written by §6. If it would, the report names the narrowest change to that operation that would preserve such edges.

§3 — Label a set and measure retrieval and Jev on it

This section gates everything after it. It follows the method that took JT-60SA code triage from AUC 0.63 to 0.96 (jt60sa-discovery-completion §25): a frozen labelled set, a prototype outside the package, and operating points read off held-out data before any code is built.

Labelled set.

  • 150 JET enriched SignalSources, stratified over the 20 physics domains they occupy: proportional, with at least 3 per domain. The set includes 20 of the 56 previously validated sources with a negative disposition, including the probe and passive examples in §1. It also includes all 13 enriched JT-60SA sources.
  • A label is the DD 4.1.1 quantity, geometry or identifier node (or nodes) that should hold the source's values, or none with a one-line reason.
  • Labels come from a reasoning pass that queries the DD through the graph (search_dd_paths, fetch_dd_paths, IDS subtrees). That pass never sees the shortlist being measured, because seeing it would inflate recall. A second, independent pass labels a 30-source subsample, and the agreement is reported.
  • Labels are frozen before any question wording is tuned. Sources are split 50/50 into dev and test, stratified by domain. Tuning reads only dev; every reported number is from test.

Measures (all on the test split):

  1. Shortlist recall@K, for K ∈ {5, 10, 20, 50}: the share of sources with a non-none label whose labelled node appears in the shortlist. Arms: compute_semantic_matches as it runs today; plus a unit-dimension filter; plus cluster expansion (the existing ClusterSearcher block in gather_ids_context); plus all three. The current query takes LIMIT $k inside the vector search and filters by category afterwards, so it can return fewer than K. Measure the returned count as well.
  2. Pair judgment. AUC of same_quantity over (source, candidate) pairs; top-1 accuracy after reranking, among sources whose label is in the shortlist; the change in both when same_object is combined (product, and minimum).
  3. None detection. Precision and recall of "best same_quantity below a floor" against none labels, across floors.
  4. Batching. One call per pair, against one call per source that carries all K candidates in state and asks 2K questions, each referencing candidates[i]. Report the mean absolute difference in probabilities, the cost and the latency.
  5. Final pick (optional). One Choice over the top 5 plus none_of_these, against plain argmax.
  6. Cost per source, and projected cost for all 2,288 JET sources.

Starting questions. The wording carries the JT-60SA lessons: explicit true and false criteria, exclusion clauses, and the facility block. Tuning on dev may change the wording; the frozen text is part of the deliverable.

  • same_quantity (noul): "Would the IMAS field at candidate.path correctly hold the values that signal_source provides?" True: storing them there needs at most a unit conversion, a sign or COCOS flip, or the selection of one array element. False: the field holds a different quantity, a different component or coordinate, a different object, or only a related or derived quantity.
  • same_object (noul): "Does the structure containing candidate.path describe the same kind of object as the source?" Objects are, for example, the same diagnostic, coil, passive element, heating unit or plasma region. True: the same kind of object. False: a different kind of object, even if the quantity matches. A PF coil current against a passive-loop current is an example.

State.

  • facility: the same data_access_patterns block that run_jev_v3.py builds.
  • signal_source: id, group_key, description, rep_description, physics_domain, rep_unit, rep_sign_convention, rep_cocos, sample_accessors, member_count and keywords.
  • candidate: path, IDS and its one-line description, documentation, unit, data_type, node_category, physics_domain, the parent structure's documentation, and the cluster label when there is one.

Node and output.

  • Node candidate-probe, role implement. It needs the live graph and the decisions endpoint.
  • Prototype scripts live in ~/.cache/imas-codex-jev-map/, outside the package, as in the JT-60SA probe. The call is POST https://openrouter.ai/api/alpha/decisions with {model: "typesafe/jev-1.13", state, questions}, keyed by get_api_key_for_service("imas-mapping").
  • Heavy steps run on the fleet allocation or a *_debug partition.
  • Prototype spend cap: $3.
  • Write paths: docs/research/mapping-candidate-probe.html and docs/figures/mapping-candidate-probe. Figures: recall@K per arm, and the same_quantity distributions for correct and incorrect pairs.

Done when the research document reports every measure above on the test split, with the label agreement and the frozen question text. It must also state three operating points as numbers: select_threshold, select_margin and floor_threshold. For each, it gives the precision and recall of the selected route and the share of sources each route receives. The document says which role the numbers support: Jev as the selector with escalation, or Jev as a pre-screen only. It names the K and the retrieval arms that §4 builds.

§4 — Candidate retrieval in code

Retrieval is deterministic and calls no LLM. A new module, imas_codex/ids/candidates.py, exposes retrieve_candidates(sources, *, gc, k, dd_version) -> dict[str, list[Candidate]]. Candidate is a dataclass with fields path, ids, retrieval_score, arms (the set of arms that produced it), unit, documentation, node_category, data_type, physics_domain and parent_documentation.

It extends the existing owners and adds no parallel ones:

  • Vector retrieval calls compute_semantic_matches. The fix that returns K hits after the category filter goes into that function, not into a copy.
  • Cluster expansion moves out of gather_ids_context into this module. gather_ids_context then calls it.
  • The unit filter uses the dimension check behind analyze_units. It drops a candidate only when both units are known and their dimensions differ.
  • Cross-facility precedent comes from fetch_cross_facility_mappings.

K and the arm set are the ones §3 names.

Node candidate-retrieval, role implement.

  • Write paths: imas_codex/ids/candidates.py, imas_codex/ids/tools.py, imas_codex/ids/mapping.py and tests/ids/test_candidates.py.
  • It may not widen gather_shared_context's return shape.

Done when tests/ids passes with tests that show the following.

  • Every returned path is an IMASNode id read from the graph or a fake; no path is built from a string.
  • The unit filter drops a dimension mismatch and keeps a candidate when either unit is unknown.
  • Cluster expansion adds members without duplicating a path.
  • The vector arm returns K hits when K matching nodes exist.

§5 — Pair judgment through Jev

This section waits on the decisions-call node in jt60sa-discovery-completion §25. That node adds call_decisions and acall_decisions to imas_codex/discovery/base/llm.py, with the model as a parameter, strict answer validation, retries through _is_retryable, cost from usage.cost, and a test guard that fails any live decisions request. This section calls that layer and builds no second client.

  • Seat. [tool.imas-codex.mapping-candidates] model = "typesafe/jev-1.13" in pyproject.toml, registered in MODEL_SECTIONS. It is a separate seat from discovery-relevance.
  • Thresholds. map-select-threshold, map-select-margin and map-floor-threshold in [tool.imas-codex.discovery], with defaults from §3. Their accessors sit beside get_triage_threshold in imas_codex/settings.py. The decisions-call node also edits that file, so this node is dispatched only after that one has merged.
  • Questions. imas_codex/llm/prompts/mapping/candidate_judgment.md carries the frozen §3 wording. It is declared and rendered through the same mechanism that §25 establishes for code/triage.md.
  • Judgment. imas_codex/ids/judgment.py builds the state, asks the questions in the batching form §3 chose, and returns one typed PairJudgment per candidate: path, p_same_quantity, p_same_object, model, judged_at and cost. It also exposes route(judgments, thresholds) -> Route, where Route is selected, escalated or no_candidate. A source is selected when its best combined score is at or above the select threshold and leads the next candidate by at least the margin. It is no_candidate when no score reaches the floor. Everything else is escalated.
  • Fail closed. A decisions failure returns no route. The source stays unjudged for a later retry and is never selected or rejected.

Node candidate-judgment, role implement.

  • Write paths: imas_codex/ids/judgment.py, imas_codex/llm/prompts/mapping/candidate_judgment.md, imas_codex/settings.py, pyproject.toml and tests/ids/test_judgment.py.

Done when tests/ids/test_judgment.py passes under the fake transport and shows the following.

  • The state carries the facility, source and candidate blocks.
  • A malformed answer is rejected.
  • A transport error yields no route.
  • route returns each of the three routes at the configured thresholds, including the margin case, where two candidates both clear the select threshold within the margin and the source is escalated.

§6 — Candidate edges in the graph

Schema. imas_codex/schemas/facility.yaml declares a MAPPING_CANDIDATE relationship from SignalSource to IMASNode. Its properties are rank, retrieval_score, arms, p_same_quantity, p_same_object, model, judged_at, and route, which says whether this candidate is the selected one. SignalSource gains candidate_status (judged once routed), candidate_route, candidate_claimed_at, candidate_claim_token, candidate_judged_at and candidate_model. These follow the claim pattern in imas_codex/discovery/AGENTS.md.

Writes. A new write_candidates(source_id, judgments, route) in imas_codex/ids/graph_ops.py replaces a source's candidate edges in one transaction. It uses UNWIND and MATCHes both endpoints. It returns the written count and raises when that count is below the number of judgments, so a candidate whose node has vanished fails loudly instead of being dropped. The same function sets the source's candidate fields and releases its claim.

Node candidate-schema, role implement.

  • Write paths: imas_codex/schemas/facility.yaml, imas_codex/ids/graph_ops.py and tests/ids/test_candidate_persistence.py.
  • It runs build-models in its own worktree and never stages the generated models.

Done when tests/ids passes with tests that show the following.

  • A re-judge replaces the earlier edges.
  • A missing IMASNode raises.
  • Claim fields are released on success and on failure.

One -m graph test, run on a compute partition against the live database, writes and removes the candidates of a single fixture source.

§7 — imas-codex discover map

Command. imas-codex discover map FACILITY is the discovery stage that follows discover signals. It is built on the shared harness (DiscoveryConfig and run_discovery in imas_codex/cli/discover/common.py) with domain="map", model_section="mapping-candidates" and no SSH check. Options:

  • --physics-domain/-d (repeatable)
  • --ids/-i (repeatable; restricts candidates to those IDSs)
  • --cost-limit/-c (default $5)
  • --time
  • --limit
  • --rejudge (re-routes judged sources)
  • --dry-run

Worker. The claim loop in imas_codex/ids/candidate_workers.py claims a batch of enriched sources that are unjudged, or stale under a claim timeout. For each batch it calls retrieve_candidates, then the judgment, then route, then write_candidates. It follows the @retry_on_deadlock + ORDER BY rand() + claim-token pattern and the orphan recovery in imas_codex/ids/workers.py. discover status FACILITY gains the counts by candidate route.

Node discover-map-cli, role implement.

  • Write paths: imas_codex/cli/discover/map.py, imas_codex/cli/discover/__init__.py, imas_codex/ids/candidate_workers.py and tests/cli/test_discover_map.py.

Done when a CliRunner test with fake retrieval and a fake transport runs discover map end to end over three fixture sources, and shows:

  • one source ends in each route;
  • the cost limit stops the loop;
  • discover status prints the route counts.

§8 — imas map run consumes the candidates

The assign stage's single all-sources call is replaced; this is a greenfield project, so nothing is kept alongside it.

  • A selected source takes its target from its selected candidate.
  • An escalated source goes to the reasoning seat with only its own shortlist. target_assignment.md and target_assignment_system.md are rewritten in place: the model chooses one listed path, or none with a disposition. It never writes a new path.
  • A no_candidate source is skipped. Its best path and probability are logged as evidence.
  • The map stage still writes transforms, units and COCOS labels. Every target_id must lie under the selected node, or be that node's /data or /time child. Anything else is rejected before persist, as an escalation.
  • Persist (imas_codex/ids/models.py:574) checks the count returned by each MAPS_TO_IMAS write and raises on zero. A binding can no longer vanish silently.
  • imas map status shows the candidate routes beside the mapping status.

Node map-run-consumes-candidates, role implement.

  • Write paths: imas_codex/ids/workers.py, imas_codex/ids/mapping.py, imas_codex/ids/models.py, imas_codex/llm/prompts/mapping/target_assignment.md, imas_codex/llm/prompts/mapping/target_assignment_system.md, imas_codex/cli/map.py and tests/ids/.
  • It runs after §4, which also writes mapping.py.

Done when tests/ids passes with tests that show the following.

§ Decisions

After §3, does Jev select targets with escalation, or only shortlist for the reasoning model?

The routing in §5 covers both. Pre-screen only is the same design with the select threshold set above 1, so every non-floor source escalates. The choice sets the default threshold, and §3's precision of the selected route should decide it. The recommendation is selector with escalation, provided that precision on the test split is at least 0.9.

Where does the candidate stage live on the command line?

The recommendation is discover map . The stage is a claim loop over a facility's discovered signals, with cost and time caps, so it shares the discover harness, status and logs. imas map keeps the work that needs a reasoning model and the mapping lifecycle (validate, activate, clear).
