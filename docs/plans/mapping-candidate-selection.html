Mapping Candidate Selection

imas-codex imas map asks a reasoning model to write IMAS target paths as free text for every signal source of an IDS in a single call. On JET, that left 146 sources marked validated and no mapping edge in the graph. This plan rebuilds the target-selection step in three parts. Code retrieves a shortlist of real Data Dictionary (DD) nodes for each source. Jev answers narrow yes/no questions about each pair of source and candidate. Code routes each source to selected, escalated or no candidate. The reasoning model then only sees the sources that stay ambiguous, and only the paths on their shortlist. The selection stage runs as imas-codex discover map FACILITY, so it fits the discovery workflow; imas map run keeps the field-level transforms, validation and activation.

§1 — What the map pipeline does today, measured

Pipeline. imas_codex/cli/map.py drives run_mapping_engine in imas_codex/ids/workers.py. It runs four workers over SignalSource.mapping_status: context, assign, map and validate.

  • Context (gather_shared_context, imas_codex/ids/mapping.py:565) embeds every enriched source description once. It then runs compute_semantic_matches (imas_codex/ids/tools.py:769) at 20 hits per source over the imas_node_embedding index, plus wiki and code chunks. So a per-source shortlist of DD nodes already exists, as source_candidates. Today it is only pasted into prompts as text.
  • Assign (aassign_targets, mapping.py:954) sends every domain-matched source of one IDS to the reasoning seat in one call, together with the IDS subtree. The model writes imas_target_path as a string, with a self-reported 0–1 confidence and a free-text disposition for sources it leaves unassigned.
  • Map (map_worker, workers.py:594) calls the ids-mapping seat once per source. The call writes SignalMappingEntry.target_id, also as a string.
  • Persist (imas_codex/ids/models.py:574–603) writes MAPS_TO_IMAS through MATCH (ip:IMASNode {id: $target_id}). A target id that names no node writes nothing and reports nothing.

Wrong dispositions that a pair judgment should catch. jet:device_xml:magprobes/NNN/r is described as "static radial position of magnetic probe 10" and is recorded no_imas_equivalent, yet magnetics/b_field_pol_probe/position/r (unit m) exists and is embedded. jet:device_xml:pfpassive/NNN/r is recorded no_imas_equivalent and its z sibling facility_specific, yet pf_passive/loop/element/geometry/rectangle/r, /z and /width exist and are embedded. A single call that judges two hundred sources against a whole IDS subtree loses exactly these. Each one is a clear yes when the source and the path are put side by side.

What a candidate is. A signal's DD home is a quantity node: magnetics/b_field_pol_probe/field (T), pf_active/coil/current (A) or nbi/unit/power_launched (W). Its /data and /time children are structural and are not embedded. Static geometry lands on geometry leaves. Candidates are therefore the embedded quantity, geometry and identifier nodes. The data/time child is resolved by code in the field-mapping step, never by a model. IMASNode's unit property is unit, not units.

§7 — imas-codex discover map

Command. imas-codex discover map FACILITY is the discovery stage that follows discover signals. It is built on the shared harness (DiscoveryConfig and run_discovery in imas_codex/cli/discover/common.py) with domain="map", model_section="mapping-candidates" and no SSH check. Every option reuses a name the CLI already has:

  • --physics-domain/-d and --ids/-i, both repeatable, as in imas map run. --ids restricts candidates to those IDSs.
  • --cost-limit/-c (default $5), --signal-limit/-n and --time, as in discover signals.

There is no --rejudge and no --dry-run. Re-judging is discover clear FACILITY --domain map: a new value of the existing option, calling §6's clear_candidates. A judgment without persistence is §3's prototype, not a production mode. The command adds five options, all existing names. §8 retires two from imas map run.

Worker. The candidate stage is a new phase in imas_codex/ids/workers.py, the module that already owns SignalSource claiming for the mapping workflow. That module already holds the claim pattern twice. This section generalises it once, and does not add a third copy.

The full SignalSource census has two more claim families. Both serve the enrichment stage on claimed_at: claim_signal_sources, release_source_claims and has_pending_sources in imas_codex/discovery/base/grouping.py, and their twins in imas_codex/discovery/mdsplus/graph_ops.py. They are a different lifecycle stage with live callers in discovery/static, so this plan leaves them unchanged. The generic routine in claims.py takes the label, status predicate and claim property names as parameters, so those families can adopt it in their own change.

  • claim_sources_for_assignment and claim_sources_for_mapping (workers.py:136, 199) become one claim routine.
  • release_mapping_claim and release_mapping_claims_batch (274, 287) become one release routine.
  • The three has_pending_* checks (303, 329, 343) become one pending check.
  • Each is parameterised by the label, the status predicate, the claim property names and the returned fields.
  • The generalised routines live in the shared owner, imas_codex/discovery/base/claims.py, not in workers.py. release_claim and release_claims_batch gain the claimed_field keyword that reset_stale_claims already has. Its default, claimed_at, leaves every existing caller unchanged. The claim and pending routines are added beside them.
  • The seven workers.py helpers become calls into claims.py, and the assign, map and candidate stages all use them.
  • The section adds candidate_worker, plus a run_candidate_engine that uses run_discovery_engine with an OrphanRecoverySpec on mapping_claimed_at, as run_mapping_engine does.
  • The claim takes a batch of enriched sources that are unjudged, or stale under the claim timeout. It keeps the @retry_on_deadlock + ORDER BY rand() + claim-token pattern.
  • Each batch goes through route_ids, retrieve_candidates (scoped to the routed IDSs), judge_candidates, route and write_candidates, in that order. IDS routing comes first because §3 measured it as the recall lift.
  • discover status FACILITY gains the counts by candidate route.

Surface. The section adds:

  • one subcommand, discover map, with five options that all reuse existing names;
  • one DISCOVERY_DOMAINS value, map (cli/discover/common.py:30), which --domain validates against. A map branch is added beside the per-domain branches in discover_status and discover_clear (cli/discover/__init__.py), because those commands dispatch on explicit branches, not on the tuple.

Against that, seven claim helpers in workers.py become three, and §8 retires two imas map run options. A separate command is needed because the candidate stage runs on a different cadence from mapping: it is cheap, it re-runs whenever signals are re-enriched, and it costs no reasoning-model call.

§8 — imas map run consumes the candidates

The assign stage's single all-sources call is replaced; this is a greenfield project, so nothing is kept alongside it.

  • A selected source takes its target from its selected candidate.
  • An escalated source goes to the reasoning seat with only its own shortlist: the top map-shortlist-size candidates, 5 by default, in Jev order. target_assignment.md and target_assignment_system.md are rewritten in place: the model chooses one listed path, or none with a disposition. It never writes a new path.
  • A no_candidate source is skipped. Its best path and probability are logged as evidence.
  • The map stage still writes transforms, units and COCOS labels. Every target_id must lie under the selected node, or be that node's /data or /time child. Anything else is rejected before persist, as an escalation.
  • MAPS_TO_IMAS has three MATCH-gated writers today: persist_mapping_result (imas_codex/ids/models.py:580), create_signal_source (imas_codex/ids/graph_ops.py:357) and run_error_derivation_only (imas_codex/ids/mapping.py:2085). grep 'MERGE (sg)-\[r\?e\?l\?:MAPS_TO_IMAS\]' imas_codex/ finds exactly these three. The error-derivation writer also calls the new function.
    • The edge write moves into one function in graph_ops.py, beside §6's write_candidates. It checks the returned count and raises on zero, so a binding can no longer vanish silently.
    • persist_mapping_result calls that function.
    • create_signal_source, whose only caller is tests/ids/test_graph_ops.py, is deleted together with that test, unless a production caller has appeared, in which case it calls the same function.
  • imas map status shows the candidate routes beside the mapping status.
  • Retired legacy retrieval. The map context stops calling compute_semantic_matches, which after §4 supplies only the wiki and code bridging matrix. An escalated source's context comes from its candidates, and wiki and code context comes from the existing fetch_wiki_context and fetch_code_context. compute_semantic_matches is deleted when no caller remains.
  • No per-IDS retrieval in the map context. After §4, gather_ids_context calls retrieve_candidates for every source on each IDS target, re-embedding every source each time. The map stage reads each source's shortlist from its MAPPING_CANDIDATE edges instead, so that call is removed here. Cross-facility precedent, which §4 did not build because the graph holds no MAPS_TO_IMAS edge to draw on, joins the escalated prompt through fetch_cross_facility_mappings once bindings exist.
  • Retired options. imas map run loses --skip-metadata, which is parsed and never read, and --skip-errors, which is the same as --stage data.
  • Retired fields. SignalSource loses mapping_target_path and mapping_target_ids. The map stage reads the target from the selected MAPPING_CANDIDATE edge, where claim_sources_for_mapping reads the scalars today (workers.py:237). mapping_target_type stays: the escalated choice call returns the TargetType with its pick, as the assign call does now, and mapping.py:1416, 1497 keep reading it.
  • One owner for the edge. The MAPS_TO_IMAS delete in _clear_mapping (imas_codex/cli/map.py:657–666), the only delete site of that edge, moves into graph_ops.py beside the write function and clear_candidates. imas map clear and --clear call it. Every create and delete of a SignalSource → IMASNode edge then lives in one module.
  • Strict selection flag. §6's _candidate_record normalises a judgment's route with bool(), so a route string such as "escalated" would mark the candidate selected. It reads only a boolean selected, and rejects any other type with CandidateWriteError. A test passes a route string and expects the refusal.

§ Decisions

After §3, does Jev select targets with escalation, or only shortlist for the reasoning model?

The routing in §5 covers both; the choice only sets whether a select threshold is configured. Measured in §3 (docs/research/mapping-candidate-probe.html): the selected route never exceeded about 0.63 precision on the test split at any threshold, and was 0.4 at the dev-tuned point. Jev is a strong ranker (pair AUC 0.924), but its absolute same_quantity is low for many correct pairs. Its reranked top 5 kept every correct node the shortlist held. Recommendation: pre-screen only. Jev routes the IDS and orders a five-candidate shortlist, and the reasoning model makes every final choice. This is §5's default.

Where does the candidate stage live on the command line?

The recommendation is discover map . The stage is a claim loop over a facility's discovered signals, with cost and time caps, so it shares the discover harness, status and logs. imas map keeps the work that needs a reasoning model and the mapping lifecycle (validate, activate, clear).

Skip sources whose best Jev score is below a floor?

A floor skips the reasoning-model call for a source whose best same_quantity is below it. On the 75-source test split, a floor of 0.1 would route 26 sources to no_candidate. 23 of those are labelled none (precision 0.88), and the floor catches 23 of the 39 none sources (recall 0.59). The other 3 have a real DD home, and skipping them loses 3 of the 36 labelled mappings. A floor of 0.2 catches 34 of the 39 nones at 0.76 precision, but loses 11 real mappings.

The default is no floor, because a mapping skipped by the floor is never seen again, while an unneeded reasoning call costs cents. Revisit once §9's JET run gives the real cost of escalating every source.
