§1 — What the panel shows today, and how it misled

On the night of 2026-09-23 to 24 the lead read the login-node panel from imas-codex host iter. It showed 98dci4-srv-1006 at 100% CPU, while vmstat read 95–98% idle. The node was at load 143 because dozens of agent processes were blocked on GPFS, and a single stat took 8.5 s. The events are recorded in imas-ambix's research note login-node-storage-contention. Every number the panel draws needs checking, not only the one that failed:

§2 — Three resources, three honest percentages

Every figure is a rate over a sampling interval, read from /proc and the cgroup files, never from a walk of any filesystem. Each is labelled with its denominator.

  • CPU. Node: busy over total from successive /proc/stat readings. The lead's slice: the change in usage_usec from cpu.stat, divided by the interval times the quota in cpu.max (four cores on the login node today), giving a percentage of what the lead may use. Beside it, the throttled fraction: the change in nr_throttled over the change in nr_periods. That is the quantity reckon's cutover plan reports against its 0.3366 baseline, so both read the same counter. Per process: the change in utime + stime over the interval. Load average is still shown, labelled as load, beside the count of tasks in D state, so a reader sees the split instead of inferring it.
  • Memory. The slice's memory.current over memory.max, the node's MemAvailable, and per-process RSS.
  • Filesystem. GPFS offers no utilisation counter to a client, and io.pressure is not supported on this kernel's user slice, so the measure is built from two direct observations. Blocked share: each of the lead's processes is sampled twice a second, and the fraction of samples it spends in D with wait channel cxiWaitEventWait is its GPFS-blocked share. It is summed per owner and shown as the percentage of the lead's non-idle processes that are blocked on storage. Latency: an in-process stat on one fixed file in home and one in /work, shown against the healthy value measured on 2026-09-24 (about 250 µs) as a multiple. The scratch sampler in the incident (fsload.py, imas-ambix session scratchpad) is the reference implementation.

The dashboard's own cost is a row in its own table. A monitor that walks the filesystem it is watching repeats the incident.

Done when each figure has a unit test over recorded /proc and cgroup fixtures. One fixture is a node whose load average is 140 with idle CPU, and the CPU bar must read idle there. A mutation that restores getloadavg() / cpu_count must fail.

§3 — Every process the lead owns, grouped by who started it

The filter becomes the lead's uid, not a name pattern. Each process is attributed to an owner and a role.

  • Owner is the nearest ancestor that is a Claude session. Its pid is the name of its socket under /run/user/<uid>/cc-socks/, which also gives the peer name other sessions message it by.
  • Where reckon records the crew session id and owning pid in the process environment (reckon:a-crew-process-ends-with-its-owner §6), that recorded owner is used instead, because it survives reparenting to init.
  • Role is one of session, follower, producer, dispatch or complete loop, worker, search, service or other. It is read from the command line of a process whose owner is already established, never used to establish ownership.

Columns: pid, owner, role, age, CPU %, RSS, GPFS-blocked %, state and wait channel, working directory. Rows fold by owner, and each owner row carries its totals.

Done when the live login node renders every process of the lead's uid. A test over a recorded process table holding two sessions, a follower reparented to init with a recorded owner, and a zellij server shows each attributed correctly. The zellij server is never attributed to a session.

§4 — Orphans and long-running background work are flagged, never selected for a kill

ppid 1 does not mark an orphan: live workers, zellij servers and system services all have it, and one coordinator's ppid-1 list held 16 processes, none of them orphans. The orphan flag is raised only when the recorded owner is dead. It waits on reckon's census (gated below). Until then the column reads "owner unknown", not "orphan".

A second flag marks background work that has outlived its attention: any process in a session's tree running longer than ten minutes that is not a follower, producer or worker. That is what a backgrounded tool call becomes, and the harness says nothing about it between its two-minute boundary and its death. The bfs over /work/projects/imas_gpu ran for 13 h 50 min that way, and a find / for 10 h 49 min.

host kill is reshaped to act on a pid list the operator has read: it takes pids, re-checks that each still has the same start time and owner, prints what it signals, and prints what it spared. The pattern options are removed.

Done when a test shows the orphan flag raised for a dead-owner stub and not for a live worker with ppid 1. A background search stub older than ten minutes is flagged. host kill refuses a pid whose start time changed since it was listed.

§5 — Two nodes in one pane

The survey keeps its ssh reach to the login nodes and gains the interactive fleet node whenever the fleet allocation is held. It resolves that node from reckon's published reservation rather than from a hostname, and samples it through a step in that allocation, so it reads the same cgroup the fleet runs in. The stat latency probe runs on both nodes at the same moment. The research note could not tell how much of the night's contention was local to the login node's GPFS daemon and how much was cluster-wide, because only one node was probed. Two simultaneous probes separate the two.

Done when with the fleet allocation held, the pane shows both nodes, each with its own three percentages and latency probe, and the fleet node's row names the job id it sampled through.

§6 — An evidence record, and a report built from it

A live pane is forgotten the moment it scrolls. Each sample is appended to a JSON-lines record, one small line per owner per interval, holding the three percentages, the latency probes and the flags. imas-codex host report --since <time> reads that record back and gives, per owner and per node: CPU-seconds against quota, memory peak against limit, GPFS-blocked process-hours, orphan and long-running flags raised, and the worst latency interval. That is the evidence cycle for the next incident: one command answers "who loaded the node, with what, and when", without a live reconstruction.

GPU and serving figures are not re-scraped here. imas-ambix's serve-telemetry-spine §10 moves gpu-watch onto the serve recorder as imas-ambix agent watch, and the report reads that recorder's figures for the same window instead of keeping a second scraper that can drift.

Done when a report over a recorded day of samples reproduces the per-owner totals computed by hand from the same records. A report run against the 2026-09-24 incident window, from records taken while it happened, names the owners the research note names.

§7 — Done when, for the plan

§2–§6 have each met their own done-when. The lead can open one pane and read, for every agent process on the login and fleet nodes: who owns it, what it is, and what share of CPU quota, memory limit and storage it is taking. The same figures are available afterwards from the report.
