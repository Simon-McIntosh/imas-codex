§1 — imas-codex pulls the rules, and keeps their history

imas-ambix holds a JT-60SA machine map whose rules were validated against data: the bundle imas-alambic-jt60sa under /home/ITER/mcintos/Code/imas-ambix/maps/jt-60sa/, 45 rules to COCOS 17 for magnetics, PF, TF and equilibrium, each with a channel_factor, a validation_state (corpus-validated or source-only) and an evidence string. It is the strongest external evidence the conventions stage (signal-cocos-conventions) and the map can read. It also moves: the bundle read v0.2.0-rc3 and then v0.2.0-rc4 on 2026-10-09, and its superseded/ directory keeps earlier states, among them the differential-loop names before a rename and the loops before differential entries existed.

The lead ruled on 2026-10-09 that imas-codex pulls the rules rather than imas-ambix pushing them, and that the graph tracks their evolution as it tracks other changing attributes. The graph already has two idioms for this. The DD has a version node per release (DDVersion) and a change record per path and version (IMASNodeChange, linked FOR_IMAS_PATH and IN_VERSION). Standard names record renames and supersedes as StandardNameChange events through HAS_INTERNAL_CHANGE. A pulled bundle becomes a version node, each rule a node keyed by a stable rule identity, and each difference between two pulls a change record on the rule. imas-ambix owns its rules; imas-codex records what it read, at which version and content hash, and when.

A pulled rule is evidence, never a settled convention. The conventions stage and the map read it beside their own judgments and their facility probe; a disagreement raises a followup through signal-evidence-followups rather than overriding either side. When a pull changes a rule that a source's convention or binding relied on, that source is re-queued.

Two translation hazards come from reading the rules naively. The DD labels magnetics/flux_loop/flux psi_like, but every imas-ambix flux-loop rule is one_like with source_cocos null: its −1 was fitted directly against a COCOS 17 prediction, so it is the total sign from raw data to COCOS 17. Read as one_like, a psi_like field would be flipped twice or not at all. The pull therefore records channel_factor as the total sign to the rule's target COCOS and takes the class from the DD, never from the rule's transformation field. Second, the flux-loop signs are not adjudicated: imas-codex's diagnostic convention audit (merged 09a095988, docs/evidence/fragments/jt60sa-discovery-completion/jt60sa-diagnostic-conventions.json) disagrees with imas-ambix in sign on all 54 flux-loop comparisons and agrees on all 34 pickup-coil comparisons. The pull records the rules as they are, with their validation state; adjudicating them belongs to jt60sa-discovery-completion §56.

§2 — Design the record before writing it

The record has to survive renames, re-groupings and sign corrections, so its identity rules are settled first. The design reads the bundle's own format (bundle.json, machine_map.json at schema version 1.10.0, maps/*.json, superseded/* and their receipts), how imas-ambix releases a bundle (imas-ambix:jt60sa-facility-mint), and the graph's change idioms in imas_codex/schemas/imas_dd.yaml (DDVersion, IMASNodeChange), imas_codex/schemas/standard_name.yaml (StandardNameChange) and imas_codex/schemas/facility_config.yaml (SourceVersion). It answers: what identifies one rule across versions when its name changes; how a rule joins a SignalSource and an IMASNode, with the live join counts for the current bundle; which change types exist; and which changes re-queue a source.

§3 — Pull a bundle version into the graph

imas-codex imas map pull FACILITY --bundle PATH reads one bundle, records its version and the sha256 of every file read, writes or updates each rule under the §2 identity, joins it to its source and target, and writes a change record for every rule whose values differ from the previous pulled version. Pulling a version whose hashes are already recorded writes nothing. The schema follows the §2 design as adjusted by the lead.

§4 — Rules reach the judgments as evidence

The conventions judgment and the map's slot context read a source's current pulled rules, labelled with provider, version and validation state. A pull that changes a rule re-queues every source that rule joins for the conventions stage, and raises a followup when the new rule disagrees with a convention already settled.

§5 — Pull the JT-60SA history

Pull every readable JT-60SA bundle state in order, oldest first: the superseded states that carry a machine_map.json, then the current bundle. The graph then holds the evolution, including the differential-loop rename and the arrival of the differential entries, as change records a later reader can query.

§ Decisions

What may a pull read: only released bundle tags, or a local checkout too?

Recommended: either, provided every file read is hashed. Release candidates change within a day and are read from the local checkout before they are released; hashing every file makes a local pull as reproducible as a tag.
