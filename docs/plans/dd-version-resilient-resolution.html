§1 — The failure this exists to prevent

On 2026-08-21 a scoped pipeline run over 42 data-dictionary paths aborted on a deterministic DDResolutionVersionMismatch. One source carried a recorded dictionary version older than the graph's authoritative snapshot, and that single label disagreement stopped the whole run. The immediate unblock was to move that one source forward, but the measurement underneath is the real finding: 8,537 of roughly 9,600 StandardNameSource nodes — about 94% — carry dd_version = '4.1.0' while the graph serves 4.1.1, against only 384 at 4.1.1 and 695 with none. Moving one source forward leaves 8,536 identical landmines.

Dictionary versions will keep moving. A pipeline that refuses work whenever a recorded label differs from the current dictionary will, at every bump, stop on almost every source it owns — and the stop is silent until something tries to run.

§2 — The correct primitive already exists in this codebase

This is not a redesign. _read_graph_field in imas_codex/standard_names/dd_resolutions.py already implements the right test, and it should be the model for everything else. Given a resolution recorded against some version, it compares the value rather than the label:

  • if the raw value equals the record's observed value, the recorded correction applies;
  • if the raw value equals the record's effective value, the field has converged — the prior review still covers it, and it resolves cleanly with converged=True;
  • only when the raw value matches neither side of any record does it raise, because that is a genuine content change no human has reviewed.

That is exactly right, and it means a resolution reviewed at 4.1.0 legitimately governs 4.1.1 whenever the underlying leaf did not change. The defect is that a second entry point does not do this. resolve_dd_row compares labels by equality with no convergence path and no content test, so it refuses a row whose content is byte-identical to what was reviewed, purely because the stamp differs.

§3 — Design: version is provenance, not identity

  1. A recorded dictionary version states when a source was extracted, not which versions it is valid for. Treating it as an identity assertion and comparing it by equality to the current dictionary is a category error, and it is the whole of this bug.
  2. Validity is decided by content convergence. A source remains valid under a new dictionary when its path is still present and its unit and documentation are unchanged. Adopt the _read_graph_field convergence test in resolve_dd_row and anywhere else a version is compared.
  3. Refusal is scoped to the leaf that changed, never to the run. Today one mismatched row aborts a scoped run over 42 paths. A changed leaf should mark that leaf for review and let the remaining work proceed, because a pipeline that stops entirely on one stale stamp cannot be run during a migration — which is exactly when it is most needed.
  4. A bump emits a worklist. On a dictionary change, compute the set of leaves whose path, unit or documentation actually moved. Only those need fresh review; everything else converges silently. The dictionary graph already carries version history and changelog tooling to compute this, so the input is available rather than needing invention.
  5. Re-stamping is a migration, not a repair. Bulk-rewriting 8,537 labels to the current version would hide the provenance of when each source was extracted and would need redoing at every bump. Prefer convergence at read time; re-stamp only where a leaf genuinely changed and its review has landed.

§4 — Test strategy

The invariant is stated as a property, because a version-resilience claim that is only tested against today's two versions will rot at the next bump:

  • A no-op bump produces zero refusals. Synthesize a dictionary version whose leaves are content-identical to the current one and assert that resolution over the full source corpus raises nothing. This is the single most valuable test in this plan and it would have caught the present defect.
  • A changed leaf refuses exactly itself. Change one leaf's unit in a synthetic bump and assert that resolution refuses that leaf and resolves every other source in the same run.
  • Convergence is not a bypass. Assert that a leaf whose value matches neither the observed nor the effective side of any record still refuses, so the fix cannot be mistaken for weakening review authority.
  • The corpus check. Assert that the count of sources whose recorded version differs from the authoritative one has no effect on how many sources resolve successfully — the number that matters is content drift, not label drift.

§5 — Non-goals

  • Not a weakening of review authority. A genuine content change must still fail closed and demand human review. This plan narrows when that fires, never whether it fires.
  • Not a bulk re-stamp. Rewriting every source's recorded version is explicitly rejected in §3 item 5.
  • Not multi-version node storage. The graph holds one authoritative dictionary snapshot with version nodes for history, and IMASNode carries no per-version stamp. That is a reasonable model and this plan does not change it.

§ Decisions

What does a recorded dictionary version on a source mean?

94% of sources are labelled 4.1.0 while the graph serves 4.1.1. Either the label asserts validity, in which case almost every source is invalid, or it records extraction provenance, in which case validity must be decided by content.

Recorded rather than freshly chosen: the plan already determines it, and a worker must dispatch against locked state. §3 item 1 states the design outright — a recorded dictionary version says when a source was extracted, not which versions it is valid for; §5 explicitly rejects the bulk re-stamp the validity-claim reading would demand; and the working code path already behaves this way. Confirmed against the tree on 2026-08-21: dd_resolutions.py:1157 _read_graph_field implements the observed/effective convergence test, while resolve_dd_row at line 1316 compares labels by equality with no content test at all.

When one leaf has genuinely changed, what should a scoped run do?

Recorded from §3 item 3 — refusal is scoped to the leaf that changed, never to the run — and from the sprint's done_when for this item. The defect locus is confirmed in code: resolve_dd_rows at dd_resolutions.py:1340 is a list comprehension over resolve_dd_row, so the first raise aborts the entire batch, which is exactly how one stale label stopped a scoped run over 42 paths. Fail-closed behaviour for genuine content change is untouched; this narrows when it fires, never whether.

§ Followups

Write the no-op-bump property test first, then adopt convergence in resolve_dd_row

Start with section 4's first test, because it is the one that would have caught this defect and it fails today: synthesize a dictionary version whose leaves are content-identical to the current one, then assert that resolution over the full source corpus raises nothing. With that test red, adopt the _read_graph_field convergence comparison inside resolve_dd_row so a byte-identical row is no longer refused for carrying an older stamp, and make refusal scoped to the changed leaf rather than fatal to the run. Do not bulk re-stamp the 8,537 sources carrying an older label; section 3 item 5 rejects that explicitly, and doing it would hide extraction provenance and need redoing at the next bump. Keep the fail-closed behaviour for genuine content changes intact and prove it with section 4's third test, so the change cannot be mistaken for weakening review authority.
