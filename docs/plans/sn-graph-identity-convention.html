§1 — The defect, and why it keeps winning

One schema uses three different property names for the same relationship — a node referencing a StandardName — and two different spellings of one axis. Neither inconsistency is visible at the point of use, and both fail silently: Cypher evaluates a missing property to null, a non-true predicate drops the row, and the query returns a clean, plausible, empty result instead of an error.

Incident 4 is the instructive one. A zero there asserts the entire names axis has never been reviewed — a claim large enough that it should provoke disbelief, and instead it renders as a tidy empty result. Incident 3 would have concluded that no document in the graph had ever been revised, hours after forty snapshots were written and reported. In both cases the number was not merely wrong; it was wrong in the direction of nothing to do here.

Documentation has already been tried and measured. A keying section was added to imas_codex/standard_names/AGENTS.md naming the two identifier properties and the silent-null mechanism. Incidents 3 and 4 happened after it landed, one of them committed by its own author. The section was then extended to all 53 relationship directions and all 12 foreign-key classes. That is worth having, and it is a mitigation: it makes the answer findable. It does not make the question occur to anyone at the moment they are writing a filter. This plan exists because the mitigation has been shown insufficient by measurement rather than by argument.

§2 — The same class already gates work, not only reporting

Chasing whether docs_review_resolution_method should exist at all revealed the cost ceiling of this defect class. That field is a pure denormalisation: across every row where both the scalar and a reachable review method exist, they agree 2,053 times and disagree 0 times. It carries no information the graph does not already hold. Yet it is presence-tested at five sites in three subsystems:

So an unwritten denormalisation did not merely withhold names from the release. A name with a null method cannot be claimed for docs refinement and cannot be promoted from reviewed to accepted. It sits in docs_stage='reviewed' indefinitely: the refine pool cannot see it, the promoter cannot lift it, and the pending counter reports it absent rather than stuck. Nothing errors. The 1,402 rows repaired by a backfill campaign were not only unpublishable — a subset were unrepairable and unpromotable by construction.

That is why the five duplicated predicates are inside this plan's scope rather than left as a tidy-up. Renaming identity properties while five copies of one eligibility test live in three files is how a rename becomes an outage.

A finding that shapes §5. The schema describes both foreign-key scalars as conveniences over an authoritative edge, in its own words: DocsRevision.sn_id is "denormalised for query convenience; the authoritative link is the DOCS_REVISION_OF edge", and StandardNameReview.standard_name_id is "back-reference; edge owned by StandardName via HAS_REVIEW". They are the same shape as docs_review_resolution_method: a copy that became load-bearing. That opens a genuine question about whether unifying the spelling is the right fix or whether the copies should go — recorded as a decision rather than settled here.

§3 — Change A: one spelling for the axis

Cheapest of the three, and the one that produced the worst incident. The mismatch is between an enum's permissible values (names, docs) and a slot-name suffix convention (_name, _docs). Reconciling from the enum side touches two permissible values and their readers; reconciling from the slot side touches 28 declared slots plus every reader of each. The enum is the cheap end.

Deliverable: one spelling, chosen by the axis-spelling decision, applied in the LinkML source with models regenerated, all readers updated, and a graph migration for stored enum values if the enum side moves. Done when a test asserts that no axis token appears in two spellings anywhere in imas_codex/, derived from the schema rather than a hardcoded list, so a future axis cannot reintroduce the split.

§4 — Change B: a misspelled property must fail closed

This is the change that would have caught all four incidents, and it is the only one that protects against the next inconsistency rather than the current one. The principle: a count or filter over a property name that does not exist must not return a plausible empty result.

Two layers, both required, because neither alone is sufficient:

  • A coverage helper used at the point of query. Before a zero is believed, the candidate count and the property-coverage count are reported together: a result of candidates > 0 with with_prop = 0 means the property name is wrong, not the set empty. This is the one-line habit both sessions arrived at independently; the deliverable is to make it a callable rather than a habit.
  • A static check over Cypher literals in the repository. Every property name appearing in a Cypher string is validated against the LinkML-declared slots for the label it is filtered on. A name the schema does not declare is a failure. This is what makes the rule survive people who have not read the AGENTS section — including its author, twice.

Done when the static check runs in the ordinary test selection, fails on a deliberately misspelled property in a fixture, and reports zero violations across the current tree — or an explicit, itemised allowlist of the cases it cannot resolve statically, each with a reason.

§5 — Change C: one foreign-key convention

Unify how a node names the standard name it belongs to. Blast radius, measured rather than estimated: 142 Cypher-context sn_id references and 18 for standard_name_id; 258 for sn_ids. The raw identifier appears 1,494 times but most are Python locals and dict keys; the graph-touching set concentrates in graph_ops.py (222 occurrences), workers.py (181) and attachment_audit.py (96), plus their tests. Data migration covers 60,230 nodes across the three labels.

Two credible shapes, and the choice is the lead's:

  • Unify the spelling. Mechanical, reversible, keeps the query convenience the scalars exist for, and leaves three denormalised copies in place.
  • Traverse and delete. Callers read through the authoritative edge; the scalars go. Removes the drift class permanently, costs a hop per row, and is a larger change to hot paths including an atomic claim.

Done when one convention holds for every declared foreign key, the migration is verified by non-zero coverage on every renamed property before and after, and Change B's static check passes with no allowlist entry for these labels.

§6 — Change D: one eligibility determination, not five

Replace the five duplicated presence tests of §2 with a single shared determination consumed by all five call sites. The export gate's real question is does a winning review exist for this name, which is answerable from the authoritative edge and cannot drift. Two constraints the implementation must respect:

  • The exclusion reason splits. Of 2,748 accepted documents, 2,303 have a winning docs review and 445 do not — and 435 of those have no docs review at all. "Never reviewed" and "resolution unrecorded" are different facts about a name and must not share one bucket.
  • A predicate correct in a projection is not automatically correct inside an atomic claim. Site graph_ops.py:24246 sits in _claim_sn_atomic; whatever replaces the presence test must be evaluable there and must not change claim semantics under concurrency.

Done when one implementation is called by all five sites, a test proves the five agree on a fixture population where the scalar and the edge disagree, and the two work-gating sites have concurrency coverage.

§7 — Test-first is the contract, not the preference

Every change above lands as a failing test before an implementation, and each worker's manifest reports the pre-change and post-change counts so the sequence is auditable rather than asserted. This is not ceremony here: three of the four changes are refactors with no user-visible behaviour, so a test written afterwards can only describe what the code now does. A test written first is the only artifact that distinguishes "the rename preserved behaviour" from "the rename changed behaviour and the tests were updated to match".

Each change therefore has two nodes. The specification node writes tests that fail against the current tree, and its done-when is that they fail for the stated reason — a test failing on an import error or a typo proves nothing. The implementation node makes them pass without editing them; if it must change a specification test, that is a signal the specification was wrong and it stops and reports rather than editing the goalposts.

Two invariants every specification node must encode, because they are what the four incidents have in common:

  • A zero is not evidence until coverage is proven. Any assertion whose expected value is zero must be accompanied by an assertion that the property or relationship being counted exists and is populated somewhere.
  • Derive the universe from the schema, never a literal list. A test enumerating relationships, axis tokens, or foreign-key properties reads them from LinkML at runtime, so a future addition fails loudly instead of being silently untested.

§8 — Sequencing, quiescence, and the way back

Nothing starts until the graph and the tree are quiescent. The concurrent release-readiness session holds live campaigns and heavy edits in graph_ops.py, which Change C touches most. Its nodes are being allowed to finish rather than killed — stopping a paid campaign mid-run leaves live claims and unattributable spend — and the gate for starting here is: that session reports quiescent, graph_ops.py is committed and pushed with no worktree holding edits, and the suite is green at that head.

Order, and the reasoning for it. Change B first, because it is the detector: with the static check in place, Changes A and C cannot introduce a silent inconsistency, and the check's own value is proven by running it against the tree before anything is renamed. Then Change A, smallest and independent. Then Change D, because it removes the five-way duplication that would otherwise multiply Change C's risk. Change C last, when a detector exists, the duplication is gone, and the tree is otherwise stable.

Rollback. Every step is a migration with an inverse, and each migration node states its inverse before applying. The failure mode this plan is guarding against is the one it is fixing: a mis-set key on 60,230 nodes fails silently and stops work rather than reporting. So every migration verifies non-zero coverage on the target property immediately after writing, and refuses rather than reporting success on a zero.
