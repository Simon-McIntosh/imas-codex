Plan · ITER plant data

ITER plant signals have one consistent place in the shared ontology

Descriptions and graph links are to be built for every plant system the archive covers. Before a pipeline does that system by system, the classes and relationships those systems will be written into are reviewed, made consistent with the rest of the shared schema, and the ITER archive part of the graph is moved onto them.

§1 — Where this starts

The schema is LinkML, and it is shared: one graph holds the Data Dictionary, the standard names and every facility's signals, and ITER's archive signals are one facility among them. The ITER archive work so far added its classes one pass at a time, for plant context, grouping, field codes, the signal vocabulary and group enrichment, each with its own state field on the signal. The pilot plant system carries context; the other systems carry their parsed names and controls-feed labels only.

On 2026-11-22 the coordinator read the schema and found six places where the structure is not yet defined well enough to repeat across the plant:

  • Each signal carries two role vocabularies, one of six values judged at enrichment from prose and one of five assigned by rule from a source. They are designed as separate axes and queried as separate filters, but nothing states how they relate or which a reader should trust when they disagree.
  • The component and control-node memberships each exist twice, as a candidate link and as an archive-grouping link, both derived from the same parsed name.
  • A field-code table, each code's role and meaning with its source, is assembled from graph sources and stored in private configuration. It is not in the graph, so no signal can be linked to what its code means or to the document that says so.
  • The official plant breakdown (PBS) is held as plant-structure nodes, but a control system is linked to it only through imported signal-list rows, which exist for the pilot system alone.
  • The graph has two document classes: the shared one, whose workflow begins at discovered but which holds no version, version state or PBS link, and the plant-context one, which holds those but requires the fetched file's digest. A signal list that has been found but not read fits neither.
  • Source text and generated text shared one description slot; their separation is landing under the enrichment plan, and this review reads the schema after it lands.

A direct record search the same day found 77 signal-list documents on the first page alone, with more withheld from the page; most of them name the PBS node they describe. Per-system self-description documents were found the same way. The lead's decisions: the ontology is settled before a pipeline runs it across the plant; it stays consistent with the current shared classes; there is enough documentation behind it to make a good start; it is expected to evolve as the work progresses; and only the ITER archive parts of the graph are migrated. Any IDM document may be fetched read-only.

§2 — The existing structure for ITER plant signals is reviewed against the shared schema

Delivers. A research record, docs/research/iter-plant-signal-ontology-review.html, that reviews every class, slot and relationship the ITER archive signals use or are reached through, and proposes the ontology the plant-wide work will write into. For each class and relationship it gives the number of ITER-facility nodes or relationships in the live graph, and a verdict: keep, rename, merge into another, or remove. For each proposed addition it names the shared class it reuses or extends, or states why none fits; what existing definition it makes redundant or retires, or why none; and the documentation that will fill it. The additions it settles are: the one document class that holds documents whether catalogued or fetched, with the slots a catalogued document needs (identity, title, current version, version state including superseded and obsolete, file type, PBS references) and what becomes of the other document class; whether the field-code table becomes a graph class and how its private configuration entries retire; the binding of a first-level control-breakdown node to its PBS node; and the stated relation and precedence between the two role axes. It answers whether the plant-structure class and the PBS are one concept and what the class should be called. For each class it changes it lists every reader and writer in the code, the plant search tools and the shared query filters among them. It states which proposed changes touch a class other facilities also use, and keeps those additive. A figure shows the proposed classes and relationships.

Done when. Every class and relationship type reachable from an ITER archive signal appears in the record with its live count and verdict; each of the six problems listed in section 1 has a stated resolution; each proposal names the shared class it reuses or the reason none fits, and what it makes redundant or why nothing; every changed class has its readers and writers listed; the documentation behind the proposal is measured, as the number of first-level control-breakdown nodes holding at least one catalogued ITER archive signal for which at least one signal list or self-description document has been found, out of all such nodes, stated as a lower bound because the census it uses is a sample, with the magnet supplies named; and the record states which changes alter any class used by another facility. The review reads the schema after the source and generated description separation has landed. No real signal, document identity or document text appears in the tracked record. Negative control: one class the review keeps unchanged is shown to have no ITER node or relationship that the proposal would leave unrepresented, and one class it removes is shown to have no reader left.

§3 — The schema carries the reviewed ontology and the ITER archive part of the graph is migrated to it

Delivers. The LinkML schema holds the ontology section 2 settles, the generated models build from it, every reader and writer of a changed class uses the new form, and the ITER-facility nodes and relationships of the archive classes in the live graph are migrated to it. The migration is repeatable, and a private before-image of everything it changes is kept under ~/.cache/imas-codex-codac-uda/ontology-migration/ with a stated way to restore it.

Done when. The schema validates and the models build; for every class and relationship section 2 decided, the live graph holds the decided form with the counts the landing record states before and after; node and relationship counts for every other facility, for the Data Dictionary and for the standard names are identical before and after; a second migration run changes nothing; the plant search and signal tools answer the same queries for a fixed set of twenty ITER signals before and after; and graph-marked statements pass on a compute partition, with the default tier for the touched packages adding no failure against the base revision. Negative control: the count comparison reports a difference when a node of another facility is changed in a scratch run, and the migration refuses to run against a label outside the classes section 2 listed.

§4 — Every signal list and self-description document found in IDM is catalogued and linked to its plant system

Delivers. The graph holds, as ITER-facility nodes in the catalogued-document form section 3 introduced, every signal-list and self-description document a records search finds, with its identity, title, current version and version state, file type and the PBS nodes it names, and a link to each archive control system it is matched to. A document is catalogued whether or not it has been fetched; fetching and importing rows is the pipeline's work and is not part of this section. The project's read-only client refuses the POST that a records search uses, so the documents come from a record export the coordinator supplies under ~/.cache/imas-codex-codac-uda/document-census/, with each search's predicate, date, pages read and rows withheld by permissions recorded beside it; a search through the client is left to the pipeline plan.

Done when. The landing record gives the number of documents found per search, catalogued, linked to a PBS node, and matched to an archive control system, and the number of first-level control-breakdown nodes with and without a matched document; the magnet supplies' signal lists and self-description documents are catalogued and matched; twenty matches are checked by hand against the document's title and PBS reference; a second run adds nothing; and no document identity or title appears in the tracked tree. Negative control: a document whose PBS reference names a system with no archive signals is catalogued but matched to no control system, and a superseded or obsolete version is recorded as such rather than as current.
