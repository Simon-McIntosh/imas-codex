Lifecycle Integrity: Plug the Leaks Before the Repairs

A standard name carries five lifecycle axes. Three are healthy. Two are damaged, and at least one is damaged by a write path that is still open — so repairing the data first would be undone by the next export. This plan closes every open write path, proves each closure with a test that fails without it, and only then hands the repair work to the plans that own it.

§2 — Leak one: the exported status is a constant

export.py:1242 writes "status": "active" as a literal. The halted candidate's catalog.yml sidecar therefore carries 386 entries all reading status: active, while the graph holds zero active, 1996 draft and 2533 null.

This is the leak that makes the ordering argument concrete. The origin-provenance backfill plan exists to recover status on the identities an import cleared. If that backfill lands while the exporter still emits a constant, the recovered value never reaches the catalog and the next reader sees active exactly as before. The repair would be invisible, and we would circle.

It also answers a question the release has been carrying implicitly: a reviewer was expected to see draft names remaining draft until approval, and instead every name ships as active whatever its real state.

Treatment. Derive the exported status from the graph rather than asserting it. Decide what a name at name_stage=accepted but not yet approved should publish as — that is the open decision below. Then gate the export: refuse to cut a candidate that would publish a name whose graph status is null, so the 52% hole becomes a refusal with a list instead of a silent overwrite.

§3 — Leak two: two lifecycle axes encoding the same thing

status (draft / active / deprecated / superseded) and name_stage (… accepted / approved / superseded) both encode lifecycle, and they have drifted apart. name_stage is maintained by the review pools and by sn approve; status is written once at creation and then overwritten at export. One is real, one is decorative, and no reader can tell which they are looking at.

Treatment. Decide which axis is authoritative for the published catalog, then make the other derived or remove it. A single authority is the only durable fix: while two fields can disagree, every future repair has to choose one and the choice will not be consistent across callers. This is a schema-level decision and it belongs to the lead.

§4 — Leak three: the import may still clear the editorial axis

The origin-provenance backfill plan records the damage: a catalog round-trip cleared origin and status on 1,091 identities, and left five generated names carrying catalog markers. Its import-write-authority decision is already locked, and it states the rule exactly — an import is entitled to record that it happened through imported_at and catalog_commit_sha, and is entitled to nothing on the editorial axis.

That decision is locked but the guard is not proven to exist. This plan's job is narrow and specific: establish whether a test exists that fails when an import writes origin or status, and if not, write one. The locked decision's own rationale makes the point — recovery without the guard buys one clean measurement before the next import undoes it. The guard must land before the backfill runs, not after, which is why this plan blocks that one.

"Can never happen again" has a testable meaning here and nothing weaker will do: a test that performs an import against an identity carrying a known origin and status, and asserts both survive unchanged. If that test does not fail when the guard is removed, the guard is not real.

§5a — A timestamp is uniform or it is noise

StandardName.updated_at is written at 3 of 218 property-write sites in graph_ops.py and read at none. Measured today after the static Cypher detector flagged two of those three writes as naming a property LinkML does not declare.

Two obvious dispositions were both wrong. Declaring it would legitimise a field that is stale after 98.6% of modifications — worse than absent, because a reader would trust it. So the field is declared AND made true: every substantive write to a StandardName maintains it, and a static check fails when a new write path omits it, because a rule without a check decays and this one already has. §6 — Ordering: why the leaks come first

The lead's instruction is the governing constraint on this plan and it is not a preference. Every item in §2 through §5 is a write path or a classifier that produces the defect a repair plan would remove. Running the repairs first means each of them is re-created by the next export, the next import, or the next compose rotation, and the measured improvement decays without anyone seeing it happen.

So the sequence is: close the write path, prove the closure with a test that fails without it, then release the repair. Concretely this plan blocks sn-origin-provenance-backfill — which must not run until §4's guard exists and §2's exporter reads the graph — and sn-west-cohort-treatment, whose classification repair in its Group C is the same fix as §5's third row and should be done once, here, rather than twice.

The one measurement that will show whether this worked is not a count of repaired rows. It is that a repeat of the same census, taken after a later export and a later import, returns the same numbers. A repair that survives one round trip is a repair; one that does not was a reading.

§ Decisions

Which axis is authoritative for the status a catalog entry publishes?

The exporter writes a literal active . The graph holds draft on 1996 names, null on 2533, and never active . Meanwhile name_stage is maintained and reaches approved through sn approve . Two fields encode lifecycle and only one is kept current.

Lead ruling 2026-09-04. The lifecycle has a single source of truth in the graph and the catalog export reads from it; the exporter never asserts a value of its own. This also corrects the framing that status and name_stage are redundant — they are different concerns and both are legitimate. name_stage is the PIPELINE lifecycle: how a name was produced, reviewed and accepted, maintained by the review pools. status is the CATALOG lifecycle: draft, active, deprecated, superseded, and it is the gate on what the export may publish. The reason history currently leaks into export paths is precisely that the exporter writes a literal active and never consults status, so the gate never fires. Persisting deprecated and superseded on status is the missing mechanism that keeps a historical record in the graph out of a published catalog.

What status should a name publish while it is accepted but not yet approved?

A review candidate contains names at name_stage=accepted that the physicist has not yet approved. They are real proposals, not yet catalog authority. The catalog site and any downstream consumer need to be able to tell the difference.

Lead ruling 2026-09-04. A name publishes as draft and stays draft until the human gate passes. There is exactly ONE mechanism that moves draft to active: approval of the upstream pull request. No pipeline stage, no score threshold and no export flag may advance it, because the point of the gate is that a human decided. A review candidate therefore ships entirely as draft, which is what a reviewer should see, and the transition to active is the recorded consequence of their approval rather than something the pipeline can reach on its own.

origin-axis-disposition

Lead ruling 2026-09-04: unmaintained infrastructure is retired, because a signal nothing maintains is costly to resolve and misleads every reader who trusts it. origin qualifies on the evidence. Only ONE writer of StandardName.origin exists in the codebase, graph_ops.py:4002, and it writes 'derived'; nothing writes 'catalog_edit' or 'pipeline' at all, so those 3384 markers are residue from a path that no longer exists. That is why the set is both stale and large, and why 182 genuinely hand-edited names sit unmarked while roughly 2031 unmarked-in-fact names sit protected. The surviving value, 'derived', duplicates the StandardNameSource source_type binding and disagrees with it 341 times (18 marked without a derived source, 323 with one and unmarked), so the relationship the composer creates is both truer and already present. Retirement therefore has three parts: repoint the six workers.py and parents.py readers at the source binding, resolve the protection gate under its own decision, and drop the field. No regeneration is implied and no LLM cost is incurred, because filter_protected only strips fields from writes the pipeline is already making and pool eligibility keys on name_stage and docs_stage, never on origin.

maintained-status-set

Lead ruling 2026-09-04: the status set must be consistent and maintainable. The retained set is four axes, each with exactly one writer and a stated meaning, and any axis that cannot name its writer is retired rather than carried. name_stage is the pipeline lifecycle (pending, drafted, reviewed, accepted, then approved), written by the review pools and by sn approve; it is currently healthy at zero nulls. docs_stage is the same shape for the documentation axis, written by the docs pools, healthy at three nulls. validation_status is valid or quarantined, written by the quarantine route, healthy at three nulls. status is the CATALOG lifecycle and the export gate: draft on creation, active only through approval of the upstream pull request, deprecated or superseded when a published name is retired. status is the axis that is currently broken at 52% null and must be brought under a single maintained writer through an idempotent sn run reconcile step. origin is retired under its own decision. The invariant that makes this maintainable is that every axis names its writer, so a future reader can ask who set a value and get an answer.

review-feedback-architecture

Lead ruling 2026-09-04, correcting this plan's §4 premise. There is NO import path and none should exist; what exists is the approve CLI tool. Exactly two things travel back from a review pull request. Comments and edits are ITERATIVE MARKERS, never authoritative content: they flush through the generate/review/score pipeline and produce a new commit on the same pull request, and that loop repeats until everything is resolved. An approval signal, once the pull request is approved, PROMOTES THE LIFECYCLE on those names, and that is the single mechanism moving status from draft to active. Verified against the code: catalog_import.py has no CLI route and writes no StandardName content - no SET sn., no MERGE (sn, no CREATE (sn - which is consistent with the separate finding that nothing in the codebase writes StandardName.origin='catalog_edit'. So the 2096 markers are residue from a path already removed, and a guard against an import writing the editorial axis defends a hazard that no longer exists. The work owed is not a guard but a verification: that no write path can put reviewer-authored content into the graph as authoritative, and that sn approve is confined to advancing lifecycle rather than importing content.

protection-trigger

Lead ruling 2026-09-04: filter_protected is scoped to approved states. The mechanism is kept, because one thing the pipeline must not do is silently rewrite the description of a name that is published catalog authority - that content passed a human gate, so changing it has to return through that gate as a steer, a new commit and a re-approval. What changes is the trigger. origin='catalog_edit' fails three ways: nothing in the codebase writes it, it is inaccurate in both directions (182 names with real edit records excluded, roughly 2031 with none included), and its own docstring encodes the blind-accept model the lead has ruled out. name_stage='approved' fails none: one writer in sn approve at promote.py:885, written only when a pull request is approved, and meaning exactly published authority. Protection becomes a consequence of approval rather than a marker someone must remember to set, which is the same property required of the status axis. It moves from 2096 names to zero today and grows one pull request at a time. Two details land in the same change: the guard must fail CLOSED, because on a query error it currently logs treating-all-as-pipeline and returns an empty set, so protection disappears exactly when something is wrong; and refuse_pipeline_authority_loss is kept unchanged, since it refuses the batch rather than silently stripping fields and becomes the more important of the two guards under this model.

operator-edit-is-marker-only

Lead ruling 2026-09-04: sn edit --docs becomes marker-only with no verbatim escape hatch. The operator's text is stored as steering guidance and the pipeline regenerates documentation from it through generate, review and score, so the intent is carried and the exact wording is never published. This is the model applied rather than a new rule: edits are iterative markers, so an operator's words steer a regeneration instead of becoming the prose. A verbatim override was offered and rejected, on the reasoning that every escape hatch eventually becomes the default path - and this is the specific hatch that produced 2096 names held beyond the pipeline's reach. The cost accepted is that an operator who expected their exact wording to land will see regenerated text; the review gate is always applied in exchange.

exhausted-is-not-deprecated

Lead ruling 2026-09-04, correcting this coordinator's first mapping. An exhausted name must NOT read status='deprecated', because deprecated has to answer 'superseded by what' and for an exhausted name there is no answer. The two markers carry opposite instructions to a reader: quarantined is a signal to REPAIR, deprecated is a signal to WALK PAST. Exhausting the refine rotations is the repair condition, so an exhausted name carries validation_status='quarantined' and its catalog status stays 'draft' - it never entered a catalog, so there is nothing to deprecate. deprecated stays in the vocabulary and becomes reachable only when a name that is actually active is withdrawn; the maintenance sweep therefore never writes it, and that is asserted rather than assumed. Superseded is unaffected: a superseded name does have a successor and the marker names it, so name_stage='superseded' maps to status='superseded' as built. The first reconcile pass had already written deprecated onto 278 live rows (267 valid, 11 already quarantined), and the repair must move them off it - which the original write predicate, accepting only null or draft, would have skipped.

semantic-gate-instrument

Lead ruling 2026-09-04: the principle is right and the instrument is wrong. A name must match its description; cosine similarity between the bare name and the description does not measure that, it measures whether a general-purpose embedding model has seen the term. Measured over the 25 names the gate condemned, it cannot tell its two populations apart. TRUE positives, where the name really is under-specified: beta, whose own description reads toroidal beta and whose source is core_profiles/global_quantities/beta_tor, so it must be spelled toroidal_beta; width, described as the radial width of the processing region for Doppler reflectometer profiles; psi_star; critical_alpha_factor; fast_count. FALSE positives, where the name is correct and the model is ignorant: etendue at 0.432 against the textbook description geometric optical throughput, area-solid-angle product; rotational_transform at 0.445; connection_length at 0.483. beta failed five separate times at 0.488 and 24 of the 25 carry validation_status valid, so neither the score nor the validity flag separates them. The instrument becomes the ISN closed vocabulary, which carries a DEFINITION for every base token: compare that definition against the name's description, because both are domain text a model can read, rather than asking an embedding to recognise a token it was never trained on. A name whose base is in the closed vocabulary is therefore exempt from a bare-similarity verdict; a low score there is evidence about the embedding, not about the name. This is the same failure that made a reviewer dock etendue and that led this coordinator to dismiss SNR and transit_time as invalid bases.

gate-does-not-route-to-refine

Lead ruling 2026-09-04, on this coordinator's advice and reversing its earlier recommendation. The gate marks and does not route. Its log line and the constant's docstring claim it routes a failing name to refine; it never has, because the null resolution method it wrote created a review_quorum_shortfall and the refine claim requires that shortfall to be null. 98 live names sit at reviewed with a shortfall while pool_pending_counts omits that condition and advertises them as pending refine work. The first recommendation here was to make the claim true by letting the typed gate method bypass the shortfall for routing. That was withdrawn on measurement: routing would have sent beta, etendue and rotational_transform into refinement to be renamed away from correct or nearly-correct spellings, which is the churn this programme has paid for twice before. The gate being inert has been accidentally protecting them. So the work owed is honesty rather than routing: the log line and the docstring stop claiming a routing that does not happen, and the pending count stops advertising work no pool can claim. Routing may be reconsidered only after the instrument is recalibrated under the decision above, and never by granting a gate reviewer authority so its rows become claimable.

which-half-is-wrong

Lead question 2026-09-04, answered by applying the new instrument to the three undecided names, and the answer runs opposite to the expected direction in two of three cases. First, none of them is a vocabulary gap. All parse as canonical ISN and suprathermal is ALREADY in the closed population segment, whose seven tokens are bulk, cold, fast, hot, molecular, suprathermal and thermal, so no upstream release is owed. Second, the population vocabulary carries the definitions that settle the choice: fast is a non-thermal or energetic population, hot is a hot population such as charge-exchange neutrals, and suprathermal is a suprathermal tail that is ECRH or LH driven. Third, the data dictionary source path is the tie-breaker where a description and a name disagree. fast_neutral_density is bound to five paths all spelled neutral/density_fast, so the DATA DICTIONARY calls it fast and the name is right; its description calls it suprathermal, which the vocabulary reserves for an RF-driven tail rather than for neutrals, so the DESCRIPTION is the error. hot_neutral_temperature is bound to temperature_hot_neutrals and hot_neutrals_temperature, so the name is right and its description's word energetic is the gloss for fast rather than for hot. Only ion_power is genuinely under-specified: its description says volume-integrated NET power COUPLED to all ion species summed over species, charge states and channels, and the vocabulary already carries both missing pieces in the aggregation segment and in the qualifier tokens absorbed, deposited and conducted. The rule this establishes: when a name and its description disagree, the data dictionary path decides which half is wrong, and refining the description is as legitimate an outcome as renaming. A gate that can only propose renames will corrupt correct names whenever the description is the defective half.

Two instruments answer whether a name is quarantined, and they disagree

A quarantine is a stored verdict that carries no observation time, so a stale one and a current one are indistinguishable by inspection. The only way to tell is to re-run the check — and there are two checks, giving different answers to what looks like the same question. One walks the audit set; the other is the validation worker that actually wrote the verdicts. They answer questions of different width, and nothing in either surface says so.

This has already produced a confident wrong result. A sweep reported 23 of 35 quarantines as stale and clearable; run through the audit route it cleared zero of 23. The claim was then “verified” by re-running the same instrument in a fresh process and treating the agreement as confirmation — which measures reproducibility, never correctness. Two runs of a wrong instrument agree perfectly.

The cost is now on the release path. Five names withheld from the published candidate are quarantined, accepted, unit-bound, source-bound and scored 0.844 to 0.906. Whether they belong in the batch depends entirely on which instrument is right, and no revalidation sweep can be believed until that is settled.

The measure is not that quarantines clear. It is that both surfaces answer the same question, or that each states which question it answers and refuses the other. Then a census means something and a sweep result can be read. A verdict with no observation time should also carry one, so the next reader does not have to re-derive this.
