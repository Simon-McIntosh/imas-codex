Plan · ITER plant data

The pipeline reads ICP and IDM through an authenticated, read-only client

Context for ITER plant signals lives in ICP records and IDM documents. A build worker cannot reach either today. This plan establishes one authenticated, read-only route into both, developed against the ICP integration instance. The lead chose their own account for development and stored its credentials, so the first section is buildable; the record and document sections follow it.

§1 — Where this starts

The lead named two ICP API documentation pages: one on the integration instance, to be used read-only for development, and one on production. Measured on 2026-11-15 from a fleet node, an unauthenticated request to either is redirected to the site's login policy, the same gate that fronts the ITER Confluence site. A worker's unauthenticated request for an IDM document is redirected the same way. A later check with the lead's stored credentials signed in through the identity provider with no second factor, read the API description (793 paths, 815 operations, 471 of them GET, a declared bearer scheme) and received answers from read endpoints for function-category codes and the plant breakdown structure using the signed-in session alone. The API's paths sit directly under the host, not under the path of its documentation page. 344 of its operations are not reads, which is why the read-only rule below is enforced in code.

A search of ICP's own documents found nothing describing this API, its authentication, service accounts, rate limits or the integration instance. The documents it found describe an older web-services design: IDM RTN78W, 348D29, RT4YYN, RBFAH7 and RT6XNK. IDM RT8Y8A covers the plant breakdown structure in ICP. For IDM downloads the only leads are a legacy service call returning a document's current version and a legacy download path. The API's own documentation page is therefore the specification, and it has to be read authenticated.

The repository already passes that login gate for Confluence, keeps session cookies, recovers from a stale session, limits its request rate, and stores credentials in the system keyring. That is the access pattern to test first.

The lead has authorised private curation of ICP content into the graph under the ITER facility. None of it may enter the repository, and it is read inside ITER only.

§2 — An authenticated session reads the integration instance's API description

Delivers. Project code signs in to the ICP integration instance with credentials held in the keyring, never in a file or a prompt, and reads the API's machine-readable description. A record lists the read operations the API offers for plant breakdown structure nodes, component lists and documents, the authentication the API itself declares, and any paging or rate rules it states. Access is strictly read-only, enforced in code and not by convention: every request to an ICP or IDM host passes through one place that allows only the GET and HEAD methods and refuses any other before a network call is made, whatever the caller asks. That includes ICP operations that read through another method, such as its list and query operations; they stay refused until the lead approves named ones. The one exception is sign-in, which the lead allowed on 2026-11-15 with guardrails after a live run showed the exchange posts to more than one host. A non-read request is allowed only while the client is in its sign-in exchange, only to sign-in hosts listed in private configuration or to the gateway's own sign-in path on the integration instance, and never to a path of the API or its documentation. Credentials go only to the identity provider. Once signed in, every request is a read of the integration instance. Requests go only to the integration instance. The refusal of a non-read method and the refusal of another host are the one new refusal family this plan adds, and they exist because the lead requires read-only access by construction; no existing client is retired, because none reaches ICP today.

Done when. The landing record gives the number of operations in the description and the number that are reads, the list of read operations relevant to plant structure, components and documents, and the declared authentication scheme; a test shows a stale session is detected and renewed; a test attempts POST, PUT, PATCH and DELETE against an ICP host through every public entry point of the client and through its underlying session, and each is refused with no request sent; a test shows a request to any host other than the integration instance and the listed sign-in hosts is refused; tests show a non-read request is refused to an API path during sign-in and after it, to an unlisted host during sign-in, and to a listed sign-in host once signed in; the live run's sign-in requests are logged as method, host and path only; and the request log of the live run shows only GET and HEAD against the integration host outside the gateway's sign-in path. A search recorded in the landing record finds no code path that reaches an ICP host without passing the method check. Negative control: with no stored credentials the client refuses before any request; and with the method check removed, the write-refusal tests fail.

§3 — Plant structure and component records read through the API match ICP

Delivers. The client reads a plant breakdown structure node by code, its children, and the component lists that reference it, in bounded pages at a stated request rate, returning typed records with the source identity of each.

Done when. For twenty nodes chosen before the run, the code, title and parent read through the API equal those read through the ITER document assistant's record tools, with the count that agree in the landing record; a subtree of a stated size is read completely, with the number of requests, the elapsed time and the number of records the account was not permitted to see; and the measured request rate stays at or below the stated bound. Fetched records stay in private storage: none is stored as a fixture in the repository, and a search of the tracked tree for fetched identifiers and titles finds none. Negative control: a code that names no node returns an explicit not-found outcome, not an empty success.

§4 — A document file is fetched from IDM by identity and version

Delivers. The client fetches one IDM document's file, given its identity and version, into private storage outside the repository, with its metadata and a digest, and reads a spreadsheet's rows through the project's existing spreadsheet extraction.

Done when. One spreadsheet and one PDF named before the run are each fetched at a stated version, with size and digest in the landing record and the stored path under the private cache; the spreadsheet's sheet names and row counts are recorded; a request for a version that does not exist returns an explicit outcome; and a search of the tracked tree finds none of the fetched content. Negative control: a document the account may not read is reported as not permitted, never as empty.

§ Decisions

Are credentials for the ICP integration instance stored in the keyring?

The lead stores them with the project's credentials command. No agent handles the password and none is placed in a prompt.

The lead stored credentials for the ITER single-sign-on service with the project's credentials command on 2026-11-15. No agent handled the password.

Which identity does the pipeline sign in with?

The ITER document assistant reads ICP through a service account. A personal account works for development but ties a pipeline to one person's permissions. The team that runs the assistant will know the sanctioned route.

The lead said on 2026-11-15 to use their own account. A service account is still to be arranged before any scheduled use.
