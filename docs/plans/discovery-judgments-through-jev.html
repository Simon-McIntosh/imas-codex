§1 — Why every discovery judgment moves

Each discovery pipeline makes the same kind of decision. A language model scores an item on several purpose dimensions from 0 to 1 against a written rubric, and code compares those numbers with fixed thresholds to decide what to keep, expand or ingest. The code pipeline showed that this is the wrong instrument.

  • The rubric places core facility code at 0.65–0.85, while the gates sat at 0.75 and 0.90.
  • The scale drifts by facility: ingested TCV files have a median of 0.85, while the JT-60SA Grad-Shafranov solver tops out at 0.75.
  • Against 128 hand-labelled files from JT-60SA, TCV and JET, the old composite separates the code a mapper needs at AUC 0.56.
  • Jev's typed judgments separate the same files at AUC 0.962.

§25 of JT-60SA Discovery Completion deployed that change for code. This plan carries it to every other pipeline.

Jev, TypeSafe's decisions model reached through OpenRouter's /api/alpha/decisions endpoint, answers three typed primitives:

  • Noul: the probability that a condition holds.
  • Choice: one option from a set, with its distribution.
  • Score: a probability-weighted position on ordered, concretely described levels.

Three rules select among them. Two are measured; the third follows from what each primitive returns.

  • Gate on Nouls. For an in-or-out decision, the maximum of the scope Nouls separated in-scope code at AUC 0.962. A five-level relevance Score reached 0.894, and the maximum of four facet Scores reached 0.913.
  • Use one Noul per label wherever several labels can hold. A Choice is single-answer. Measured by the mapping-candidate-selection plan: a JET plasma-current source received 1.0 on magnetics and 0 on equilibrium and summary, although it belongs in all three.
  • Use Choice for an exclusive classification, and Score for a graded facet that is stored and tracked. Facets are read only for items that pass the gate: outside it, MINPACK's least-squares routines scored 2.5 of 3 on signal processing.
  • Store every distribution beside its value. The lead decided this on 2026-10-07. Every Jev judgment a pipeline persists keeps the model's own uncertainty, as typed fields that Cypher can query:
    • A Score field X is stored with X_probs, ordered by level index, and X_confidence.
    • A Choice is stored with X_probs, aligned to the schema enum's fixed order, and X_confidence.
    • A Noul's value is its probability.
    Confidence near 0 marks a judgment whose mass is split between levels. Such a judgment is worth a second look, and the expected value alone hides it.

Text generation stays with the language model: descriptions, keywords, signal names, cluster labels, and the DD, IDS and identifier enrichment text.

§3 — One judge function, and stale judgments as claimable work

Most stored rows carry the text Jev needs, so re-judging them needs no facility traffic. Counted on 2026-10-07:

At the measured $0.0001 and 0.4 s per call, re-judging every row with stored text costs about $55–60 and about 8 hours at a concurrency of 8.

Re-judging extends the owners that already exist and adds no driver for any pipeline.

  • One judge function. It goes in a new module, imas_codex/discovery/base/judgment.py. It takes a batch of rows, a state builder, a question builder and an applier. It runs acall_decisions under a concurrency bound, books the cost, applies the answers, and leaves a row unjudged when its decision fails. The code pipeline's two arms are extracted into it from code/workers.py and code/scorer.py (build_triage_questions, build_triage_state and their content-arm counterparts) and become its first two callers. Each later pipeline supplies only its own three functions (§4–§6).
  • A stale judgment is claimable work. Each pipeline's own judgment claim also admits a row that is past judgment when its stored judgment model differs from the seat's model and its judgment text is stored. Rows that have never been judged are claimed first. Scoping comes from the run's facility and --path-prefix, as for any claim, and spend is bounded by the run's existing cost limit. A future model change therefore re-judges through an ordinary run.
  • One owner for the claim. The stale-judgment predicate and the never-judged-first order are written once, in claim_batch (imas_codex/discovery/base/claims.py), which gains an ordering hook beside its status_predicate. The code pipeline's two judgment claims (claim_files_for_triage and claim_files_for_scoring in code/graph_ops.py) move onto it here, and each later pipeline's judgment claims move onto it in its own section. The pending counters that count the same state (has_pending_triage_work and has_pending_score_work in code/graph_ops.py, and the counts in code/parallel.py) read the same predicate, so counts and claims agree. The reset field registries (_CODE_RELEVANCE_FIELDS in discovery/base/reset.py and _RELEVANCE_FIELDS in code/scorer.py) carry every judgment field, the stored distributions included.
  • The applier never moves a row backwards. An ingested row keeps its status, chunks and embeddings, and only its judgment fields change. A skipped row that is now admitted moves to its pipeline's admitted status and enters the normal fetch. An admitted row not yet ingested that is now skipped moves to skipped.
  • Why not --reset-to. The reset owner in imas_codex/discovery/base/reset.py keeps its meaning, which is full reprocessing from a stage. Its targets clear ingest fields, for example ingested_at and chunk_count on wiki pages, so re-judging through them would re-fetch and re-embed rows that are already ingested.

Interface account: one public function and one module added, and the code pipeline's inline decision loops retired. No CLI option, no seat and no driver.

Done when:

  • A scoped code run re-judges rows whose stored judgment model differs from the seat's with no SSH call, and a test asserts that the remote executor is never invoked. Never-judged rows are claimed before stale ones.
  • An ingested row keeps its status and chunks through a re-judge.
  • No inline decision loop remains in code/workers.py: both arms run through the judge function.
  • It writes the same fields the pipeline's own judgment writes.
  • Its spend is recorded.

§4 — Paths through Jev

Path judgments gate everything downstream: code discovery scans only paths above the discovery threshold of 0.9. On 2026-10-06 that admitted 94 of the 692 JT-60SA paths outside /home, and excluded the getseldata, SAeqfame, eqdbms and client_eqdbms equilibrium trees.

Prototype first, as for code:

  • a labelled sample of at least 120 paths across JT-60SA, TCV and JET;
  • the questions from §2, with the facility's data_access_patterns injected;
  • AUC and operating points measured against the current composite.

Then deploy:

  • Path triage and scoring write Jev judgments.
  • The scan, expand and enrich gates read Nouls.
  • The 0.9 threshold retires from path gating.
  • The language model keeps only the description.

Done when the deployed path judgments reproduce the prototype's AUC within 0.02 on its labelled set.

§5 — Wiki pages and documents through Jev

The same pattern applies, with one open question carried in. At JT-60SA, 3,754 of the 4,476 wiki pages are SystemDailyReport pages. Their previews show only the blank form template, because TWiki stores filled-in form values in %META:FIELD lines that the preview may drop.

The node first checks one raw page. If the values are there, the preview builder includes them, before any judgment is re-run.

Done when:

  • Wiki and document ingest are gated on a Jev Noul.
  • The prototype's AUC on a labelled page sample is recorded.
  • The daily-report question is answered from a raw page.

Interface account: the wiki and document pipelines supply §3's three functions and move their judgment claims onto claim_batch. They retire their language-model scoring calls, the score fields of WikiScoreBatch and DocumentScoreBatch, and the scores and decisions of ImageScoreBatch, whose vision model keeps only the caption, OCR and diagram text.

§6 — Signal enrichment and DD domain classifications through Jev

Signal enrichment keeps the language model for the generated name and description, and moves its classifications to Jev:

  • physics domain as Nouls per label;
  • diagnostic and context quality as Choices;
  • a Noul asking whether the generated description is supported by the source context the enrichment read. A low value sends the signal back for enrichment rather than accepting the description.

The DD domain classifier becomes the same physics-domain judgment over DD paths.

Done when both deploy behind a prototype that measures agreement with a labelled sample, with the change against the current assignments reported.

Interface account: signal enrichment supplies §3's three functions for its classifications and retires those classification fields from its language-model response model. The DD domain classifier's language-model call retires for the same physics-domain judgment.

§7 — Re-judge the stored rows

After §3–§6 land, each pipeline's own run re-judges its stored rows once per facility through §3's stale-judgment claim:

  • JT-60SA first, then TCV, JET and ITER;
  • each run scoped and bounded, in foreground passes;
  • spend recorded against the estimate in §3.

A row whose decision changes from skip to admit enters its pipeline's normal fetch. A row whose decision changes from admit to skip keeps what it already ingested, and is only reported.

§9 — Search-time reranking with Jev

The lead decided this on 2026-10-07. score_composite stays a code-assembled value, and the search tools gain a Jev rerank.

The two answer different questions:

  • The composite is absolute. It says how much a file matters for diagnostic mapping in general. Asked directly as one holistic Score it reached AUC 0.894, against 0.962 for the composite assembled in code.
  • A rerank is relative to a query. Given this question, which retrieved candidates are most useful? That is the TypeSafe rerank pattern: one comparable Score per candidate, with the query and the candidate's text as the state.

Prototype first (node search-rerank-prototype):

  • 15–20 real queries over the JT-60SA code and wiki content now ingested. Examples: where the flux-loop positions are defined, how getseldata reads EDDB, which routine writes the equilibrium to EDDB.
  • For each query, the top 30 candidates from _search_code or _search_docs in imas_codex/llm/search_tools.py, hand-labelled relevant or not.
  • Embedding-only order compared with the order after a Jev relevance Score per candidate, by nDCG@10 and mean reciprocal rank.
  • Cost and latency per query recorded.
  • The prototype's scripts and raw data are in /home/ITER/mcintos/.config/reckon/crew/reports/imas-codex/search-rerank-prototype/, because a dispatch cannot write outside the repository. The evidence is in the plan's fragments.

Prototype result (landed 2026-10-07, evidence):

  • Mean nDCG@10 rises from 0.246 to 0.509 over 18 questions, and from 0.340 to 0.704 over the 13 whose top 30 holds a relevant candidate. The paired gain is +0.36 (95% CI 0.22–0.52). The rerank is better on 11 questions, worse on Q10 and equal on Q03.
  • MRR rises from 0.384 to 0.544.
  • A random order scores 0.207, so the embedding order carries only a little signal above chance within the top 30.
  • The rerank costs $0.019 for 540 calls. Wall time is about 2 s per question for 30 candidates (median 2.04 s, max 2.58 s).
  • Five questions retrieved no relevant candidate at all, which a rerank cannot repair. §10 classifies them.

Docs score ties first (node docs-score-ties). §11 found that _search_docs scores saturate at exactly 1.0. For Q14, 268 chunks tie there and are ordered arbitrarily by set order, so the answers with the 2nd- and 4th-highest cosine in the facility land at ranks 164 and 181.

  • The node measures, over the 18 §9 questions by nDCG@10 with Q16 as the control:
    • the current order;
    • a secondary sort by raw cosine within tied scores;
    • the score without its clamp;
    • the reserved-vector-slot change §11 recommends (20 leaders at ranks 10–29).
  • It deploys the variant that keeps Q16 and lifts the most answers into the top 30, in imas_codex/llm/search_tools.py, with a test that a tie at the clamp is broken by cosine or no longer occurs.

Deploy (node search-rerank), after docs-score-ties, since both write search_tools.py:

  • _search_code and _search_docs rerank their top candidates through call_decisions, on the existing discovery-relevance seat, so the rerank adds no seat, with the query and each candidate's text as state.
  • Because ranking is not a gate, a failed or slow rerank returns the embedding order unchanged and says so in the result, rather than failing the search.
  • The rerank runs its candidates concurrently under a wall-time budget, sized from the measured 2 s per question. A candidate still unscored when the budget runs out keeps its embedding position.
  • The rerank waits for the code score-stage node to merge, because that node also writes imas_codex/llm/search_tools.py.

Done when:

  • The prototype's measured nDCG@10 and MRR, for both orders, are recorded.
  • If the rerank wins, the deployed tools rerank with that measured gain reproduced on the same queries.
