§2 — Do we need a signal search, and does the graph support it?

Yes, the tool is needed, and the graph supports it. The question "which signals measure X" is how an agent enters a facility's data. Without it, an agent must already know the facility's naming: 70 EDDB categories at JT-60SA, 46,872 signals at JET. Cypher and repl() answer only once the names are known, which is exactly what the ripple session lacked. A dedicated tool is right because signals carry facets the other search tools do not: unit, data class, measurement role, access template and check status. It should share its retrieval core with them, so §4 fixes fusion once for all four search paths rather than for signals alone.

§3 — A golden set any facility can join

This section builds the instrument every later section is judged by. It has four parts. The first is eligibility. A signal enters the golden set only after the Jev-era signal pipeline has enriched it. That pipeline reranks enrichment context through Jev (43290a049, 2026-10-07). It keeps the catalogue wording (b4c89a8fc, 2026-10-09). Its context rerank completes within its budget (93bfb7e9d, committed 2026-10-11T21:08:21Z). The cutover is 2026-10-11T21:08:54Z, when the first run with that commit loaded started; the run before it took SIGTERM at 21:08:29Z and finished its last batches with the old code, so the commit time would admit them. The predicate is enriched_at at or after the cutover. It holds today for 14,190 JT-60SA signals at the time of that derivation, 14,312 when the labels were pooled, and for no JET signal; the count grows as enrichment continues. JET was enriched earlier by another model and joins only when it is re-extracted (§11). The predicate and its cutover live in the fixture as data, not code. A labelled signal that is no longer eligible fails the fixture by name rather than being skipped. The fixture was first written with 2026-10-11T19:08:21Z, two hours early, which admitted 801 signals enriched before the fix, two of the held-out seeds among them. The labelling node sets the fixture's cutover to 2026-10-11T21:08:54Z, lets the harness name those two seeds, and replaces them with eligible signals.

Every arm is scored on the eligible population. The live tool still returns signals the predicate excludes, about 800 JT-60SA signals enriched before the cutover among them, and pooled labelling would otherwise have to grade signals the eligibility check forbids. So before cutting an arm at k, the harness drops each candidate outside the population, and labels hold eligible signals only. An arm is neither credited nor refused for a signal outside the eligible population. An eligible signal without a label still refuses the arm, and a signal that becomes eligible later enters the pool the next time an arm places it in its top 10.

Second, the questions. The eleven draft questions in goldens_draft.json are kept. At least six held-out questions are added, written by someone who has not seen the orderings: the lead, or a worker briefed only with the eligible population. Every question is phrased in physics terms, with no facility name and no data-source vocabulary such as MMSYS or BPS, so a ranking tuned to it is not tuned to one facility.

Third, the grading rule, which follows the DD-path rerank labels in tests/tools/fixtures/dd_mapping_questions.json:

  • 3: a measurement of the queried quantity, on any circuit the question names.
  • 2: a commanded, reference or setpoint value of it, or the same quantity measured at an adjacent point such as a lead's inlet gas rather than its body.
  • 1: related hardware, such as a status flag, a configuration value or a neighbouring measurement on the same circuit.

Fourth, pooled labelling. Every candidate that any arm places in its top 10 is labelled under that rule before arms are compared. The arms are the product tool at the head being measured, the additive rule frozen in the harness, vector only and RRF, plus any arm a later section adds; §7 adds the two reranks. Until §4 lands, the first two return the same order. Each label is enumerated by Cypher and confirmed by reading the name and description. This removes the prototype's bias, where an arm that lifted an unlabelled but relevant signal was scored as wrong.

The harness is one @pytest.mark.graph module, tests/llm/test_signal_search_goldens.py, with its fixture at tests/llm/fixtures/signal_search_questions.json. It reports mean nDCG@10, grade-3 precision@5, grade-3 recall@30 and the zero-hit count for each arm, plus a random-order control. It runs on the fleet allocation, not the login node.

The section is three nodes. The first writes the held-out questions. Its worker gets a brief, not this plan, because §1 and its figure show the orderings. It may enumerate the eligible population by Cypher over categories, data names and descriptions. It must not run any search tool or open the prototype directory. It writes at least eight questions, so that six survive if pooled labelling finds one ill-posed, spread over at least four EDDB categories, and records for each the grade-3 signals it found by enumeration. It commits them to the fixture marked held_out. The harness then takes two nodes, because labelling and code do not fit one hour together. The second node builds the harness and adds the eleven draft questions; it shows the refusal naming the unlabelled candidates of the fixture as it stands. The third pools and labels every arm's top 10, runs the four arms and the control, and writes the evidence.

A label of 0 records a candidate that was read and judged irrelevant, so an unlabelled candidate stays distinct from an irrelevant one. The tool arm calls the product ranking, so each later section measures its own head: extract the ranking inside _search_signals into a function that returns ordered signal ids, with no change in behaviour. The other arms live in the harness. The additive rule among them is frozen there, as its own arm beside the product arm, so the baseline survives §4 rewriting the product ranking. The prototype did not keep its role-aware question text, so write it from §7's five levels and keep it in the harness; §7 moves it into the product beside _RERANK_QUESTION. The random control is a seeded permutation of each question's labelled pool. The live graph moves between runs: two runs minutes apart moved the tool arms, which cut at 30, by up to 0.012 mean nDCG@10, while the pool-100 arms did not move. A later section comparing its head with its base runs the two back to back and treats a difference inside that spread as no change.

Done when the fixture holds at least seventeen questions, six of them held out. The harness refuses to score an arm whose top 10 on any question holds an unlabelled candidate, and names the candidate. It prints the arm table on the pooled labels, and the random control scores below every arm on mean nDCG@10; a control that does not means the labels are wrong. §4 — One rank fusion for every search tool

Replace the additive rule score * 0.7 + text_score * 0.3 + 0.1 at the four sites a tool reaches with reciprocal rank fusion. The sites are _rank_signals, the ranking _search_signals calls, _search_docs and _search_code in imas_codex/llm/search_tools.py, and _hybrid_ids in imas_codex/ids/slot_context.py. The fusion already exists as rrf_fuse and RRF_K = 60 in imas_codex/standard_names/search.py. Move it to imas_codex/search/fusion.py, which exports rrf_fuse and RRF_K and nothing else, and have the standard-name search and these four callers import it from there. This moves a definition rather than adding one. Do not write a second fusion. The code path fuses three streams: chunk vector, chunk text with its reference hits, and code-example vector, which today adds 0.05 to the larger of its own score and the chunk's. Signal search over-fetches 100 vector candidates and a full-text stream before fusing, then cuts to k. The full-text stream is requested at 50, the prototype's value, and _text_search_signals returns up to twice its argument, so it carries up to 100 rows in the product and the harness alike. _vector_search_signals duplicates _find_signals_semantic in imas_codex/graph/domain_queries.py: both build the facility_id-prefiltered query over facility_signal_desc_embedding. Raising the pool in one copy would leave the two disagreeing, so give that query one owner and have the other call it, adding no helper beside both.

The docs and code tools rerank after fusing, so their gain will be smaller. Their 18 JT-60SA questions and hand labels, built for discovery-judgments-through-jev, guard against regression. The questions and labels are queries.json and labels.json in ~/.config/reckon/crew/reports/imas-codex/search-rerank-prototype/, and the recorded 0.4821 comes from the pool sweep in docs/evidence/fragments/discovery-judgments-through-jev/search-rerank.html. That plan's §13 places four code and docs answers at embedding ranks 159 to 181; the additive rule may be part of why, so re-place them after this lands. _hybrid_ids feeds the map candidate stage, so land this between imas map run invocations, never during one.

hybrid_dd_search in imas_codex/graph/dd_search.py keeps its own blend. It scales BM25 to the range 0 to 1 before weighting, in _text_search_dd_paths in imas_codex/tools/graph_search.py, so it does not have the mixed-scale defect, and its tie-breakers are tuned against tests/tools/fixtures/dd_mapping_questions.json. Moving it to RRF is a change to measure on that fixture, not part of this section.

The same expression also appears in HybridSearchStrategy in imas_codex/search/search_strategy.py and HybridSearchEngine in imas_codex/search/engines/hybrid_engine.py. No tool constructs either: SearchService has no production caller and defaults to mock engines. Both are left as they are, because nothing that reaches them could measure a change.

The section is two nodes. The first writes the fusion: the shared module, the four call sites, one owner for the signal vector query, and the two unit tests. The second measures it: the signal harness at the first node's head against the frozen additive-rule arm, labelling any eligible candidate the fused tool lifts into a top 10 under §3's rule, and the docs and code question set at pool 60, which spends Jev on their rerank and so runs as a measurement outside pytest, as §7's does. Its table goes in docs/evidence/fragments/signal-search-finds-the-measured-signal/fusion.html.

Done when all of the following hold:

  • On §3's pooled labels, held-out questions included, fused signal search beats the frozen additive-rule arm on mean nDCG@10 and grade-3 precision@5, and no question has zero grade-3 hits in its top 30.
  • Labelled-only nDCG@10 on the docs and code question set stays within 0.02 of its recorded 0.4821 at pool 60.
  • A unit test shows a candidate ranked first by vector alone (cosine 0.9) outranking one ranked fifth by full text alone (BM25 14). The old rule must fail the same test.
  • A test asserts that no facility identifier appears in the fusion or ranking code.

§5 — Embeddings follow the text they embed

GraphClient.create_nodes embeds a description only when it writes a node that carries no embedding. The signal pipeline rewrites descriptions through Cypher, both when individualising group members and when propagating a representative's text, so the vector keeps describing the old text. By timestamp, 3,537 JT-60SA and 39,471 JET signals were embedded before their last enrichment. Individualisation writes no timestamp at all, so timestamps undercount; the cosine probe in §1 is the true measure.

Give signal descriptions one writer. It sets description, embedding, embedded_at and a new embedded_text_hash slot together, and every description write in imas_codex/discovery/signals/ goes through it. Then re-embed every FacilitySignal, at every facility, whose stored hash is missing or differs from the hash of its current text. JET is included: a stale vector harms any search, whatever the age of the description.

Decision embed-text is settled here by measurement. Embed the description alone, or a composed name — description (unit) text, and keep whichever scores higher on §3's harness.

The section is three nodes. The first measures the decision without touching stored vectors. It embeds the eligible JT-60SA signals both ways, ranks each harness question by cosine over those vectors in memory, scores a vector-only arm and an RRF arm with the full-text stream for each text on §3's labels, and labels any eligible candidate either text lifts into a top 10 under §3's rule. The second, in parallel with the first, writes the single description writer, taking the embed text as a parameter so the decision can set it, with its test. §7 — Rerank signal search with a role-aware Jev score

Route _search_signals through rerank_candidates, the owner the docs, code and DD-path searches already share. It gets a signal state builder: name, description up to 1,200 characters, unit, data class and accessor. It also gets the role-aware question the harness keeps. The question's five levels run from "a different quantity" through "a commanded, reference or setpoint value" to "a measurement of exactly the quantity asked for". The pool is 60 and the budget 5 s. The seat is the existing discovery-relevance model on the facility-discovery service. The switch is its own flag, off by default, not the DD-path rerank's server-mode flag. Once the measurement passes, the fourth node sets it to follow the server mode as the DD-path rerank does: on for a full or facility server, off for a read-only or DD-only server. If the measurement fails, the flag stays off.

The prototype could not settle whether the rerank earns its place. On the draft labels it raised recall@30 and lowered precision@5, and most of its losses were unlabelled relevant signals. Pooled labels settle it.

§8 — Signal role as a stored judgment

Judge each signal's role once, at enrichment, with a Jev Choice: measured, commanded, reference or setpoint, status or flag, configuration parameter, or derived or computed. Store it as signal_role. It serves three readers:

  • a role= filter on search_signals;
  • the rerank state in §7, to which this section adds the role once it is stored;
  • the mapping stage, where a reference belongs in pulse_schedule and a measurement belongs in the measured IDS. This is the same distinction the DD-path labels grade as 2 against 3.

A prototype on a stratified sample of 300 eligible signals, hand-labelled, measures agreement and cost before any backfill. This section is held by decision signal-role.

Two precedents draw the same line elsewhere, and neither applies to a facility signal. _PULSE_SCHEDULE_REFERENCE_RE in imas_codex/core/node_classifier.py marks a DD path under a pulse_schedule reference as a commanded waveform; it is the mapping-side counterpart a stored role pairs with. OPERATIONS_PATTERNS in imas_codex/discovery/paths/enrichment.py scores code files by keyword. A pattern over signal names would serve one facility's naming, so the role is judged from name, description and glossary. This section adds one stored property and one search_signals option. When the decision is taken it names what the option retires; the candidate is the physics_domain filter, which §2 found unreliable on plant signals.

Done when the prototype's agreement with the hand labels and its cost per signal are recorded. § Decisions

What is one row of a signal search result?

JT-60SA's 15,111 signals sit in 5,172 SignalSource families, mostly singletons, because each coil's channel is its own source. So searching families would not merge the six EF coil voltages a physicist thinks of as one row. The SignalSource vector index exists but holds no embeddings. JET's families reach 2,366 members, where per-signal rows would flood any report.

Lead decision, 2026-10-13: collapse rows that share a name template within one data-source category for display, while the harness keeps scoring individual signals. It merges the per-coil channels SignalSource keeps apart, folds JET's large families, and needs no new index. §9 is written for this choice.

Where is a signal's measurement role judged?

The ripple search's central failure was ranking references and commands above measurements. A stored role can filter a search, feed the rerank, and tell the mapping stage a pulse_schedule reference from a measured home. A query-time judgment costs nothing until a search runs, but it is re-paid on every query and helps no other reader.

Lead decision, 2026-10-13: judge each signal's role once at enrichment and store it as signal_role, after §8's 300-signal prototype records agreement and cost. §7 measured the role-aware rerank question at 0.913 nDCG@10 against the generic question's 0.905, so the stored role's main value is the role= filter and the mapping stage rather than ranking.

What text does a signal's embedding encode?

Today it encodes the description alone. A composed text, name followed by description and unit, gives the vector the identifier and unit a searcher often types. §5 measures both on the harness before choosing; no recommendation precedes that measurement.

Settled by §5's measurement, as the plan specifies: over the 14,312 eligible JT-60SA signals embedded in memory, the description alone beats the composed name, description and unit on both arms and every metric (RRF mean nDCG@10 0.776 against 0.762, vector only 0.689 against 0.664, RRF grade-3 precision@5 0.682 against 0.664).
