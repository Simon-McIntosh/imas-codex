§1 — The tool already exists, and two of its three layers are blind

The instinct is to build a new sn audit. That would be the wrong move, because sn review already is the tool: it runs independently of sn run, it has a three-layer pipeline (deterministic audits → batched LLM scoring → cross-batch consolidation), and it already accepts --ids, --physics-domain, --stage, --force, --models, --batch-size, --cost-limit, --concurrency, --dry-run and --target names|docs. The local lane is already reachable through --models, and --dry-run already means exactly what it should: run Layer 1, show the batch plan, make no LLM call.

What is missing is not the command. It is that the command cannot currently see. Two independent defects, both measured on 2026-09-21, make the review pass structurally incapable of finding the class of defect that independent investigation keeps finding. Both have the same shape as every other fail-open in this repository: a lookup returns empty and the caller proceeds as though it had looked.

Layer 1 findings never reach the reviewer. review/pipeline.py:1709's _extract_audit_findings iterates getattr(audit_report, "findings", []). The AuditReport model declares embedding, lint_findings, link_findings and duplicate_components — there is no findings field, verified against the live model, so the expression returns the empty default on every call. Layer 1 runs, and one hundred percent of what it produces is discarded before the reviewer prompt is built. No test anywhere referenced the attribute, so nothing failed.

Layer 2's catalog comparators are exhausted part-way through each batch. In workers.py near line 5608 the name-review path builds nearby_existing_names by embedding search, k=5 per item, appending into one batch-level list capped at 30 — and on reaching the cap it breaks the outer loop. With sn-compose batch-size 25 (50 for names-only), the first six or so items consume the entire budget and every later item contributes nothing. Worse, the list is rendered batch-level, so all 25 candidates are judged against comparators drawn from the neighbourhoods of the first six. The reviewer prompt instructs the model to flag a redundant spelling; for most of the batch it has nothing to flag against.

That is sufficient to explain the measured outcome. An independent opus audit of the WEST cohort judged 341 accepted bindings and found 74 defects, 21.7 percent, concentrated in exactly the classes these two layers exist to catch: redundant spellings, minority base tokens, and names asserting more than the data dictionary supports. The pipeline's own review had passed all of them.

§2 — The calibration fixture already exists, and it is the point

This plan is test-driven in the graph sense the lead described: write the instrument first, confirm it reproduces a known cohort of reds, only then fix, then re-run and watch the reds clear. That is only possible because the red cohort is already committed and independent of the instrument.

docs/evidence/sn-west-catalog-release/west-name-repair-worklist.md carries 74 defects over 341 bindings, collapsing to 61 repairs — 51 renames and 10 splits — each row naming the rejected spelling, the proposed spelling, every source path the identity binds, and which audit record produced it. It was produced by a different instrument (opus reading DD text) than the one this plan repairs, so it is a genuine external control rather than a restatement of the tool's own output.

Calibration is two-sided and both sides are gates. Recall below a floor means the instrument is still blind and no amount of green from it licenses a release. Precision below a floor means it will bury a reviewer in false positives and be switched off, which is the same outcome by a slower route. The floors themselves are a decision in §4, not something this plan should assume; what is not negotiable is that both are measured against the fixture before the instrument is trusted.

Six rows of the worklist are contested between the two audit records — the volume_of_flux_surface family, a vacuum-field spelling, three toroidal-angle loci, and launched-versus-coupled power on two lower-hybrid nodes. Those are deliberately excluded from the recall denominator: an instrument cannot be scored against rows whose correct answer is unsettled. They are adjudication input for sn-west-catalog-release, not calibration input here.

§3 — What the instrument must gain

Four capabilities, in the order they should land. The first two are repairs that make the existing layers functional; the second two are the genuinely new surface.

Route Layer 1 findings into the prompt. Read the three declared lists rather than a field that does not exist, and carry each finding to the candidates it names. This is small, and it is the single highest-value change in the plan because it restores a whole layer that is currently inert. It must land with a test that fails against the getattr form, and with a static check for the general shape — a three-argument getattr whose literal attribute no model on the object declares — because a peer session found the same shape at several sites and a per-site fix leaves the rest.

Give every candidate its own comparators. Replace the shared batch budget with a per-item one so no candidate is starved, and carry comparators per item so the prompt shows each candidate the names it is actually being compared against. Add the unit-anchored comparator the catalog currently has no way to produce: accepted names sharing the candidate's unit but carrying a different physical_base. That is the only signal that catches a split base, and the catalog holds a live example — brightness (2 accepted names) and photon_radiance (4) both at m^-2.s^-1.sr^-1, describing the same quantity. hard_xray_brightness was accepted precisely because same-base comparison showed it a consistent pair.

Add grouped review as a first-class target. Today --target takes names or docs, both per-identity. The defects that per-identity review cannot see are the cohort ones: a base split across two spellings, a family whose members disagree, an identity bound to loci of different kinds. Prior art exists and should be extended rather than duplicated — harmonize.py already assembles sibling families by HAS_PARENT or shared physical_base and computes a deterministic drift metric, but it is docs-only, read-only, and has no CLI surface at all (sn harmonize does not exist). The grouped target is that module's detection, widened to the name axis and given the command-line entry point it never had.

Scope a run to a release batch. --ids and --physics-domain cannot express "the cohort this release publishes". A manifest-scoped selector closes that: given west_production_dd_paths.yaml the instrument reviews exactly the 230 distinct identities the cut would publish. Note the denominators, because they have already caused one wrong report — 342 manifest paths resolve to 343 source nodes (one duplicate), 344 producing edges, and 230 distinct identities. The release unit is 230.

§4 — Concurrency, cost, and the dry run

The instrument is meant to be run often and over the whole catalog, so its economics decide whether it is used. Reviewing 5,130 identities per-name and per-doc, plus grouped passes, is far beyond what a paid quorum can absorb; on the local lane it is free of marginal cost and bounded only by wall clock. That makes local-lane concurrency the design centre rather than a tuning detail.

The concurrency target and the last measurement disagree, and the disagreement must be resolved by measurement rather than assumed either way. The lead's instruction is that the lane now sustains upwards of 30 concurrent DSv4.1 tasks and the pipeline should lean on it. The most recent recorded probe of this repository's compose path found the knee at roughly 4 on two H200s with real payloads, where exceeding it produced 69 API timeouts rather than throughput. Both can be true — that probe predates the current served variant, and deepseek-v4.1-flash reports a 512,000-token context under sglang — but the plan must not encode a number neither side has re-measured. The first node re-runs that probe against the current endpoint with review-sized payloads and records the knee; the default concurrency is then set from the result, with the lead's 30 as the value to confirm rather than to assume.

The dry run is the safety property, not a convenience. --dry-run already runs Layer 1 and prints the batch plan without an LLM call. Once Layer 1 findings are routed, a dry run becomes genuinely informative: it reports every deterministic finding over the selected cohort at zero cost. It must state the cohort size, the batch plan, the resolved concurrency, the model that would be used, and the projected spend — and a run whose projected spend exceeds --cost-limit must refuse rather than start and stop partway.

§5 — Order of work, and what must not happen

The order is the method. Repair the instrument, calibrate it against the fixture, and only then repair the catalog. A fix landed before the instrument can see it is a fix nothing verifies, which is the situation this plan exists to end.

No catalog repair lands under this plan. The 61 repairs belong to sn-west-catalog-release, they route through sn edit --hint … --reason … so the review quorum decides the spelling, and they are paid work the lead has not authorised. This plan's deliverable is the instrument and its calibration report. The temptation to fix a name while looking at it is exactly what would destroy the fixture's independence.

The re-run is the acceptance test. When the repairs do land, under their own plan, this instrument re-runs over the same cohort and the reds it previously reported must clear. A repair that clears a red without the instrument agreeing is not finished, and an instrument that reports green over a cohort a human audit still finds defective has failed its own calibration and must be re-opened.
