§1 — The tool already exists, and two of its three layers are blind

The instinct is to build a new sn audit. That would be the wrong move, because sn review already is the tool: it runs independently of sn run, it has a three-layer pipeline (deterministic audits → batched LLM scoring → cross-batch consolidation), and it already accepts --ids, --physics-domain, --stage, --force, --models, --batch-size, --cost-limit, --concurrency, --dry-run and --target names|docs. The local lane is already reachable through --models, and --dry-run already means exactly what it should: run Layer 1, show the batch plan, make no LLM call.

What is missing is not the command. It is that the command cannot currently see. Two independent defects, both measured on 2026-09-21, make the review pass structurally incapable of finding the class of defect that independent investigation keeps finding. Both have the same shape as every other fail-open in this repository: a lookup returns empty and the caller proceeds as though it had looked.

Layer 1 findings never reach the reviewer. review/pipeline.py:1709's _extract_audit_findings iterates getattr(audit_report, "findings", []). The AuditReport model declares embedding, lint_findings, link_findings and duplicate_components — there is no findings field, verified against the live model, so the expression returned the empty default on every call. Layer 1 ran, and one hundred percent of what it produced was discarded before the reviewer prompt was built. No test anywhere referenced the attribute, so nothing failed.

This one is repaired. A concurrent session landed the fix on 2026-09-21 and it is on main: _extract_audit_findings now reads audit_report.lint_findings and audit_report.link_findings directly. The plan keeps the account because the shape recurs — the same session found further sites and is landing a static check that refuses any three-argument getattr whose literal attribute the target model does not declare. What this plan still owes is the calibration that would have caught it: a whole layer producing nothing reached no gate, because no gate asked whether the layer had executed.

The catalog comparators are starved, and correcting where that happens makes it worse rather than better. This was first recorded here as a review-path defect. It is not: workers.py:5609 sits inside compose_batch and :3732 inside compose_worker, both of which render sn/generate_name_dd. The starved list feeds name generation, not review. Each builds nearby_existing_names at k=5 per item into one batch-level list capped at 30, and on reaching the cap breaks the outer loop, so with a 25-item batch the first six or so items consume the whole budget and every later item composes against comparators drawn from other items' neighbourhoods. Those comparators exist to make the composer reuse the cohort's established spelling, and minority spelling of a base the cohort already fixes is one of the five defect classes, present in every block of the census. So this is a mechanism that produces the defect, not merely a detection limit — a stronger and more useful finding than the one it replaces.

The review path has its own, different blindness. It does not share the compose builder. build_neighborhood_context (review/enrichment.py) issues one query for the whole batch, assembled from the cluster label plus the first three descriptions, and returns k=10 neighbours — so a batch is never searched per item at all, and every candidate is judged against a neighbourhood derived from at most three of its peers. Its all_names parameter, the full catalog, is documented in its own docstring as "unused in current impl". And the standalone path sets "existing_names": [] at review/pipeline.py:1952 with the comment "not needed for standalone review", while the compose path passes up to 200. The tool this plan means to calibrate is therefore the one with the least catalog awareness of any surface in the pipeline.

That is sufficient to explain the measured outcome. An independent opus audit of the WEST cohort judged 341 accepted bindings and found 74 defects, 21.7 percent, concentrated in exactly the classes these two layers exist to catch: redundant spellings, minority base tokens, and names asserting more than the data dictionary supports. The pipeline's own review had passed all of them.

§2 — The calibration fixture already exists, and it is the point

This plan is test-driven in the graph sense the lead described: write the instrument first, confirm it reproduces a known cohort of reds, only then fix, then re-run and watch the reds clear. That is only possible because the red cohort is already committed and independent of the instrument.

docs/evidence/sn-west-catalog-release/west-name-repair-worklist.md carries 74 defects over 341 bindings, collapsing to 61 repairs — 51 renames and 10 splits — each row naming the rejected spelling, the proposed spelling, every source path the identity binds, and which audit record produced it. It was produced by a different instrument (opus reading DD text) than the one this plan repairs, so it is a genuine external control rather than a restatement of the tool's own output.

Calibration is two-sided and both sides are gates. Recall below a floor means the instrument is still blind and no amount of green from it licenses a release. Precision below a floor means it will bury a reviewer in false positives and be switched off, which is the same outcome by a slower route. The floors themselves are a decision in §4, not something this plan should assume; what is not negotiable is that both are measured against the fixture before the instrument is trusted.

Six rows of the worklist are contested between the two audit records — the volume_of_flux_surface family, a vacuum-field spelling, three toroidal-angle loci, and launched-versus-coupled power on two lower-hybrid nodes. Those are deliberately excluded from the recall denominator: an instrument cannot be scored against rows whose correct answer is unsettled. They are adjudication input for sn-west-catalog-release, not calibration input here.

The calibration now sits on the far side of the compose repair, and the record must say so. The comparator starvation landed as 064476e26 at 2026-09-21T07:22:04Z, verified here as an ancestor of main: both compose sites now call one extracted _collect_nearby_name_comparators, which gives every item max(1, cap // len(items)) comparators in a first pass before a second spends what is left. The node's own reproduction of the old behaviour is the figure to quote — 6 of 25 batch items contributed a comparator at cap 30. The fixture does not move, because it is a set of already-accepted identities and a generation change cannot reach them; but every calibration run must record which side of this commit it sits on, since a recall figure taken before and after measures two different pipelines.

That commit was the partial fix, and the baseline is the later one. 064476e26 restored a per-item share only up to a fixed cap of 30, while name-only-batch-size is 50 — so a dense name-only batch still left twenty items with no comparator, and neither landed test could see it because both used 25 items. The complete repair is the merge 8d2518116 at 2026-09-21T08:11:05Z, which carries three changes: the cap became a floor (effective_cap = max(cap, len(items)), landed in f0a7c40b8 at 07:57:59Z) so the comparator block grows linearly with the batch; the allowance test moved before the append, so the max(1, …) floor governs what it appeared to govern rather than being held by statement order; and both compose sites offload the search pass through asyncio.to_thread, verified present at workers.py:3792 and :5656. Measured here against current main with distinct neighbours: zero items receive zero comparators at n = 25, 30, 31, 50 and 200. Calibration runs pin to 8d2518116.

Three commits, three timestamps, and two of them have been quoted wrongly in this programme already — including by me. The sequence is 064476e26 07:22:04Z (partial), f0a7c40b8 07:57:59Z (the floor), 8d2518116 08:11:05Z (the merge carrying all three changes). Every one of those commits records +02:00, so a timestamp read off git log without normalising is two hours fast; the merge has been reported elsewhere as "10:11:05Z", which is its local time with a Z appended. A calibration baseline is exactly the kind of record where a two-hour error survives unchallenged, so the normalisation belongs in the procedure: TZ=UTC git log -1 --format=%cd --date=iso-local <sha>, never --date=format-local with a literal Z in the format string.

The remaining question is not starvation but sufficiency, and it is a real one for the calibration to answer. With heavily overlapping neighbours the deduplicated list collapses to the shared set regardless of batch size — correct behaviour, since identical neighbours are not several comparators — but it means the number of distinct comparators a composer sees is set by how much the cohort's neighbourhoods overlap, not by the cap. Whether that is enough to make a composer reuse an established spelling should be settled by measuring the defect rate at different shares, not by choosing a number.

§3 — What the instrument must gain

Four capabilities, in the order they should land. The first two are repairs that make the existing layers functional; the second two are the genuinely new surface.

Route Layer 1 findings into the prompt. Read the three declared lists rather than a field that does not exist, and carry each finding to the candidates it names. This is small, and it is the single highest-value change in the plan because it restores a whole layer that is currently inert. It must land with a test that fails against the getattr form, and with a static check for the general shape — a three-argument getattr whose literal attribute no model on the object declares — because a peer session found the same shape at several sites and a per-site fix leaves the rest.

Give every candidate its own comparators. Replace the shared batch budget with a per-item one so no candidate is starved, and carry comparators per item so the prompt shows each candidate the names it is actually being compared against. Add the unit-anchored comparator the catalog currently has no way to produce: accepted names sharing the candidate's unit but carrying a different physical_base. That is the only signal that catches a split base, and the catalog holds a live example — brightness (2 accepted names) and photon_radiance (4) both at m^-2.s^-1.sr^-1, describing the same quantity. hard_xray_brightness was accepted precisely because same-base comparison showed it a consistent pair.

Add grouped review as a first-class target. Today --target takes names or docs, both per-identity. The defects that per-identity review cannot see are the cohort ones: a base split across two spellings, a family whose members disagree, an identity bound to loci of different kinds. Prior art exists and should be extended rather than duplicated — harmonize.py already assembles sibling families by HAS_PARENT or shared physical_base and computes a deterministic drift metric, but it is docs-only, read-only, and has no CLI surface at all (sn harmonize does not exist). The grouped target is that module's detection, widened to the name axis and given the command-line entry point it never had.

Scope a run to a release batch. --ids and --physics-domain cannot express "the cohort this release publishes". A manifest-scoped selector closes that: given west_production_dd_paths.yaml the instrument reviews exactly the 230 distinct identities the cut would publish. Note the denominators, because they have already caused one wrong report — 342 manifest paths resolve to 343 source nodes (one duplicate), 344 producing edges, and 230 distinct identities. The release unit is 230.

A prior question was measured before any of these four land: can the rubric express the defects at all? Reading the ten reviewer prompt files in imas_codex/llm/prompts/sn/ against the structured output models the reviewer must fill, 4 of 6 defect classes have both a dimension that expresses them and a field that carries the correction. For two of those four the prompt's language is sharper than the audit's own — source-fidelity is called "the #1 silent failure" and its worked example is a strike-point path from this very cohort. So the rubric is mostly not why the defects shipped, which supports the ordering above: the first two capabilities are repairs to what the reviewer is shown, and that is where the constraint sits.

Two classes are the exception, and they fail for opposite reasons. An identity whose bindings span loci of different kinds has no dimension and no field: the repair is two or three names and the model offers two single-string slots (revised_name, suggested_name), neither addressed to a binding, so a reviewer can only write prose into issues that nothing reads as a correction. That is the class the name audit found 10 times over 24 bindings and called unrepairable by a reader — the rubric agrees by construction. This is a capability the grouped-review target above needs and does not yet have: grouped detection without a per-binding correction field can find the cohort defect and still not report its repair. A documentation that contradicts its own bindings has the opposite problem — both a dimension (physics_accuracy) and a field (revised_documentation) are waiting, but the docs prompt hands the reviewer the binding list under "dock if cited in output" where the name prompt calls the same field the "authoritative bound-source cohort". One of those two sentences is wrong about what bindings are for, and the measured vertical_coordinate_of_strike_point case is what the disagreement costs.

The ordinal convention is encoded and is backed in code, but reaches 3 of the 10 reviewer prompts and lands on no dimension. It is absent from every docs and description prompt — where the audit's most-repeated description defect lives — and a reviewer following it has no told place to dock, while the validator that clears an unparseable suggestion does not clear an ordinal one because an ordinal-qualified name parses cleanly. Full reading with every quoted line: the rubric expressiveness record, anchored in the cumulative record.

Score a description against the bindings its identity actually holds. This axis was not in the original four and the evidence for it arrived afterwards, from two directions that agree. The lead's ruling that ordinal dimensions are not carried in names makes a shared identity the normal case rather than an ambiguity — so the descriptions written while shared identities still looked like defects are where the damage now sits. The measured instance: vertical_coordinate_of_strike_point binds the inner leg, the outer leg and a constraint path, while its description reads as the inner strike point specifically; its radial twin documents the correct both-legs convention verbatim. Same binding shape, contradictory prose, and a physicist reading the Z one attributes outer values as inner. No rename repairs it, and the name axis cannot see it because the name is correct. A concurrent session predicts this axis is now richer than the name axis and names a second instance outside the repair list. The check is mechanical once stated: a description that restricts to one member of a set its identity binds across is wrong, and the identity's own binding list is the evidence.

§4 — Concurrency, cost, and the dry run

The instrument is meant to be run often and over the whole catalog, so its economics decide whether it is used. Reviewing 5,130 identities per-name and per-doc, plus grouped passes, is far beyond what a paid quorum can absorb; on the local lane it is free of marginal cost and bounded only by wall clock. That makes local-lane concurrency the design centre rather than a tuning detail.

The concurrency target and the last measurement disagree, and the disagreement must be resolved by measurement rather than assumed either way. The lead's instruction is that the lane now sustains upwards of 30 concurrent DSv4.1 tasks and the pipeline should lean on it. The most recent recorded probe of this repository's compose path found the knee at roughly 4 on two H200s with real payloads, where exceeding it produced 69 API timeouts rather than throughput. Both can be true — that probe predates the current served variant, and deepseek-v4.1-flash reports a 512,000-token context under sglang — but the plan must not encode a number neither side has re-measured. The first node re-runs that probe against the current endpoint with review-sized payloads and records the knee; the default concurrency is then set from the result, with the lead's 30 as the value to confirm rather than to assume.

The dry run is the safety property, not a convenience. --dry-run already runs Layer 1 and prints the batch plan without an LLM call. Once Layer 1 findings are routed, a dry run becomes genuinely informative: it reports every deterministic finding over the selected cohort at zero cost. It must state the cohort size, the batch plan, the resolved concurrency, the model that would be used, and the projected spend — and a run whose projected spend exceeds --cost-limit must refuse rather than start and stop partway.

§5 — Order of work, and what must not happen

The order is the method. Repair the instrument, calibrate it against the fixture, and only then repair the catalog. A fix landed before the instrument can see it is a fix nothing verifies, which is the situation this plan exists to end.

No catalog repair lands under this plan. The 61 repairs belong to sn-west-catalog-release, they route through sn edit --hint … --reason … so the review quorum decides the spelling, and they are paid work the lead has not authorised. This plan's deliverable is the instrument and its calibration report. The temptation to fix a name while looking at it is exactly what would destroy the fixture's independence.

The re-run is the acceptance test. When the repairs do land, under their own plan, this instrument re-runs over the same cohort and the reds it previously reported must clear. A repair that clears a red without the instrument agreeing is not finished, and an instrument that reports green over a cohort a human audit still finds defective has failed its own calibration and must be re-opened.

§1a — Seven gaps named, and the shape behind all of them

The five review modules and the sn review surface were read against the five defect classes the independent WEST audit found. One class is detectable today, two are detectable only through a single context channel that can vanish silently, and two are structurally undetectable by any layer.

Four further instances of this pipeline's fail-open shape, three CONFIRMED. The costliest is review/pipeline.py:737-740: the DD source-doc fetch swallows every non-resolution exception at debug level, path_docs stays empty, and the consumer at :786-788 guards with if docs: — so dd_source_docs is never set at all, not set empty. The batch is then scored at full cost as though the Data Dictionary had been consulted and had nothing to say. The asymmetry is the tell: a partial omission logs at warning with every path named (:711), while total failure logs at debug. The hybrid comparator channel is nested inside the same branch, so one swallowed exception removes two independent context channels. This is exactly the channel the two recoverable WEST classes depend on.

Two classes no layer can reach. A physics error in the modifier — radial_derivative_of on a dpsi_drho_tor path — is grammatical, semantically coherent, conventional and complete, and physics_accuracy exists only on the docs axis (pipeline.py:2205-2212), so a names-axis review is never asked the question. An identity bound to loci of different kinds is a property of the set of source paths, and every Layer 1 audit is per-name-record while Layer 3 sees only scores.

Why consolidation never caught any of it. Layer 3's detectors measure variance — drift within a domain, scores more than 1σ below a group mean. A blindness that is systematic scores a whole class alike, and a variance detector reports nothing from a uniform column. Layer 3 is loudest exactly when Layer 2 is working and silent exactly when Layer 2 is blind, which is why 74 defects in 341 bindings passed without one consolidation warning.

And the dry run conceals rather than reveals it. sn.py:6012 runs Layer 1 on every dry run and prints its findings — the one surface where that layer's output is not discarded. The flag that exists to show the layer working is what hides that it is inert on a real run.

Seven sites of one shape in one pipeline says the individual repairs are not the durable fix. A report must carry whether each check executed, and a review must refuse rather than score when a channel it depends on did not load. Full record, every finding with its file and line and a concrete triggering scenario: the capability-gap review.

A second failure mode has emerged that this rule does not cover, and the instrument should be aimed at it too. An independent review gate run against the repairs themselves has examined two changes and found something real in both — and in both, the defect was the same class as the one being fixed, one call site or one test away. What it keeps finding is not a wrong implementation. It is a missing guard on a correct one: a precedence rule that a docstring states and no test pins, so swapping the two branches leaves the whole suite green; an invariant that holds at twelve construction sites and not the thirteenth. That is structurally different from a fail-open, and a green gate cannot see it — the behaviour is right today, and nothing would notice it becoming wrong. A calibration that only measures whether the instrument reproduces known defects will not measure this at all, because these are not defects yet. It is the same shape as the suite that pinned "an audit that did not run equals a clean audit" as correct: the test encodes the absence of a guard as the contract. The cheapest instrument for it is an extension of the rule above — require a check to declare that it ran, and a test to declare which behaviour it pins.

§ Decisions

What recall and precision against the 74-row fixture qualify the instrument as calibrated?

The cost is asymmetric: a missed defect ships a wrong name to a physicist and cannot be corrected after publication, while a false positive costs a reviewer a minute. At the measured 21.7 percent rate this flags roughly 150 of 341 for triage, affordable because the instrument runs on the free local lane. Precision is a floor, not a target: a first calibration landing materially under 50 percent is a finding about the instrument, to be reported rather than engineered around by loosening the recall gate.

How should grouped review be exposed?

One command, one cost ceiling, one dry run, and one place for the local-lane routing to be right. A whole-catalog audit stays a single invocation and shares the batching, concurrency and reviewer-profile machinery already present. harmonize.py's family assembly and deterministic drift metric are wired underneath rather than duplicated, which also gives that module the CLI surface it has never had.

May the instrument write to the graph when it finds a red, or does it stay read-only and emit a worklist?

The method depends on re-running the instrument as a measurement, and a tool that mutates on each run changes what the next run measures, destroying the fixture's independence. It also avoids repeating the origin-field incident, where a property written for one purpose later acted as a delete permission across 2096 rows. Findings leave as a worklist; applying them stays a separate authorised act through sn edit.
