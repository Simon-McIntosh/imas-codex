§1 — Why this exists

A measurement commissioned by graph-destructive-command-safety asked a narrow question — how far offsite is the graph, really — and returned a verdict that plan had no authority to act on. Release cadence is acting as the backup schedule. The only full-graph offsite copy is pinned to a software release, so the recovery point drifts with how often code ships rather than with how often data changes.

That plan's scope was to measure and decide adequacy, and it did: not adequate. Establishing a cadence is new scope, it is outward-facing and recurring, and it needs decisions the measurement cannot make. That is why it lives here rather than as one more section there.

The positive result is that catastrophic loss of the shared filesystem would not leave zero state — the full archive still resolves. The unacceptable part is only its age.

What was not established, and is this plan's problem: registry presence and manifest fetchability were verified; no trial restore and no content-equivalence check were ever performed. An archive that resolves in a registry is not yet a demonstrated recovery path.

§3 — What already exists to build on

The prerequisite plan left three pieces of machinery this work should consume rather than reinvent, which is most of why it is cheap to start.

  • get_backup_currency() in imas_codex/graph/neo4j_ops.py already measures the newest non-empty backup against the newest live database file and returns a typed current / stale / no_backup result. It measures the local floor; the offsite equivalent is the same shape against a registry timestamp.
  • graph_archive_stamp() gives every archive a filename carrying its code revision and a UTC timestamp, so a scheduled push produces artifacts that can be ordered and retained without a name collision.
  • The archive manifest now carries node_count, relationship_count and label_counts measured from the graph each dump represents — which is exactly the cheap half of a content-equivalence check, available without a trial restore.
  • graph prune already takes --keep, so a retention policy has an existing mechanism and needs a number rather than new code.

§4 — Deliverables

  • A full-graph offsite push that runs on its own schedule rather than on the release schedule, so the recovery point tracks data change instead of shipping cadence.
  • A retention policy expressed as a number of full copies kept, applied through the existing --keep mechanism, with the registry storage cost of that choice stated rather than assumed.
  • An offsite currency figure surfaced where the local one already is, so graph status answers both “how far behind is my local restore point” and “how far behind is the copy that survives losing this filesystem”.
  • A recovery-path verification whose depth is the decision below — at minimum a manifest-count comparison against the live graph, since the counts are already recorded and the check costs nothing.
  • A recorded measurement of what one scheduled push actually costs in wall time and registry storage, taken from a real push rather than projected, so the cadence decision can be revisited against a number.

§ Followups

Decide the cadence, the retention and what a copy must prove before it counts

Three decisions gate the work and all three are the lead's, because each commits recurring outward-facing effect or spend: how often a full push runs, how many copies the registry keeps, and what a push must demonstrate before the copy counts as a recovery point. The measured starting state is in §2 and does not need re-deriving — the exposure is 56.238 days, no combination of the filtered subsets closes it, and no trial restore has ever been performed. §3 lists the machinery the prerequisite plan already landed, so most of this is consuming existing pieces rather than building new ones.
