Generated Map Hand-off

The lead asked on 2026-10-09 for a working prototype of the whole chain, from discovery to a tokamap directory. The tokamap must carry both the machine description and the signal mappings, with the signal mappings at draft. The work is split between two repositories, and each runs in its own session.

  • imas-codex discovers signals, judges DD candidates, and generates mappings from facility signals to Data Dictionary paths.
  • imas-ambix owns the machine description, which is its catalogue built from the SELENE deck. It resolves each draft signal to its probe or coil index, checks rules against data, and writes the tokamap directory and the IDS.

This plan builds the imas-codex half. imas-ambix's plan imas-ambix:jt60sa-tokamap-from-generated-maps builds the other half against the same hand-off format. The two sessions coordinate by message.

The lead also ruled that a map is never promoted by default without a validation step. Today, imas-codex imas map run promotes to active unless --no-activate is given. The discover sequence's opt-in mapping stage calls the same command with no_activate=False (imas_codex/cli/discover/sequence.py). §2 reverses both.

The command names are confusing, and §3 fixes them.

  • imas-codex discover map does not map anything: it is the candidates stage, which judges DD candidates. The sequence already calls it candidates.
  • Mapping generation lives under imas-codex imas map. The imas group is otherwise the Data Dictionary group, and map was attached to it in March (9b93c7790).

Mapping is the end of discovery, but managing a mapping record is its own lifecycle. So discover candidates judges candidates, and a top-level imas-codex map group owns run, status, show, validate, activate, clear and the new export. The imas group keeps only the Data Dictionary.

The hand-off format

There is one JSON document per facility. Both sessions build to this definition. Its top-level keys are:

  • format, which is "imas-codex-mapping-handoff";
  • format_version, which is 1;
  • facility;
  • dd_version;
  • exported_at, in UTC ISO 8601;
  • ids, a list.

Each ids entry has ids_name, mapping_id, status (the IMASMapping status, for example generated), signals and unexpanded. Each signals row is one facility signal, not one signal source, and carries these keys:

  • signal_id
  • source_id
  • data_source, for example edas
  • source_group, for example MDAC
  • source_array, for example magPbTC10
  • member_identifier, the segment that varies between members of the source, or for a singleton source the array name's trailing number
  • source_property, the property of the source the binding reads, for example value or time
  • target_path, the DD path with no array index, for example magnetics/b_field_pol_probe/field/data
  • transform_expression
  • source_units
  • target_units
  • cocos_label
  • confidence
  • evidence

Each unexpanded row carries source_id, target_path and reason. It records a binding whose source could not be expanded to member signals, whose member lacks a field above, or an error binding derived from the same signal that feeds its data field, which has no error signal behind it.

A key whose value the graph does not hold is written as null, never guessed. The document assigns no array index: imas-ambix resolves each index from its machine description.
