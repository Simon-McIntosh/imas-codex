§1 — The census, and the two different things inside it

A StandardNameSource is an extracted Data Dictionary quantity that should produce a standard name. Of 9,900 such rows, 5,441 are bound to a name through a PRODUCED_NAME edge and 4,459 are not. The unbound population is not one thing:

The 1,652 stale rows are not a defect and this plan does not touch them: a source rebinds when its name is superseded, so residue there is the mechanism working. Naming that explicitly matters, because a census that reports 4,459 unbound sources as a single backlog overstates the problem by more than a third.

§2 — 1,283 extracted quantities that never became a name

These carry status = 'extracted' and no producer edge: the pipeline pulled the quantity out of the Data Dictionary and never composed a standard name for it. That is throughput, not damage — but it is throughput nobody has counted, and it sets the ceiling on Data Dictionary coverage. For scale, 5,072 of 61,366 IMASNode paths currently carry a standard name; most of that gap is program incompleteness rather than defect, and this 1,283 is the part already extracted and therefore cheapest to close.

The work is a bounded sn run composition pass, not a repair. Before running it, establish how many of the 1,283 are eligible under the current admission rules rather than assuming all are — a source that was extracted before a rule tightened may now be correctly inadmissible, and composing it would mint a name the review pool then rejects.

§3 — 1,413 skipped, and 398 of them say nothing about why

This is the half that is a defect. A skipped source is permanently excluded from composition, so the reason is the only thing standing between a deliberate exclusion and a silent one. 398 rows carry no recorded reason at all.

The mechanism is known and it is narrow: non_nameable_reason is written only when source_status == 'skipped' (imas_codex/standard_names/graph_ops.py:12324), and it never reads last_error — so a source that failed with a diagnostic and was later marked skipped loses the diagnostic. The same shape appears in the failed population: rows carrying failed with an empty last_error.

Two deliverables, and the first is the one that lasts: make the write path unable to record a skip without a reason, then reconstruct the missing 398 from whatever evidence survives and mark as unknown the ones where nothing does. An honest unknown is a finding; a blank field is not.

§4 — Why this is separate from the deletion recovery

The deletion incident of 2026-09-08 left 67 standard names absent and their sources unbound, and it would be easy to fold this backlog into that recovery because both surface as unbound sources. They are different work and folding them would put a 1,283-name composition job behind a recovery that must not wait for it. The recovery is owned by the deletion-protection plan; this plan owns the sources that never had a name in the first place.

§ Decisions

Should a skip without a reason be refused at the write path, or reported by an audit?

Recommendation: refuse at the write path. An audit finds the 399th blank row after it exists; a refusal means there is never one. The 398 already present are a one-time reconstruction either way, and this repository's own pattern is to bind a rule to the moment that always happens rather than to a check someone must remember to run.

Every source in a committed manifest reaches an accepted name, and difficulty is not a reason to carry an exclusion

Lead direction, 2026-09-17: it must be possible to generate all names from a manifest, and the fact that a residue is hard does not license carrying it as an exclusion. This reframes what the pipeline owes. Today a manifest is treated as a set of candidates and whatever fails to compose becomes a documented exclusion in the release body. That makes an unnameable source a reporting problem. Under this direction it is a pipeline defect, and the exclusion list is the defect count.

The measured position on the WEST manifest at 2026-09-16 is 340 of 342 sources carried, counted per source rather than per identity row. The two that are not are the whole of the current gap and each fails for a different reason, so together they are a fair test of the invariant rather than a single bug.

calorimetry/group/component/energy_total/data lost its binding when its name reached exhausted. That is the terminal-binding invariant behaving correctly in both directions: reconcile_source_status_liveness frees a source from a terminal name so it can regenerate, and sn attach refuses to bind a source onto a terminal name because acquiring a source there is how terminal-target corruption is created. The source sits at extracted with a fresh attempt budget, so the route is a composition, not a reattach, and nothing blocks it but scheduling.

camera_x_rays/camera/camera_dimensions is the harder one and the more instructive. It has spent its five-attempt cap; extent_of_camera is superseded, size_of_camera and total_size_of_camera are exhausted, and the nearest accepted name, extent_of_soft_xray_detector, is refused on a device-locus mismatch because a camera is not a detector in the locus registry. Clearing the cap and re-composing only re-runs a search that has already failed five times. The real question is whether the locus registry should admit camera as a device, which is a grammar-repository decision rather than a pipeline run — and it is the second genuine vocabulary gap this manifest has produced, after the emissivity-peak locus that unblocked the hard-x-ray half-width.

What closing this actually requires, beyond naming two sources. An invariant needs an instrument: a manifest-generability check that, given a committed manifest, reports every source as carried or names the exact mechanism preventing it, and that a release path can refuse on. Without that, the next manifest rediscovers its own residue by hand as this one did. The check is also the honest place to distinguish the three mechanisms this manifest exposed — a vocabulary gap the grammar must close, an attempt cap that has genuinely exhausted a search, and a source whose composition simply has not been scheduled — because only the first is a reason to wait on another repository.

The exporter has no producer-edge predicate, so a name with no data-dictionary justification can reach a catalog

Measured 2026-09-16 and traced to code. Export selects identities on accepted or approved at imas_codex/standard_names/export.py:607 and applies no producing-source eligibility predicate anywhere in the candidate construction at lines 798-836. Nine accepted names currently carry no PRODUCED_NAME edge; four of them entered a candidate set, and nothing published only because an unrelated halo_current token-collision gate failed the run first and left emitted at zero.

This is the exposure that matters most for human review, because it is the one a reviewer cannot detect. A name reads as well-formed whether or not anything in the data dictionary justifies it; the missing provenance is invisible in the artifact under review. Every other integrity defect in this sprint degrades a name a reviewer could in principle question.

The predicate has one carve-out it must respect. A structural parent with live children is legitimately source-free — graph_ops.py:26233-26238 classifies exactly that case as source_free when live_child_count is at least one and no producer exists — and beta is a live instance. So the rule is not simply that every exported name carries a producer: it is that a name with no producer and no source_free origin is not exportable.

The detach routes that could create such a name are separately audited, and the rename path that produced five of the nine is already closed at imas_codex/standard_names/edit.py:1931-1938. This followup is the export-side half, and it is worth landing independently of that audit because it converts the accident into an invariant regardless of which route produced the orphan.
