§5 — Remaining: the DD graph holds the correct value and links to what it bridges

Lead direction 2026-08-18, superseding the previous reading of this section. The DD graph entries should carry the corrected values, so every consumer reading the graph gets usable physics without an overlay. What each corrected node then owes is a link to a resolution node that records the defect it is bridging: what the DD publishes, why that is wrong, and how it should be fixed upstream. Correctness in the graph, provenance beside it — not raw-in-graph with correctness computed at read time.

Measured 2026-08-17, the graph already holds the corrected values for the covered paths: the five equilibrium/time_slice/constraints/*/reconstructed paths hold Pa, m^-3 and A.m^-2 where DD 4.1.1 publishes 1, and the ionisation-potential paths hold eV where it publishes e. What is missing is the link: nothing on those DD nodes says a bridge is in force, which defect it covers, or which upstream change retires it. A reader of the graph cannot currently tell a corrected node from an uncorrected one.

The work is therefore additive provenance, not value repair. Give each corrected DD node an explicit edge to a resolution node — the defect, the published value, the corrected value, the upstream reference, and the DD version at which the bridge retires. Done-when: every corrected DD path is reachable from its resolution node and vice versa, a reader can enumerate every bridge in force with one query, the published value is recoverable from the resolution rather than lost, and a DD release that lands the upstream fix is detectable by comparison so the bridge can retire. §1 — Why: the pipeline meets DD defects with no first-class channel

Lead direction (2026-07-29): “the pipeline and its agents should have the authority to flag errors in the DD; we should perhaps build a mechanism similar to vocab_gaps (DD-gaps?) that permits this.”

The pipeline keeps encountering genuine Data-Dictionary defects — and each discovery has been handled ad hoc. The record so far: ~90 DD unit defects registered in units/dd_unit_exceptions.yaml; the ece/channel/position/psi facet declared W while its identically-documented sibling declares Wb (the self-contradiction class); unit vectors tagged m and charge numbers tagged e; the wall neutral energy-flux type-wiring bug filed upstream by hand (DD issue #272 / PR #273). Each mechanism is partial: the units registry covers units only, is applied at DD build time (an entry added later never reaches stored paths without the self-applying reconcile), and has no lifecycle; upstream filing is manual and leaves no graph trace an agent can consult, so the same defect gets re-derived, re-argued, or silently worked around.

Meanwhile vocab_gaps proved the pattern for the grammar side: a first-class node the composer writes when it cannot express a quantity, with multiplicity, a diagnosed reason, mechanical triage, and lifecycle buckets. The DD side deserves the same standing. A reviewer reading the WEST batch should be able to see “this path's DD declaration is flagged, with this argument, filed upstream here” rather than a name that silently disagrees with its source.

§2 — Prior art to build on (do not reinvent)

  • VocabGap — the template: id vocab_gap:<segment>:<token>, distinct-fact nodes with example_count multiplicity, the diagnosed reason on the report edge, classify_gap verdicts, reconcile_vocab_gaps re-validation against new grammar, and the triage buckets landed 2026-07-29 (triage_vocab_gaps).
  • units/dd_unit_exceptions.yaml — the units-only registry: most entries suppress a mismatch (DD wrong, name right, axis keeps reporting); correct_in_graph only when the DD contradicts itself; reconcile_dd_unit_corrections makes it self-applying. This registry stays the enforcement backend for the unit kind — DD gaps add lifecycle and provenance around it, they do not replace it.
  • The upstream filing precedent — DD issue #272/PR #273 (wall neutral energy-flux type wiring): proof the loop can reach the DD maintainers; what was missing is the graph-side record linking the flagged paths to the filing.

§3 — Design sketch

  • Node: DDGap, id dd_gap:<path>:<kind> — one node per distinct (path, kind) fact, example_count for repeat encounters, the flagging argument on the report edge (mirroring vocab_gaps' edge-borne reason).
  • Kinds (initial): unit_defect, self_contradiction (two facets, one quantity, different declarations), doc_mismatch (documentation contradicts type/unit/shape), type_wiring (the #272 class), missing_declaration (no unit where one is physical), rename_inconsistency (DDv3→v4 renames leaving contradictory siblings).
  • Writers: any pipeline seat or audit — the compose unit-injection path (already detects SN↔DD disagreement), the attachment guard, the unit detector, review seats (a reviewer prompt gains “if the DD declaration itself is wrong, flag a DD gap with your argument” — the same authority shape as reporting a vocab gap), and humans via a CLI verb (sn ddgap).
  • Lifecycle: flagged → triaged → {registered_exception | upstream_issue(url) | rejected} → resolved_upstream(dd_version). Triage is human-adjudicated (an agent's flag never changes pipeline behaviour by itself — behaviour changes only through the existing registry/reconcile instruments after triage). A reconcile pass re-validates open gaps against each new DD release and auto-retires those the release fixed.
  • Reporting: the release/PR-body seat states the flagged count and links the upstream filings, so a reviewer sees the DD-side caveats alongside the nameset; the SPA can badge affected paths.

Done-when: TDD'd write path; flags visible in sn status.
  2. Back-fill from the known record. Done-when: every registry entry has its graph-side provenance node; zero behaviour change.
  3. Agent authority. Done-when: a drain over known-defective paths mints the expected flags with substantive arguments and no behaviour change ahead of triage.
  4. Triage + upstream loop. A triage instrument (buckets above, mirroring triage_vocab_gaps); an upstream-filing workflow that drafts the DD issue body from the flag's argument + affected paths (human files it; the url lands on the node). A DD-release reconcile that retires fixed gaps. Done-when: the end-to-end path flagged→filed→retired demonstrated on one real defect.
  5. Reporting surface. Release notes/PR body carry the flag summary; the catalog export optionally annotates affected paths. Done-when: the next review batch's PR body states its DD-gap caveats.

§ Decisions

D-ddgap-authority — what may an agent's DD flag change by itself?

Locked by the lead 2026-07-29: flag only. A DD-gap flag is evidence; pipeline behaviour changes only through the existing registry/reconcile instruments after human triage. Mirrors the vocab_gaps model and keeps the DD authoritative until a human rules.

D-ddgap-storage — where does DD-gap truth live?

The live foundation already contains 35 DDGap facts and 451 path-evidence edges. Graph storage provides transactional concurrent observations, multiplicity, provenance, lifecycle, and DD-version traversal, while the curated YAML registry remains the sole unit-enforcement backend under the locked flag-only policy. Registry-only storage would require destructive export/removal or create two lifecycle authorities, and installed workers cannot safely mutate a tracked package YAML. Keep graph facts observational and require separate governed registry changes for behavior.

May imas-codex consume a reviewed repo-local DD correction before the upstream DD release contains it?

Several known DD defects already have upstream pull-request solutions. Waiting for those releases would block correct local interpretation and graph repair, while untyped exceptions would hide authority and drift.

Locked by the lead as 2A/3A: do not hold the pipeline for upstream DD PRs. Reuse and extend the graph-owned DDGap mechanism so approved local resolutions are explicit, typed, exact, version-bound, traceable to the upstream solution, and retired when the DD catches up.

D-ddres-storage-and-gates — where do DD resolutions live, and which gates on them actually earn their cost?

The shipped design keeps DD defect facts in the graph but DD resolutions in a packaged YAML behind a governed approval ceremony: content-addressed approval receipts, recomputed evidence tokens, monotonic revisions, an expected-manifest-digest compare-and-set, an exclusive flock, and a per-candidate-digest lead delegation. The lead's challenge (2026-08-18): a resolution record is reversible and recording a DD defect is routine engineering, so most of that ceremony looks like unnecessary authority, and the truth should live in the graph rather than across many files.

Locked by the lead 2026-08-18. DD resolutions become graph nodes: the corrected IMASNode links to a DDResolution recording the published value, the effective value, the DD version, the upstream reference, and the release at which the bridge retires, with that resolution in turn edged to the DDGap fact that evidences the defect. Exactly two gates survive: the edge to the DDGap observation, which cannot be forged because it either exists or does not, and an upstream reference or an explicit none-yet marker, which keeps a record a temporary bridge rather than a private fork of the DD. A plain who/when/why trail stays. Content-addressed approval receipts, recomputed evidence tokens, monotonic revisions, expected-manifest-digest compare-and-set, the exclusive flock, and the per-candidate-digest lead delegation are all removed: they exist to make an irreversible authority grant auditable, a resolution record is reversible, and three of them exist only because the store was a mutable tracked file that a transactional graph makes moot. The real risk in a resolution is a wrong physics claim, which no receipt addresses. Consequence accepted at lock time: because the graph already carries corrected values, the read-time overlay landed across 14 consumer sites reduces to provenance reporting and should be simplified rather than preserved to justify prior work.

Earns its cost — evidence binding. A resolution must point at a real observed DD defect, otherwise anyone can assert a correction for a path that is not broken. That is the one control preventing invented physics. But the binding does not need a recomputed content-addressed token: in the graph it is a relationship to the DDGap fact, which cannot be forged because it either exists or it does not.

Earns its cost — upstream reference. Naming the PR or issue that fixes the defect is what makes a record a temporary bridge rather than a permanent private fork of the DD, and it is what lets the bridge retire when a release lands. Keep it, with an explicit none-yet marker so a defect with no upstream filing is visible rather than unrecordable.

Does not earn its cost — everything else. Content-addressed approval receipts, recomputed evidence tokens, monotonic revisions, expected-manifest-digest compare-and-set, the exclusive flock, and the per-candidate-digest lead delegation all exist to make an irreversible authority grant auditable. A reversible record with an ordinary audit trail needs none of them, and three of them (digest CAS, flock, revision) exist only because the store is a mutable tracked file that concurrent workers must not clobber — a problem that disappears once the record is a node in a transactional graph. The real risk in a DD resolution is a wrong physics claim, and a cryptographic receipt does nothing about that.
