Summary

The IMAS Standard Names grammar work landed on upstream main, was published as the project's first stable release, and every dependency declaration that had been resolving a fork commit now resolves that release. The measurement the whole exercise existed for — that the exporter stops reporting a locus collision the vocabulary no longer has — was taken against the released wheel and passes.

The release

Upstream pull request 19 on iterorganization/IMAS-Standard-Names merged at 49fe54b4. It had been mergeable and green for some time and was blocked only on a credential: the pull request touches .github/workflows/release.yml, and the API refuses a merge from a token without the workflow scope. Refreshing the token cleared it; no evidence changed.

v0.8.0 was tagged on that merge commit and pushed, which fires upstream's trusted-publishing job. The release was then confirmed by reading the package index directly — latest on PyPI: 0.8.0, wheel and source distribution both present — rather than inferred from a green workflow run. A green run says the job finished, not that the artifact is fetchable, and a published version can be yanked but never reused, so the distinction is worth the extra call.

The tag is stable rather than a sixty-eighth release candidate because the work landed upstream rather than on the fork. The 67 rc tags were fork-side prototyping and stay there.

Provenance was proven rather than assumed. A version string alone does not distinguish a registry install from a git build of the same commit, because both report a similar version; the discriminator is that the installed distribution carries no direct_url.json. That was checked on both sides. uv.lock in imas-codex resolves the hashed wheel imas_standard_names-0.8.0-py3-none-any.whl; the catalog keeps no lockfile, which was confirmed against the active .gitignore rule rather than assumed from its absence.

The catalog change carried its contributor guidance in the same commit. That repository's AGENTS.md had stated that tracking the branch was a deliberate design choice and showed the git reference as the required form, so pinning pyproject.toml alone would have left the next contributor reverting the pin with the repository's own documentation behind them. The section now states the rule in force: pin a published stable release, ignore release-candidate churn, bump deliberately on each new stable release.

The measurement the pin existed for

imas-codex had been resolving ISN at 93195dd, which predates the minimum_absolute_safety_factor locus rename, so the exporter was judging identities against the pre-rename vocabulary and reporting a collision the vocabulary no longer has. Against the released wheel, a read-only WEST regeneration reports:

  • identity_token_collision — passed=true, skipped=false, issue_count=0, issues=[]
  • every enabled gate passing, 328 of 412 identities exported, and all 355 sources reconciled as 297 emitted, 48 excluded, 10 documented non-nameable
  • focused export tests: 25 passed, exit status 0

A measurement trap worth carrying forward

The first attempt at that gate measurement contradicted itself. The worker proved the import at 0.8.0, then had the regeneration report 0.8.0rc68.dev8+g93195dde4 and reproduce the collision. Nothing was flaky.

A detached worktree shares the one root environment, and that environment syncs from the main checkout's committed pyproject.toml — not from the worktree's edited copy. Main still pinned the fork commit, so every concurrent peer running anything at all deterministically reinstalled the fork build over the worker's install. The failure mode is worse than a plain error because it is intermittent in a way that looks like flakiness: measure once and the answer is right, measure again after a peer runs and the old defect is back.

The general rule: a pin change is not real to any other process until it is committed to the main checkout, so a single node cannot own both a pin change and the behavioural evidence for it. Split them, or serialize — which is what this worker eventually did to obtain the verdict above.
