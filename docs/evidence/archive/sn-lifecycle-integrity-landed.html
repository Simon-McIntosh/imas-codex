The four maintained axes

The plan opened by measuring five axes and asking which were real. The answer that survived measurement is four, and the invariant that makes them maintainable is that each one can name its writer. An axis that cannot is not a weak signal — it is a signal every reader trusts and nothing keeps true.

What publishes a name

The defect underneath every symptom was that status had no writer for its one meaningful transition. Nothing in the code did what an approval is supposed to mean, so the exporter compensated by writing the literal active on every row it cut — which is why history in the graph reached published catalogs. The gate could not fire because the gate was never read.

The exported status is no longer a constant

export.py wrote "status": "active" as a literal on every entry it cut, so the graph's own value was never consulted and the export gate could not exist. The export now reads the graph, and a null status refuses the whole cut rather than defaulting — including under skip_gate and force, because a missing value is exactly the case where guessing publishes the wrong thing.

Landed at bee0e296. Measured: the literal mapping greps to zero, a draft status survives into catalog.yml, and a null status in any population row fails the gate before any file is written.

Protection follows approval, and fails closed

filter_protected keyed on origin = 'catalog_edit', a marker nothing writes. It was wrong in both directions: 182 names with real edit records were excluded from protection while roughly 2031 names with none were protected. It now keys on name_stage = 'approved' — published authority, one writer, set only when a pull request is approved — so protection is a consequence of the human gate rather than a marker someone has to remember.

The same change removed the except Exception that turned a failed protection lookup into “no names are protected”. That mattered more than the trigger did: closing the swallow exposed 38 failures and 5 setup errors across 13 files, none of them regressions. Every one had been green because the guard switched itself off. The worker refused to re-swallow the refusal to make its own gate pass, and proved the combined state by virtual merge against the repair rather than asserting only its own half.

Landed at baf6480f and 3570246e. Measured: the approval-only query present once, the origin clause gone, thirteen explicit fixtures, the fail-open swallow at zero, and the standard-names suite green at the merged head.

The generic graph tool cannot touch governed name state

The MCP add_to_graph tool accepted any label in the schema and MERGEd by id, so an agent could create a StandardName at name_stage = 'approved', status = 'active' in a single call — no review, no pipeline, no protection. The rule that there are zero hand-edited names in the graph had nothing enforcing it at that boundary.

The tool is kept, because it is the documented write path for facility discovery in four separate client surfaces, including the shipped pipeline prompts. What changed is that it refuses every concrete class owned by the standard_name and grammar_graph schemas. The refusal is derived from each LinkML class's declared from_schema through a public GraphSchema accessor, so a class added to either schema later is covered with no list to maintain — and a test asserts exactly that for a future label.

Landed at adbb6847 and 5369731c. Measured: 10 independent counterfactual failures with the refusal neutralized, 31 passing with it in place, and SourceFile and FacilityPath writing unchanged.

Approval is the only thing that publishes

sn approve advanced name_stage and never touched status, so the transition the whole architecture rests on did not exist in code. The approval fold now writes active atomically with the catalog receipt, and --undo reverses both axes together.

Its first cut required status = 'draft' exactly. Against the live graph that predicate matched 1372 of the 2284 eligible accepted names and silently refused the other 912, whose status was null — a real fold would have promoted 60% of a batch and skipped the rest with nothing reported. A null status now reads as not-yet-published; the quarantine exclusion is unchanged, keeping 11 names out.

The reporting defect mattered as much as the predicate. At one call site the boolean return was discarded and the name was appended to report.accepted anyway, so a name whose row never moved reported as approved; at the other, a refusal only dropped out of a count. Both surfaces now name the refused ids with a precondition reason, and the CLI exits nonzero before writing a fold-back receipt.

Landed at 3b1f1d15 and 32f8b014. Measured: 36 passing on the scoped gate, and two counterfactuals — deleting the status write, and restoring the strict predicate — each failing by name.

What the sequencing bought

The plan's ordering rule was that leaks come before repairs, because a repair that runs while a write path is open buys one clean measurement before the next run undoes it. Two things in this record only exist because of that order.

The export literal is the clearest: backfilling status while export.py asserted active would have produced correct graph rows and identical published output, and the measurement would have said the repair worked. The approval transition is the second: a status reconcile is meaningless while nothing can move a name off draft, because the axis would be maintained and permanently unpublishable.

The discipline that produced the strongest evidence here was requiring each counterfactual — deleting the write, neutralizing the refusal, restoring the strict predicate — and recording that it fails by name. Three separate guards in this record would have passed their own tests while providing nothing.

Leak three: the guard did not exist

The section asked narrowly — establish whether a test exists that fails when an import writes origin or status, and if not, write one. The answer was that neither the test nor the guard was there. Committed at d606bf09.

What did exist is guard_catalog_write_payloads, which protects pipeline-owned review scores and authority relationships and does not touch the editorial axis at all. A reader finding it would reasonably have concluded the axis was covered, which is exactly why this section insisted on a test rather than an argument.

The guard is a positive allow-list, which is the shape that fails closed by construction. record_catalog_import_provenance matches an existing identity and writes exactly imported_at and catalog_commit_sha — the two things the locked import-write-authority decision entitles an import to record. The restored values are the argument. Each is the unit its own quantity carries, against a raw declaration that had flattened all five to dimensionless. The resolutions were not stylistic overrides — they encode the physics that a reconstructed constraint carries its parent quantity's unit, and the rebuild was erasing exactly that. 49 paths were exposed to it; 5 had been overwritten and 0 disagreements predated the cohort run, which is what made the finding attributable.

A held-open test settled a decision rather than a number. The tracked holdout expecting m^-3 was left failing across three nodes on the stated reason that refreshing it to the raw value might fix in place a number a repair would reverse. That is what happened: m^-3 was right, and a session that had "fixed" the red test by updating its expectation would have written the wrong unit into the holdout and called the suite green. It now passes on its own, never having been edited in either direction.

The scope rule is narrow and its exclusions are tested, not just its positive case: a resolution applies only when active, on the unit field, at exactly the version being written, and the focused suite pins the fall-back to raw for both a retired record and an other-version record. The projection sits before the scalar write and the unit-edge normalization alike, so the two write paths cannot drift.
