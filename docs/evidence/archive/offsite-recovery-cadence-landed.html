§4 — Deliverables: a scheduled, verified, bounded, restore-proven offsite copy

The design decisions were the lead's and were locked before any node ran: a weekly push that no-ops when the store is unchanged; tiered retention of four weekly and three monthly copies with release tags never pruned; and a copy that counts only when its manifest census equals the live graph, with one trial restore now and quarterly after. The reuse map showed almost everything already existed: graph push, graph prune, graph_archive_stamp, the manifest scope counts and the local BackupCurrency shape. What was built is composition over those seams plus the two things they lacked, a currency read against the registry and a scheduler.

Negative result: the registry is unreachable from the compute node

The first scheduled cycle ran as a SLURM job on titan, resolved api.github.com and could not open HTTPS; no proxy exists. So the locked decision's "SLURM-scheduled job" could not be the upload path. The redesign runs the weekly timer on the login node through a systemd user unit, the same pattern the embedding service already uses, while the dump still happens through the existing remote Neo4j path. The self-resubmitted SLURM successor was cancelled. A second attempt then failed because the generated unit's PATH omitted the directory holding oras; the installer now resolves the uploader at install time and refuses without it, and a failed upload leaves a receipt.

Negative result: a restored scratch instance was unreachable and relabelled the live one

The trial restore loaded correctly but could not be queried from the login node because graph init wrote loopback listeners for new instances while production binds 0.0.0.0; the census had to run on the node through the repository's remote executor. Afterwards graph status on the codex instance reported the trial archive as its load source because load bookkeeping was global. Both are repaired: new and restored instances render production listeners, and load metadata is stored per instance.
