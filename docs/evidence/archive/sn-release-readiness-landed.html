The unsourced chain-cap cohort, partitioned by recoverability

The plan's f-srr-unsourced beat exists to drain the chain_length >= 3 identities that carry no producing source, and its remedy turns on how many of them can have a source recovered from their refinement ancestry. Measured read-only against the live graph on 2026-09-17, the cohort is 174 identities of which 102 are unsourced — the audit's re-measured figure exactly, and 38 percent above the section's own cohort of 126. Of the 102 unsourced, 10 have a sourced ancestor at any depth and 92 have none, so the class is rebuild-dominant and only ten identities are recoverable at all, six of them from an immediate predecessor. The two parts sum to the whole (10 + 92 = 102) and the recoverable part splits exactly (6 + 4 = 10). Every identity in the smaller partition is listed in the partition evidence, together with the queries, the positive controls and the verdicts. No graph mutation was performed.

An endpoint drop is not distinguishable from a model refusal

Benchmark composition calls the LLM layer once per batch with benchmark.py:1647 max_retries=2, which the loop at llm.py:2393 reads as two provider attempts at most, gated on whether the error message matches a retryable token (llm.py:2473, tokens at llm.py:645-672). Measured along that path (/tmp/endpoint-drop/probe.log, exit 0): a connection refusal is not retried and reports after one attempt; a timeout is retried once and reports after two; a model refusal - a provider response that arrives and cannot be parsed - also reports after two. The three terminal exceptions drops differ - from each other and by type, since LLMStructuredCallError carries response_count - and the distinction survives only as log prose. Every one of them reaches benchmark.py:1688, which catches Exception and keeps result.batch_errors += 1.

A test drives composition against a simulated endpoint drop and against a simulated model refusal and asserts the recorded outcome names which occurred: 3 failed, exit 1 before the change (/tmp/endpoint-drop/test_before.log) and 3 passed, exit 0 after it (/tmp/endpoint-drop/test_after.log), with the existing benchmark suite at 82 passed on both sides. The change that makes them distinguishable is a candidate patch, reproduced in the evidence document and not landed here: this node's write fence is documentation only, so benchmark.py and the test file fall outside it and a follow-on implementation node owns them.
