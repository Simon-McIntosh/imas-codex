The graph was serving compose a stale grammar, and a version comparator ranked rc9 above rc65

Found and fixed 2026-08-20 — the most consequential defect this programme surfaced, and it was invisible until a node had to justify a sub-threshold score. graph_ops.py resolved "latest grammar" with a raw ORDER BY v DESC over GrammarToken.version, reached exactly when no tokens exist for the pinned version. Because ISN 0.8.0rc66 had been pinned as a dependency without ever being synced into the graph, that fallback fired on every compose and the string sort returned 0.8.0rc9 — '9' sorts above '6', so rc9 outranked rc65. It logged a warning each time, so the evidence had been in the logs all along.

A second, larger gap emerged during the fix: the native ISN graph spec supplies only 781 tokens and omits all 175 public physical_base tokens — the closed segment carrying the core quantity vocabulary. A correctly run sync would still have served an incomplete vocabulary missing its most important token class.

After the fix the graph carries a 0.8.0rc66 snapshot as its sole active version with all 956 public-context tokens across 22 of 22 declared segments, zero missing segments and zero count mismatches. Resolution order is exact runtime tokens, then the single active version, then PEP 440 ordering. The regression proves rc66 > rc65 > rc9 and fails when mutated back to a plain descending string sort, so it cannot pass vacuously; a grep shows zero remaining max or raw-descending grammar resolutions. Suite: 6,533 passed, 8 skipped, 0 failed. Consequence worth carrying forward: every name composed or scored before this fix was judged against rc9's vocabulary, which plausibly depressed the three sub-threshold position identities and the two fold ancestors that failed their draws.
