A changed leaf refuses itself, not the run

Landed 2026-08-21 — commit 6be291be, 7 files, 199 insertions, 37 deletions. resolve_dd_rows was an all-or-error list comprehension, so the first raise ended the batch — which is how one stale stamp stopped a scoped run over 42 paths. It now returns a typed DDResolutionBatchResult of resolved rows beside refusal records, each refusal carrying its exact path and DDResolutionField. The changed-leaf property was observed failing first, then passes: 9 of 10 synthetic rows resolve and exactly one refusal is returned, at synthetic_resilience/source_0/value:unit.

Every call site associates by row index, never by position. All 7 live production callers were converted. This mattered more than it looks: one caller, pool_adapter.py, paired rows to results with zip(items, contexts, strict=True). Under a contract that can return fewer results than inputs, a silent compatibility iterator there would have misassociated a source row with another row's resolution — invisibly, which is strictly worse than the abort it replaced.

Narrowing refusal did not weaken authority. A structural authority error that carries no leaf and no field still fails the entire batch closed. Per-leaf scoping applies only to what is genuinely leaf-scoped.
