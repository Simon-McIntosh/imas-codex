§3 — the apply mechanism, anchor-first

sn harmonize --apply runs each pattern family as an anchor-gated, two-batch documentation campaign on the existing campaign runner (imas_codex/standard_names/campaign.py, which now accepts an explicit batch plan). The anchor batch (select_anchor) is snapshotted, reset, drained and reviewed first. If the anchor does not reach acceptance, its members are never reset, and removing that gate turns the test red. Otherwise one member batch follows, scoped to exactly the other members. A second apply over an unchanged scope plans zero calls, read from the harmonized-family stamp. --dry-run writes nothing and prints the planned calls and estimated cost. §3 — the recommended-name guard

Before the first reset, sn harmonize --apply calls recommended_name_protections in imas_codex/standard_names/protection.py. It returns per-identity evidence for the three classes: a member of a frozen review roster that recorded a candidate request (candidate_request=<url>), name_stage=approved, and name_stage=contested. Without --force the family is refused, and the refusal names each protected identity with its evidence. With --force REASON the family applies and the reason is recorded on the run. Merge 825e1f3c7. Independent review 100/120.

One limitation, recorded. The code holds no open or merged state for a candidate request, since the release path reads pull-request state only through a live GitHub call. Every roster that recorded a request therefore counts as open. That is a conservative superset: it refuses more names, never fewer, because a merged request's members move to approved, which is refused anyway. Follow-ons: the new function repeats the approved clause that automatic_deletion_protections derives; and the test file names a seam with a plan label and attributes the three classes to a person, which a cleanup node fixes.
