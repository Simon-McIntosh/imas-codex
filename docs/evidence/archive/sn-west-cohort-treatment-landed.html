A cut that matches the manifest it claims

The halted candidate published 411 names from a 355-path manifest. The cause was one line: run_review_release computed its names as dict.fromkeys([*mint.names, *terminal_ids]), and mint_sn_list deliberately adds each name's parent, siblings and children on top of its authoritative PRODUCED_NAME join. The two structural-parent figures are what prove the ruling was honoured in both directions. Six accepted derived identities remain, and each remains because it is itself a terminal identity selected by a manifest path — not because parents are waved through. The unbound count is zero. So the cut carries the parents an included name needs to be well-formed and nothing else, rather than reintroducing the published-child-with-no-published-parent condition that withholding them would cause.

The exporter and the approved-baseline assembly are untouched, so an already-published name is still preserved byte-for-byte and the new rule constrains only the new batch. A second seam closed fail-closed: a source with several direct bindings and no authoritative matching scalar now returns a release-report error before freeze and export, instead of silently taking the lexicographically first id.

Two recorded figures were wrong and the live census corrected them. The graph read 378 published with 181 unbound before the change, not the 384 and 182 the plan recorded; and the resulting roster is 228, not the roughly 260 predicted. Both were reported rather than reconciled.

A consequence nobody predicted, recorded rather than acted on. mint_sn_list is now called from nowhere in imas_codex. It is still defined and still exercised by two test modules, so it looks maintained — but the release path was its only production caller. The reuse map verdicted it reusable "for the broader review-cohort callers that intend it", and there are no such callers in the current tree. Whether that route is retired or awaits a caller yet to be written is a judgement, not a repair.
