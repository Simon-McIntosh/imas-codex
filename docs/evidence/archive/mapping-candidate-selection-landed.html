§2 — what removed the mapping edges

Read-only investigation mapping-edge-loss, revision 3380f837e. Mechanism, verified in code: imas map --clear runs _clear_mapping (imas_codex/cli/map.py:647–695). It deletes MAPS_TO_IMAS on every source the remapped IDS uses, and DETACH DELETEs the IMASMapping node, which takes POPULATES with it. The re-persist in persist_mapping_result (imas_codex/ids/models.py:530, 579) guards every edge write behind MATCH (ip:IMASNode {id}), so a target id that names no node writes nothing. It still re-creates the mapping node and its USES_SIGNAL_SOURCE edges. That matches the measured residue: 53 mappings, 207 USES_SIGNAL_SOURCE, 0 MAPS_TO_IMAS, 0 POPULATES.

Ruled out: a DD rebuild. DDVersion 4.1.0 was built 2026-06-18, the DD build log was last written 2026-07-22, and the DD update path never deletes IMASNode (cli/imas_dd.py:409–412).

Rejected on audit: the report dates the removal to JET map runs on 2026-10-06 between 05:21 and 08:35. Those log lines are test runs. Their tracebacks pass through unittest.mock from another worktree, and the tests persist through a mock graph client, so they write to the shared map_jet.log and not to the graph. The report also calls imas_codex.discovery.map a missing module; it is a logger name (cli/discover/common.py:170). The date of the real removal is not established.

Consequence for this plan: both protections the report asks for are already in it. Candidates use their own MAPPING_CANDIDATE type (§6), and every MATCH-gated write raises on zero rows (§6, §8).

§3 — labelled set, retrieval and Jev measured

Four nodes, all measured on a 75-source adjudicated test split; tuning read the 87-source dev split only. Research document: mapping candidate probe.

  • Labels. 163 sources (150 JET over 20 domains, 13 JT-60SA), labelled by a top-down DD walk. An audit sent them back once: 11 labels named removed DD3-era nodes, and 37 failures had been stored as none. Two labelling models agreed exactly on 0.633 of a 30-source subsample, so the test split was re-labelled by the stronger model and adjudicated into acceptable node sets. 23 of the 75 test labels changed.
  • Retrieval. Recall@20 on the 36 labelled test sources: compute_semantic_matches 0.444, hybrid_dd_search 0.556, physics-domain filter 0.389, and Jev IDS routing (one Choice over every IDS, top 3, then hybrid_dd_search scoped to them) 0.694. The routing Choice has the correct IDS at top 1 for 0.861 of sources and inside its top 3 for all of them. Unit and cluster modifiers moved nothing.
  • Pair judgment. same_quantity AUC 0.924, with top-1 accuracy 0.80 where the label is in the shortlist. Reranked recall@5 is 0.694, which keeps every hit the shortlist held, against 0.417 unranked. same_object added nothing. Batching all candidates into one request agrees with per-pair calls within 0.03 at a quarter of the cost.
  • Selection. The selected route never exceeded about 0.63 precision at any threshold, so the numbers support Jev as a pre-screen. A final Choice over the top 5 was right 2 times in 7.
  • Cost. About $0.0002 per source; all 2,288 JET sources project to about $0.47. Probe spend $1.77 of the $3 cap, plus the Jev calls.

An audit also sent the Jev probe back to fix its dev operating-point metrics, which disagreed with its own floor table, and a slug collision in the research document.
