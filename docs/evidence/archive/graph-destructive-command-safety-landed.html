Graph Operational Safety — cumulative execution evidence

An audit commissioned to answer an unrelated question found three safeguards that were named, documented, and did not hold. Every one of them read as protective from the outside; none was found by reading the documentation, which asserted the opposite in each case. What is recorded here is what each fix actually changed, measured, rather than that it was applied.

The service ignored its configured partition, and that took the graph down

Landed 2026-09-01 — node n-graphpartition, commit 68e79fb2. Record: partition-fix.

Fifteen lines in _submit_service_job(). CPU graph partition resolution moved from _general_partition_name(), whose live value was sun, to the partition the graph’s own compute location declares, so partition: titan stopped being dead config. An invalid non-compute target now fails loudly instead of falling back — a misconfigured location should not quietly land on a shared queue.

It ended a live outage rather than merely correcting a setting: job 1260741 had been sitting PENDING on reason Priority with port 7687 refused. Its replacement 1260760 reached RUNNING on 98dci4-gpu-0002.

The function named for backing up data now backs up data

Landed 2026-09-01 — node n-realbackup, commit d9f54eff (merged 4edf6c30).

The defect was in the name, not the docstring, and that is why it survived. backup_existing_data() was documented as “Create a marker for pre-operation recovery (lightweight)” and did exactly that — it touched a zero-byte graph_data_existed.marker. Its own docstring never claimed a backup. Only the name did, so anyone who opened the function would have seen the truth and nobody needed to. Meanwhile backup_graph_dump(), which produces a genuine neo4j-admin dump, sat unused immediately below it in the same file. This was never a trade between protection and speed: two destructive commands were calling a marker-writer while the real thing was in reach.

  • Both destructive sites — pre-load in cli/graph/data.py and pre-pull in cli/graph/registry.py — now call backup_graph_dump.
  • A failed dump blocks archive extraction and registry fetch, per the locked fail-closed posture.
  • Pre-pull dumps with the service stopped and restores it even when the operation aborts.
  • backup_existing_data renamed to write_data_presence_marker with zero remaining references and no compatibility alias.
  • The helper rejects a missing or zero-byte output, which closes the defect class rather than the instance — the original fault was an artifact that existed and contained nothing.

Pre-fix 0 passed / 2 failed, because both commands continued without calling the dump helper. Post-fix 2 passed; final suite 14 passed, 0 failed, ruff clean. Regression: tests/cli/test_graph_destructive_backup.py.

A coordinator error is recorded here rather than tidied away, because it recurred twice in one day. The node was first fenced to three source files plus a new test, but renaming the function requires updating tests/core/test_neo4j_ops.py, which imports it. The worker stopped at its fence with a complete NEEDS-HELP brief and wrote nothing; its leaning was correct, and it self-rejected a compatibility alias as contrary to this repository’s no-alias rule. The failure mode is changing a name without scoping the tests that reference it.

Destructive commands now name their target

Landed 2026-09-01 — node n-targetname, commit f02560ac (merged fb8a8b7c).

graph load ARCHIVE TARGET and graph clear TARGET now require an explicit destination and refuse when the resolved symlink disagrees, with a message naming both the requested and the active graph.

Where the check runs is the substance of the fix. _require_matching_graph_target runs immediately after resolve_neo4j and before password lookup, remote transfer, service-state checks, backup, and any graph-client write — so a mismatch costs no side effect at all, rather than being caught partway through a stop-the-world operation. resolve_neo4j is unmodified, its signature pinned by assertion, so the twelve read-only callers stay untouched: a two-command problem did not acquire a twelve-file blast radius.

Pre-fix 1 passed / 4 failed; post-fix 24 passed, 0 failed. Proven in tests/cli/test_graph_destructive_target.py: both commands refuse a scratch target while the active graph is codex, with zero backup and zero client calls and an unchanged live-data sentinel — and a matching scratch clear still succeeds, so the guard blocks the mistake rather than the operation.

Landed 2026-09-01 — node n-offsiteinventory, commit a8780e61. Record: offsite-inventory.

The preceding node reported that the only package the registry returned was TCV-scoped. That was true of what it asked and false as a statement about the registry. It followed the local manifest’s last-push record to one package and queried that one. An account-wide census finds four. This is the aiming failure in its canonical form: the instrument fired correctly, returned a real package with a real timestamp, and answered a question nobody had asked. No archive filename may assert a property that decays

Landed 2026-09-01 — node n-archivestamp, commit 7c2aa040.

One graph_archive_stamp formatter now names both default producers as dev-<short-revision>-<YYYYMMDDTHHMMSSZ>. The two had each been holding the half the other omitted: the exporter carried the revision and no timestamp, so two exports at one revision collided; the dump helper carried the timestamp and no revision, so a dump could not say which code it restores into. Proven defaults: imas-codex-graph-dev-6fc745c-20260901T125109Z.tar.gz and codex-dev-6fc745c-20260901T125109Z.dump.

The formatter fails closed: with no git revision available it raises rather than emitting a name that cannot state what it restores into — the same posture as the backup decision one level down.

Focused regression 0 passed / 1 failed → 1 passed / 0 failed; combined suite 181 passed / 1 failed, the single failure being the out-of-fence inert regression below; ruff clean. Verified against the release path before merge, because the change replaces a tag-bearing default: graph_push always passes its own -o output path so the default never reaches it, and version_label still names the inner archive directory, so tag identity is preserved exactly where it was.

A regression that exits at argument parsing pins nothing

Landed 2026-09-01 — node n-inertregression, commit cfdf8c11.

tests/cli/test_graph_destructive_backup.py was written before graph load required a target. Once the target check landed, the invocation exited with Click status 2 and Missing argument 'TARGET', so the command under test never reached the mocked dump failure the test exists to observe. Pre-fix the file ran 1 passed / 1 failed; post-fix 2 passed / 0 failed, with the full tests/cli plus test_graph_cli_package run at 176 passed / 0 failed. The change is one insertion and one deletion.

Main was red and nobody had noticed. Two independent measurements found it within minutes — the reconnaissance pass reading the file, and n-archivestamp hitting it as the sole failure in an otherwise green 181-test run — after it had sat on origin/main since the target check landed. The repair went to the roster member that wrote the file rather than a fresh worker, so it reached someone who still remembered why the mocks were arranged as they are.

This is the third instance of one failure mode in a day, and the first to escape. The other two — both a change whose references were not scoped — were caught by a worker’s own fence, because the reference and the change sat inside one node’s write scope. This one crossed a node boundary: each node was green in isolation and the interaction broke the earlier one, which is precisely the arrangement no single fence can see. The generalisable countermeasure is to enumerate every reference to a surface before fencing a node that changes it, and to treat a suite run that is green only within a fence as unverified outside it.
