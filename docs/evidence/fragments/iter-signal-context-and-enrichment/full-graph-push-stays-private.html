Every facility graph push reads its package back private

A graph push decided whether to verify package visibility from the command's own flags: the check ran only when --facility was combined with --without-dd. The weekly offsite timer runs iter-codex graph push --cycle, which runs a full-graph push with neither flag, so the archive that carries every ITER node reached GHCR with no visibility read at all. The package rename moves the archive into iter-codex-graph, so the first cycle after the rename creates a package that nothing verifies.

The push now decides from the archive's own record of what it holds. The export writes a manifest.json into the archive carrying label_counts, and the push reads that label set, derives the facility-owned labels from the schema (every label whose nodes carry a required facility_id, which is the positive statement of what a DD-only dump deletes), and requires the package to read back private when any of those labels is present with a nonzero count. A missing or unreadable label set answers that the archive holds facility content, so a scope that cannot be read cannot clear a package. The check runs after the write and before the latest tag, and it fails the push with a nonzero exit when the registry reports anything other than private; it never changes a package's visibility.

The registry is the fork owner's ghcr.io/<owner> when the checkout is a fork and ghcr.io/iterorganization otherwise. This node made no push: every registry call in the tests is faked, so nothing was written to GHCR and no package's visibility was read or changed on a live registry.

The check is what catches a public package

With _require_private_package returning before it reads visibility, test_full_graph_push_refuses_a_public_package lets the push complete and fails on the exit code and on the recorded tag: the full-graph public case then passes the push, which is the behaviour this change removes. Restoring the check turns it green again.
