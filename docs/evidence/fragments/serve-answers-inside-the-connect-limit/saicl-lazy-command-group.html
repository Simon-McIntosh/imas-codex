§2 — First answer in under ten seconds

The command group now resolves each command module when that command is invoked, so imas-codex serve imports serve and nothing else. On the debug-partition node the median of five cold starts fell from 7.25 s to 3.34 s to first answer, and serve --help from 5.69 s to 0.13 s. On the fleet node at a load average of 28–32 the five starts answered in 9.87–11.71 s (median 10.46 s), every one inside the 15 s bound, against base-revision starts of 34.0 s and 35.9 s.

What changed

register_commands() imported all fifteen command modules at package import, so every command — including the MCP server entry point — paid for every other command's imports. It is replaced by a table of (module, attribute, help) entries and a DeferredCommandGroup that imports a module in get_command only. list_commands and format_commands answer from the table, so --help never imports a command module; the help strings moved into the table for that reason.

The server entry point carried the same kind of import one level down: imas_codex/llm/server.py imported imas_codex.graph.query_builder at module level, which pulled the imas_codex.graph package and the linkml_runtime schema runtime onto the path that answers initialize. That import now sits in the query builder that uses it, so the schema runtime loads when a code-chunk search first needs it rather than during start-up.

The control, failing at the base revision

Three tests were added. test_help_imports_no_command_module asserts that imas-codex --help exits with no command module in sys.modules. test_initialize_path_imports_no_command_module_or_schema_runtime resolves serve through the group, builds the object that answers initialize, and asserts that no other command module and not litellm was imported; in its warm-up-suppressed arm it additionally asserts that neither imas_codex.graph nor linkml_runtime is in sys.modules. The suppressed arm exists because with the background warm-up running those modules legitimately arrive from its threads; the arm that runs the warm-up therefore asserts the command and client part only, and both arms must pass.

Against the base tree all three fail, 3 failed, and their own output names the cause:

AssertionError: ['imas_codex.cli.compute', 'imas_codex.cli.config_cli', … 'imas_codex.cli.tunnel'] and AssertionError: litellm imported. A separate probe of the base tree with the warm-up stubbed shows the schema runtime arriving on the same path: ['imas_codex.graph._ensure_models', …, 'imas_codex.graph.schema', 'linkml_runtime', 'imas_codex.graph.schema_context_data']. In this tree the same probe is empty.

The guard gives the same verdict on ten consecutive runs in each warm-up state — ten in fresh interpreters and ten with imas_codex.llm.server pre-imported so the warm-up has already started — 20 of 20 passing both arms. The twenty runs were launched concurrently, which stresses the race rather than hiding it, and that approach found one: an earlier cold run failed with dictionary changed size during iteration because the guard walked sys.modules while the warm-up threads imported into it. The guard now snapshots the keys first. Records: guard-verdicts.json.

The tool list is unchanged in each of the three serve modes: 38 tools by default, 31 read-only, 15 DD-only, identical by name to the base revision, asserted by test_tool_names_per_serve_mode.
