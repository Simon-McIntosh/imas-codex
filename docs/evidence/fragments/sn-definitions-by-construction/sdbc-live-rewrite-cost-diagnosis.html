Why a live rewrite edit cost USD 0.39 and did not settle

The reported rate is not the edit's spend. The bulk report reads StandardName.llm_cost into its spend_usd field. That property is the name's cumulative lifetime cost, so USD 0.391 a name is the whole history of five names, not the cost of these five edits. Measured from the pipeline's own LLMCost records, the five edits spent USD 1.2267 in total, USD 0.2453 a name. Of that, two escalation-seat refine calls are USD 0.7055, or 57 percent.

The 280 seconds is the batch wrapper's own timeout 280, not a pipeline limit. Two of the five edits had in fact reached the acceptance threshold when the wrapper signalled them. One edit is refused for the right reason: its definition cannot be written without the neutral-inclusive wording its base name still carries, so the base names must be rewritten before the names derived from them. The pipeline defect that makes an edit expensive is a documentation refinement that was never shown the settled shared wording it is forbidden to paraphrase.

Why the writer counts neutral atoms under a bare species name

The writer is not the defect, and neither is the name's own Data Dictionary source. volume_averaged_oxygen_density and volume_averaged_boron_density resolve to summary/volume_average/n_i/<species>, an ion density. Neutral atoms enter only through the stored text of the base species names the writer copies as its nearest accepted neighbours: oxygen_density reads "Total number density of oxygen atoms and ions across all charge states, from neutral to fully stripped", and boron_density reads "Elemental boron number density, summed over neutral atoms and all ionic charge states through fully stripped B5+". Those two sentences contradict the ions-only ruling. The writer reproduced them accurately and the population gate correctly refused them.

The remedy is ordering, not a rename. Rewrite the base species names first, so the volume_averaged_* names derived from them copy an ions-only definition instead of an elemental-atom one. The base names are the defect; the derived names are downstream of it, and a rename would have moved the problem rather than fixed it.

The related error in the bulk pass is the blanket application of the species hint to volume_averaged_neutral_species_density, a name whose subject is an aggregate the population rule deliberately excludes. The pipeline generated text that was right for the name and spent three rotations and one escalation call trying to make it say the opposite.

The repair

generate_docs gives the model every settled shared part verbatim through shared_parts. The refine path built neither that context key nor a template block, while the renderer still installs the stored sentence and the persistence gate refuses a paraphrase of it. Each rotation therefore re-guessed wording it could not land, was refused, and spent a rotation until the escalation seat happened to reproduce the sentence. That is why the expensive call is the one that settles.

The refine prompt now carries the same settled-wording block as generate (6b94875), and that block is one partial (sn/_shared_parts.md) included by both templates, so the two cannot drift apart again.

The first version of this page said the template test guarded the fix. It did not: the template tests build their own context, so removing the lines in worker_refine_docs.py that populate shared_parts left them green. A test now drives the worker's own context-building path and asserts on what the worker hands the renderer. It fails against a tree carrying the base worker and passes with the fix, and it fails again when those lines are reverted from the head tree.

The covering suite (tests/standard_names/) was run as a SLURM all_debug job against the repaired tree: 8756 passed, 0 failed, EXIT=0. The first run of that suite caught a defect in the partial extraction, a stray newline that shifted the refine prompt's no-edit render and tripped its golden capture; the partial now renders nothing at all when a name carries no shared part.
