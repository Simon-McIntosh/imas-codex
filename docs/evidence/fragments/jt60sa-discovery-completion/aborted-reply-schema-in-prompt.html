Discovery carries each response schema in its prompt, not in response_format

The dedicated local OpenAI-compatible client no longer forwards response_format: _local_call_kwargs in imas_codex/discovery/base/llm.py translates only model, messages, max_tokens, temperature, seed, timeout and extra_body. The shared _build_kwargs is unchanged, so an OpenRouter model and a local/ model without a local API base still send it. Because the schema no longer travels in the request, each prompt owns it: the central _DEFAULT_SCHEMA_NEEDS table in imas_codex/llm/prompt_loader.py and its two fallback reads are deleted, and every discovery call-site prompt declares its schema providers in its own schema_needs frontmatter. Each renders its example and field list through the shared partials under imas_codex/llm/prompts/shared/schema; the signal source-unwind prompt gains a SignalSourceCodeUnwindBatch provider and a source-unwind-output partial in place of its hand-written JSON example. An engine-aborted reply (finish_reason='abort') is now rejected through _reject_unusable_reply in all four structured loops — the truncated prefix raises the existing retryable EmptyResponseError instead of reaching the JSON parser, and only finish_reason='length' grows the token budget. The strict renderer accepts the frozen tuple it reads back from prompt metadata, so a frontmatter-declared need no longer trips a list-only type check.
