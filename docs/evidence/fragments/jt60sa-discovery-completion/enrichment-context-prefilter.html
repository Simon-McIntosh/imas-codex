Signal enrichment context searches pre-filter by facility

The two vector lookups that feed the signal-enrichment prompt now select their candidates inside the index instead of discarding them afterwards. The wiki-context lookup (fetch_semantic_wiki_context in imas_codex/discovery/signals/scanners/wiki.py) and the code-context lookup (_build_code_context_query in imas_codex/discovery/signals/parallel.py) each pass ["node.facility_id = $facility"] as prefilter_clauses to build_vector_search (imas_codex/graph/vector_search.py), which renders the predicate as a WHERE between FOR $embedding and LIMIT — inside the SEARCH parentheses. The WikiPage and CodeChunk source joins are kept only for the fields the prompt renders, and the two facility post-filter predicates (p.facility_id, src.facility_id) are retired.

Each predicate used to be a post-filter over a global ANN cut, so a facility holding a small share of the index lost its own rows to the global winners before the filter saw them. Measured on the live graph for the PSRC signal jt-60sa:general/dcsv_1pdatpsrc at the default limits (wiki k = 5, code LIMIT 3), same embedding for both arms:

lookupbefore (global cut, then facility filter)after (facility predicate inside SEARCH)
wiki-context4 jt-60sa chunks (global top-5 held one tcv page)5 jt-60sa chunks, all jt-60sa
code-context0 jt-60sa chunks (global top-3 was jet, tcv, tcv)3 jt-60sa chunks

The code-context query additionally moves its score >= $min_score threshold behind a WITH: the WHERE placed immediately after SEARCH tripped a live planner error (Neo.DatabaseError.Statement.ExecutionFailed), so the branch had been returning no rows at all. With the threshold behind the join and WITH, the rebuilt query plans and returns three jt-60sa chunks.

Tests pin both in-SEARCH predicates (tests/discovery/test_scanners.py, tests/discovery/test_signals_pipeline.py) and that neither post-filter remains.
