Three defects the live code run exposed in the relevance path are repaired

A live JT-60SA code run surfaced three defects on the relevance path deployed by §25 — a decisions validator that refused legitimate answers, a scan progress line that killed the scan on an unscored path, and a status panel that reported the llm down while every code-discovery model call was in fact served. Each defect was reproduced before it was repaired, each repair carries a test, and all three are gated together on this allocation.

The decisions probability tolerance now scales with the criterion count

_validate_decisions_answers in imas_codex/discovery/base/llm.py refused a choice whose probabilities summed to 1 outside a fixed tolerance of 0.01. Jev rounds each offered probability to two decimals, so an eight-criterion distribution can legitimately sum to 0.99 or 1.03 — up to 0.005 of rounding error per criterion. Reproduced before repair: an eight-criterion choice summing to exactly 0.99 was refused with decision 'role' probabilities sum to 0.9900, not 1.

The tolerance is now 0.005 * len(criteria) + 1e-9. Fine in tests/discovery/test_llm_decisions.py: an eight-way choice summing to 0.99 and one summing to 1.03 are accepted, and one summing to 0.90 is refused. The two-criterion refusal that previously used a 0.7 sum still holds, because its slack is 0.01.

An unscored path renders as a placeholder, not a crash

scan_worker in imas_codex/discovery/code/workers.py built its progress line with f"{p.get('score', 0):.2f}". A FacilityPath admitted by --min-score 0 carries no score, and .get('score', 0) returns the stored None rather than the default, so str.format raised TypeError: unsupported format string passed to NoneType.__format__ and killed the scan. Reproduced before repair against a path dict carrying "score": None.

The score is rendered through _render_score, which returns "-" for any non-numeric value, and the line construction is extracted into _scan_progress_message so it can be driven directly. tests/discovery/test_code_scan_progress.py builds the message from all-unscored paths and from a mixed batch, and checks a boolean is not formatted as a number.

A local-free seat is probed at its own endpoint

The code status panel reported llm down because llm_health_check in imas_codex/discovery/base/services.py probed the LiteLLM proxy readiness whenever [llm].location is not local, while every code-discovery model call goes direct to the ambix router on an endpoint-class = "local-free" seat. The proxy is not on that path, so its readiness says nothing about whether the model answers.

For a seat whose model is an explicit free local endpoint, the check now sends GET to the models listing of that seat's resolved api-base with a 10 s timeout, reading the api-base through get_model_config (which resolves the named route) rather than a literal. For discovery-score that route is ambix-local, so the probe is GET http://98dci4-gpu-0003:18802/v1/models. imas_codex/cli/discover/code.py passes model_section="discovery-score", the seat its model calls actually use, replacing discovery-score's predecessor value. tests/discovery/test_base_services.py replaces the HTTP call and asserts the models URL is built from the configured api-base with a 10 s timeout, that the proxy readiness probe is not called, and that an unreachable endpoint reads unhealthy.
