Where the EQDBMS record layout is defined, and why the search criterion misses it

The EQDBMS equilibrium record layout — the sequence of typed sections EQ10…EQ32 a reader decodes an equilibrium record with, and the field-list COMMON blocks (#AAA, #CNT, #GEO, #EQU, #EQV, #OUT, #PAR, #VAC, #MSEDB, #EQ2M) that fix each section's fields — is defined across the EQDBMS library trees, and it is only partly in the graph. At its default pool the criterion _search_code('EQDBMS record layout', facility='jt-60sa') names the wrong sources: it returns EDAS eqread_pac client code (eqdata_get.f, Fledd.py, eqlist_get.f), none of which holds the layout. The layout surfaces only when the candidate pool is widened to k=50 and then re-ranked. So the criterion should name the EQDBMS-library readers/writers rather than the EQDBMS clients, and the layout still needs fuller ingesting — the field-list include files are absent from the graph entirely.

What holds the layout, and its graph state. The field list is reproduced (inlined as _BF COMMON declarations) inside the two ingested readers /analysis/lib/eqdbms/eqdbget2m.f (status ingested, relevance_stage content, score_composite 0.54, 4 chunks, IRDM_BF/IZDM_BF present) and /analysis/src/SAeqread/eqdbget.f (ingested / content / 0.57 / 5 chunks, IRDM_BF, IZDM_BF, EQ10 present). The per-section readers and writers eqrdNN.f/eqwtNN.f live in the EDAS EQDBMS library at /analysis/src/edas2/v2.1.15/edas_share/eqread_pac/fledd.pac.20160412/eqdbms/eqdbms/EQDB/, of which only eqwt10.f (ingested / content / 0.56) and eqwt11.f (ingested / content / 0.52) are ingested; eqwt13.f and eqwt2.f are only triaged and eqwt15.f is skipped. The variant reader /analysis/src/SAeqfame/eqdbget.f also carries the _BF field list (5 chunks). The definitive per-section write layout is the Fortran WRITE statement in EQDB/eqwtNN.f (e.g. eqwt10.f under C::EQDATA TYPE(EQIDX.EQ.'EQ10')). These statuses were read from the live graph between 09:12Z and 09:37Z on 2026-10-07, while the JT-60SA code pass was re-judging files.

What the graph lacks. The include files that carry the field list as a standalone definition (#AAA.bf, #GEO.bf, #EQU.bf, #EQV.bf, #OUT.bf, #PAR.bf, #VAC.bf, #MSEDB.bf, #EQ2M.bf) have zero CodeFile rows; a path query for .bf/#AAA/#GEO/#EQU/#VAC/#MSEDB matches nothing. The whole client reader/writer set /analysis/src/client_eqdbms.EQ32.Rev1/eqdbms/EQDB/* (eqdb_get.f, eqdbio.f, eqdblist.f, eqrdNN.f, eqwtNN.f, ftplistget.f) is skipped at name, i.e. identified but never fetched or chunked. /analysis/lib/JT60SAEQDB has no CodeFile rows. So an operating reader/writer, the EQDBGET interface a JT-60SA client calls, is in the graph only through the SAeqread/SAeqfame readers and the two EDAS eqwt writers.

Rank of the layout's chunks. Under the tool's own hybrid order (rerank off) the layout is absent from the default pool entirely: at k=10 and k=30 every returned candidate is EDAS client code (mostly eqread_pac; 3 of 10 and 10 of 30 come from the eslice_esurf, eslice plugin, eslice_data_area and egis trees), and the layout's chunks first appear only at k=50 — lib/eqdbms/eqdbget2m.f at #39 (0.886), EDAS EQDB/eqdbio.f at #44, SAeqfame/eqdbget.f at #45–46, geteddbt.c at #50. With the Jev rerank on (one score question per candidate, typesafe/jev-1.13) the outcome depends on the pool: over the k=30 pool the layout chunks are not present, so the rerank cannot surface them and the criterion still fails (top = EDAS eqread_pac files) — this is the failure the criterion reports. Over the k=50 pool, once the layout chunks are in the pool, the rerank lifts them hard to the top: SAeqfame/eqdbget.f to #2 (jev 2.01), lib/eqdbms/eqdbget2m.f to #4 (jev 1.72), EDAS eqdbms/EQDB/eqdbio.f to #8 (jev 1.52), while the tool's own #1 (eqdata_get.f) falls to #9. The criterion's defect is therefore a retrieval (pool-size) defect, not a ranking one.

Verdict. The criterion names the right topic but the wrong sources: it should name the EQDBMS-library readers and writers (eqdbget2m.f, SAeqread/eqdbget.f, SAeqfame/eqdbget.f, EDAS EQDB/eqwtNN.f) that hold the record structure, not the EDAS eqread_pac clients that consume it. The layout also needs further ingesting: the standalone field-list include files and the client_eqdbms reader/writer set are absent or skipped, so a search for the record layout cannot reach the definition itself, only its reproduction inside the two ingested readers.
