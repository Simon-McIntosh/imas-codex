JT-60SA ingested files can be re-judged from their stored chunks

The content arm now re-judges a code file from the text it already carries in the graph. A file sitting at ingested with a content-stage relevance and no recorded facet answer is put back in front of the same content question set, through the same seat, but its state is rebuilt from its own stored CodeChunk text — joined in reading order (start_line) and cut to the same 1500 characters the fetched path uses — instead of a remote fetch. The judgment fields are rewritten in place; the file's status, its CodeExample and its chunks are left as they are. Admission is not re-decided: a file whose new composite and facets both fall below their gates stays ingested and is reported. The path is reached through the existing reset owner (CODE_RESET_SPECS["ingested"] plus --rejudge-ingested) and the existing score claim; no second pipeline was added.

A bounded read of the live graph (jt-60sa, one facility-scoped count) puts 552 JT-60SA files at ingested with a content-stage relevance, of which 540 still carry no facet answer — the rows a re-judge pass takes. The claim's drain key is exactly that absence: coalesce(sf.score_data_access_confidence, 0.0) = 0.0, so a file the pass has judged drops out of the claim: later passes take the remainder.

The reset's content-stage scope is an AND restriction, not an OR widening. The widened form (n.status IN $source_statuses OR (n.relevance_stage = 'content')) admits every content-stage file whatever its status, so a single pass would have demoted and cleared the facility's scored, skipped and triaged content-stage corpus. ResetSpec.extra_filter renders n.status IN $source_statuses AND n.relevance_stage = 'content', so only ingested content-stage files are touched: the set the re-judge takes and no other.
