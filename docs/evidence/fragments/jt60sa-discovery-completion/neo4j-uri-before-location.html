NEO4J_URI outranks location resolution

In imas_codex/graph/profiles.py the NEO4J_URI escape hatch in resolve_neo4j is evaluated before resolve_location is called. When the variable is set, the function returns a Neo4jProfile carrying the environment address immediately, so nothing reads the location file. The profile's bolt and HTTP ports still follow the location convention, so a location beyond the first in the list keeps its offset slots.

Before the change the env override was applied after resolve_location (and after the port convention helpers, which call back into it). §10 removed the client wrapper that previously applied the env value first, so an operator who set NEO4J_URI with an unreadable location file got a raise from the location read instead of the address they named. The ports come from the convention helpers when the location is readable and, when it is not, from the locations list alone (which reads no file), so the override neither raises nor loses the offset slots. The raise itself is the correct default and is kept for the no-override case: tests/graph/test_client_address_resolution.py still pins that an unreadable location surfaces rather than being swallowed into a fallback address.
