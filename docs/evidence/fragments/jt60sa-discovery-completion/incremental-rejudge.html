The ingested re-judge resets once and resumes

The JT-60SA ingested re-judge restarted the whole set on every pass because discover code --rejudge-ingested ran the ingested reset over all ingested content-stage files on each invocation, and the re-judge worker's attempted guard broke only when a whole batch repeated — so a batch that mixed already-attempted files with fresh ones re-judged the attempted ones again and its count overstated the work (660–740 for 581 files over seven passes). The reset is now the explicit, once-per-request --reset-to ingested step, whose owner stays reset_to_status; a plain --rejudge-ingested invocation clears nothing and takes only the ingested content-stage files with no recorded answer, so a following pass resumes on the files a prior pass left unanswered. In the worker each claimed batch is filtered to the fresh files, so no file is judged twice in one pass and rejudged counts the distinct files judged. The claim's drain key is the facet confidence the reset clears, so the reset and the claim stay coupled.

Two passes over three ingested content-stage files with one decision failing on the first pass: the second pass judges only the failed file (test_second_pass_judges_only_the_file_the_first_left_unanswered). A batch that mixes an attempted file with a fresh one takes only the fresh file (test_no_file_is_judged_twice_in_one_pass_and_count_matches). The CLI tests assert a plain re-judge issues no reset call and that --reset-to ingested --rejudge-ingested reaches reset_to_status exactly once with the ingested spec.
