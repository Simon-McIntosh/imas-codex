The graph client no longer owns a SLURM discovery copy

The graph client's _slurm_service_uri carried its own discovery of the SLURM service node — a direct discover_compute_node_local call with an _resolve_compute_host fallback — while imas_codex/remote/locations.py had just become the one owner of that discovery. The copy is routed through the owner: the client now obtains its bolt URI from _service_url_for_slurm, so the graph and embedding paths cannot diverge.

What landed

  • Client delegates. _slurm_service_uri asks imas_codex.remote.locations._service_url_for_slurm for the SLURM address, passing protocol bolt, the active location's service job name and local=False, so its contract is unchanged: None still means "undiscoverable here — keep the profile's resolution", and an unreadable location still raises rather than restoring the loopback tunnel.
  • Why delegate, not delete. The only production caller is _resolve_graph_uri's SLURM branch, and the profile's Mode 2 resolves the same node, so the copy is redundant. But an existing test module outside this node's write scope (tests/graph/test_client_address_resolution.py) imports and pins _slurm_service_uri, so deleting the symbol would leave that module red. Delegation removes the duplicate discovery while keeping the pinned contract intact.
  • Six retired tests removed. The five TestResolveUrlForCompute cases of the deleted loopback rewrite and the TestEmbeddingHostDiscovery case of the retired _embed_host_from_facility are deleted from tests/embeddings/test_readiness.py. The one claim that still matters — the graph and embedding services may sit on different nodes — is re-expressed against resolve_service_url in tests/remote/test_locations_resolution.py.
  • New coverage. Two cases pin the graph client: that from a compute node it resolves the discovered node's bolt URI, and that it takes that URI from the shared owner unchanged. A third case shows the graph and embed jobs resolving to their own nodes by their own service job names.
