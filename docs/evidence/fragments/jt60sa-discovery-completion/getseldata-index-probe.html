Which getseldata sources fill JLOOP/JTPRB/JNPRB, and why no chunk names them

No getseldata file in the graph mentions the arrays: the 15 CodeFile rows under /analysis/src/getseldata_v4.2 are the graph-visible set, and with the hop down the tree was not grepped on the host, so a file the scanner never discovered is not excluded. The chunk-text search that finds eddbreadTime in 10 getseldata chunks finds JLOOP, JTPRB and JNPRB zero times, case-insensitively. The arrays are filled in the equilibrium tree, not getseldata: JLOOP(I)=K in SAselene_v2.0_forPSRC/eqvacu.f and SAeqread/eqvacu.f, immediately after CALL MGPOS(RPOSLP(I),ZPOSLP(I),K,XX,YY,IR,IZ); JTPRB(K) and JNPRB(K) in SAselene_v2.0_forPSRC/mgfild.f, mirrored in edas2 Eqread.py (f_vars.ILOOP, f_vars.IPROB). The getseldata tree is the EDDB channel reader, channel names into ADB columns; it holds no sensor-index array. The plan fallback clause, "or the run records that the source fills them elsewhere", is the outcome.

Why no chunk names the arrays. One class, because the premise that getseldata fills them does not hold:

  • The arrays do not live in getseldata. They live in the equilibrium tree (SAeqread, SAselene_v2.0_forPSRC) with a mirror in the edas2 Python reader; no getseldata source references them, so no getseldata chunk can name them. Repair: none in getseldata; the map reads the fill sites named here, and those trees already hold scored FacilityPath rows and named chunks.
  • Four files never reached a chunk. out96st.h, gettime12.c and elapsed.c sit below the 0.5 ingest gate, and getfame96/main.c was skipped at triage (0.24, below the 0.4 gate). None is a plausible array-fill site by name, role or score. Repair: none; they are utility and record-format files.
  • Extensionless Fortran includes are outside the scanner. The getseldata mains use INCLUDE eddbaccess.i and getseldata.i, and 0 .i CodeFile rows exist under the tree. This is the include-file class, but it is not the cause here: the arrays are absent from the getseldata sources themselves. Repair: relevant only if the map needs getseldata EDDB interface, which the eddbaccess.h chunk already documents.
  • Files with no CodeFile row cannot be enumerated from the graph while the hop is down; the honest bound is the 15 rows above plus the statement that the live tree was not greppable. Repair: rerun the on-host grep when the hop answers, closing the never-discovered arm.

What the ambix machine map needs from these arrays. The map asked whether getseldata holds the raw flux-loop and pickup-coil channel mapping; it does not. JLOOP, JTPRB and JNPRB are SELENE grid-cell indices set by MGPOS from the sensor positions. A raw channel joins its position only through the shared sensor index, so the ordering the map needs is the one that leaves eqvacu.f (flux loops) and mgfild.f (probes), read against the geo.in input RPOSLP and ZPOSLP.
