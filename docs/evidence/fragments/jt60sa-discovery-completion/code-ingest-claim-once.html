Code ingestion claims stay with one worker

The retry-failed pass recorded 62 ingestion events for 46 unique files: 16 duplicate events. Its log shows both workers claiming a ten-file batch at 15:13:14, naming the same first three files, and finishing their batches 3.9 and 4.3 seconds later. The claim timeout is 300 seconds, so expiry did not cause this overlap. The two-step claim wrote a token and then read it back in a separate transaction. Each worker could read its own token before the other's claim overwrote it, and both proceeded to fetch and ingest the same files.

Claim selection now takes a write lock on the facility before reading eligible files, serializing concurrent batches. A working batch renews its own token-checked claim at one-third of the stale-claim timeout, so a long ingest remains owned until its holder finishes. Ingestion runs on a separate thread because its synchronous graph writes can otherwise block the event loop that renews the claim.

A second live probe held one claim for 1.4 seconds against a one-second timeout and the contender took zero files; it removed its single probe node.
