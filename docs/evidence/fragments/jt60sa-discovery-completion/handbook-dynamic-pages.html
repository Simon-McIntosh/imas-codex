Dynamic handbook tables link to the catalogue they front

The JT-60SA Data Handbook renders one table per database at request time: the topic markup carries only column headers and a search form, and a CGI plugin fills the rows from the catalogue. Ingest therefore kept an empty-header chunk and linked it to no signal, so the handbook page reached none of the data it documents. A dynamic page now records the database(s) it fronts on WikiPage.fronts_database, its empty-header chunk text is replaced by a one-line stub naming those databases, and the page anchors DOCUMENTS edges to every FacilitySignal of the catalogues it fronts.

The database a page fronts comes from the ?db= parameters of the links that reach it — the handbook's [[CategoryInformation?db=EDDB][Experiment database (EDDB)]] and its siblings — parsed from the linking page's own stored chunk text. A page is read as dynamic when its extracted text is a table with no data row beneath any header: a data row is a table row that sits under a header separator and is not one of the header rows the empty table repeats. The literal word "search" is not required, because the Datatype Information topics carry no search label and are dynamic all the same.

link_chunks_to_entities gained a fourth MERGE keyed on fronts_database. A page that fronts database D has each of its chunks linked to every FacilitySignal whose data_source_name is the scanner source for D. The database→source map (EDDB → edas) is a small dict beside the function; a database with no scanner source links to nothing, so adding a scanner is the only change needed to extend the map.

Applied to the live graph through the pipeline's own functions (apply_dynamic_page_rule for the handbook topics, then link_chunks_to_entities("jt-60sa")), not through hand Cypher. The rule reads the linking page's stored chunk text rather than a fresh fetch, because the JT-60SA wiki host is not reachable from the compute node this ran on; the derivation is from the same markup the ingest stored. CategoryInformation now carries fronts_database = ['EDDB', 'PMDB'] and DataInformation carries ['UDDB', 'EQDB', 'FAME'], both still ingested. The linker created 12,596 DOCUMENTS edges; the EDDB-fronting page reaches 6,298 FacilitySignal nodes, and the signal jt-60sa:general/psrc_magfluxlp1 is reached from both of that page's chunks. The brief's 6,240 was the EDAS scan size when it was written; the graph has since grown to 6,298, and the page reaches every one of them.

Negative control: removing the fronts_database derivation from detect_dynamic_page (so a header-only, database-less page reads as dynamic) fails test_header_only_without_database_is_not_dynamic with a non-zero exit; the unmodified detector passes the same test.

Two follow-ons. The stub text is written to the graph but the chunk's embedding is not recomputed, because the embedding backend was unreachable from the compute node during this run; a re-embed pass is needed before the stub text is searchable by vector. And PMDB, UDDB, EQDB and FAME front pages that reach no signal until a scanner writes those source names — extending DATABASE_SIGNAL_SOURCES is all that is required.
