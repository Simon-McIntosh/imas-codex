search_code pre-filters by facility inside the vector index

search_code now selects its vector candidates inside the code_chunk_embedding index rather than discarding them afterwards. The code_chunk_embedding index registers facility_id as an additional vector index property (WITH [n.facility_id] in CREATE VECTOR INDEX), and _vector_search_code_chunks (imas_codex/llm/search_tools.py) passes the facility predicate as a prefilter_clauses argument, which build_vector_search (imas_codex/graph/vector_search.py) renders as a WHERE between FOR $embedding and LIMIT $k — inside the SEARCH parentheses, so the ANN cut is taken over the facility's own chunks.

The predicate used to be a post-filter: the index returned a global top-k across all 271,661 CodeChunk nodes and the facility check ran after the cut. A facility holding a small share of the corpus therefore lost its chunks to the global winners before the filter ever saw them. Measured on the live graph: jt-60sa holds 201 of 271,661 chunks (0.07%). The same query, embedding and k at 10, on the rebuilt index — with the predicate inside SEARCH returns ten chunks of which two are /analysis/src/SAselene_v2.0_forPSRC/eqequb.f; with the predicate as a post-filter (WHERE after ) SCORE AS score) it returns zero rows, because no jt-60sa chunk is in the global top ten at all. The starvation is total, not marginal.

The path from schema to index statement is schema-derived and single-sourced. A vector_index_filters: facility_id annotation on CodeChunk.embedding (imas_codex/schemas/facility.yaml) is read by GraphSchema.vector_index_filters (imas_codex/graph/schema.py), emitted by scripts/gen_schema_context.py as VECTOR_INDEX_FILTERS into the generated schema_context_data.py, and consumed by GraphClient.ensure_vector_indexes through _vector_index_ddl (imas_codex/graph/client.py). ensure_vector_indexes now compares each live index's dimension and property set against the schema and drops an index whose live shape differs, so the filter registration is applied by an ordinary ensure_vector_indexes call rather than a manual rebuild. vector_indexes stays a list of 3-tuples and the generated VECTOR_INDEXES stays a mapping to 2-tuples; the filter map is a separate surface. The signal and wiki chunk searches are unchanged — they keep their post-filter facility predicate, since their indexes do not carry the filter property.
