The dead triage models are retired and the four relevance defects are closed

The triage models the decisions route replaced are gone. FileTriageResult and FileTriageBatch are removed from imas_codex/discovery/code/scorer.py, and imas_codex/discovery/code/__init__.py no longer re-exports them or apply_triage_results. In imas_codex/llm/prompt_loader.py the file_triage_schema provider and the file_score_dimensions provider are removed with their _SCHEMA_PROVIDERS registrations; no prompt reads either key. The legacy symbol apply_triage_results was live — its only caller is triage_worker, which persists the names-arm relevance — so retiring the name while keeping the pipeline intact meant renaming the function to apply_name_relevance (behaviour unchanged), not deleting it. file_scoring_schema stays: the code scorer prompt still needs it.

The relevance-stage predicate has one owner, relevance_predicate(alias, stage, threshold_param) beside the score_composite comparison in imas_codex/discovery/code/scorer.py, with the stage names RELEVANCE_STAGE_NAME and RELEVANCE_STAGE_CONTENT. Every claim, has-work and count site now renders it: the triage-stage enrichment claim (claim_files_for_enrichment) and its has-work check (has_pending_enrich_work), the has_pending_code_work ingest predicate, the ingestion claim in workers.py, and the pending_enrich, pending_ingest and chunk-embed counts in parallel.py. A file's status and the arm that set it can no longer disagree between the claim, the has-work check and the count.

In score_worker each content decision is paired with its own file by path rather than by position. The old zip(files, content_decisions) shifted every later file onto the wrong decision as soon as one decision failed mid-batch, so a refused file could be described on another file's decision and the last file dropped. test_content_arm_pairs_each_description_with_its_own_file fails the first file's decision and asserts the two survivors are each described as themselves. Run against a copy that zips files onto the successful decisions again, the test exits non-zero with /analysis/src/refused.f — a file its decision did not admit — as the first described file.

A code reset to discovered or triaged now deletes the reset files' CodeExample and CodeChunk nodes through a post_cypher on those ResetSpecs in imas_codex/discovery/base/reset.py. The traversal is the one clear_facility_code uses (CodeFile <-FROM_FILE- CodeExample -HAS_CHUNK-> CodeChunk), scoped to the files being reset; collect() drops the nulls an optional match yields and WITH DISTINCT n keeps the trailing count(n) a count of files rather than of deleted examples. The scored reset, which is not below ingestion, is untouched. tests/discovery/test_code_reset_chunks.py pins the rendered Cypher.

One registry, CODE_RELEVANCE_FIELDS in imas_codex/discovery/base/reset.py, holds the relevance fields a CodeFile carries; the code scorer reads it as RELEVANCE_FIELDS and the discovered reset clears it, so the fields the decision arms write and the fields a reset clears cannot drift. It lives in reset.py because that module is imported before the code package and importing the code package from it would close an import cycle.

Every Cypher statement this node changed was compiled with EXPLAIN against the live graph: 16 statements, 16 ok, 0 failed. The set covers the three graph_ops statements, the six index/claim/count statements in parallel.py's stats query, the ingestion claim and its read-back, and both rendered reset queries.

Reported, not deleted: 1,252 CodeFile nodes workstation-wide are below ingested yet still carry CodeChunk nodes — tcv 826 (488 skipped, 255 scored, 75 failed, 8 enriched), jet 373 (340 failed, 19 enriched, 13 scored, 1 skipped) and jt-60sa 53 (23 skipped, 22 scored, 8 triaged). These are the residue a pre-fix reset left behind; the new cascade removes it for the files a reset touches, and this count is the remaining at-rest population.
