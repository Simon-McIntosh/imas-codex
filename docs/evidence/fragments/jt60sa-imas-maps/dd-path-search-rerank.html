DD-path search rerank — one call into the shared owner behind a mode switch

search_dd_paths now reorders its hybrid hits through rerank_candidates in imas_codex/llm/search_tools.py — the shared search-time owner the code and wiki search tools already use — rather than carrying a second rerank of its own. The switch is a construction-time decision: GraphSearchTool(..., rerank=…), plumbed through Tools(..., rerank_dd_paths=…). The MCP server sets it on for a full or facility server and leaves it off for a read-only or DD-only server, recording the decision on the mode in AgentsServer.__post_init__ and reading it when the lazily-created Tools singleton is built. Each hit rides its own candidate dict under _hit, with its path as the locator and its documentation and description as the judged text, so the judged order maps back to the hits without a path lookup (paths are not unique across IDSs). A failed or slow judgement returns the embedding order unchanged, so the result is never worse than the search that produced it.

nDCG@10 on 15 hand-labelled mapping questions

tests/tools/fixtures/dd_mapping_questions.json holds 15 mapping questions — each a facility-style natural-language query and the data-dictionary paths that answer the query would answer it, graded 3 (the named quantity), 2 (the same quantity in a second IDS) or 1 (a related quantity). The measurement scores the same retrieval twice on the same labels, at k=10, against the live graph and a live Jev judge: once in the tool's embedding order (rerank=False) and once after the rerank (rerank=True).

The measurement is a live judge on a sparse label set: the four 0.0000 questions are retrieval misses, and the labelled set covers only the paths a mapping question names, so a retrieved candidate no label covers counts as irrelevant. That flatters neither order. The finding stands on the three questions where a labelled answer was demoted: the judge reorders on documentation and description text, and where the embedding order had already placed the answer first, that text is not enough to hold it there.

The switch honours the server mode

AgentsServer.__post_init__ sets the module-level switch to not (read_only or dd_only), so a full server reranks and a read-only or DD-only server — the public containers — never does, spending no judgement on an external query. A directly-constructed Tools or GraphSearchTool defaults the switch off, so a caller that wants the rerank asks for it. The tests pin all four: full reranks, read-only never, DD-only never, and the default is off.

Checks

tests/tools/test_dd_path_search_rerank.py pins the construction-time switch, that the rerank is exactly one call into rerank_candidates, that each candidate carries its path and text, that the judged order is applied to the hits, and that a disabled tool never calls the owner; it also verifies the nDCG@10 helper and the fixture. It passes 14/14 alongside tests/tools/test_tools.py (11/11) and tests/tools/test_search_dd_paths_regression.py under -m graph (6/6). The negative control sets the switch on regardless of mode (_rerank_dd_paths = True) and the read-only and DD-only tests then fail because the switch is on for those modes — the red log is ~/.cache/imas-codex-dd-path-rerank/negative_control_red.log.
