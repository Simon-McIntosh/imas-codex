IDS mapping runs locally; cluster labelling stays put

Change

ids-mapping, which the mapping engine uses for both the escalated set choice and the field mappings (imas_codex/ids/mapping.py:744 and :772), was the one seat on the JT-60SA path still sending language calls to OpenRouter. It now carries the same endpoint keys as discovery-describe — model = "local/deepseek-v4.1-flash", model-route = "ambix-local", api-key-env = "AMBIX_API_KEY", endpoint-class = "local-free" — so it resolves the ambix-local route, and carries reasoning-effort = "high" because the escalated choice is reasoning work and the local model is otherwise non-thinking. The seat's reasoning effort was inert until _call_llm and _acall_llm began forwarding get_reasoning_effort("ids-mapping") to the call layer, the pattern standard_names/workers.py uses with its seats. imas map run probes the reasoning seat at start-up (imas_codex/cli/map.py:450) though its calls go through ids-mapping, so a local run checked one model and called another; the start-up probe now names ids-mapping.

cluster-labels is deliberately left on OpenRouter. It routes no call: the labelling call is ClusterLabeler's, which defaults to get_model("dd-enrichment") (imas_codex/clusters/labeler.py:88), and both constructions pass no model (clusters/extractor.py:650, graph/build_dd.py:4578). get_model("cluster-labels") is read only as the label-cache match key and as provenance (clusters/label_cache.py:176-191, :222, :289; extractor.py:566). Routing it locally would turn every cached cluster label into a cache miss and force a full relabel on the next DD cluster build, paid on OpenRouter. Cluster labels are produced at DD build time, not on the JT-60SA path. Moving DD labelling and enrichment local is a separate decision held for the lead; that decision would relabel every cluster.
