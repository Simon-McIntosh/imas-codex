Why five review checks invert on accepted names

Control. The unmodified prototype score reproduces the re-measure: calibration AUC 0.606 [0.553, 0.666] on 363 names and validation AUC 0.638 [0.581, 0.692] on 338, matching the recorded 0.606 and 0.638.

A Noul is read as a pass probability of one minus its defect probability, so an AUC below a half is a question the model answers backwards against the golden label. The five checks below are the five lowest such AUCs, each with a 95% interval below a half.

The state builder drops nothing. Every field these five checks declare reaches the state: build_name_state wraps each one through _observed (imas_codex/standard_names/review/jev_review.py:213-218, with the flag set at :152-161), so a field the item does not carry is recorded as observed-and-absent rather than omitted. No declared field is never filled; what varies is whether the review item the builder is handed already carries the value. The table below is that distinction, and it is the fields whose value in the item is thin — cocos_label, source_paths, dd_source_docs, existing_names — that name the starved checks.

The inversion is a ranking inversion. Because a check's firing cut is a half, a check whose accepted and rejected defect probabilities sit on the same side of a half does not fire differently on the two classes: owner_erased_outline never reaches a half on either class in either split, yet its AUC is the lowest but one. So the five are not firing falsely on accepted names so much as ordering accepted names above rejected ones, which is the shape of evidence starvation rather than of a mis-set threshold.
