Disposable Neo4j teardown fits the test timeout

The shared session fixture in tests/standard_names/conftest.py stopped the disposable database and then deleted its store directory synchronously in teardown. A Neo4j store is thousands of small files, so the recursive delete pays one metadata operation per file; on a shared filesystem each unlink is a round trip, and the removal was recorded at 37.1 s — longer than the 30 s per-test timeout, so a graph run could fail in teardown for reasons unrelated to the code under test.

Teardown keeps its order: the database is stopped first. The store tree is then renamed away in one metadata operation, so the store path is gone immediately, and the recursive delete is handed to a detached process under the run's own TMPDIR. The session waits at most a 2 s budget for that process and never for the delete itself; a removal that fails leaves its traceback beside the tree instead of vanishing. The fixture logs the stopped database, the removal outcome and its blocking time, so its own budget is measurable from a gate log.

Both arms are under the 30 s budget on this node's node-local TMPDIR, and here the delete is effectively free (0.00 – 0.21 s), so the recorded 37.1 s does not reproduce on xfs: it is a property of the shared filesystem, where the same delete costs tens of seconds. What changes is who pays it. At base the delete ran inside the session's teardown and its duration was the session's to absorb, whatever the filesystem; at head the blocking cost no longer contains the delete at all, so the same store on a shared filesystem leaves the session blocking by the stop and the rename only. The remaining 15 s of blocking is the existing stop_temp_neo4j SIGTERM wait inside imas_codex/graph/temp_neo4j.py, which is outside this change and still inside the budget.

The measure reads the gate log: it requires a teardown line naming the store path and a detached remover, blocking time at or under 30 s, no test teardown over 30 s, and the named store path absent afterwards. Against the head log it passes (EXIT=0); against the mutation log — the same tree with the synchronous directory.cleanup() restored — it fails with test_teardown_budget.py::test_session_teardown_fits_the_test_timeout and EXIT=1, because the log then reports the store removed synchronously rather than handed to a detached remover. On this filesystem the deleted tree is small enough that the synchronous arm still meets the duration bound, so the discriminating fact is the handoff, not the seconds; the seconds are what the handoff protects when the tree lives on a shared filesystem.
