Disposable Neo4j teardown fits the test timeout

The shared session fixture in tests/standard_names/conftest.py stopped the disposable database and then deleted its store directory synchronously in teardown. A Neo4j store is thousands of small files, so the recursive delete pays one metadata operation per file; on a shared filesystem each unlink is a round trip, and the removal was recorded at 37.1 s — longer than the 30 s per-test timeout, so a graph run could fail in teardown for reasons unrelated to the code under test.

Teardown keeps its order: the database is stopped first. The store tree is then renamed away in one metadata operation, so the store path is gone immediately, and the recursive delete is handed to a detached process under the run's own TMPDIR. The session waits at most a 2 s budget for that process and never for the delete itself. A remover that ends within the budget is judged by its exit status: a non-zero exit keeps the tree and its traceback where they are and fails the session's teardown, naming the log, rather than reporting a removal that did not happen. The fixture logs the stopped database, the removal outcome, its blocking time, and whether the store path is absent once the session has ended, so the gate log itself carries the post-session check.

Both arms are under the 30 s budget on this node's node-local TMPDIR, where the delete is close to free, so the recorded 37.1 s does not reproduce on xfs: it is a property of the shared filesystem, where the same delete costs tens of seconds. What changes is who pays it. At base the delete ran inside the session's own teardown and its duration was the session's to absorb, whatever the filesystem; at head the blocking cost contains only the stop and the rename, so the same store on a shared filesystem leaves the session waiting on those alone. The remaining ~15 s is stop_temp_neo4j's SIGTERM wait in imas_codex/graph/temp_neo4j.py, outside this change and inside the budget.

The two guards live in tests/standard_names/test_disposable_neo4j_teardown.py and each fails only when its own guarantee is removed. Reverting the fixture's teardown to a synchronous directory.cleanup() fails the wiring test, because the fixture no longer hands the removal off and no budget protects it. Deleting the remover's exit-status branch fails the failure test, because a remover that exits non-zero is then reported as a completed removal and its log is unlinked. The behavioural test that a removal outlasting the wait is detached runs the removal against a remover which never touches the tree, so it measures the handoff rather than how fast this filesystem deletes.
