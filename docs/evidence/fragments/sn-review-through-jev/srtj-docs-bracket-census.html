§1 — The future-name convention: syntax, writer, swapper, reader

The convention is a link whose target is a DD path, written so a name that does not exist yet can be cited and later repointed once it does. Four places define it:

  • Syntax. [label](dd:<dd-path>) in documentation, and dd:<path> as a value of the structured links field. The gate accepts the target form: _VALID_LINK_TARGET_RE (docs_gates.py:65) is r"(?:name:[a-z0-9_]+|#[a-z0-9_]+|dd:[a-z0-9_/]+|https?://\S+)$", and the JSON's dd_link_syntax_is_a_valid_gate_target control records fullmatch("dd:equilibrium/time_slice/profiles_1d/electrons/density") as true.
  • Writer. The documentation pipeline writes it, and the schema names it: the links field is documented as "Related standard names (name:xxx or dd:path format)" (imas_codex/standard_names/models.py:1905). The docs prompts never ask for it — grep -rn "dd:" imas_codex/llm/prompts/sn/ returns nothing — and the cross-reference rule they do carry permits only [label](name:bare_id) written "only to a name that EXISTS — do not invent a related-name to link" (imas_codex/llm/prompts/sn/generate_docs_system.md:315-319).
  • Swapper. resolve_links_batch (imas_codex/standard_names/graph_ops.py:9426): for each dd:<path> link it runs MATCH (n:IMASNode {id: path})-[:HAS_STANDARD_NAME]->(sn:StandardName) and replaces the link with name:<sn_id>; an unresolved path is retried (graph_ops.py:9379, _MAX_LINK_RETRIES = 5) and then marked link_status = "failed". _compute_link_status (graph_ops.py:492) names the intermediate state: a node carrying any dd: link reads "unresolved" until the swap lands.
  • Reader. _extract_links_from_docs (imas_codex/standard_names/graph_ops.py:522) reads both forms with _LINK_RE (graph_ops.py:505) and _DD_LINK_RE (graph_ops.py:513) and writes the order-preserving deduplicated links index on the node.

Can that syntax ever render as a bare bracketed phrase with no target? No, at any of the four stages. As authored the dd: token always carries its target — either [label](dd:path), or a bare dd:path with no brackets at all. As stored and as read by the rule, the whole link is masked before the prose scan runs: _masked_spans (doc_links.py:38) adds every _MARKDOWN_LINK_RE match (doc_links.py:19, r"!?\[[^\]]*\]\([^)]+\)") to the spans find_prose_bracket_phrases (doc_links.py:121) skips. The bare-reference rule independently excludes a link label — _BARE_BRACKET_RE (doc_links.py:20) is r"(?<![!\\A-Za-z0-9_])\[([a-z][a-z0-9_]+)\](?!\()" and both of its guards matter here: the lookbehind (?<![!\\A-Za-z0-9_]) refuses an image !, an escaped \[, and an identifier-adjacent bracket, while the lookahead (?!\() refuses a bracket immediately followed by a link target — which is exactly the shape of a [label](dd:path) label. Its content class [a-z][a-z0-9_]+ is a single snake_case token and admits no space. After normalisation _normalize_bare_doc_links (graph_ops.py:9602) only rewrites or strips bare snake_case tokens and never touches a dd: link; after export the link-pruning pass (tests/standard_names/test_export_link_pruning.py) drops internal links to unpublished targets from the links field and never edits prose.

Empirically the form does not occur. Of the 2,530 accepted documents, 0 contain the token dd: and 0 contain a (dd: link. The scan's positive control (dd_token_scan_positive_control in the JSON) runs the same predicate against a document known to carry the token: a selection across every stage for documentation CONTAINS 'dd:' returned nothing, so the token was planted in a disposable copy as [density](dd:equilibrium/time_slice/profiles_1d/electrons/density), and the same predicate found it (predicate_on_planted_text: true) and the dd: link pattern matched it, passed: true. So the zero is the scan seeing nothing, not the scan being blind.

The rule's precision as measured

Against the concern that motivated this census — that the check might fail a legitimate future-name link — the rule's precision is 1.000: 0 of the 637 flagged documents is a dd: placeholder, and 0 is notation the exclusions should have spared. All 637 flag a construct that genuinely renders as literal [text] (613) or is a name: self-loop (24).

Positive controls prove the instrument sees each construct before any zero is reported: the gate's scanner returns ["ion density"] for a text holding one; the gate predicate rejects [m^-3] as a unit; the independent instrument classifies a planted [m^-3] and [0, 1] and $[a b]$ and [x](name:y) into unit, interval, math and link label; the gate fails a document holding a bare prose bracket and a document linking its own name; the description index holds 4,874 entries and the DD documentation corpus 40,000; and the dd: scan's own predicate finds a planted dd: link.

§3 — Where the bare phrases came from

One writer accounts for them: the documentation generation prompt, and the accept-path normaliser that cannot see this form.

  • The writer is the docs generation LLM. imas_codex/llm/prompts/sn/generate_docs_system.md:315 carries the hard rule that forbids exactly this construct — "No bare brackets — every [...] MUST have a (name:bare_id) target (HARD)" — over the offending example at :334, captured by [radial_derivative_of_elongation_of_flux_surface].. The rule has been in the prompt since 2026-06-21 (8319cc043, fix(sn): docs cross-refs — ban bare [name] brackets and self/mismatched links), and the model writes them anyway. The refine prompt carries a weaker form of the same instruction (imas_codex/llm/prompts/sn/refine_docs_user.md:185, "preferring a [label](name:id) link").
  • The accept-path normaliser is blind to this form, which is why it survives to accepted. _normalize_bare_doc_links (imas_codex/standard_names/graph_ops.py:9602) is meant to repair exactly this defect — "each bare [snake_case] (no (name:...) target) becomes [snake_case](name:snake_case) when snake_case is a real StandardName id, else the brackets are stripped". It finds its candidates with find_name_references(..., known=None) (doc_links.py:53), whose bare-candidate pattern is _BARE_BRACKET_RE (doc_links.py:20) — a single snake_case token, \[([a-z][a-z0-9_]+)\], admitting no space. All 613 phrases contain a space, so none is a candidate, and the sweep neither links nor strips them. The partition is clean at zero: no accepted document holds a bare single-token snake bracket (bare_snake_bracket_count is 0), so the form the sweep can see is the form that is already absent and the form that is present is the form it cannot see. The same gap explains the 261 that snake-case to an existing id: written [neon_count] the sweep would have linked it, written [neon count] it is invisible. The sweep runs on the accept path (persist_reviewed_docs) and again on every rotation's reconcile, so it is not that it never ran.

No normaliser strips a link target to leave a bare bracket: the only bracket-stripping code path is that same _normalize_bare_doc_links, and it removes the brackets and the markup to leave the plain word, not a bracket.

The two answers

Must the prose rule change to spare the future-name convention? No. The convention writes [label](dd:path) or a bare dd:path, both of which the rule already masks or accepts, and no accepted document contains a dd: token at all — 0 of the 637 failures is a future-name placeholder, so nothing in this set needs the rule relaxed.

Which classes are real defects needing repair? Two: the 24 self-links (a name: link to the documented name itself, already forbidden by the prompt and dropped by the links index) and the 613 bare prose brackets (a bracketed phrase that renders as literal text, 613 of which no renaming of the catalogue can help: 261 name an existing identity the writer evidently meant to link, and the rest are phrases with no target at all). The 10 documents failing the older unsupported-target rule sit beside these and are not part of the 10: they are counted, listed above, and left outside the 637.
