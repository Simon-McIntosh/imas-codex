§1 — The future-name convention: syntax, writer, swapper, reader

The convention is a link whose target is a DD path, written so a name that does not exist yet can be cited and later repointed once it does. Four places define it:

  • Syntax. [label](dd:<dd-path>) in documentation, and dd:<path> as a value of the structured links field. The gate itself accepts the target form: _VALID_LINK_TARGET_RE (docs_gates.py:61) is (?:name:[a-z0-9_]+|#[a-z0-9_]+|dd:[a-z0-9_/]+|https?://\S+)$, and the positive control in the JSON confirms fullmatch('dd:equilibrium/...') is true while every 637 failure is not a dd: link.
  • Writer. The documentation pipeline writes it, and the schema names it: the links field is documented as "Related standard names (name:xxx or dd:path format)" (imas_codex/standard_names/models.py:1905). The docs prompts themselves never ask for it — grep -rn "dd:" imas_codex/llm/prompts/sn/ returns nothing; the cross-reference rule they carry permits only [label](name:bare_id) to a name that already exists (imas_codex/llm/prompts/sn/generate_docs_system.md:312-321: "only to a name that EXISTS — do not invent a related-name to link"). So a dd: link is an indexed-link form produced by the ingestion/generation path, not a prose form the model is told to write.
  • Swapper. resolve_links_batch (imas_codex/standard_names/graph_ops.py:9426): for each dd:<path> link it runs MATCH (n:IMASNode {id: path})-[:HAS_STANDARD_NAME]->(sn:StandardName) and replaces the link with name:<sn_id>; an unresolved path is retried (graph_ops.py:9379, _MAX_LINK_RETRIES = 5) and then marked link_status = "failed". _compute_link_status (graph_ops.py:490) names the intermediate state — a node carrying any dd: link reads "unresolved" until the swap lands.
  • Reader. _extract_links_from_docs (imas_codex/standard_names/graph_ops.py:513) reads both forms with _LINK_RE (:509) and _DD_LINK_RE (:515) and writes the order-preserving deduplicated links index on the node.

Can that syntax ever render as a bare bracketed phrase with no target? No, at any of the four stages. As authored, the dd: token always carries its target — either [label](dd:path) or a bare dd:path outside brackets entirely. As stored and as read by the rule, the whole link is masked before the prose scan runs: _masked_spans (doc_links.py:38) adds every _MARKDOWN_LINK_RE match to the spans find_prose_bracket_phrases (doc_links.py:121) skips. The bare-reference rule independently excludes a link label — _BARE_BRACKET_RE (doc_links.py:25) ends with the negative lookahead (?!\(). After normalisation _normalize_bare_doc_links (graph_ops.py:9602) only rewrites or strips bare snake_case tokens and never touches a dd: link; after export the link-pruning pass (test_export_link_pruning.py) drops internal links to unpublished targets from the links field and never edits prose. And empirically the form does not occur at all: of the 2,530 accepted documents, 0 contain the token dd: and 0 contain a (dd: link.

This is a real defect by construction: the structured links index drops a self-reference (_extract_links_from_docs, graph_ops.py:513: "a self-loop is meaningless"), and the ISNC catalog enforces UNIQUE(name, link), so a self-reference that survived reached validate_catalog and crashed it. The prompt already forbids it (generate_docs_system.md:324: "Do NOT link an entry to itself").

The rule's precision as measured

Against the concern that motivated this census — that the check might fail a legitimate future-name link — the rule's precision is 1.000: 0 of the 637 flagged documents is a dd: placeholder, and 0 is notation the exclusions should have spared. All 637 flag a construct that genuinely renders as literal [text] text (613) or is a name: self-loop (24). The rule's own exclusions are working: re-testing every flagged phrase with the rule's exclusion predicates found no unit, interval or citation among them.

Positive controls prove the instrument sees each construct before any zero is reported: the prose scanner returns ["ion density"] for a text that holds one; the gate fails a document holding a bare prose bracket and a document linking its own name; the description index holds 4,874 entries and the DD documentation corpus 40,000, so a zero phrase match is an absence and not an empty index.

§3 — Where the bare phrases came from

One writer accounts for them: the documentation generation prompt, and the accept-path normaliser that cannot see this form.

  • The writer is the docs generation LLM. imas_codex/llm/prompts/sn/generate_docs_system.md:315-321 carries the hard rule that forbids exactly this construct — "No bare brackets — every [...] MUST have a (name:bare_id) target (HARD)" — over the offending examples at :334 (captured by [radial_derivative_of_elongation_of_flux_surface].) and :316. The rule has been in the prompt since 2026-06-21 (8319cc043 fix(sn): docs cross-refs — ban bare [name] brackets and self/mismatched links), and the model writes them anyway. The refine prompt carries a weaker form of the same instruction (imas_codex/llm/prompts/sn/refine_docs_user.md:185, "preferring a [label](name:id) link").
  • The accept-path normaliser is blind to this form, which is why it survives to accepted. _normalize_bare_doc_links (imas_codex/standard_names/graph_ops.py:9602) is meant to repair exactly this defect — "each bare [snake_case] (no (name:...) target) becomes [snake_case](name:snake_case) when snake_case is a real StandardName id, else the brackets are stripped". It finds its candidates with find_name_references(..., known=None), whose bare-candidate pattern is _BARE_BRACKET_RE (doc_links.py:25) — a single snake_case token, \[([a-z][a-z0-9_]+)\], with no space allowed. All 613 phrases contain a space, so none of them is a candidate, and the sweep neither links nor strips them. The same gap explains the 261 that snake-case to an existing id: written [neon_count] the sweep would have linked it; written [neon count] it is invisible. The sweep runs on the accept path (persist_reviewed_docs) and again on every rotation's reconcile, so this is not a matter of it not having had a chance to run.

No normaliser strips a link target to leave a bare bracket: the only bracket-stripping code path is that same _normalize_bare_doc_links, and it removes the brackets and their content markup to leave the plain word, not a bracket.

The two answers

Must the prose rule change to spare the future-name convention? No. The convention writes [label](dd:path) or a bare dd:path, both of which the rule already masks or accepts, and no accepted document contains a dd: token at all — 0 of the 637 failures is a future-name placeholder, so nothing in this set needs the rule relaxed.

Which classes are real defects needing repair? Two: the 24 self-links (a name: link to the documented name itself, already forbidden by the prompt and dropped by the links index) and the 613 bare prose brackets (a bracketed phrase that renders as literal text, 261 of which name an existing identity the writer evidently meant to link). The 10 documents failing the older unsupported-target rule sit beside these and are not part of the 637.
