The fan-out proposer is told which checks opened its search

The refine fan-out fires only on a failed named check, but the trigger still returned an always-empty excerpt and the dispatcher rendered it as a comment-feedback section reading (none). The proposer was therefore asked to plan retrieval with no statement of why, and a candidate that had just failed a check was indistinguishable from one that failed none.

Route chosen, and why

The slot is filled, not removed. The deciding route's failed-check records already carry the check's criterion, the judge's reason and the field evidence that decided it, so the reasons are in hand at the refine call site and no reader of graph state is added. Removing the slot would have been the fallback only if producing them needed a new graph read.

Two functions carry it. check_results_from_failed_checks turns a route's named failures into the trigger's check-result mapping, keeping the criterion, the reason and the evidence beside the probability of 1.0 each failure already implies. failed_check_reasons renders the checks that actually fired — retrieval checks, answered, at or above the threshold — as one line each, capped at six lines of 240 characters, and only when the result carries a reason, so a caller supplying bare probabilities still gets an empty excerpt rather than a list of identifiers. The prompt section is renamed from reviewer feedback to the named checks that fired, since that is what it now carries.

The selection was the new test file, the fan-out confinement lint, every test under tests/standard_names/fanout/, and tests/standard_names/test_refine_name_chain.py, run with default markers in a separate extracted tree per arm, each with its own --basetemp. Each arm's log header records the module under test as imported (module.__file__) and the resolved working directory, so the tree a result came from is readable rather than assumed.

The declared mutation restores the always-empty excerpt by returning fire, "" from the trigger. Under it test_prompt_names_the_checks_that_fired fails while the other two pass, which is the direction that matters: the passing suite alone would not have shown that the check can see an empty slot.

What the new tests lock

tests/standard_names/test_fanout_review_feedback.py asserts that a fired trigger puts the check's identifier, its reason and its evidence into the rendered proposer prompt with no (none) left behind; that a check-free candidate keeps the empty slot and reports no failure; and that a failure which does not request retrieval never reaches the prompt, so a grammar-only failure cannot manufacture retrieval intent.
