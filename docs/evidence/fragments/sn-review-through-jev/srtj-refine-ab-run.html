Retry pass

The 29 calls that failed or answered empty on their first attempt were each retried once, which is 29 of the 240 cohort calls re-asked and none of the successful ones. The pass made 31 calls: two keys carry a third call, made by an earlier retry launch and repeated by the run that closed the pass, so the arm split is 13 calls on the comments arm and 18 on the checks arm. It cost USD 4.0787, no call was skipped for the ceiling and none exhausted its attempts. After the pass, 20 calls still answer with an empty name and 6 still raise; together they are the 26 calls that contribute no output.

A retry call is identified as a receipt line whose case and arm already have an earlier line, which is the only instrument that works here: the receipt's own attempt field cannot separate the passes, because the retry receipts were written by a launch that predates the counter and every line in the file reads attempt: 1. The two counts agree — 31 lines repeat a case and arm, and 271 lines stand 31 above the 240 calls — and the script raises if they ever part.

Retrying is only honest if the retried call is the call that was asked the first time. The pass therefore rebuilds every case from the corpus loader at the same seed and asserts that its stored critique matches the critique the original call was given, so a prompt that had drifted would stop the pass rather than be measured.

DD source context

Every sheet row carries the DD source the refined name is bound to — its path, its description and its unit — because the labeller is judging a name against the data element it names and cannot do that from the name alone.

When a corpus case carries no source path, the source is read from the graph instead: the case's ancestor name and its refined name are looked up through (StandardNameSource {id: 'dd:<path>'})-[:PRODUCED_NAME]->(StandardName), and the IMASNode reached that way supplies the description and the unit. Of the 224 names asked, 24 resolve this way.

A case whose source cannot be resolved from the case, its ancestor or its refined name contributes no row: it is dropped and counted, never shipped with a blank path. 62 of the 104 complete cases are dropped on that ground. A further 7 cases would resolve only through the other binding the graph carries, IMASNode-[:HAS_STANDARD_NAME]->StandardName; that projection is recorded in the results as a measured diagnostic and is not used: it binds a DD node to whatever name is projected onto it, which is not the provenance PRODUCED_NAME records.

The arm key, and how it is held

The key records, for each row, which case and which arm produced the output that row carries. It is built from the outputs, never from the arm loop: a row credits an arm only for the cases whose output for that arm is that row's output. A row therefore names both arms exactly when the two arms produced the same output for the case in question, which is 2 rows here, and a row that names one arm is evidence about that arm alone. Building the key from the loop instead — marking every row with both arms — would credit each arm for outputs it did not produce, which is the defect this shape removes.

Three assertions hold the key to the outputs, and the build refuses to write either file when any of them fails:

  • every output the run produced for a case and arm appears in exactly one row;
  • every credit names a case and arm whose output is that row's output;
  • the number of rows listing both arms equals the number of identical output pairs.

--check-key re-derives the population from the receipts and the graph and re-runs those three against the delivered key, so the check does not inherit the builder's mistakes. It then plants the defect the assertions exist to catch — a copy of the delivered key with one row crediting both arms for a case whose two outputs differ — and requires the check to refuse it.

Sheet check, and its negative control

The check reads the committed sheet and fails on any row carrying an unexpected field, any field that would disclose the arm or the sheet-to-case mapping, any row with a blank DD source path, and any row with a blank refined name. It then plants three rows — one carrying arm, one with a blank source_path, one with a blank refined_name — and requires the detector to refuse all three, because an over-permissive check would otherwise report a safety it does not provide.

How the delivered files were produced

The results JSON, the label sheet and the key reported here were regenerated from the receipts by the committed script in its rescore mode, which buys no call: it reads the receipt lines, sums the spend over every one of them, and rebuilds the three files. Nothing in that pass reaches the provider, so a file reported here is what the committed code makes of the committed receipts. The regeneration is rescore.log in the run directory and ends EXIT=0; the label sheet it wrote is byte-identical to the committed one, so the sheet the labeller gets is the sheet the code produces. The two checks above were then run against that regenerated state.
