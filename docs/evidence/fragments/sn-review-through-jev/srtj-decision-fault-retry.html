A failed decision call now says what failed, and a transport fault is retried whatever its message

The Jev-only dry run left four documentation items on no usable judgment, and the run's own log could not say why: the one line the batch writes for a failed item ended in an empty field, and the call layer gave that fault a single attempt. Both halves are one defect — the fault was classified by its message text, and the message was empty — so the item was neither explained nor retried.

The defect, reproduced

One failed decision call is driven through a replaced transport seam that raises an HTTP read timeout carrying an empty message (empty-fault-probe.py, run once per revision; no live call, USD 0). The base revision prints a fault label with nothing after it and takes one attempt; the change names the fault and takes the three attempts its retry budget allows.

base 5e8ea3b8e

RETRYABLE False
ATTEMPTS 1
RESULTS [None] 0.0
head f8a9be00b
DEBUG imas_codex.discovery.base.llm decisions error (attempt 1/3): ReadTimeout: ReadTimeout(''). Retrying in 0.0s...
DEBUG imas_codex.discovery.base.llm decisions error (attempt 2/3): ReadTimeout: ReadTimeout(''). Retrying in 0.0s...
WARNING imas_codex.discovery.base.judgment decision batch item 0 failed: ReadTimeout: ReadTimeout('')
RETRYABLE False
ATTEMPTS 3
RESULTS [None] 0.0

RETRYABLE is _is_retryable(""), the message-only verdict, and it reads the same in both runs — which is the point: the retry the second run takes does not come from the text. ATTEMPTS is how many times the transport seam was entered.

The change

  1. A fault's reported text is never empty. fault_text in imas_codex/discovery/base/llm.py returns the exception's message when it has one and the type name with the exception's repr when it does not. It is used at the call layer's two retry log lines, in decide_one's and decide_batch's warnings, and by _settle_call, which now records the text on the outcome beside the exception it already carried.
  2. A transport fault is retried by its type. _decisions_retryable decides the timeout, connection, read and protocol errors the HTTP client raises — plus the builtin timeout and connection errors — before it reads any message, so a fault raised bare is retried rather than taken as permanent. The transient classes are read from the client the seam itself posts with and memoised, so there is no second retry policy and no second list of names. A DecisionsValidationError is refused ahead of that test, so a contract violation keeps its single attempt even when its message happens to match a retryable pattern.

The message-only policy was not merely weak: because the honest text now names the type, "ReadTimeout" contains a retryable token by accident while "ConnectError", "ReadError" and "RemoteProtocolError" do not. Type-based classification is what makes the verdict independent of how the class happens to be spelled.

The declared negative control restores message-only retry classification: _decisions_retryable's original body, _is_retryable(str(error)) over the message alone. It scores 10 failed, 4 passed (EXIT=1, negative-control.log) against the head arm's 14 passed, and the four that still pass are the ones whose guard this node does not own: the validation refusal it preserves and the controls around it. A partial application of the same mutation — restoring the message-only test while keeping the honest fault text — failed only 4, because a type name written into the message contains a retryable token for the timeout classes by accident and none for the connection and read ones. That is why the verdict is taken on the type rather than on the words.
