A versioned record for pulled machine-map rules

This design covers the 61 signal conversion entries in the current JT-60SA maps/*.json files and the 432 machine-description bindings in machine_map.json (216 per phase). These are two rule families: signal entries may join a SignalSource and an IMASNode; machine-description bindings have an IMAS target but no corresponding SignalSource by definition. The remaining machine-map declarations stay in the hashed bundle snapshot; they are not silently cast as signal rules. An earlier 45-rule count is the magnetics file alone: the current PF, TF, and equilibrium files contribute another 16.

ExternalMapRuleRevision id (rule id + version id), source_file, source_pointer (JSON pointer), raw_rule_sha256, raw_json (canonical complete provider entry), semantic_id, name, binding_set, phase, source_group, source_array, source_role, source_location, source_rank, struct_array_entry, target_path (the signal target_path or binding dd_path), target_index, source_unit, target_unit, source_cocos, target_cocos, transformation, channel_factor, unit_factor, sign_convention, validation_state, evidence, standard_name, dd_cocos_class, source_join_state (joined, unjoined, not applicable), target_join_state (joined or unjoined), and join_reason (nullable explicit failure reason). Fields not present in one rule family are null; raw_json retains every provider field without guessing a schema translation.
ExternalMapRuleChange id (rule id + from/to version ids), change_types (one or more types below), field_changes_json (each changed field with exact old/new JSON values, including null), observed_at, and requeue_needed. One rule has one change record per comparable version transition, even if name, entry and evidence all change.

A signal revision stores channel_factor as the provider's total raw-channel sign to its target COCOS; it must not be applied once more as a COCOS class transform. dd_cocos_class is resolved from the target DD metadata, never from the rule's transformation. For magnetics/flux_loop/flux/data the intended DD class is psi_like while the current provider entries say one_like and have null source_cocos. If the selected DD version cannot supply its class, leave it unknown and fail closed for class-based interpretation; the live graph's present IMASNode does not currently carry cocos_transformation_type for this path.

Stable identity across versions

A signal selector is the facility, provider, signal kind and normalized physical channel (source_group, source_array). A machine-binding selector adds the semantic operating phase (from the maps[].name that names its binding set), source_role, source group and array, and normalized struct_array_entry. An FLn-FLm pair is canonicalized to the unordered pair solely for identity; the original order remains in the revision because it affects orientation. Neither name/semantic_id, binding-set grouping, JSON file, DD target, nor sign participates in the key. These selectors are unique within the current 61 signal entries and 432 bindings. If a physical locator itself changes, require a verified old-selector → new-selector alias and attach it to the same rule; an ambiguous match blocks that rule's pull rather than minting an unreviewed identity or merging two rules.

The transition is one change record containing name, ordered entry and evidence differences, not one deletion and one addition. Only compare families covered completely by both states. An archived machine_map.json without all four maps/*.json files cannot prove absent signal rules were removed. The provider's release command excludes superseded/ and source/ from its OCI artifact; a local archive's label and hashed files therefore form an observation, not an invented registry release. A repeat pull with the same file hashes adds no revision, change or re-queue receipt.

Re-queue and evidence rule

On first observation or a new comparable revision, re-queue each SignalSource joined by the old or new revision when any provider field, source join or target join changed. This includes added and removed rules, a rename, grouping/file move, sign, unit or target correction, validation-state change, and evidence edit; pulled_at and version bookkeeping alone do not qualify. A source whose settled convention or binding used the prior revision gets a followup when the new external evidence disagrees; never overwrite that judgment. Keep an unjoined rule and its reason in the graph, and queue its newly matched source if a later explicit alias resolves the join. A machine binding can re-queue a source only through a recorded dependency on that binding; do not fan its change out to every source sharing an IMAS target. The current flux-loop sign disagreement is retained as competing evidence, not adjudicated by the pull.
