The admission this node added, and the refusals it kept

The new case is decided on two graph-readable facts: the two ids are one quantity under the two locator vocabularies (_at_separatrix and _at_plasma_boundary strip to the same head), and no live successor other than the renaming name sits at a DD container the renaming name occupies. When the lineage has no live tip at all, the case is admitted only if at least one descendant still records the quantity, so an archive with no holder is written for a quantity the lineage proves existed; a tombstone with neither a live tip nor a descendant is still refused.

The three pre-existing routes are untouched and their refusals still hold. Why the fourth was refused, and the repair that unblocked it

toroidal_lithium_velocity_at_separatrix is bound to two DD paths: summary/local/separatrix/velocity_phi/lithium/value, which is live and composed, and summary/local/separatrix/velocity_tor/lithium/value, whose IMAS node carries lifecycle_status = 'removed' in the current data dictionary and whose source row therefore carries status = 'stale'. The rename migrates the name's whole authoritative source cohort, and the cohort's compare-and-set refuses a stale binding:

RuntimeError: source migration compare-and-set failed:
dd:summary/local/separatrix/velocity_tor/lithium/value
(exists=True, status='stale', claimed=False,
 bindings=['toroidal_lithium_velocity_at_separatrix'],
 scalar='toroidal_lithium_velocity_at_separatrix')

The refusal is correct about the binding and wrong about the rename: a stale source can never satisfy the compare-and-set, so leaving it in the cohort refuses every future rename of its live name, not only this one. The repair is to keep it out of the migration while leaving it recorded: a source whose data-dictionary path is removed is excluded from the cohort the rename migrates and from the cohort it verifies, keeps its status = 'stale' and its PRODUCED_NAME edge to the retired spelling, and is named in the successor's stale_source_ids and in the rename receipt. Every live binding still migrates under the same compare-and-set on the same manifest, and a name with no live binding at all is still refused, because a live name must be produced by a live source.

The other route, sn detach of the removed path, was dry-run and would rewind the stale source to extracted for re-composition, putting a source for a DD path that no longer exists back into the compose queue and dropping the name's source_paths entry for it. That is a graph-state regression dressed as a repair, so it was not taken.
