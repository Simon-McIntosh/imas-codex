Serving the ISN 0.10.1 grammar from the graph

The graph now serves the 0.10.1 grammar. The shared environment's imas_standard_names moved from 0.10.0 to 0.10.1, the grammar was synced through sync_isn_grammar_to_graph(), and the readback shows exactly one active ISNGrammarVersion — 0.10.1 — with a token count of 983, not below the previous active version's, and the physical_base token separatrix_distance present for it.

The first step of this node was refused inside the worker's write fence (the rebuild of an editable install's metadata writes the shared virtualenv and the sibling ISN checkout, both mounted read-only here), so it was run from the coordinator's own unfenced shell and the result handed back. That history is recorded below because the fence refusal is the interesting part of the node: the sync itself is a few seconds of ordinary work, and the ordering constraint on it — do not sync while the version still reads 0.10.0 — is what made the refusal matter.

The defect, and why the sync had to wait

Before the metadata rebuild the environment was internally inconsistent. Its resolved package was the editable sibling checkout at tag v0.10.1 (4c59393cb111f5f257570f6eb3e9c7e037cb2747), yet the version it reported was 0.10.0: 

imas_standard_names.__version__  0.10.0
imas_standard_names.__file__     /home/ITER/mcintos/Code/imas-standard-names/imas_standard_names/__init__.py

The gap is structural. __version__ is importlib.metadata.version("imas-standard-names") (imas_standard_names/__init__.py, lines 16–22) — it reads the installed distribution's frozen dist-info, not the checkout's tag. site-packages/imas_standard_names-0.10.0.dist-info/METADATA carried Version: 0.10.0 while the source it pointed at was already 0.10.1.

sync_isn_grammar_to_graph binds from imas_standard_names import __version__ as isn_version and passes it as the target version (imas_codex/standard_names/grammar_sync.py, lines 288 and 323). A sync run in that state would have filed the 0.10.1 grammar under the 0.10.0 label. The sync was therefore withheld until the version read correctly, which is the whole reason the fence refusal was a blocker rather than an inconvenience.

Before: the graph served 0.10.0, on stale content

A bounded read-only probe (grammar-state-probe.py in the run directory) enumerated the version nodes, with property controls first, so that no absence would be read from an empty graph: the query is shown to see a populated graph before any negative is taken from it — count(v:ISNGrammarVersion) is 123 and count(t:GrammarToken) is 81102. Exactly one version was active, 0.10.0, with 983 tokens and 22 segments. The separatrix_distance physical_base token already existed for 0.10.0: the base arrived with 0.10.0, and 0.10.1's change is the midplane wording, not the base.

The content was stale even though the version count looked settled. The installed package's content digest and the graph's active digest differed, which is exactly the condition the startup freshness check reads:

_auto_sync_grammar in imas_codex/cli/sn.py compares the active node's content_digest against grammar_content_digest() and syncs when they differ (lines 1369–1382). The digests differed, so the next sn run would have triggered the automatic sync — and with the version still reading 0.10.0, that automatic run is precisely the wrong-label write the ordering constraint above prevents. This is why the sync was not run by hand while the environment was unfixed: writing the wrong label into the shared graph would have been worse than leaving the mismatch, because the mismatch at least self-corrects once the version is right.

The metadata rebuild, and the write fence

The rebuild the brief names is:

Run from inside this worker it exits 1. The editable build runs the ISN package's hatch hook, which regenerates the grammar models and writes them back into the sibling source tree; the write is refused: 

OSError: [Errno 30] Read-only file system:
  '/home/ITER/mcintos/Code/imas-standard-names/imas_standard_names/grammar/model_types.py'

The refusal is the write fence, not the repository. Process id 1 in this worker's namespace is bwrap, and the sandbox's read-write bind set is exactly the run directory, the session scratch directory, the worktree, and the git object store:

Each of the four done-when conditions holds. Exactly one version is active and it is 0.10.1. Its token count 983 is not below the previous active version's 983. That figure sits above both numbers the brief names for comparison — the 956-token merge figure and the 781 floor — so the physical-base merge has not regressed; the count is unchanged from 0.10.0, which is what a wording change should produce, since the tokens themselves did not move. And separatrix_distance exists as a physical_base token for 0.10.1, distinct from the 0.10.0 node that was already there.

The 0.10.1 midplane locus definitions

The graph holds no locus prose — a search for any node carrying a definition-like property returns no rows, against the same populated-graph control above — so the definitions are quoted from imas_standard_names, the editable sibling at tag v0.10.1. The registry states the maximum-major-radius definition for both the general and separatrix outboard loci (grammar/vocabularies/locus_registry.yml, lines 676–689):

outboard_midplane (type position, relations at/of): “The low-field-side equatorial midplane: the point of maximum major radius on the flux surface in question. For a value at the separatrix intersection use outboard_midplane_separatrix.”

outboard_midplane_separatrix (type position, relations at/of): “The point where the separatrix reaches its maximum major radius, on the low-field side. A separatrix point value at the outboard midplane is evaluated here.”

inboard_midplane (type position, relations at/of): “The high-field-side equatorial midplane: the point of minimum major radius on the flux surface in question.”

The same definition is carried as an equation in the concept registry (grammar/vocabularies/conventions/concepts.yml, lines 422–440), which is the wording the docs writer restates:

outboard_midplane: phrase “outboard midplane”, equation R = \max_{S} R,\quad R > R_{\mathrm{axis}}, where S is the magnetic flux surface the point lies on and R_{\mathrm{axis}} the major radius of the magnetic axis.

inboard_midplane: phrase “inboard midplane”, equation R = \min_{S} R,\quad R < R_{\mathrm{axis}}.

Both halves state the maximum-major-radius (outboard) and minimum-major-radius (inboard) definition, and neither names a data dictionary field, an IDS path or an option value — the physics-terms rule the upstream change was made to satisfy.

What this node did not do

The node changed no code and no plan state; its only written artifact is this fragment. The metadata rebuild was performed outside the worker because the fence refuses it — that refusal, not the sync, is the node's interesting finding, and it is the follow-on below. The graph write is a normal sync: it added one version node (0.10.1), its segments, tokens and templates, and rotated the single active flag from 0.10.0 to 0.10.1; the 0.10.0 node and its tokens remain in the graph and are not deleted by a sync.
