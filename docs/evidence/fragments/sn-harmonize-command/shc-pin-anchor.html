The anchor a run chose is kept until its family is stamped

A family's apply resets its anchor first, so an interrupted run leaves that anchor mid-pipeline with a null documentation score. A plan re-derived in that window would rank the members afresh and pick a different member, discarding the one the run already started on. The anchor is now recorded on the family's own run state and reused until the family is stamped harmonized.

Where it is recorded

The anchor rides the member nodes that already carry the family's run state — the same nodes stamped with run_id by reset_standard_name_docs and with harmonized_group_signature by stamp_harmonized_families. No second store is introduced. harmonize.py adds two helpers over that property:

  • _record_family_anchor(gc, member_ids, anchor_id) sets sn.harmonized_anchor on every member. It is called from apply_families for each family marked apply before that family's first batch is drained, so the recorded anchor precedes any reset the run performs.
  • pinned_family_anchor(members, force=False) reads it back. The family read carries the column: _family_member_collect in families.py now selects m.harmonized_anchor alongside harmonized_group_signature.

When it is reused, and when it is released

plan_family_applies selects its anchor with select_anchor, then, for any family not already carrying the current harmonized_group_signature, replaces that choice with the recorded anchor when one exists and is still a live member. So a family mid-run keeps the anchor the run started on even when a second member is accepted and outscores it.

The anchor is released in the same step that stamps the family: _stamp_applied_family calls _clear_family_anchor(gc, member_ids) once stamp_harmonized_families reports success, removing the property. A later apply over that family therefore selects normally. A forced apply does the same — apply_families passes force=True to its own plan_family_applies when a force reason is given, and pinned_family_anchor returns None under force, so a fresh choice is made.

The report's name-id read follows the same owner

The dead-link test resolves a link target against every name the graph holds, not against the scoped members alone. harmonize.py no longer defines its own name-id query: known_name_ids(gc) reads through families.existing_name_ids when a client is in hand, and with no client it calls the owner directly — graph_ops.get_existing_standard_names(). Neither path falls back to the scope, so a report invoked without a client still counts an out-of-scope link to a name the graph holds as live.
