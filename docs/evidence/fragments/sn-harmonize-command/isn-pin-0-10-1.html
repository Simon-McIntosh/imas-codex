imas-codex pins the released IMAS Standard Names 0.10.1

Both imas-standard-names pins in pyproject.toml now read ==0.10.1: the one in [build-system] requires and the one in the serve extra of [project.optional-dependencies]. No other dependency moved. grep -c 'imas-standard-names==0.10.1' pyproject.toml prints 2 and grep -c 'imas-standard-names==0.10.0' prints 0. The released tag is the upstream v0.10.1, the single midplane definition taken by maximum major radius on each flux surface.

The lock is byte-identical after regeneration

uv.lock records no version for this package at all, so the pin bump cannot reach it. [tool.uv.sources] points imas-standard-names at the sibling editable checkout, and uv records that source in place of a version specifier — the metadata row reads { name = "imas-standard-names", editable = "../imas-standard-names" } and the package entry carries source = { editable = ... } with no version line. The string 0.10.0 does not occur anywhere in the lock, and neither does 0.10.1.

Regenerating the lock against the bumped pyproject.toml produced a file with sha256 5d6d2e0bcec967a55e7372f2ffd6b8412c603e7393596844b73f1960f404629d — the same digest as the committed uv.lock. The change is therefore one file, not two: git diff --stat shows pyproject.toml | 4 ++-- alone. The brief anticipated that the lock records the path rather than a version and required the override to be left in place; this is that expectation carried to its conclusion.

How the lock was regenerated from a worktree

uv lock run in this worktree fails before resolving: Failed to generate package metadata for imas-standard-names @ editable+../imas-standard-names ... Distribution not found at <worktree-parent>/imas-standard-names. The relative source path resolves against the project root, and the sibling exists only beside the main checkout at ~/Code/imas-standard-names. The fence refuses the symlink that would bridge it, so the regeneration ran in a scratch project under $TMPDIR: a directory holding a copy of the edited pyproject.toml and the committed uv.lock, with ../imas-standard-names pointing at the real checkout (which is at v0.10.1). The relative path uv writes into a lock is the same string in either root, which is why the two files compare byte for byte.

The lock check was shown able to fail

uv lock --check exits 0 against the bumped pyproject.toml. That result is only worth quoting once the instrument has been seen to refuse, so two controls were run in the same scratch arrangement:

  • A synthetic project whose idna requirement is tightened after its lock is written. uv lock --check exits 1 and prints The lockfile at `uv.lock` needs to be updated, but `--check` was provided. A stale lock is therefore reported, not passed through.
  • The pinned requirement restored to ==0.10.0 against the same unchanged lock. The check still exits 0. The check cannot witness this pin either way, which is the whole reason the lock digest above is the evidence rather than the exit status.
