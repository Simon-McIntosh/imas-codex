Why a family-scoped harmonize apply redrafted two names outside its family

The apply sn harmonize --family electrostatic_potential --apply --cost-limit 3.59 ran one family batch through the ordinary documentation pools. That drain reaches run_sn_pools, which runs the graph-wide DD-source-drift refresh. The refresh is not family-scoped, its steering is not family-scoped, and the run id it hands back is attached to every name it steers, so the names it steered were claimed by the family's own drain and regenerated under the family's cost ceiling. Twelve model calls, all charging to $0.59457 of the family's $3.59, went to electron_temperature_at_separatrix and gap_at_outboard_midplane; the family's one member did not move (0.849 before and after, apply log lines 2862–2867).

1. Why the family scope does not bind the refresh

The call path, read from the worktree source (base 20a162d65):

  1. sn harmonize --apply calls apply_families(…) with the family plan (imas_codex/cli/sn.py:6240).
  2. apply_families runs CampaignRunner.run(…, drain_fn=family_drain, batch_plan=fam_plan["batches"]) (imas_codex/standard_names/harmonize.py:1776–1782); the runner calls the drain per batch as drain_fn(run_id, self.budget.per_batch_cost_cap) (imas_codex/standard_names/campaign.py:1026–1032).
  3. The drain is _docs_drain_factory's inner _drain, which issues a docs-only flush carrying the batch's run id: _run_sn_cmd(…, skip_generate=True, docs_only=True, flush=True, source="dd", scope_run_id=run_id, …) (imas_codex/cli/sn.py:815–843).
  4. That flush runs run_sn_pools, which calls the refresh before any pool: sr = await _global_maintenance_call(refresh_drifted_sources, scope_run_id=run_id, default={}) (imas_codex/standard_names/loop.py:2064–2068, refresh_drifted_sources at line 2065 and scope_run_id=run_id at line 2066). Only the run id is passed. No target set, no name list, no family filter.
  5. refresh_drifted_sources(*, dry_run=False, include_accepted=True, scope_run_id=None, gc=None) (imas_codex/standard_names/source_refresh.py:334) calls detect_source_drift(include_accepted=…) (line 361), whose signature has no id or family parameter at all (line 157) and whose query scans every (src:StandardNameSource)-[:PRODUCED_NAME]->(sn:StandardName) row with sn.name_stage <> 'superseded' AND sn.source_path IS NOT NULL (lines 179–197), ORDER BY sn.id — the whole graph.
  6. For each drifted name that needs steering, the refresh attaches it to the drain's run id: MATCH (sn:StandardName {id: $id}) SET sn.run_id = $scope_run_id, sn.updated_at = datetime() (imas_codex/standard_names/source_refresh.py:413–421, the SET sn.run_id = $scope_run_id at line 417). The docs pools then claim only names whose sn.run_id matches the scope (imas_codex/standard_names/graph_ops.py:16178, 18421, 26332: AND sn.run_id = $scope_run_id). So the attach is exactly what grants the pool access to the two outsiders.
  7. The batch's measured spend is charged to the family ceiling: _family_budget_drain gives each batch min(batch_cost_cap, ceiling - spent) and accumulates spent += float(cost) (imas_codex/standard_names/harmonize.py:1638–1679), with the ceiling set from the CLI's --cost-limit (imas_codex/cli/sn.py, per_batch_cost_cap=cost_limit and campaign_cost_ceiling=cost_limit). The runners' per-name accounting is the receipt: {"calls_total": 12, "per_name_usd": {"electron_temperature_at_separatrix": 0.256174, "gap_at_outboard_midplane": 0.338396}, "spend_usd": 0.59457} (runner-pipeline.log).

The missing argument is a target scope: neither refresh_drifted_sources nor detect_source_drift accepts an sn_ids (or family) filter, although the sibling stamp_source_snapshots(sn_ids=None, *, only_unstamped=False, gc=None) does (source_refresh.py:71–72). scope_run_id is not a restriction — it is the opposite: it is the mechanism that pulls an outsider into the family's drain.

2. Why these two names, and from what

Both names' deltas survive on the graph in sn.edit_reason, written by apply_edit at the moment of steering. Read back per name (read-only, bounded to the one id):

gap_at_outboard_midplane

  • Persisted reason (verbatim): “DD source drift — the anchoring Data Dictionary path changed (path renamed: ‘langmuir_probes/embedded/distance_separatrix_midplane’ → ‘summary/boundary/distance_inner_outer_separatrices/value’; documentation: ‘Distance between the measurement position and the separatrix, mapped along flux surfaces to the outboard midplane, in the major radius direction. Positive value…’ → ‘Value’; raw_documentation: ‘…’ → ‘Value’)”.
  • Stored snapshot compared against: source_path now summary/boundary/distance_inner_outer_separatrices/value, source_unit m, source_documentation Value, marker resolved-dd-context, manifest digest sha256:02dd37c7…4361d, resolution ids []. Its producing source was composed 2026-07-23 (src.composed_at), and its docs were last regenerated on 2026-10-20 (the sibling fragment shc-gap-docs-regen, run sn-edit-20261020T205652Z).
  • What changed: the name's anchoring DD path moved from langmuir_probes/embedded/distance_separatrix_midplane to summary/boundary/distance_inner_outer_separatrices/value, and the live node's documentation collapsed from the long flux-surface sentence to Value. This is a real source change — the midplane-release re-anchor — not a missing stamp.
  • Not a per-run re-fire: the refresh re-stamps after steering (source_refresh.py:422–423, “Re-stamp so this exact change is not re-detected next run”), and the name's sn.updated_at moved to 2026-10-22T18:43:15.931Z when its own docs accept landed. It is no longer among the drifted set (see §3).

electron_temperature_at_separatrix

  • Persisted reason (verbatim): “DD source drift — the anchoring Data Dictionary path changed (path renamed: ‘summary/local/separatrix_average/t_e/value’ → ‘summary/local/separatrix/t_e/value’)”.
  • Stored snapshot compared against: source_path summary/local/separatrix/t_e/value, unit eV, documentation Value, marker resolved-dd-context, same manifest digest, resolution ids []; its source was composed 2026-10-20.
  • What changed: the snapshot named the pre-rename leaf summary/local/separatrix_average/t_e/value while the live source had already settled at summary/local/separatrix/t_e/value. Again a real DD path change; the snapshot was simply behind it.
  • Not a re-fire: re-stamped by the refresh, then rewritten to 2026-10-22T18:40:35.122Z by its docs accept; it is not in the restamped window of §3.

No RENAMED_TO edge was traversed for either name. The readback's resolved-path field is None for both, i.e. the source's source_id is its own terminal node with no outgoing RENAMED_TO lineage, so _repoint_source (source_refresh.py:321–331, which requires a RENAMED_TO*1..12 path) was a silent no-op on both. The word “renamed” in both reasons is cosmetic: _format_reason renders the label "path renamed" for any source_path delta (source_refresh.py:311: label = "path renamed" if d["field"] == "source_path" else d["field"]). The log line “80 name(s) drifted (2 renamed)” (apply log line 58) counts those same two path deltas; the refresh's renamed/RENAMED_TO sense is a different quantity.

3. The 80: classes, counts, and why only two steered

The refresh's re-stamp writes each drifted name with sn.updated_at = datetime() one id at a time, so they cluster in a single second. A bounded window scan (sn.updated_at ≥ 2026-10-22T18:35:40 AND < 18:35:45) enumerates them. Grouping by name (three names carry more than one producing source, so the raw row count is 81) yields 78 distinct names — the two steered names sit outside the window because their own docs accepts rewrote updated_at later (18:40:35Z, 18:43:15Z). 78 + 2 = 80, matching the log exactly (line 58, line 141).

The 80 names the refresh reported, classified by cause. The detector sets requires_steering from content fields only (source_path, units, documentation; source_refresh.py:280–283), so a class is decided by whether the delta touches a content field.

The 78 share one fingerprint: source_dd_resolution_marker = 'resolved-dd-context' with size(source_dd_resolution_ids) = 0 and the identical manifest digest sha256:02dd37c7…4361d. Their producing sources were composed overwhelmingly on 2026-10-19 (the marker/digest provenance fields post-date some of those snapshots, which is what the refresh's first pass after the fields were introduced is clearing out). 77 of the 78 are name_stage='exhausted', against 150 of 2466 in the live population — the provenance-only class is concentrated in names the documentation pipeline had already exhausted, i.e. names an earlier regeneration wrote without touching source_*.

How many would be steered next run: 0. The proof is a read-only re-run of the detector itself at the current head — detect_source_drift(gc=gc), which stamps nothing:

The single remaining drifted name is not one of the 80, so none of the 80 would be steered again: the 2 were re-stamped after steering and the 78 were re-stamped as provenance-only. The reason only two steered on this run is the same property: the 80 were partitioned by content, and only 2 had a content delta.

Two adjacent populations the detector cannot see (counted read-only, both excluded from the 80 and from the next-run receipt):

  • 46 names carry source_dd_resolution_marker IS NULL and their source's source_id is the name's own id, not a DD path, so detect_source_drift's inner MATCH (o:IMASNode {id: src.source_id}) (source_refresh.py:180) matches nothing and the row is silently skipped — a missing node returns zero rows, not an error.
  • 3 names have more than one producing StandardNameSource; the resolver collapses them with head(collect(n)) (source_refresh.py:39), so which source is compared is arbitrary and only one of them is re-anchored.

Confirmed defects and their fixes

  1. Family apply leaks a graph-wide refresh. Thread a target scope through the docs drain so refresh_drifted_sources and detect_source_drift accept an sn_ids filter (as stamp_source_snapshots already does) and have _docs_drain_factory pass the batch's member ids, so a family-scoped apply can only steer its own members.
  2. “path renamed” mislabels every path delta. In _format_reason, label a source_path delta “source path changed” and reserve “renamed” for the case where the refresh actually followed a RENAMED_TO edge, since a stale-snapshot path delta is the common case and is not a rename.
  3. Docs regeneration never re-stamps the source snapshot. When the docs pools rewrite a name, have them re-stamp its source_* snapshot too, so a real source re-anchor that landed before the regeneration is not deferred to the next global refresh (78 of the 80 were exactly this backlog).
  4. 46 source-linked names are invisible to the detector. Make the drift query left-join the IMASNode (or assert src.source_id before the refresh) so a source that does not resolve is reported rather than silently skipped.
  5. Multi-source names are compared against one arbitrary source. Compare every producing source of a name in detect_source_drift instead of collapsing with head(collect(n)), and re-anchor each renamed source.
