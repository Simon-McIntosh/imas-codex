A scoped docs reset stamps its batch even when it resets nothing

The defect, reproduced before repair

reset_standard_name_docs counted its eligible names and returned at once when the count was zero. That return preceded the query that binds the batch to the run id, so a harmonize anchor already at docs_stage = 'pending' reset nothing and stayed bound only to whatever run had left it there. The scoped generate-docs claim then matched no node, and the convergence gate halted the family after zero calls — the eligibility diagnosis measured exactly this on electrostatic_potential.

The reset and the scope stamp answer two different questions, so only the reset is gated on eligibility now. A scoped call stamps its batch whenever a run id is set, whatever the reset count; an unscoped call still writes nothing; reset carries a default so the no-reset path reports a number rather than indexing an unbound result. The reset query, the stamp query and the empty-input guard are unchanged.

The tests, and the control

Three tests in tests/standard_names/test_docs_reset_scope_stamp.py run against the package's disposable Neo4j instance. A scoped reset over two names already at docs_stage = 'pending' reports {"eligible": 0, "reset": 0}, both nodes carry the run id, and claim_generate_docs_batch(scope_run_id=...) returns both. An unscoped reset over the same names returns the same zero result and leaves their carried run id untouched. A scoped reset over an eligible name still snapshots a revision, resets the stage and binds the run.

The control restores the early return before the scope stamp and keeps its own run. test_scoped_reset_stamps_names_that_need_no_reset fails there and the other two pass, so the check is aimed at the early return rather than at the surrounding machinery: 1 failed, 2 passed, EXIT=1.
