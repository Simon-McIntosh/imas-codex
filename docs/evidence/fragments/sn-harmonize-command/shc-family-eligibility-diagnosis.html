Why the electrostatic-potential family yields no harmonize work

Every member of the non-WEST locus family electrostatic_potential was read against the predicates the harmonize apply passes on its way to the docs pools, read-only on the live graph. The family holds five members and its anchor is genuinely docs-eligible — name_stage = 'accepted', docs_stage = 'pending', reviewer_score_name = 0.99375, an unclaimed node with a composed source — yet the apply made zero LLM calls and moved nothing.

The cause is (a), a predicate that wrongly excludes an eligible member. The anchor batch contains exactly one name and that name is already at docs_stage = 'pending', so reset_standard_name_docs counts zero eligible, returns at graph_docs_persistence.py:410, and never reaches its own scope-stamping query at lines 418-423 — the query written precisely to bind an already-pending name to the run's scope. The drain then claims with AND sn.run_id = $scope_run_id against a uuid no node carries, and claims nothing.

The chain, and where it stops

  1. Family enumeration — families.py:1098, the only stage filter on a family member (coalesce(m.name_stage, '') <> $superseded). Admits the invariant family ('electrostatic_potential','','','','') with n = 5. Members at name_stage = 'reviewed' are admitted here and only surface as ineligible at the claim.
  2. Anchor selection — select_anchor would pick floating_electrostatic_potential (accepted, reviewer_score_docs = 0.9375, the highest in the family). resolve_family_anchor (harmonize.py:940-943) instead overrides it with the recorded harmonized_anchor pin, which all five members carry as electrostatic_potential_at_langmuir_probe_position. The stamp that releases the pin is only written on convergence, so a family that cannot converge never reranks — the pin and the failure reinforce each other.
  3. Anchor batch — anchor_gated_batches places the anchor alone in batch 1 (campaign.py:1026-1032); the other four members wait in batch 2.
  4. Reset and scope binding — reset_standard_name_docs (graph_docs_persistence.py:406-423). This is the stop. Its eligibility requires docs_stage IN ['accepted','exhausted','reviewed','drafted']; the anchor is pending, so eligible = 0 and the function returns at line 410. The scope-stamp query at lines 418-423, whose predicate does match the anchor (accepted + pending), is never issued.
  5. generate_docs claim — graph_docs_persistence.py:53-56 carries no scope clause of its own; the claim layer ANDs AND sn.run_id = $scope_run_id (graph_cost_and_claims.py:329, wired from loop.py:771-773). With the fresh uuid never stamped, the claim matches nothing.
  6. review_docs claim — graph_review_persistence.py:688-694 requires docs_stage = 'drafted' plus the same scope clause. Nothing can be drafted, so this pool is idle.
  7. Scoped name set — _scope_name_ids (loop.py:331-393) reads sn.run_id = $rid or a StandardNameSource.run_id = $rid producing edge. For a fresh uuid it returns 0 ids; for each member's own carried run id it returns exactly that member. The read is sound — it is empty because nothing was bound.
  8. Convergence gate — campaign.py:1098-1103 halts the family on the first non-converged batch, so batch 2 is never marked or drained.

An earlier harmonize had also reset this name from docs_stage = 'accepted' at reviewer_score_docs = 0.9437, and that reset is what makes the strand permanent: this apply refuses to regenerate it because it is already pending, and the early return is the reason it is also unbound. The family's strongest member is held by the same predicate twice over.

Classification

(a) a predicate that wrongly excludes an eligible member. The anchor satisfies every substantive eligibility condition — name_stage = 'accepted', docs_stage = 'pending', reviewer_score_name = 0.99375, validation_status = 'valid', unclaimed, with a composed producing source — and it passes the generate_docs claim outright when the scope clause is not applied (docs_claim_core matches it). It is unclaimable only because AND sn.run_id = $scope_run_id is checked against a uuid that mark_members_for_regen minted (harmonize.py:703-709 returns one unconditionally) and that no node ever received.

The other four members are not the cause of the zero-call drain, but they set the family's ceiling. ..._at_outboard_midplane and ..._at_wall are at name_stage = 'reviewed', so no docs pool can claim them until name-axis work completes. electrostatic_potential (0.849) and floating_electrostatic_potential (0.9375, and the family's best docs score) sit at stages the reset step accepts, so both would be recovered by batch 2. Only the anchor is blocked at batch 1 by the defect; the other four are simply starved by the halt. This is a property of the family, not a second defect, and it does not make the family the wrong choice under (b): its anchor is eligible and four of five members are recoverable once the anchor batch drains.

What a fix needs

One change, in imas_codex/standard_names/graph_store/graph_docs_persistence.py, in reset_standard_name_docs. The early return at line 410 conflates two different outcomes — "nothing to reset" and "nothing to stamp" — and the scope stamp is the second, in scope for a scoped run regardless of the first. Split it, and give reset a default so line 424 no longer indexes an unbound result: 

        if dry_run:
            return {"eligible": eligible, "reset": 0}
        reset = 0
        if eligible:
            result = gc.query(
                eligibility + "…",          # unchanged
                sn_ids=sn_ids,
                run_id=run_id,
            )
            reset = result[0]["reset"] if result else 0
        if run_id:
            gc.query(
                "…AND coalesce(sn.docs_stage, 'pending') = 'pending'…",   # unchanged
                sn_ids=sn_ids,
                run_id=run_id,
            )
    logger.info(
        "reset_standard_name_docs: %d/%d reset to docs pending (run_id=%s)",
        reset, len(sn_ids), run_id,
    )
    return {"eligible": eligible, "reset": reset}

Nothing else moves: the reset query, the stamp query and the empty-sn_ids guard are all unchanged. The docstring at lines 391-392 ("names already pending … are skipped — they regenerate anyway") stays true for the reset count and becomes true under a scope only because the stamp now runs. A scoped run with zero reset names is exactly the anchor-batch case this node measured.

The test that would fail without the fix. Add test_reset_stamps_scope_on_an_already_pending_name in tests/standard_names/test_docs_revision_snapshots.py, beside the existing test_empty_reset_is_a_graph_free_no_op. Its fake graph answers {"eligible": 0} to the count query and records every Cypher string it is asked to run; the test asserts the stamp query (coalesce(sn.docs_stage, 'pending') = 'pending') is issued with params["run_id"] == "scoped-docs-refresh". It fails today at line 411, before that query is reached. The existing _CollisionGraph already asserts the same invariant on the eligible = 1 path (lines 135-137), so the new case is its eligible = 0 twin and needs no new harness.

Consequence for the convergence measure

This family stays the right choice for the locus arm. Its anchor is eligible, four of five members are recoverable once the drain works, and the failure is a defect in shared machinery rather than a property of the family, so fixing it should be measured on the same family the defect was found on. With the fix, batch 1 would stamp and drain the anchor (one docs generation + one docs review), then batch 2 would reset and drain electrostatic_potential and floating_electrostatic_potential. The two name_stage = 'reviewed' members remain outside a docs drain until name-axis review completes, so the family's docs convergence should be read as a measure over its reclaimable members, not as an all-five stamp. That arithmetic belongs to the convergence node; this node records only which members a working drain would reach.

How this was measured

Every predicate above was transcribed into docs/evidence/fragments/sn-harmonize-command/shc-family-eligibility-diagnosis-run.py and each transcription is asserted present in the function's own source via inspect.getsource before the query runs, so a predicate cannot drift from the code it claims to measure; all seven verified true on this run. The scoped claim carries a positive control: the same query matches the anchor under the run id the node already carries, and matches nothing under the fresh uuid — so the empty result is the binding, not a malformed query. The run opened the graph read-only, issued no write, made no LLM call and spent nothing; those guards are recorded in the JSON beside the per-member results.
