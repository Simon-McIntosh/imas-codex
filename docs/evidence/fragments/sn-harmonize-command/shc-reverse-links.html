A harmonize apply leaves no sibling link without its reverse

A name's links are not authored; they are derived from its documentation, and each member's documentation is regenerated from its own prompt in which the family's sibling block is one of many inputs. The contract that produces the asymmetry is the generation prompt's family rule — "Cross-link the family … link the parent and at least one adjacent sibling inline where the prose supports it" (imas_codex/llm/prompts/sn/generate_docs_user.md, rule 3). Each member satisfies it on its own, choosing a sibling its own prose supports, and two members need not choose each other. Nothing in the apply then closes the loop: the per-member regeneration is what created the asymmetry, and it ran again for each member.

The twelve live findings and what wrote each one-way link

Reproduced against the live graph on the boundary-averaged density family (17 members, all flux_surface_averaged_*_density_at_plasma_boundary, anchor flux_surface_averaged_tritium_density_at_plasma_boundary) by reading each member's links and running the audit function itself, run_link_integrity in imas_codex/standard_names/review/audits.py: missing_reverse count = 12. Every one is the same shape — the source's regenerated documentation rendered a name: reference to a sibling, and the linked sibling's own regeneration chose a different adjacent sibling, so the reverse is absent. The source wrote the link; the target never wrote it back.

The writer used, and why no second one was added

During an apply the field that carries links is persist_generated_docs (imas_codex/standard_names/graph_ops.py, called from workers.py), which derives them with _extract_links_from_docs(documentation, self_name=sn_id). It is the wrong writer for this step: it requires a live claim_token and sets docs_stage='drafted', which would reopen the documentation the apply had just converged.

The step therefore calls write_enrichment_results from harmonize.py — the graph_ops function whose stated job is exactly these fields (description, documentation, links, validity_domain, constraints), with the same _compute_link_status derivation the pipeline uses, claim-free, and leaving docs_stage alone. graph_ops.py is not edited and no second writer is introduced; the members' current description, validity_domain and constraints are passed through unchanged, so only documentation and links move. Clearing review_input_hash, which that writer does, is correct here: the documentation changed, so a stored review hash is stale.

reconcile_family_reverse_links in imas_codex/standard_names/harmonize.py runs in apply_families once a family's members converge and before _stamp_applied_family, so the stamped harmonized_group_signature covers the reconciled documentation. It adds the reverse of every sibling link the family holds, and removes a link only when no name in the catalog carries its target — so no reverse could ever exist for it. A name: link to a live name outside the family is a legitimate cross-family reference and is kept, in the index and in the prose: the step reconciles the sibling relation, it does not police the rest of a member's references. A reverse is likewise added only between siblings — a reference to a name outside the family is never made reciprocal, because the two are not siblings and no such relation is being asserted. A dd: path or an external URL carries no standard-name target and is untouched. An added link is written into the member's documentation as well as its derived index: the index is derived from the prose, so an index edited alone would lose the addition at the next derivation. Nothing is written when the family's links are already symmetric.

Two removals were considered and one was rejected. Removing a name: link whose target is merely outside the family looks tidy and is wrong: members legitimately carry cross-family references (name:poloidal_magnetic_flux, name:volume_averaged_*_density), and a rule of that shape deletes them from every member the apply touches. A link is removed only when it is impossible, never when it is merely inconvenient to reconcile.

A member the catalog has edited is not written — and its row is not handed to the writer either. write_enrichment_results runs filter_protected with protection in force, and that function does not skip a protected name: it strips that name's editorial fields and returns the stripped row. The writer then turns each absent field into an empty one (sn.documentation = "", sn.links = null), so handing it the row clears the documentation and links protection instead of keeping them. The step therefore resolves protection itself and drops the protected rows before the writer is called: it never hands over a name whose fields the writer would empty. The withheld ids are still returned under "protected", and the apply still logs them, so a partly written family cannot read as a whole one. Protection is never overridden — passing the batch through and letting the writer strip it is not protection, it is the same write performed with the guard's own output as the payload. The step's returned added and removed counts cover the rows the writer was given and no others: a withheld member's computed additions and removals are computed and then left out of the totals, because counting them would report a change that did not land. Without that, a protected member carrying a dead link would raise removed by one while nothing about it was written.

The test, its green run and its red runs

tests/standard_names/test_harmonize_reverse_links.py drives the real apply_families over a three-member fixture family whose regenerated members link one way — the anchor links to the boundary member, the probe member links to the anchor, and the probe carries two planted references: name:other_at_axis, live in the catalog but in another pattern family, and name:base_of_ghost, which no catalog name carries. Its graph's documentation-field writer is stubbed and reproduces the real writer's protection handling down to the detail that matters: a stripped row's editorial fields are written back as empty, exactly as the writer's Cypher does, so the stub is capable of failing on the behaviour production has. The audit function itself judges the result.

  • Green (green.log: 4 passed, EXIT=0): the apply converges; the audit reports zero missing_reverse findings over the family's links; the live out-of-family reference name:other_at_axis survives in the probe's links and in its prose, and is not made reciprocal; the dead reference name:base_of_ghost is gone from both, with no dead_link finding left to report; and the anchor's external URL is carried through untouched.
  • Red, step removed (red_step_removed.log, out-of-tree plugin -p red_step_removed, EXIT=1): with the step patched to a no-op the fixture apply ends with missing_reverse findings and test_apply_leaves_no_sibling_link_without_its_reverse fails on its empty-findings assertion. This is the declared negative control "remove the reverse-link step and the fixture apply ends with missing_reverse findings".
  • Red, sibling-only keep rule (red_sibling_only_rule.log, EXIT=1): restoring the rejected rule — keep a name: link only when its target is a family sibling — fails exactly test_a_live_name_outside_the_family_survives (1 failed, 3 passed). This is the run that shows the survival assertion is load-bearing rather than decorative.
  • Red, removal rule absent (red_no_removal_rule.log, EXIT=1): with the removal rule gone — every name: link kept regardless of whether the catalog carries its target — test_a_link_to_a_name_the_catalog_lacks_is_removed fails on the dead link it still finds (2 failed, 2 passed). The second failure is a consequence worth naming: the probe is protected, and with no removal computed for it the step computes no change for it at all, so it enters no batch and has nothing to report as withheld. The step reports protection only where it had a write to withhold, which is why the count is a report rather than a census. With the fields assertion first the test now fails at its opening assertion instead, assert step["protected"] == [_PROBE], reporting [] — the same fact, stated where it belongs.
  • Red, the protected row handed to the writer (red_writer_unprotected_targeted.log, EXIT=1): with the step passing the whole batch through — the pre-repair write(batch) — the writer strips the protected probe's five editorial fields and writes them as empty, and the test fails at assert f"name:{_GHOST}" in probe["links"] with TypeError: argument of type 'NoneType' is not iterable: sn.links is null. Run over the whole file the same reversion fails one test of four (red_writer_unprotected.log). This is the run that names the harm the finding identified.
  • Red, with the stub as it was — the false green (red_stub_cannot_fail.log, EXIT=1): the same reverted step, but with the earlier stub that treated a stripped row as no change. The two assertions that read the probe's fields then pass; the test fails only on the bookkeeping below them, assert graph.protected_by_writer == []. That is the second finding measured directly — a stub that does not clear what the writer clears cannot fail on the clear, so the first finding was invisible to it. The pair differs in one file only: the stub.
  • Red, the counts covering the withheld rows (red_counts_include_withheld.log, EXIT=1): with the totals accumulated over every member that had a change computed rather than over the rows the writer was given, the protected test fails at assert step["removed"] == 0 — assert 1 == 0, the probe's dead link counted as a removal even though nothing about the probe was written. The counts assert 2 added and 0 removed, which is the anchor's and the boundary's two additions and the withheld probe's removal left out.

The red runs are produced by removing one mechanism each and re-running, so each assertion is tied to the code it measures rather than to a shared fixture. The step-removed control patches the whole step out from an out-of-tree plugin file, so no test hook is carried in the repository or the environment; the others change the step's own source, or the stub, for the length of one run. Every reverted source was restored and verified byte-identical to the committed file afterwards.
