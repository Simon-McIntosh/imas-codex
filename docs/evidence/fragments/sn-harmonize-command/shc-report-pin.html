The report names the anchor the apply will use

A family held mid-run carries a recorded anchor (harmonized_anchor) that the dry run and the apply honour, but sn harmonize --report re-selected each family's anchor through select_anchor alone. When the pinned member sits mid-pipeline with a null documentation score, a live ranking picks a different, higher-scoring member, so the report named an anchor the apply would not use. The anchor a family displays is now resolved in one place — resolve_family_anchor(members, *, member_ids=None, signature=None) in imas_codex/standard_names/harmonize.py — which reads the recorded pin through pinned_family_anchor and falls back to select_anchor only when no pin is recorded, or the family is already stamped harmonized (the stamp releases the pin). The report and the dry run call it, so what the operator sees is what the apply does.

Every select_anchor call site and its decision

SiteSurfaceDecision
report_family_rows (harmonize.py, the row build) sn harmonize --report — prints each family's anchor. Changed. The anchor is now resolve_family_anchor(members). This is the operator surface whose anchor disagreed with the apply; it reads the pin the same way the planning does.
plan_family_applies (harmonize.py) The dry run — prints each family's planned anchor. Refactored, no behaviour change. It already read the pin inline; the inline select_anchor-then-pin logic is replaced by the shared resolve_family_anchor, so the rule has one definition rather than a copy per reader. The signature/ member_ids it already derived are handed in so the stamp-release test is not recomputed.
assemble_family (harmonize.py §273 parent route, §294 pattern route) sn harmonize --family <seed> — prints Anchor: …. Unchanged. It is operator-facing, but it assembles a different family than the apply's: it prefers the parent-grouped family, while the pin is recorded over pattern families. Its two member reads moreover do not project harmonized_* (the pattern read is in families.py), so the pin is not on its members and cannot be read within this node's write scope. Follow-on below.
build_worklist (harmonize.py §384 parent route, §438 parentless route) The drift worklist (ranked families to re-align). Unchanged. Its anchor is never displayed: the only CLI consumer takes len(drifted), and the apply re-derives its own anchor through plan_family_applies. It promises nothing about the apply, so nothing is introduced.

Measure

tests/standard_names/test_harmonize_anchor_pin.py::test_the_report_names_the_anchor_the_apply_would_use stubs a family of two members — the pinned member mid-pipeline (null docs score) and an accepted, higher-scoring sibling — and asserts the plan and the report name the same member, the pinned one. With the report's pin read removed (the anchor resolved through select_anchor directly), the test fails (assert 'base_at_axis' == 'base_at_axis' vs the outscorer named instead); the red run is recorded with the run's manifest. The harmonize test files (grep -rl harmonize tests/standard_names/, 14 files) ran green at the base revision (134 passed) and at the head (135 passed — the one added test), so the change adds 0 failures.

Follow-on

sn harmonize --family <seed> can still show an anchor the apply would not use for a pinned family whose route is the parent branch, because assemble_family reads a family the apply does not. Projecting harmonized_anchor onto its member reads — the pattern read _PATTERN_FAMILY_MEMBERS_QUERY in families.py is the blocker — and routing its anchor through resolve_family_anchor would close it; the change reaches families.py, outside this node's write scope.
