Which hold note held each rewritten anchor member

Fourteen of the fifteen members held at 0.849 were held by one guard, on one branch, for one reason: the member is a derived parent and carries no DD-source binding. The branch is the fallback in _documentation_contradiction_note (imas_codex/standard_names/workers.py:10915-10922), whose note text is DD source text unavailable; claim comparison could not run. The fifteenth member is held by a real contradiction with its DD source. The error-severity lint cap in imas_codex/standard_names/review/pipeline.py:1963-1989 fired zero times across all twenty arm logs, so it held nothing.

How the note was recovered. The arm records do not store the reviewed documentation or the review notes. The arm's own apply-*.log does: documentation review emits review_docs: <member> held from acceptance — <notes> immediately before persist_reviewed_docs: <member> → docs_stage=reviewed (score=0.849…). Pairing those two lines per member gives the guard, its text, and the persisted floor from the production path itself. This driver then re-ran the three notes and the lint cap through their own code paths on each member's prompt-bearing item, loaded with _load_docs_review_source_item and enriched by _fetch_review_dd_context exactly as the veto path does.

The branch that fires, and why the guard is not simply broken

_bound_docs_review_dd_paths keeps only bindings whose source_type == "dd". A derived parent's single binding has source_type == "derived", so the required-path list is empty. With no required paths and no dd_documentation, sources stays empty. The guard then reaches if item.get("source_paths") or item.get("source_bindings") — and that test does not filter to DD bindings, so the derived binding alone satisfies it and the note is returned. The same test is what the previous diagnosis read as a reason the note could not fire; it can, because the binding exists even though it is not a DD binding.

The control that shows the cause. Re-running the contradiction note on a copy of the same item with the non-DD binding dropped returns None for all fourteen — the hold is produced by the derived binding's presence, not by the member's prose. For the one pipeline-origin member the note is unchanged by that drop, because its fourteen DD bindings do not go through the fallback branch at all.

Where the re-run disagrees with the record, the record wins. The contradiction branch is selected from the binding shape and returns before the documented text is read, so it reproduces faithfully. The registry-conformance and banned-prose notes depend on the rewritten text, which the arms did not retain; the re-run reads the live pre-rewrite text and is indicative only. Two members (wavelength_of_visible_camera and source_rate_due_to_thermal_fusion, both Jev arms) additionally raised a template_opening conformance note in production. Either note alone clamps the score to the same 0.849.

Recommended fix, its owner, and the families it unblocks

1. Correct the hold check — owner: imas_codex/standard_names/workers.py (_documentation_contradiction_note). The fallback branch must test for DD bindings, not for bindings of any kind: when _bound_docs_review_dd_paths(item) is empty and there is no dd_documentation, there is nothing unavailable to compare against and the note should be None — which is what the branch's own comment intends and what the neighbouring return None already does for a bare item. This is the smallest change that clears the false hold, and it is the one the evidence supports. Every held member is held on this branch, so it unblocks all fourteen.

2. Restrict anchor eligibility — owner: the anchor selection that feeds the campaign, imas_codex/standard_names/harmonize.py (select_anchor) or the Jev scorer beside it. Fix 1 alone will let these members through, but a derived parent with no DD source still makes a poor template: its rewrite cannot be verified against a source, and it anchors a family it has no textual authority over. Excluding derived-parent members from anchor candidacy unblocks the same families and removes the exposure at its source. The two fixes are complementary, not alternatives.

Not recommended: relaxing the convergence check. The 90% docs-acceptance gate in imas_codex/standard_names/campaign.py:521-530 correctly refused a batch where the only member was held. A one-item batch that is held is a real failure of the batch, not an artefact of its size; skipping the check below N members would let a genuine hold (member 10 above) pass unnoticed in a small family. Keep it intact.
