Angular-width-of-camera family: jev arm (aborted at the isolation proof)

The jev arm of the angular_width_of_camera family was launched against a fresh scratch copy of the fixed archived export, on the runner revision c96f0f0d8 with the unmodified per-family selection. The arm did not reach harmonization. It aborted in the scratch-only isolation proof before any apply was issued, so no spend was incurred and no live write occurred.

The failure

Isolation proof failure, from the runner log's traceback:

RuntimeError: Scratch-only marker contrast failed:
{'scratch_uri': 'bolt://127.0.0.1:28002', 'live_uri': 'bolt://98dci4-gpu-0002:7687',
 'scratch_nodes': 1770101, 'live_nodes': 1771162,
 'marked_scratch_nodes': 1770104, 'scratch_probe': 1, 'live_probe': 0,
 'restored_scratch_nodes': 1770101, 'at': '2026-10-19T13:10:27Z'}

The check requires the node count to rise by exactly one when its single probe node is created. Here marked_scratch_nodes - scratch_nodes = +3, while the probe query itself returned exactly 1 matching node, and restored_scratch_nodes returned to the baseline 1770101 after a delete that removed only that one probe. A one-node create/delete therefore moved the instance's total node count by three. The live graph was not touched (live_probe = 0).

Reading of the evidence

No APOC triggers are installed on this graph (the live instance rejects both SHOW TRIGGERS and apoc.trigger.list), so a create-cascade does not explain it. The pattern — a count that moves by ±3 around a one-node create/delete, on a private scratch instance — is what a second connected writer produces. The runner picks its bolt port from free_port_pair(), which test-binds and closes before the instance binds; with five arms launched inside three minutes that test-then-bind window is a race, and two arms can select the same pair. A peer arm sharing port 28002 would write and delete its own probe into this instance, and every count in this proof would see the churn.

This is not a defect in the harmonize path, which was never reached. It is a concurrency hazard in the arm runner's scratch-port allocation, exercised by running arms in parallel where the plan's node re-cut assumed they would be serialized per family.

Cost and state

  • Spend: USD 0.00 — the apply was never issued; the runner stopped before run_apply.
  • Wall time to the abort: 2,268 s, of which roughly 2,160 s was the dump extract and Neo4j load under four concurrent loads on the shared allocation.
  • The partial arm record (outcome_status: running) was written by the runner at ssog-anchor-ab/angular_width_of_camera-jev.json; it holds the family row, the target anchor vertical_angular_width_of_camera, the code digest and the scratch-tree bookkeeping, and is left uncommitted as an incomplete intermediate.
  • The scratch instance was stopped and its tree removed by the runner's teardown (stopped_instance / scratch_removed in the partial record).

What is needed

A rerun with the arm runners serialized — one scratch instance loading at a time — removes both the load contention and the port race. The completed record must carry outcome_status: complete, its lint before/after, every member's documentation score after, calls, spend, wall time, the containment verdict and the code digest.
