The compose comparator block can be reranked by Jev behind a default-off switch

The compose and regen prompts carry a nearby-name comparator block whose order is the embedding retrieval's. rerank_name_comparators in imas_codex/standard_names/context.py reranks a batch's block through rerank_pool under the sn-judge seat with service standard-names: each batch item judges the whole block once, the item's description and DD path are the query, and each comparator's name and description are the state. A comparator's final rank is its mean rank across the items, with ties keeping the embedding order, so the merged order is never worse than the retrieval order it replaces. rerank_pool's own failure-order guarantee is pinned by test_rerank_pool_keeps_the_pool_order_when_every_judgement_fails in tests/discovery/test_judgment.py, so the rerank inherits it rather than restating it.

Both compose sites — compose_worker's per-batch body and compose_batch — now call the block through _rerank_comparators_for_compose in imas_codex/standard_names/workers.py. It reads comparator_rerank_enabled(), which is off unless IMAS_CODEX_SN_COMPOSE_RERANK_COMPARATORS is set, and returns the block untouched with zero cost when off, so the composed prompt is identical to a run without the rerank. The rerank's cost is returned and booked by each site — to state.compose_stats.cost in compose_worker and through a BudgetManager lease in compose_batch — the way every other Jev call in these paths is booked.

A rerank is billed by the judge seat, not by the compose model, and its price is only known once it returns. So the batch site opens a floor lease before the call and charges the actual spend through the lease already held, naming the seat that billed it; a charge the provider has already made is never dropped for want of a reservation. A pool that cannot fund even the floor lease runs the batch in the embedding order and charges nothing, because nothing was spent. The switch is read before the lease is opened, so a batch run with the rerank off books nothing at all — no reservation, no charge — and touches the budget exactly as it did before the switch existed. Ranking is not a gate: the caller wraps the rerank like its siblings in imas_codex/llm/search_tools.py and imas_codex/discovery/signals/parallel.py, so a raise out of get_model("sn-judge") or a state builder keeps the embedding order instead of aborting the compose batch.

tests/standard_names/test_comparator_rerank.py stubs rerank_pool's decisions and records what it is asked: the query and, through the same state_for the real pool is handed, each comparator's judged state. The on-arm test asserts both — the query is the item's description with its DD path, and each state pairs that query with the comparator's own name and description — so a rerank fed the wrong text fails the test rather than passing on a call count. Removing the rerank call from _rerank_comparators_for_compose turns the on-arm reorder test red (EXIT=1, test_switch_on_reorders_the_comparator_block_by_score and test_comparator_rerank_merges_item_orders_by_mean_rank), and altering _comparator_rerank_query in a scratch copy so it drops the DD path turns it red on the query assertion alone (EXIT=1); the off-arm test stays green under both, which is what pins the switch as the only path to the reorder.
