A family anchor must be entailed by a DD source

A member with no Data Dictionary producing source is no longer an anchor candidate. A family takes its documentation template from its anchor, so the opening the anchor sets for its members is only checkable against source text when the anchor has a DD source of its own. A name with none — the derived parent the held-cause record found holding fourteen of fifteen members — sets a template its own rewrite cannot be verified against, and then templates members it holds no textual authority over. Both selectors in imas_codex/standard_names/families.py now require the flag: the heuristic select_anchor and the judged scorer's candidate filter _eligible_anchor_candidate.

What the rule reads

A row is DD-sourced when :StandardNameSource {source_type: 'dd'} reaches it along PRODUCED_NAME and that source is not retired (status = 'stale') — the same producing-edge shape source_invariant.py guards writes with, so the two cannot disagree about what a producer is. One builder, dd_source_exists(alias), is the single spelling of it; every family query in the module that returns a member row projects it under has_dd_source: _PATTERN_FAMILY_MEMBERS_QUERY, the per-family collect in _family_member_collect, and _FAMILY_BASE_QUERY. member_has_dd_source(row) is the one reader.

Every ranking branch applies it, not only the top one. The accepted-parent rule reads the parent's own row when the parent is one of the members, so an accepted derived parent no longer wins by rule 1; the accepted-and-scored branch, the accepted-but-unscored branch and the last-resort branch each draw from the same eligible set. The judged scorer drops the same rows before any call is made, so an unsourced member is never asked about and never returned as the choice.

A row that carries no has_dd_source key at all is read as DD-sourced, so a selector handed rows built by a caller's own query ranks exactly as it did before the flag existed rather than silently deferring the whole family. That default is reachable only from harmonize.py, whose parent-grouping rows are assembled inline in that module; see the follow-on below.

A family with no DD-sourced member has no anchor

The caller already handles a family without one, and the new rule only routes more families into that existing path — no new failure mode is introduced. harmonize.build_worklist stamps "deferred": anchor is None on the worklist entry, and the planner reads it as elif anchor is None: decision, batches = "deferred", [] (harmonize.py:1253) — no batches, nothing rewritten. context.fetch_sibling_family returns anchor: None with defer semantics and still returns the siblings for structural comparison, as its own docstring states. The judged scorer returns AnchorScore(reason="no member is eligible as the family's template") rather than a default anchor. So an all-unsourced family is deferred and never templated from a member with no source to check against.

Which comparison families change anchor

Method. Both arms read the same live rows through the fixed module's own fetch_pattern_family, so the only difference between them is the rule: the base revision's select_anchor, loaded by path from the scratch base tree, against the fixed one. A family changes anchor when the two rules name different members. The judged arm cannot be recomputed this way — the experiment stored each member's documentation score, not the judge's expected score, so that arm's replacement cannot be named from the record; what is reported for it is the weaker, checkable fact that the anchor the arm landed on is itself no longer eligible.

Caveats

The ten-family delta is measured on the live graph, not on the 2026-10-18 export the A/B ran against, so its anchors need not equal the recorded ones and, for six of the ten, do not. The comparison that carries the claim is the one made here, base rule against fixed rule over identical rows; the snapshot columns are context, not the measurement. The DD-source column is provenance rather than documentation state and is therefore the part least exposed to that drift, but it is still a live reading. No LLM spend was incurred by this node: every arm is a pure selection over rows already in the graph.

Follow-ons

harmonize.py's parent-grouping path builds its member rows in an inline Cypher query in that module, so those rows carry no has_dd_source and the flag's absence default applies to them. A derived parent with no DD source reached through that path is still an anchor candidate until that query projects the same flag — outside this node's write scope, and the one place the guard can still fail open.

Distinct from, and complementary to, the hold check owned by ssog-docs-hold-dd-bindings (_documentation_contradiction_note in workers.py): that repair stops the false hold firing on a rewritten member, this one keeps an unverifiable member from being chosen as the template in the first place.
