ssfms-cleanup-test-doubles — one statement-capturing double, and checks a regression fails

The signal suites each carried a private recording graph client, so a change to how a statement was captured had to be repeated in every copy, and three checks in the role suite compared production output against the value production had just produced — a fake judge that returned whatever the assertion then read, and a criteria set compared against the module's own constant. Those checks pass whatever the code does. This node lands one shared double and rewrites each check against a value the test supplies, so the check fails when the behaviour it names is replaced by a hardcoded answer.

Changes, each with its check

One statement-capturing double. tests/recording_graph_client.py holds RecordingGraphClient, which records every (cypher, params) pair it is handed and answers with no rows. It replaces the private _RecordingClient in tests/discovery/test_signal_embedding_sweep.py and the private recording logic in tests/graph/test_dd_path_domain_upsert.py. The DD-path test keeps its domain-assignment model by subclassing the shared double (_DomainCompletingClient) and overriding query, so the capture lives in one place and the fixture's behaviour stays with the test that asserts on it. Check: grep -rn 'class _RecordingClient' tests/discovery tests/graph returns nothing, both suites run the shared class, and the DD-path test's domain assertions still discriminate the two upsert forms.

The offered criteria set is compared against a literal. tests/discovery/test_signal_role.py now writes the six-role vocabulary once, as SIX_ROLES, and asserts set(criteria) == SIX_ROLES over what signal_role_questions() returns. Previously the check compared the set against ROLE_CRITERIA, the same constant the production function returns, so a criteria set that lost a role still agreed with itself. Check: with signal_role_questions returning a hardcoded two-role set, the criteria assertion fails (nc-01-hardcoded-criteria.log).

Each accepted row's role is checked on its own. The fake judge answers a different role per input (measured for the sensor, reference_or_setpoint for the target), and the test asserts each row's signal_role against the literal it expects for that row. The earlier check read the role out of the accepted rows and compared it to the value the same fake had just returned, so it could not fail. Check: with the judge's decision discarded for a hardcoded measured on every row, the accepted-row assertion fails with assert 'measured' == 'reference_or_setpoint' (nc-02-hardcoded-role.log). This is the node's declared negative control.

The batched response cost is compared against a literal. The fake judge prices each decision at USD 0.002 over a two-row batch, and the test asserts the returned cost equals 0.004 — a value the test supplies rather than one read back out of the module's return. Check: with the returned cost replaced by a hardcoded 0.0, the cost assertion fails with assert 0.0 == 0.004 (nc-03-hardcoded-cost.log).

The live census population is checked against an independent count. test_census_statement_runs_against_the_live_graph reads the census population from census_signal_embeddings() and compares it to a FacilitySignal count issued in the same test through a second GraphClient, and requires it above zero. The earlier check asserted a frozen literal (still present on the facility-scoped test as result["n"] == 15111, recorded as a follow-on below) and so could pass on a census that read nothing, since both sides of a subtraction that agrees at zero agree. Check: with the census's population hardcoded to 0, the live check fails with assert 0 == 61983 (nc-04-hardcoded-population.log).

The role measurement takes its fixture as an argument. tests/llm/measure_signal_role.py binds its fixture through --fixture, defaulting to tests/llm/fixtures/signal_role_random_labels.json, and the one loader validates both role fixtures. Check: each fixture loads and reports its row count with no spend — --load-only on the default prints 200 rows and on tests/llm/fixtures/signal_role_labels.json prints 300 rows, both at USD 0.000000, against the USD 0.02 ceiling for this check. A loader that still accepted only the stratified set would refuse one of the two.

The graph test package states what needs a live server. tests/graph/__init__.py's docstring now says that only the tests marked graph need a live Neo4j, that the default run excludes that marker, and that the package also holds guards which need no graph and run by default — which is the case the DD-path guard establishes, as it runs under the default markers. Check: the docstring's claim matches observed behaviour, since tests/graph/test_dd_path_domain_upsert.py is collected and passes under -m 'not slow and not graph'.
