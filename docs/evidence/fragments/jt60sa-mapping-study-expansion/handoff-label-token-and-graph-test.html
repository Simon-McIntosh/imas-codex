One absence token, and a live-graph test for the nearest-label query

imas_codex/ids/handoff.py now reads the absence token from CocosLabel.NONE in imas_codex/ids/models.py and defines no token of its own: the module-level COCOS_ABSENT = "none" and its comment are gone, and the three absent-value sites in _nearest_cocos_labels and its caller read CocosLabel.NONE. The absence token therefore has one source, shared with imas_codex/ids/transforms.py. The document contract is unchanged: CocosLabel.NONE is a StrEnum whose value is none, so serialised rows and format_version are identical.

tests/ids/test_mapping_handoff_graph.py drives the real Cypher, which the mocked tests cannot: they reimplement hop selection in Python, so a green mock does not prove the query's ORDER BY hops / collect(label)[0] idiom. Against the live graph, _nearest_cocos_labels resolves magnetics/b_field_pol_probe/field/data to one_like from xml, magnetics/flux_loop/flux/data to psi_like from inferred_forward, and a .../time target to none for both. A set-equality assertion first requires every requested target to come back, so a silent zero-row query cannot read as a pass on the absence token.

Declared negative control: drop ORDER BY hops from the nearest-label query. The graph test stays green (2 passed, EXIT=0), so this node records why the result is order-insensitive rather than a failing arm. On the live graph a cocos_transformation_type label is unique to its structure: 553 IMASNode nodes carry one, and no node's HAS_PARENT chain reaches a second labelled node (0 matching chains at 1–10 hops). A target therefore reaches at most one labelled ancestor, so collect(label)[0] holds a single entry and hop order cannot change any row. The second graph test, test_an_ancestor_chain_carries_at_most_one_cocos_label, pins that invariant: a chain that ever stacks two labels turns it red, which is the signal that the ordering must then be proven.
