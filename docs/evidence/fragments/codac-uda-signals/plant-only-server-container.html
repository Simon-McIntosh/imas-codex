A private container that serves the ITER plant graph and nothing else

The plant catalogue is served by a second image built from the same Dockerfile, with the serve mode fixed at build time: ARG SERVE_MODE="--dd-only" is recorded as IMAS_CODEX_SERVE_MODE, and the entrypoint applies it to the serve command, so the image mode is a property of the image rather than of the command line. AgentsServer(plant_only=True) forces read-only operation, names the MCP server imas-codex-plant, and deletes every tool component outside PLANT_TOOLS — search_signals, search_pulses, get_signal_load_recipe, signal_analytics, fetch_content and get_facility_coverage — before prompts are registered.

The package is produced by the export command's own filter. graph export --facility <f> --without-dd refuses without a facility, forwards the flag, and the filter deletes every node owned by another facility (by Facility id, since those nodes carry no facility_id), every facility-less node except the facility node itself and GraphMeta, and records plant_only on GraphMeta. Each push then reports the registry's visibility for the package and requires it to be private; the same report runs on the local and the remote push path.

imas_codex.graph.plant_scope holds the acceptance rule as code: the package must hold the same number of nodes of every facility-owned kind and of every relationship between two facility-owned nodes as the graph it was exported from, no node of another facility, and no facility-less kind beyond the two the server reads. The export run and the focused tests use the same function.

The export is a bounded read of the live graph, not a dump of the recorded archive. The newest recorded dump (2026-11-15, product git c266404) predates the plant-component and pulse imports: it holds 12 facility kinds, 5 PlantComponent nodes and no Pulse, ControlNode or PulseCategory, so a package built from it cannot serve any of the behaviours above. That build ran and reported exactly one violation — the facility-less Facility count — which is the comparison's own fixture corrected in this change: the expected count now includes only the kept facility node. The live export instead copies the facility scope into an empty temporary Neo4j, injects the foreign node, applies the product filter and dumps the result. The shared graph was never stopped, and no neo4j-admin dump was attempted against a mounted database.

This cluster has no reachable Docker daemon, so the image is built with apptainer build --fakeroot from neo4j:2026.01.4-community, copying the project's resolved environment, the worktree's imas_codex, and the sibling standard-name package the server imports during warmup, then loading the package dump at build time. Two build faults were measured and repaired: binding the environment onto /opt hid the image's JDK (JAVA_HOME is not defined correctly), and the console script's shebang names the build host's environment, so python -m imas_codex started the legacy stdio module instead of the CLI; the wrapper now runs the console script through the image's interpreter, and TRANSPORT=streamable-http is part of the image environment as it is in the Dockerfile.

The image's /data, /logs and /var/lib/neo4j are read-only mounts, and an overlay image created on GPFS cannot be made writable to the fenced user, so the verification run gives the server a tmpfs root plus three writable binds: a data directory seeded once from the image, a log directory, and the run directory. That is a property of this cluster's build path, not of the Docker image the Dockerfile produces.
