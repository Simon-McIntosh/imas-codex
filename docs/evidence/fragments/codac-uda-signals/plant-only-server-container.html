A private container that serves the ITER plant graph and nothing else

The plant catalogue is served by an image built with apptainer from a private definition in the run directory, not by the Dockerfile: this cluster has no reachable Docker daemon, so the Dockerfile's plant recipe exists but has not been built. The image's serve mode is its start command — the compose service passes serve --plant-only … — so the image's own default and the entrypoint stay exactly what the data-dictionary image already starts with. AgentsServer(plant_only=True) forces read-only operation, names the MCP server imas-codex-plant, and deletes every tool component outside PLANT_TOOLS — search_signals, search_pulses, get_signal_load_recipe, signal_analytics, fetch_content and get_facility_coverage — before prompts are registered.

The data-dictionary image's start path is unchanged, and the diff says so: git diff 1875455e..HEAD -- docker-entrypoint.sh is empty (byte for byte), and every changed line of git diff 1875455e..HEAD -- Dockerfile is a ## comment line — CMD still reads ["serve", "--dd-only", "--host", "0.0.0.0", "--port", "8000"], there is no serve-mode build argument, and no IMAS_CODEX_SERVE_MODE anywhere. A test runs the entrypoint itself with Neo4j, curl, cypher-shell and imas-codex stubbed, and compares the argument list the server receives against the list each start command names: the Dockerfile's CMD yields serve --dd-only --host 0.0.0.0 --port 8000, the compose plant service's command yields serve --plant-only --host 0.0.0.0 --port 8000, an environment the plant image never sets changes neither list, and dropping --plant-only from the plant command fails the test.

The package is produced by the export command's own filter. graph export --facility <f> --without-dd refuses without a facility, forwards the flag, and the filter deletes every node owned by another facility (by Facility id, since those nodes carry no facility_id), every facility-less node except the facility node itself and GraphMeta, and records plant_only on GraphMeta. Each push then reports the registry's visibility for the package and requires it to be private; the same report runs on the local and the remote push path.

imas_codex.graph.plant_scope holds the acceptance rule as code: the package must hold the same number of nodes of every facility-owned kind and of every relationship between two facility-owned nodes as the graph it was exported from, no node of another facility, and no facility-less kind beyond the two the server reads. Both filter paths run that rule and refuse the package before the dump exists: the local Bolt filter measures before it deletes and after, then verifies before calling the dump, while the generated compute-node script prints SCOPE_BEFORE= and SCOPE_AFTER=, runs the same check through the same module, and aborts under set -e before neo4j-admin database dump, so no dump file is written and none is moved into place. The caller re-reads the two printed scopes after the job as an independent check of what was measured.

The filter's statements have one definition, used by both paths: the local filter executes them through a session with parameters, and the script substitutes the same text for cypher-shell, which takes none. Statement order, batch size and the orphan keep list therefore cannot differ between a package filtered locally and one filtered on a compute node.

The export is a bounded read of the live graph, not a dump of the recorded archive. The newest recorded dump (2026-11-15, product git c266404) predates the plant-component and pulse imports: it holds 12 facility kinds, 5 PlantComponent nodes and no Pulse, ControlNode or PulseCategory, so a package built from it cannot serve any of the behaviours above. That build ran and reported exactly one violation — the facility-less Facility count — which is the comparison's own fixture corrected in this change: the expected count now includes only the kept facility node. The live export instead copies the facility scope into an empty temporary Neo4j, injects the foreign node, applies the product filter and dumps the result. The shared graph was never stopped, and no neo4j-admin dump was attempted against a mounted database.

This cluster has no reachable Docker daemon, so the served image is built with apptainer build --fakeroot from the private plant-only.def in the run directory, over neo4j:2026.01.4-community, copying the project's resolved environment, the worktree's imas_codex, and the sibling standard-name package the server imports during warmup, then loading the package dump at build time. Two build faults were measured and repaired: binding the environment onto /opt hid the image's JDK (JAVA_HOME is not defined correctly), and the console script's shebang names the build host's environment, so python -m imas_codex started the legacy stdio module instead of the CLI; the wrapper now runs the console script through the image's interpreter, and TRANSPORT=streamable-http is part of the image environment as it is in the Dockerfile.

The image's /data, /logs and /var/lib/neo4j are read-only mounts, and an overlay image created on GPFS cannot be made writable to the fenced user, so the verification run gives the server a tmpfs root plus three writable binds: a data directory seeded once from the image, a log directory, and the run directory. That is a property of this cluster's build path, not of the Docker image the Dockerfile produces.

Provenance: the export ran as batch job 1332723 on partition rigel (1,052 s), the container verification under unshare -rn on a login node. Run-directory receipts include plant-package/scope-report-live.json, plant-package/publish-report.json, plant-container-run.log, plant-gate.log, plant-negative-control.log and plant-private-value-scan.log. Generated models were not rebuilt and the shared environment was not synced.
