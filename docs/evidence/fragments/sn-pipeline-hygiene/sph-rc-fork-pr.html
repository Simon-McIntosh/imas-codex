§4 — A whole-catalog candidate opens a fork review pull request

Only the final branch of the catalog cut opened a pull request, so a whole-catalog candidate reached the fork as a tag and nothing else: the reviewer had no page carrying the catalog diff, no body, and no link to the export accounting. The candidate v0.4.0rc8 reached the fork in exactly that state.

A candidate now reaches the fork as the branch release/<tag> plus one pull request raised in the fork itself (repo and head_owner both the fork), so the request carries a readable diff. The body names the candidate revision and, when the export wrote accounting, the per-reason exclusion report — both as markdown links. The exclusion-ledger helper the review-batch path uses appends nothing here: a whole-catalog cut has no focus manifest to hold a ledger, so that leg of the reuse map has no input on this path.

A candidate aimed at the upstream catalog is refused before anything is published — before the export, before the tag, before the first push. The upstream remote is recognised by name and by the repository it resolves to, so a checkout that clones the canonical catalog under another name is refused too. The package release CLI's upstream guard carried the same gap: it ran only under if final, so a candidate pointed at upstream passed. Its condition is extended rather than a second guard added — final now requires upstream, and a candidate requires the fork.

The fork-branch delivery applies only to a candidate: the final path keeps its own transport (branch pushed to the fork, pull request against upstream), and the batch path (run_review_release) is untouched. A checkout that records no GitHub fork identity — a mirror, or a local stand-in remote — keeps the previous transport, pushing the released commit to the remote's main, and opens no request.
