A scoped run no longer starts the graph-wide maintenance passes

A review of one edit's names (sn run --only review_name --edits --scope-run-id <edit-run-id>) asked the orchestrator for a scoped run and still forwarded skip_global_maintenance=False, so the run executed the whole maintenance sequence — the pass that returned 24 unrelated names' sources to the pool. The scope is now resolved once, by resolve_scope_maintenance() in imas_codex/standard_names/pipeline.py: a run given a run id, focus paths, exact names, or the edits predicate carries the bypass whether or not --skip-global-maintenance was repeated, and an action that cannot be bounded by a scope refuses with a reason. The decision is applied at both seams a scoped run crosses: the CLI's own graph-wide startup writes (the global run_id clear) and the orchestrator entrance (_run_sn_cmd), which drops the passes for every caller.

Read against the plan section: a scoped run stays in scope by default with no extra option, and an option combination that cannot be confined is refused at start with the reason. No flag is needed to obtain the scoped behaviour, and the refusals name the offending combination.

An edits-only run names its scope by run id 

The edits predicate is a scope, but the loop accepts a maintenance bypass only for a run id, so sn run --only review_name --edits reached the loop with the bypass set and no run id and aborted on skip_global_maintenance requires scope_run_id or drain_scope_id. The orchestrator entrance now binds the pending successors before it resolves the policy: PENDING_EDIT_SCOPE_QUERY reads the edit_status='open' names that are not terminal, _bind_pending_edit_scope() stamps exactly that set with a fresh run id through the same preflight an exact-name run uses, and the run starts scoped with its claims selecting precisely the edit's names. A stale edit_status on a superseded or exhausted name is not work and is excluded rather than refusing the whole run; with nothing pending the command is a no-op.

Measured on the live graph: imas-codex sn run --edits --only review_name --dry-run prints Scoped run: graph-wide maintenance is bypassed; only this scope's names are touched. and exits 0. The guard test drives the real entrance into the real run_sn_pools — the loop is stopped only after its guard — and at reviewed head 6862a3d1a the same test fails with that guard's ValueError.

What the policy decides 

Scoped inputs come from the concrete flags after manifests, batches and --name conflicts have resolved, so a manifest URL is judged as its expanded focus paths, not as a token.

runmaintenancewhy
no scopefull sequencethe catalogue-wide run
run id, focus paths, exact names, or --editsbypassedthe run is about those names only
scoped + --only reconcile/attach/validate/linkrefusedthe phase is itself graph-wide
scoped + --reset-to without focus pathsrefusedevery matching name is rewritten
scoped + --revalidaterefusedthe whole validation backlog is cleared

A focus run's one pre-seeding write — clearing stale run_id stamps from a previous run of the same paths — was a whole-catalogue statement. It is now FOCUS_STAMP_CLEAR_CYPHER in imas_codex/cli/sn.py: one statement over the run's own StandardNameSource ids and the names those sources produced, so an out-of-scope source keeps its stamp and its name keeps its own. The graph-marked test ::test_focus_stamp_clear_is_bounded_by_the_named_sources plants an in-scope and an out-of-scope source, runs the statement, and reads both stamps back: the named pair is null, the other pair still reads previous-run.

The set of graph-wide --only phases has one owner, GRAPH_WIDE_ONLY_PHASES in imas_codex/standard_names/pipeline.py. Both readings use it: the --skip-global-maintenance compatibility check in the command and the entrance policy call, so a phase added to one cannot quietly stay outside the other's refusal. The entrance applies that refusal to direct callers too: ::test_orchestrator_entrance_refuses_a_graph_wide_phase_under_a_scope passes a scope and --only reconcile straight to _run_sn_cmd and requires the same reason the command gives.

Reviewing one edit's names 

The documented way is the command's own scope, in three steps:

# 1. the pending edit successors, as a scoped plan, zero writes
imas-codex sn run --only review_name --edits --dry-run

# 2. review exactly those names; the entrance binds their run scope
imas-codex sn run --only review_name --edits

# 3. read the outcome back
imas-codex sn status

Adding --scope-run-id <edit-run-id> narrows the same run to one edit's stamped successors; it is optional, not a prerequisite for the scoped behaviour.

Step 2 is recorded by tests/standard_names/test_scoped_run_stays_in_scope.py::test_edits_scoped_review_forwards_the_bypass_without_the_flag, which drives the command and observes the orchestrator receiving the edit's own scope, the edits predicate, and the bypass. The orchestrator entrance is recorded by ::test_orchestrator_entrance_forces_the_bypass_for_a_direct_caller, which calls _run_sn_cmd with a scope and no flag and observes skip_global_maintenance=True.
