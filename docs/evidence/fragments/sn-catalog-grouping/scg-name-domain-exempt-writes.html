The derived-parent domain write goes through the one writer

The single-writer guard refused every direct SET of a standard name's domain except two, both in the derived-parent materialiser (graph_store/graph_lineage.py), and each carried the same reason: the materialiser seeded the parent's scalar from its children's most frequent domain before calling the writer. The rule held only by exemption, so the guard could not see a new direct write as a defect while those two entries stood.

Both entries are gone. The majority rule now lives in domain_decision.derived_parent_domain_decision(decision, child_domains): a stored choice wins, because a settled decision outranks an inherited one; otherwise the domain most children carry becomes the parent's choice, ties broken by name so the same child set always yields the same parent, through the one ranking path_counts already publishes for the writer's own counts; a parent whose children carry no domain keeps the scalar it holds and stays undecided. The materialiser writes no domain at all — it calls write_name_domain for every parent it materialises, passing that decision, so the scalar, the source set and the HAS_PHYSICS_DOMAIN edges land in the writer's one transaction.

One value was carried across one step further than the exemption named: the StandardNameSource copy (sns.physics_domain = coalesce(parent.physics_domain, ...)) read the parent's scalar from the same statement that wrote it. With that write retired the copy now reads the derived domain from the statement's own parameter, so the composed source's recorded domain is unchanged.
