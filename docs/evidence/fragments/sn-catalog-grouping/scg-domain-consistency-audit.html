Live-name domain consistency audit

A new read-only instrument, imas_codex/standard_names/domain_audit.py, re-asks the domain derivation's own question of every live standard name and reports the names that disagree. It writes nothing: it opens the live graph, reads the live names in one bounded scan, and returns a count and the failing ids per check. The four checks, in the order the module states them, are that physics_domain is set; that physics_domain equals select_primary_domain(expected) (the one selector in domain_ranking, not a re-ranking); that source_domains equals the expected set — the domains of the name's current StandardNameSource DD paths, or, for a derived parent with no DD source, the union of its live children's expected sets; and that its HAS_PHYSICS_DOMAIN edges are exactly source_domains. Every comparison is between sets, so arrival order and duplicates carry no meaning.

Run once against the live graph from the audit module landed at revision f17b64387 (log: census.log, which records the command line, the tree revision it ran at, and EXIT=0 last). The read saw 2,677 live names — those holding stage accepted, reviewed, drafted or pending — against the 2,675 the plan's section-3 census of 2026-10-13 recorded. Two names were added in the interval, which is why the counts below are read as a fresh figure rather than as a corrected census.

Three of the four checks measure more names than their census row, and the direction is the same in each case: this audit treats a disagreement as a failure wherever it sits, while the census's rows partition the same population differently. The edges check is the exception only in magnitude — it agrees with the census exactly on method and reads 1,015 against 777, which is what a 2,675-to-2,677 population change and a fresh measurement look like together. The per-check ids are in scg-domain-consistency-audit-results.json beside these counts.

The schema property that carries “live”

The live set is read from name_stage on StandardName. Every property and relationship the query touches was checked against imas_codex/schemas/standard_name.yaml first, because a query on a property the schema does not define returns zero rows rather than an error. The two lines that decide the row set, quoted from the schema: 

      name_stage:
        description: >-
          Name-pipeline stage for this StandardName. Set by
          _finalize_generated_name_stage (drafted), the name-review worker
          (reviewed, accepted, exhausted), persist_refined_name (superseded
          on predecessor, drafted on new node), and the refine_name claim
          (refining). See NameStage enum for all values.
        range: NameStage

NameStage declares pending, drafted, reviewed, accepted, exhausted and superseded. The audit takes the first four as live: an exhausted or superseded name is no longer claimed by the catalog, so its edges are the deliberate provenance record and there is no derivation for it to contradict.

The disagreement runs in both directions, so it is not one stale writer being read off one name: seven of the twenty have no agreement at all, and the derivation answers a different domain from the stored one for safety_factor, normalized_poloidal_flux_coordinate, atomic_number, area_of_diagnostic_aperture and both line-of-sight coordinates. Where the stored value and the derivation agree but the approval does not — electron_temperature, electron_density, atomic_count, ion_charge — the derivation is doing exactly what the graph's sources say, and the lead's approval is a different claim: the sources classify the quantity by where it appears, the approval by what it is. That distinction is the repair node's to settle, not this audit's; this audit only reports that 13 of the 20 names are stored on a domain the lead-approved sheet does not name.

Everything above is read-only output of one run. The instrument itself is covered by tests/standard_names/test_domain_audit.py: each check has a passing and a failing fixture, a derived parent carries its own, an order-and-duplicate-only difference must pass, and removing the four comparisons turns the file red (8 failed, 10 passed, recorded in negative-control.log) before the module is restored byte-for-byte.
