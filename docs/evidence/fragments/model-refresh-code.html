Jev pinned to release 1.14, because the decisions endpoint resolves no moving alias

The lead asked whether the Jev seats could track the newest release by naming an alias rather than a version. They cannot: the OpenRouter decisions endpoint refuses every alias with an explicit HTTP 400, and answers only a release id. The seats therefore name typesafe/jev-1.14, and this fragment records the probe that settled it.

Probe: one minimal decision per candidate id

Each row is one call_decisions call — imas_codex.discovery.base.llm.call_decisions, the same function a seat calls — asking a single two-criterion choice question (which word describes the number two?) with a minimal state, run 2026-11-07. The HTTP seam was wrapped so the raw payload and response headers survived: the public function returns only (answers, cost), and the release that answered is the fact in question. The incumbent typesafe/jev-1.13 was probed as a positive control — without it, a row failing for an unrelated reason would be indistinguishable from a non-existent alias.

The decision, and why

The brief's rule is: use an alias only if it succeeds and reports the release that served it; otherwise pin the release. No alias resolves — three independent alias spellings were refused by name in the endpoint's own error body — so the seats pin typesafe/jev-1.14. The pinned id answers and reports its build as typesafe/jev-1.14-20261014, so the endpoint does carry the release field an alias scheme would need; what is missing is alias resolution, not release reporting.

Release tracking: the dated build is recorded beside the spend

The pinned id fixes what a seat asks for, not what answers. The probe above shows the endpoint reporting its build in the response's own model field (typesafe/jev-1.14-20261014), and that field was being discarded by _parse_decisions_response. A re-point of the same id at a newer build would then have left every cost record unchanged.

It now reaches the cost record. call_decisions and acall_decisions hand the reported build to an optional record_release sink, and judgment._book_cost — the single place a decisions call's cost becomes a tracker entry — books it under the same step as the spend. The return value stays a two-tuple, so no caller had to change, and a tracker that keeps no releases still books the spend. PipelineCost carries the pair in steps and releases.

The decisive property is the one a test can state: the same pinned id served by two different builds leaves steps bit-identical and shows only in releases.

The build reaches the graph row, one record per call

A tracker that only accumulates totals cannot answer the question the record exists for: which build answered, on what day, for what spend. The release therefore travels to the :LLMCost node itself.

One record per call is the property that matters. A batch is many calls: decide_batch fans a step's states out under one concurrency bound, and two states in one step may be served by two builds. The charge hook fires per call and carries that call's own model and release, so nothing collapses into a step total. The suite asserts it directly — two calls under one step through a bound tracker produce two charges with two different releases.

A free answer is still an answer. The endpoint admits a zero usage.cost, and pricing a reservation from a spend already reported as zero is meaningless — the pool refuses an amount of zero outright, so a successful free response would have crashed the stage after the provider had replied. BudgetManager.record_llm_cost_event writes such a call straight to the writer queue: no reservation, no overspend, and the row still carries the build. A negative cost remains an error. Two tests guard the wiring rather than the intent — the enrich worker's tracker must be constructed with a charge sink, and the review_docs Jev charge must stamp model_release — and each turns red when its line is reverted.

The stored row is asserted where it is built: record_llm_cost is the only writer of a :LLMCost node, and the test reads the Cypher parameter set it computes, requiring both llm_model and llm_model_release.

Reading it: which build served which model, per day

MATCH (c:LLMCost)
WHERE c.llm_model_release IS NOT NULL
RETURN date(c.llm_at)          AS day,
       c.llm_service           AS service,
       c.llm_model             AS llm_model,
       c.llm_model_release     AS release,
       count(*)                AS calls,
       round(sum(c.llm_cost), 6) AS usd
ORDER BY day DESC, llm_model, release

A pinned id that was silently re-pointed shows as a second release row under the same llm_model, with the day it started appearing; a seat that never moved shows one row per day. Spend is summed per build, so the cost of a re-point is separable after the fact.
