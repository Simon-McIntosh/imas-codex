Why four embedded answers rank below 30 — Q05, Q12, Q14, Q18

For each of the four §11 questions this traces how _search_code and _search_docs build the candidate list and score in imas_codex/llm/search_tools.py, computes each answering chunk's raw cosine to its question with the same encoder the tools use (Qwen/Qwen3-Embedding-0.6B, 256-dim, the encoder.Encoder the tool passes into both functions), and reports it beside the rank the tool gives it. All reads are bounded by facility_id = 'jt-60sa' (an in-index vector property on code_chunk_embedding and wiki_chunk_embedding).

The pipeline both tools run

  • Vector index and k. Code: code_chunk_embedding (COSINE, 256d) with an in-index cc.facility_id = $facility pre-filter. The index is queried with max(k*2, 50) candidates but only the top k are kept, so the vector cut that reaches the merger is exactly k: 30 at the §9 label depth and 200 at the depth the census calls the tool. Docs: wiki_chunk_embedding, same pre-filter, same k-wide cut. This matters below: the cut width, not the scoring, decides whether an answer is reachable at all.
  • Keyword term (hybrid boost). A fulltext/BM25 query over code_chunk_text / wiki_chunk_text with the raw question string, limited to k*2. An existing candidate is re-scored score = 0.7*vector + 0.3*BM25 + 0.1 (unbounded in the BM25 term); a text-only hit enters at its BM25 score alone. Code adds a third source, code_example_desc_embedding (cut max(k,20), child chunks inherit the parent score, max(vec,ex)+0.05); docs adds document_desc_embedding and image_desc_embedding.
  • Final sort. sorted(set(ids), key=score, reverse=True)[:k]. Because the sort key is a set, ties carry no defined order — a fresh process hunts them differently. Docs then apply a title-match boost min(1.0, score + 0.1*overlap) to the already-selected top-k; because it runs after the cut it can saturate displayed scores but cannot change which chunks were selected.

The change, and what it measures over the 18 §9 questions

Because the burying mechanism differs by answer (a low cosine for Q05, an unbounded BM25 term for Q12, a saturated tie for Q14/Q18), three candidate changes were applied in a scratch copy of the scoring only — no repository code is touched; the scratch copy lives in fusion_eval.py and is scored by final_metrics.py:

  • bounded fusion — the BM25 term is normalised by the query's own maximum before weighting, so no chunk dominates the vector term by raw magnitude: 0.7*vec + 0.3*(BM25/max BM25) + 0.1.
  • reciprocal rank fusion — the vector list and the BM25 list are fused by rank, 1/(60+r_vec) + 1/(60+r_bm25).
  • saturating keyword term — the linear BM25 term is replaced by a bounded one, 0.7*vec + 0.1 + 0.3*BM25/(BM25+1), so the keyword contribution is capped at 0.3 and cannot swamp the [0,1] vector score.
  • reserved vector slots — the current top 10 is kept exactly and the next slots (ranks 10–29, or 10–49 for the 50-slot variant) are filled with the vector leaders not already shown. This reorders nothing displayed, so it cannot cost an existing hit.

Two reading notes, added at merge. First, the current-order nDCG@10 here (0.420) is not comparable with the 0.246 of the §9 rerank prototype. This probe re-ran the search, counts 17 questions as answerable because the retrieval-miss census located answers for Q05, Q12, Q14 and Q18, and scores the 303 unlabelled top-10 slots its variants bring in as 0, a lower bound that weighs against the reweighting variants. Their failure of the Q16 control stands regardless, because that control tracks known-relevant chunks. Second, the reserved-slot lift ranks and the Q12 column are 0-based positions, so each reads one lower than the rank a reader counts: Q14 lands at 15, Q18 at 11 to 13, and Q12 at 85, 141 and 60.

New candidates a change introduces are labelled by the same rule as labels.json (is the candidate the answer named by answer_contains), using the answering artifacts named in the retrieval-miss census for Q05/Q12/Q14/Q18; a top-10 slot neither labelled nor an answer artifact scores 0, so a reweighted variant's figure is a lower bound. The nDCG@10 figures are at the §9 label depth (k=30). The Q12 column gives the rank of shtrd.f chunk_1 at k=200, where it is a candidate; at k=30 it is not one — the vector cut is 30 wide and its facility rank is 49.

Every reweighting fails the declared preservation control; only the reserved-slot change meets it. Bounded fusion, RRF and the saturating keyword term all lift Q14/Q18 by demoting the BM25-carried relevant candidates: Q16's known relevant chunks leave the top 10 entirely under bounded fusion (0.968 → 0.000), under the saturating term (→ 0.000) and, partly, under RRF (→ 0.412). The saturating term fails the control alone and combined with reserved slots (0.000), because it changes the top 10 the control inspects. Their mean figures are also below the current order (0.309 / 0.379 / 0.349 vs 0.420), though 610 top-10 slots across the reweighting variants are unlabelled and scored 0, so those are lower bounds rather than a demonstrated loss.

The reserved-slot change leaves the top 10 of all 18 questions identical to the current order — so the mean nDCG@10 is unchanged (0.420) and Q16 is preserved exactly (0.968) — and it lifts the answered docs chunks into top 30: use_compiler-en.html:chunk_0 to rank 14 (Q14) and use_login-en.html chunks 4, 5 and 0 to ranks 10, 11 and 12 (Q18). Q14's called-depth rank was 181 and Q18's 164, so both enter top 30 from below it. The tension it avoids is structural: a single monotone reweighting that raises a zero-BM25, high-vector answer above a BM25 candidate must demote the BM25-carried answers, so it cannot both lift Q14/Q18 to rank 0 and keep Q16. Reserved slots add recall instead of reweighting.

Q12 (shtrd.f, facility vector rank 49) is reached by neither the saturating term nor the 50-slot reservation: at k=200 the 50 reserved slots place it at rank 59 (a top-30 window holds only 20 leaders after the top 10), and at k=30 it is not a candidate at all (the vector cut is 30 wide). Q05 (eqgrd.f) cannot be reached by any scoring change — cosine 0.438 is the 442nd of 907 code chunks, outside every candidate cut. Both need a candidate-generation change (a wider k, a lexical term, or a better encoder) that this node did not measure.

Recommendation for the deploy node: the reserved-vector-slot change, reserving at least 20 vector leaders at ranks 10–29, applied to the docs tool. It is the only measured change that meets the preservation control: it costs the existing top 10 exactly nothing (mean nDCG@10 0.420 unchanged, Q16 0.968 unchanged across all 18 questions), and it moves the two answered docs chunks into top 30. No combination does better — the saturating term, alone and with reserved slots, and the two reweightings all score below the current order and all fail the control. Q12 and Q05 are out of reach of any scoring change at these depths and are handed back as candidate-generation work.
