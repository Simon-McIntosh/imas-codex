Why four embedded answers rank below 30 — Q05, Q12, Q14, Q18

For each of the four §11 questions this traces how _search_code and _search_docs build the candidate list and score in imas_codex/llm/search_tools.py, computes each answering chunk's raw cosine to its question with the same encoder the tools use (Qwen/Qwen3-Embedding-0.6B, 256-dim, the encoder.Encoder the tool passes into both functions), and reports it beside the rank the tool gives it. All reads are bounded by facility_id = 'jt-60sa' (an in-index vector property on code_chunk_embedding and wiki_chunk_embedding).

The pipeline both tools run

  • Vector index and k. Code: code_chunk_embedding (COSINE, 256d) with an in-index cc.facility_id = $facility pre-filter and an ANN cut of max(k*2, 50). Docs: wiki_chunk_embedding, same pre-filter, same cut. At the tool default k=10 the cut is 50; at the answered-questions depth k=30 it is 60.
  • Keyword term (hybrid boost). A fulltext/BM25 query over code_chunk_text / wiki_chunk_text with the raw question string, limited to k*2. An existing candidate is re-scored score = 0.7*vector + 0.3*BM25 + 0.1 (unbounded in the BM25 term); a text-only hit enters at its BM25 score alone. Code adds a third source, code_example_desc_embedding (cut max(k,20), child chunks inherit the parent score, max(vec,ex)+0.05); docs adds document_desc_embedding and image_desc_embedding.
  • Final sort. sorted(set(ids), key=score, reverse=True)[:k]. Because the sort key is a set, ties carry no defined order — a fresh process hunts them differently. Docs then apply a title-match boost min(1.0, score + 0.1*overlap) to the already-selected top-k; because it runs after the cut it can saturate displayed scores but cannot change which chunks were selected.

The change, and what it measures over the 18 §9 questions

Because the burying mechanism differs by answer (a low cosine for Q05, an unbounded BM25 term for Q12, a saturated tie for Q14/Q18), three candidate changes were applied in a scratch copy of the scoring only — no repository code is touched; the scratch copy lives in fusion_eval.py and is scored by final_metrics.py:

  • bounded fusion — the BM25 term is normalised by the query's own maximum before weighting, so no chunk dominates the vector term by raw magnitude: 0.7*vec + 0.3*(BM25/max BM25) + 0.1.
  • reciprocal rank fusion — the vector list and the BM25 list are fused by rank, 1/(60+r_vec) + 1/(60+r_bm25), which removes the raw BM25 magnitude entirely.
  • reserved vector slots — the current top 10 is kept exactly and ranks 10–29 are filled with the facility's vector leaders not already shown. This reorders nothing already displayed, so it cannot cost an existing hit; it guarantees the vector-leading chunks appear within top 30.

New candidates a change introduces are labelled by the same rule as labels.json (is the candidate the answer named by answer_contains), using the answering artifacts named in the retrieval-miss census for Q05/Q12/Q14/Q18; a top-10 slot neither labelled nor an answer artifact scores 0, so a reweighted variant's figure is a lower bound.

The reweighting changes lift the buried answers but fail the declared preservation control; the reserved-slot change lifts the docs answers into top 30 and meets it. Both bounded fusion and RRF move Q14 and Q18 to (or near) rank 0 — and, for the same reason, evict the BM25-carried relevant candidates of Q16, Q06, Q09 and Q13. Q16's known relevant chunks leave the top 10 entirely under bounded fusion (0.968 → 0.000) and only partly survive under RRF (→ 0.412), so the declared control — that Q16 keeps its relevant candidates in the top 10 — is not met by either reweighting. They also lower the mean, though 303 of the 540 top-10 slots the three variants produce are unlabelled and scored 0, so those two figures are lower bounds.

The reserved-slot change is the one that satisfies every stated requirement. It leaves the top 10 of all 18 questions identical to the current order, so the mean nDCG@10 is unchanged (0.420) and Q16 is preserved exactly (0.968) — and it lifts the answered docs chunks into top 30 from where the tool buries them: use_compiler-en.html:chunk_0 to rank 14 (Q14, was 1734) and use_login-en.html chunks 4, 5 and 0 to ranks 10, 11 and 12 (Q18, was 1330). The tension it avoids is structural: any single monotone reweighting that raises a zero-BM25, high-vector answer above a BM25 candidate must demote the BM25-carried answers, so it cannot both lift Q14/Q18 to rank 0 and keep Q16. Reserved slots add recall instead of reweighting, which is why they lift the answers without moving a displayed result.

Two answers need a stage ahead of scoring. Q12 (shtrd.f) is inside the vector cut (rank 49) but outside the 20 reserved slots, so the slack must come from a saturating BM25 term that bounds the tail without renormalising it away — the change that carries the least risk to Q16. Q05 (eqgrd.f) cannot be reached by any scoring change: its cosine (0.438) is the 442nd of 907 code chunks, outside every candidate cut, so it needs a lexical or encoder change at candidate generation.
