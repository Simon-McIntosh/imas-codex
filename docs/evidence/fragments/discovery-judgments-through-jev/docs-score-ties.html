Docs search ordered its score ties arbitrarily

_search_docs in imas_codex/llm/search_tools.py ranked wiki chunks with a plain descending score sort, so the many chunks that share a hybrid score came back in set-iteration order, and the unbounded keyword term let keyword-only chunks enter at their raw BM25 score (9 to 16, far above any cosine) and take the whole window. Both effects push the facility's nearest embeddings out of the returned results. Decision: deploy the raw-cosine tie-break alone. The tie-break makes the tie order deterministic and changes no reported mean. The reserved-slot variant (keep the top 10, fill the rest of the k=30 window with the facility's vector leaders) was measured and not deployed: it lowers nDCG@30 and, on three of the six docs questions, lower recall@30. The two answering chunks the reserve lifted into the window are left for the Jev rerank, which the plan sizes over a pool larger than 30.

The defect reproduces

  • Q14 — the answering chunk jt-60sa:use_compiler-en.html:chunk_0 (raw cosine 0.856) is not in the tool's returned k=30 window, because keyword-only chunks outscore the whole clamp tie block.
  • Q18 — the answering chunk jt-60sa:use_login-en.html:chunk_0 (raw cosine 0.882) is likewise absent from the returned window.

Measurement

The measurement reproduces the tool's own wiki-chunk order instead of re-deriving it: docs_ties_eval.py calls the same stage functions _search_docs calls and merges them with the tool's own rule (0.7*vec + 0.3*bm25 + 0.1, rounded, with the title boost excluded because _search_docs fixes the chunks' order before it applies the display boost and never re-sorts). Fidelity is asserted before any number is reported: the reimplemented order's top 30 overlaps the rerank prototype's stored docs candidate set at q13 30/30, q14 30/30, q15 30/30, q16 27/30, q17 30/30, q18 30/30 — the shortfall on q16 is the one passing document that occupies a slot in the prototype's 30. nDCG uses a fixed ideal set taken from the whole label pool, so changing which chunks are in the window cannot inflate the score. Relevance labels are the rerank prototype's labels.json (keyed by candidate id) plus the answering chunks it does not cover, labelled by the same rule and written to reports/imas-codex/docs-score-ties/new_labels.json. Because the deployed change is in _search_docs, every mean is over the six docs questions q13–q18, not over all 18.

Per-question recall@30, fixed denominator

recall@30 is the number of a question's relevant chunks inside the returned k=30 denominator the question's whole relevant pool (from the merged labels), so a variant cannot gain by shrinking the window. The reserve lifts the Q14 and Q18 answers in (0.00 → 1.00) but drops recall on Q13, Q15 and Q17 — the decision rule was to keep the reserve only if recall@30 does not fall on any docs question with known answers.

The deployed tie-break leaves the result untouched where it can be read: the displayed top 10 is bit-identical to the current order on every docs question, so nDCG@10 is unchanged (0.4076), nDCG@30 is unchanged (0.5298), recall@30 is unchanged (0.6667), and Q16 stays at 0.9675. Its whole effect is that the tie order within a saturated hybrid score is now deterministic by raw cosine rather than by set-iteration order — a bare tie-break cannot move the Q14/Q18 answers, because they sit inside a score tie that the keyword-only chunks outrank as a block, so they remain outside the returned window. The reserve was rejected: it lowers the docs mean nDCG@30 from 0.5298 to 0.4784 (q13 0.6457 to 0.3026, q15 0.9058 to 0.5320, q17 0.6596 to 0.4372) and lowers recall@30 on Q13, Q15 and Q17 while raising it only on Q14 and Q18, so the mean recall@30 falls slightly (0.6667 to 0.6646) and the decision rule fails. The window problem — the two answers that neither the plain order nor the tie-break can surface — is deferred to the Jev rerank, which the plan sizes over a pool larger than 30 (its answer eqgrd.f sits at merged rank 85, for example).
