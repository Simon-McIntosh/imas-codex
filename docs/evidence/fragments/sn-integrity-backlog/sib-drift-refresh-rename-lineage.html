A DD path move that lineage explains is a rename, not a documentation reset

The startup DD-source drift refresh compared a name's stored source_path snapshot against the terminal path its producing source resolves to, and appended a source_path delta whenever the two differed. Every such delta was counted as content drift, so the refresh steered a documentation refine and reset the name's docs — even when the Data Dictionary had only renamed the path. This node makes that comparison read RENAMED_TO lineage: a snapshot path that is a direct or transitive ancestor of the resolved terminal is a rename.

Mechanism

  • The detect query now returns lineage_rename_explains, an EXISTS subquery over (sn.source_path)-[:RENAMED_TO*1..12]->(t0) with t0.id = n.id, so the flag is answered by the graph for each row.
  • _source_deltas carries that delta with "rename": true; the delta is still reported, so the record still names the move.
  • requires_steering excludes a rename-flagged source_path delta and nothing else, so units and documentation deltas steer exactly as before, and a path change no lineage explains still steers.
  • The drift record's renamed verdict, and therefore the summary's renamed counter, is true for a lineage-explained move even when the source anchor already sits on the terminal path.
  • A rename-only drift takes the existing re-stamp branch: the snapshot is written to the terminal path, so the next run is a no-op rather than a second false drift.

Measure: read-only live dry run

Both arms are refresh_drifted_sources(dry_run=True) against the live graph from a git archive of revision 55af2a7ff with the main checkout's .venv.

The count does not fall, and that is a measurement about the live population rather than about the predicate: a read-only probe over the same bindings counts 3247 whose snapshot path differs from their resolved terminal, and 0 of them are reachable from the snapshot along RENAMED_TO.

The zero is instrumented, not assumed. The same predicate returns true on a pair known to carry the relation — charge_exchange/channel/identifier reaches charge_exchange/channel/name and …/description — while the drifted pairs return false because their snapshot nodes carry no outgoing edge at all (for example edge_profiles/ggd/j_parallel_viscosity/r, which has no RENAMED_TO neighbour and is not the ancestry of the mhd/ggd/j_r/values terminal it resolves to). The graph holds 2864 RENAMED_TO edges, so the relation is present and the empty line is about these rows.

What this node therefore fixes is the classification, not today's count: a lineage-shaped move no longer resets documentation. The 1061 live drifts are not lineage-shaped — their snapshot paths are stale, non-lineage identities — so a residual of 1061 genuine deltas remains, and the documentation-reset risk those rows carry is not retired by this node.

Tests

  • Five tests in tests/standard_names/test_source_refresh_rename_lineage.py: a lineage-only move steers nothing and counts one rename (and re-stamps the terminal path); its delta carries "rename": true; a lineage move plus a unit change still steers; a path change with no lineage still steers; and the detect query still asks the graph for the flag.
  • Gate: tests/standard_names default tier, both arms from a git archive of the same revision with the main checkout's .venv. Base 22 failed / 8627 passed; head 22 failed / 8632 passed (the five new tests). The failing-id sets are byte-identical, so this node adds no failure.
  • Negative control: reverting the three source lines that implement the lineage check makes the lineage-only fixture steer a docs reset again; 3 of 5 tests fail, including test_lineage_only_move_steers_no_docs_reset_and_counts_one_rename.

Limits and notes

  • The shared .venv does not carry pytest-xdist, which the gate command needs. A uv sync --extra test against the main checkout was refused as a read-only file system under the worker fence, and duplicating the environment is not permitted, so the gate ran with an ephemeral overlay (uv run --no-sync --with pytest-xdist), which installs nothing into the shared environment.
  • This node does not explain why 3247 snapshot paths are stale non-lineage identities, nor whether the refresh should re-stamp those without steering; that is a separate question with its own census.
