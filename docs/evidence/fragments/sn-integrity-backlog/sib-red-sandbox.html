sib-red-sandbox: the suite without a writable /tmp or a Git checkout

Two sandbox artefacts held 36 ids of tests/standard_names/ red. Both are test scaffolding, so both are repaired in the tests. No product code changed, and the export's refusal of an untimestamped manifest is untouched.

Reproduction before the repair

Both were reproduced at base 966f3d965 before anything changed, and again afterwards as this node's negative control (36 ids, 36 failures).

  • S1. In a user namespace with a read-only tmpfs on /tmp, test_cli_export.py gives 14 failed, 5 passed, each failing with OSError(30, 'Read-only file system') from imas_codex/cli/sn.py:4484. The same 14 also fail in the parallel gate against a writable /tmp, because eight workers share the one literal /tmp/stg.
  • S2. In a tree extracted with git archive 966f3d965, the 22 export ids give RuntimeError: export provenance timestamp unavailable: run from an imas-codex Git checkout or set SOURCE_DATE_EPOCH for an archive/install export, raised at imas_codex/standard_names/export.py:2656 and reached from run_export writing its manifest with require_provenance=True (export.py:3753).

The refusal is correct product behaviour: a cut that cannot state when it was generated is not reproducible, and tests/standard_names/test_export_determinism.py asserts it directly. Nothing in the product changed for these 36 ids.

What changed

  • test_cli_export.py takes its staging root from a staging fixture built on tmp_path, so each test owns its directory and no test writes to a path it does not own.
  • A pinned_export_provenance fixture in tests/standard_names/conftest.py sets SOURCE_DATE_EPOCH; the eight export test modules that drive a real export use it through a module-level autouse fixture. The pinned value is the reproducible-build stamp, which is the documented archive path, not a weakening of the refusal.

Gate

Two git archive trees, base 966f3d965 and head e8e7376a5, each with its own --basetemp, running tests/standard_names/ on default markers with -n 8. Each tree imported the module it ran: python -c "import imas_codex; print(imas_codex.__file__)" printed the tree's own imas_codex/__init__.py, and each gate log's header names that path, the cwd it resolved from and the literal command.

  • Base arm: 101 failed, 8419 passed, 15 skipped, EXIT=1.
  • Head arm: 65 failed, 8455 passed, 15 skipped, EXIT=1. An earlier head arm at c464126e3 read 66 failed; the id that differed is the flake below.
  • All 36 ids present in the base failure list and absent from every head list: 14 S1 and 22 S2 fixed, nothing of mine left red. Compared set-wise against the base list, the final head arm adds zero ids.
  • One id, test_harmonize_apply.py::test_apply_reports_no_fall_when_no_member_scores_worse, failed in the first head arm only and in no base arm. It was then run three times per arm, each time from its own freshly extracted archive tree of base and of head: 1 passed in all six runs. That file references neither the new fixture nor any module this node changed (grep -n "pinned_export_provenance\|SOURCE_DATE_EPOCH\|from tests.standard_names" test_harmonize_apply.py prints nothing), and the only shared file touched is tests/standard_names/conftest.py, which gained a non-autouse fixture. The id is therefore an order-dependent flake under -n 8, not an added failure.
