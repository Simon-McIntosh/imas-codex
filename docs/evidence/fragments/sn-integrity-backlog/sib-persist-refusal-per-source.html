A refused compose winner now costs its own source, not the compose pool

The rerun run (SLURM 1308283) ended EXIT=1 with 23 generate_name pool processes failed, every one of them on RuntimeError: rich standard-name write rejected an exact-claim winner. The refusal behind every one of them is the standard-name writer's grammar gate dropping the batch's only candidate. The persistence path treated the resulting count mismatch as a batch-level fault, so a candidate the writer would not mint took the whole compose batch with it. It now attributes that refusal to the source the candidate came from: the other winners in the batch finalize, the refused source is released through the claim-fenced failure writer carrying a last_error that names the candidate and the refusal, and a refusal the writer cannot attribute still fails the batch.

What the persistence path does now

  • A winner missing from the finalize batch is attributed by candidate identity. If the writer did not return that candidate's id, the suppression is the writer's per-candidate refusal: the source is recorded for release and the rest of the batch finalizes.
  • The refused source's provisional PRODUCED_NAME reservation on its pending identity is deleted inside the same transaction, so the pending stub reads as unowned and the next attempt may adopt it. The stub node itself is not deleted.
  • After the batch's effects commit, each refused source is released through mark_sources_failed — the existing claim-token-fenced failure writer — with last_error reading rich standard-name write refused candidate '<name>': the writer refused to mint this identity, so the source produced no name. The writer increments the attempt count and parks the source at failed at the claim cap.
  • A candidate the writer accepted and that nonetheless produced no finalize entry has no attributable source state, so it still raises rich standard-name write rejected an exact-claim winner and rolls the batch back.
