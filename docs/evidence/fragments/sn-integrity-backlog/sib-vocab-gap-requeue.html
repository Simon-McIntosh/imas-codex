How the sources left vocab_gap

The repository's own status-transition path is the startup maintenance call retry_vocab_gap_sources_on_grammar_change (imas_codex/standard_names/graph_store/graph_audits.py): a source whose recorded vocabulary signature differs from the live one is returned to extracted for one compose attempt under the new vocabulary. It ran at 2026-11-10 21:18:38 UTC in a peer pipeline's startup, and its own log line is the transition receipt: "vocabulary-bump retry - 15 of 15 parked source(s) returned to 'extracted' under the current ISN vocabulary". This node wrote no Cypher: it read the live state, recorded one receipt row per source (transition.json) and reran the sources through the CLI.

The before column of the outcome table is this node's own census read of each source, taken before the rerun launched; the vocab_gap status the sibling run recorded is the prior run's state, not this run's starting point, and the two differ because the retry pass above had already moved every source to extracted by the time this node read them.

Deviation, stated plainly. The retry pass is keyed on the vocabulary signature, not on per-source resolvability, so it also revived the parked source whose token this release did not add: summary/global_quantities/current_alignment/value. It therefore stood at extracted rather than at vocab_gap as the node's brief expected, and it was excluded from the rerun scope. It now reads extracted still, reporting current_alignment_factor as the missing physical_base token, and re-parks as vocab_gap on the next vocabulary bump.

Controls

  • Positive control. The same query that returns a deciding spelling absent returns thermal_shield and tangency as GrammarToken rows of 0.11.0, and the same spellings absent at 0.10.1, so an absence is reported on an instrument shown to see.
  • Negative control. sourced, one of the five tokens the lead accepted for a later release, returns no row at either release, and the parked source's missing token current_alignment returns none at 0.11.0 either.
  • Recomputation, and what it does not prove. The runner's check action recomputes every composable/parked verdict and the eligible set and fails if either differs from the stored census. It calls the same classify() the census used, so it guards against the inputs having drifted since the census was written - a changed worklist row, a changed grammar snapshot - and it is not an independent re-derivation of the verdicts. Only the composer's own pre-validation tests those, and it is what the four re-parked sources are reported from.
