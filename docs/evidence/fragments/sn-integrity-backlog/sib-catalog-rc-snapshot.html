Pin equivalence, and why the version string is not the pinned literal

imas-standard-names is an editable dependency: [tool.uv.sources] resolves it to the sibling checkout ../imas-standard-names, and the installed _editable_impl_imas_standard_names.pth points there. That checkout's head ef1bc401e8 is one commit past the v0.11.0 tag 9c9443370d, so hatch-vcs stamps the distribution 0.11.1.dev1+gef1bc401e while the code being imported is the pinned release plus a documentation commit. The measurable statement is that the difference between the pinned tag and the running head is empty for every file the package ships: git diff v0.11.0..HEAD -- imas_standard_names/ prints nothing, zero lines. The version string is a sync artifact; the code is the pin.

The dry run cannot show this refusal

The recipe places a dry run immediately before the cut, and this dispatch required it to exit 0 with no unresolved source finding. It did. The refusal still arrived one step later, and that is not an accident of where the gate happens to sit: the dry-run path does measure the export leg in a scratch tree, but its summary prints only the batch identity, the batch size, the unmatched-source count and the artifact path, and it returns 0 whether or not the measured export failed a gate. So a rehearsal can be green on a cut that the same command refuses outright, which is how this node reached the cut believing its preflight was complete. The gap is in imas_codex/cli/sn.py, outside this node's write fence, and is reported rather than changed here.

The rehearsal did name the one unmatched source in its count, and the export report names it: camera_x_rays/camera/camera_dimensions, the recorded_refusal row above. The first attempt's fragment recorded that count as unexplained; it is now explained.
