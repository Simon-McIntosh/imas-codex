What the supersede landed with

The supersede in sib-last-source-supersede stopped a write draining a name's last producer, and its review raised four gaps in the code that does it. Two were correctness risks in the very path meant to stop source loss:

  1. Ordering. stage_claimed_generated_candidates superseded the former holder towards a staged candidate whose PRODUCED_NAME edge was not written in that transaction. A rich write that failed afterwards left a name superseded towards a successor that produces nothing — the loss the node exists to prevent, moved one step later.
  2. One builder, one receipt. _MOVE_SOURCE_BINDING_CYPHER carried its own copy of the drained test and the supersede update, already diverging from source_invariant.py, and the clause wrote its own StandardNameChange instead of using record_standard_name_change.

Two were coverage gaps: the claimed-attachment writers (_supersede_released_bindings and the released_out plumbing) and mark_sources_attached had no test at all, and the [refine] case re-ran the retarget primitive under a different operation label without ever entering persist_refined_name.

Mechanism

The staged writer now binds first, exactly as the attachment writer does: the winner's PRODUCED_NAME edge is MERGEd inside stage_claimed_generated_candidates's transaction before _supersede_released_bindings runs, and the claim stays extracted so the rich write still consumes the same fence. The supersession and the binding therefore commit or roll back together, and the successor always produces the source it is named successor for.

supersede_drained_name_cypher now writes only the retirement and the (new)-[:REFINED_FROM]->(old) edge and returns the pair it superseded. record_supersede_receipts records each pair through record_standard_name_change, the repository's single StandardNameChange writer, on the caller's transaction, so the receipt and the retirement commit together. _MOVE_SOURCE_BINDING_CYPHER embeds that clause rather than a copy.

Two integrity defects in that first attempt are repaired here.

  1. Receipt atomicity. _move_sources_to_name ran the move and its retirement in one autocommit query and then wrote the receipt in a second, so a failure between the two left a superseded name with no StandardNameChange — the state the receipt exists to make auditable. The move, the supersession and the receipts now run inside one transaction opened on the caller's client, and a failure rolls all three back.
  2. A suppressed receipt. The retarget guard skipped the last_source_supersede receipt for a drained name whenever the caller asked for no ordinary change receipt, which is every refinement and supersession retarget. A drained name is its own lifecycle event, so the receipt is written whatever record_change says.
