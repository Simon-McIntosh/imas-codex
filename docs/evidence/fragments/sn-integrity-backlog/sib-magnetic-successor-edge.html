The edge type, stated plainly

The dispatch note names this measure as a REFINED_FROM edge. The write is HAS_SUCCESSOR, and the difference is the graph's, not a shortcut. REFINED_FROM is the refinement lineage and is scalar per name: the schema documents refined_from as “a refined name has exactly one direct predecessor”. The accepted successor already carries its own REFINED_FROM parent, so a second one would break that cardinality. HAS_SUCCESSOR is the schema's supersession lineage — “the target of the receipt-stamped HAS_SUCCESSOR edge written by a signed supersede mutation” — which is exactly what §48 asks for: a signed supersede with a receipt-carrying successor edge. The prior read-back counted zero successor edges on this name while it already carried one REFINED_FROM, so the measure has been counted on HAS_SUCCESSOR throughout.
