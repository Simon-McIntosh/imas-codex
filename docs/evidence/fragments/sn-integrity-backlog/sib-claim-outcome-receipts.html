sib-claim-outcome-receipts — every ended claim writes its outcome on the source

A composition claim could end without leaving any per-attempt record. The source carried a single last_error, overwritten by whichever writer touched it last, so a failure census could not tell five refusals from one, nor a batch that raised from a source that was genuinely refused. This node adds StandardNameSourceClaimAttempt, an append-only receipt reached from the source by HAS_CLAIM_ATTEMPT, and writes one entry inside each claim-ending statement.

The stored-status writer maps the batch status to an outcome in one place (claim_outcome_for_status), so failed and vocab_gap record refused, a skipped source records skipped, and a source a batch hands back as extracted records requeued. None of them is reported as a refusal, so a census cannot count a skip as a failure.

Writers left out, and why

  • release_generate_name_claims / release_generate_name_failed_claims (graph_claim_release.py, called from worker_common.py) releases a claim for retry on the empty- description and worker-failure paths. It is outside this node's write scope, so it appends no receipt; a claim it releases reads as an attempt with no outcome entry until a later node or the sweep accounts for it.
  • graph_catalog.py's PRODUCED_NAME merge is claimed by the sibling node sib-persist-refusal-per-source, so this node leaves it untouched. The produced outcome is recorded at the attach statement in graph_source_bindings.py, which is the fenced writer that ends the claim.

Bounded, append-only, and fenced

The entry identity is claim-attempt:{source}:{claim_seq}:{outcome}. A source holds one claim per sequence number, so the MERGE is idempotent under a deadlock-retried write, and the record is bounded by the claim-attempt cap: a source that fails five times holds five entries and is then parked capped. Every entry carries claim_seq, which the append's WHERE clause compares against the source's live sequence, so a delayed duplicate worker cannot append a receipt to a claim it no longer holds. The append runs on the same client or transaction as the statement that ends the claim, so the receipt and the ending are one unit of work.

A source the sweep parks carries no live sequence to key on, so its entry is keyed on the attempt number (claim-attempt:{source}:attempt-{n}:capped). The attempt number the receipt stores is never taken from the caller's row: the append reads sns.attempt_count off the source inside the same statement, so a writer holding a stale count cannot record it. The append reports the number of receipts it created rather than the number of MERGE matches, so a retried write reads zero.

One transaction per ending

Each receipt is written inside the unit of work that ends the claim, so a claim cannot end without its outcome. In persist_claimed_attachments and in the binding lock (_lock_claimed_name_bindings, shared with the catalog writers) the append runs on the caller's own transaction, before the statement that clears the claim token. persist_claimed_source_outcomes opens one transaction and writes the receipt and the status write in it together, so the receipt and the status it describes commit or roll back as a pair. The batch-failure path is the one deliberate exception: it runs after the batch has already raised, holds no client, and records best-effort so a graph fault cannot replace the exception that ended the batch.

Negative controls

Mutations, all run against the node's own test file. Removing the claim_seq from the entry — the defect this round fixed — leaves the append fenced on a null and every token-carrying receipt unwritten: 12 tests fail and the run exits non-zero. The declared mutation removes the append from the batch-failure release; run against it, test_compose_batch_records_the_receipt_before_it_reraises fails and the run exits non-zero.

Both would have passed a suite that asserted the entry a writer built rather than the receipt the graph stored. Every outcome test now drives the real writer through a graph double that implements the append's fence and its create-once identity, and one -m graph test runs the real statement against a disposable Neo4j: it creates and links a receipt, stores the source's own attempt count, proves a stale sequence writes nothing, and removes its probe nodes.

Three further mutations remove the append from one writer at a time — persist_claimed_attachments (produced), the binding lock (released) and persist_claimed_source_outcomes (stored outcome). Each leaves one test failing and no receipt, so no writer can lose its append without a test noticing.

A third guard covers the sweep's own call. Replacing _orphan_sweep_tick's append with a no-op fails test_the_sweep_tick_issues_the_capped_append and nothing else, so the tick cannot park a source without leaving its receipt.
