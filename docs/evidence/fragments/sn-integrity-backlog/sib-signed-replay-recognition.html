Signed supersede replay recognition

A signed supersede that names a successor rewrites the predecessor's node properties, and those properties are folded into the participant snapshot the manifest digest covers. The digest the next preview computes therefore differs from the one the apply was minted under, and the receipt lookup keyed on that digest missed the receipt and re-admitted the row. The replay recognition is now keyed on the authority payload instead, and it verifies each admitted row's postcondition against the digest its receipt and successor edge were minted under. Previewed live from the worktree's code, the committed authority from the sibling node now returns already_applied with zero changes.

Mechanism

The supersede mutation writes node properties and stamps a successor edge in one statement (imas_codex/standard_names/signed_manifest.py):

4830  elif kind == RepairMutationKind.supersede.value:
4834          else "target.source_paths = [],"
4842      SET target.superseded_from_stage = coalesce(
4843            target.superseded_from_stage, target.name_stage),
4844          target.name_stage = 'superseded',
4845          target.status = 'superseded',

The edge is written by _supersede_successor_edge_write (line 2367):

2380    MERGE (target)-[edge:HAS_SUCCESSOR]->(successor)
2381    SET edge.receipt_id = $receipt_id,
2382        edge.signed_at = datetime()

Those node properties are part of the participant snapshot _participant_snapshot folds (properties(node) plus property_fingerprint), so the manifest digest _digest(manifest) covers them. The successor edge itself is not in the snapshot: the relationship snapshot set _RELATIONSHIP_TYPES is {"PRODUCED_NAME", "HAS_PARENT"}, and HAS_SUCCESSOR is not among them. So the property rewrite alone moves the digest. The sibling node's authority wrote no new property values — its four targets were already superseded — so its digest was stable and its receipts were found by digest; the rows of a fresh supersede are not.

The fix keys the receipt lookup on the authority payload rather than the manifest digest, and verifies postcondition against the minted digest:

3763      authority_payload_sha256: $payload_sha256

The caller now consults _replay on the preview path, not only on the apply path (apply_signed_*, line 7886), so a preview recognises an applied row without writing.

What a second apply would have written

Under the digest the next preview computes, a second apply would have written a second receipt and no second edge. The receipt id is _change_id(manifest_sha256, row_id) (sn-change:signed-manifest:<digest>:<row_digest>), so a new digest mints a new node id and _write_receipts MERGEs a second StandardNameChange beside the first. The edge is MERGE (target)-[edge:HAS_SUCCESSOR]->(successor) SET edge.receipt_id = $receipt_id, an upsert on the one edge, so the second receipt only overwrites edge.receipt_id — no duplicate edge. The correct outcome for a replayed row is neither write: a preview returns already_applied with changed = 0.
