Landing record: a signed successor edge for the scalar-only superseded names

Three superseded names reach their successor only through the superseded_by scalar and carry no HAS_SUCCESSOR edge and no REFINED_FROM route (flux_due_to_thermal_fusion, area_of_flux_surface, lower_energy). Each was driven through the signed supersede mutation in imas_codex/standard_names/signed_manifest.py via apply_signed_manifest, never with ad-hoc Cypher. A signed apply wrote 2 of the 3 edges, each carrying its minting receipt id; the third row was withheld by a mandatory guard and is reported below.

First dry run (instrument)

Bounded read over the superseded population (2,163 names) selecting those whose scalar names an existing successor, with no incoming REFINED_FROM and no outgoing HAS_SUCCESSOR. It lists exactly the 3 expected names, so the instrument sees the relation it must: 

MATCH (n:StandardName {name_stage:'superseded'})
WHERE n.superseded_by IS NOT NULL AND n.superseded_by <> ''
  AND EXISTS { MATCH (t:StandardName {id:n.superseded_by}) }       // scalar names a live successor
  AND NOT EXISTS { MATCH (n)<-[:REFINED_FROM]-(:StandardName) }      // no lineage route to a successor
  AND NOT EXISTS { MATCH (n)-[:HAS_SUCCESSOR]->(:StandardName) }    // no successor edge
RETURN n.id AS id, n.superseded_by AS successor ORDER BY id
-> [flux_due_to_thermal_fusion, area_of_flux_surface, lower_energy]   // 3 rows

Live edge counts (instrument control)

The same instrument reports both relations, so a query blind to either would read a zero count rather than an empty worklist. Before apply: HAS_SUCCESSOR 48, REFINED_FROM 1850. After apply: HAS_SUCCESSOR 50 (+2), REFINED_FROM 1850 (unchanged).
