A DD build now records IDS and array-of-structures renames as RENAMED_TO edges

The rename record read only a field's change_nbc_previous_name, so a whole IDS renamed between DD releases (gyrokinetics to gyrokinetics_local) and an array of structures renamed between releases (ec_launchers/launcher to ec_launchers/beam) left no RENAMED_TO edge. The old node existed, its successor existed, and nothing connected them, so a name whose producing source sat on the old path had no successor to move to.

What changed

  • imas_codex/graph/dd_lifecycle.py: dd_path_index reads the IDS element's change_nbc_previous_name and seeds the old prefix with it, so every descendant path of a renamed IDS maps to its new spelling exactly as a renamed structure already did.
  • imas_codex/graph/build_dd.py: _detect_container_renames matches a removed and an added STRUCTURE/STRUCT_ARRAY node under the same parent by their shared descendant paths. A pair is accepted only when the match is unique on both sides and clearly ahead of the runner-up, so an ambiguous pair is left alone rather than guessed. Matched paths become one path_renamed event at the subtree root and stay out of the add/remove events. collect_renamed_to_mappings merges the packaged path map, the detected container renames and the DD-derived renames into the shape _batch_create_renamed_to writes.

Scope

This node records the edges. Moving a binding onto the successor, or superseding when a live name already holds it, is the reconcile-side rule and belongs to a separate node. The DD build was exercised through its rename-record and writer functions; a full build on a disposable graph is the integration check the coordinator owns.
