The transaction-shaped double, and the ids that were reading the wrong surface

These suites failed for one reason: each persistence path runs its compare-and-set statement inside gc.session().begin_transaction(), so a double that answered only gc.query recorded nothing and returned nothing for the statement under test. The same transaction also issues its hold scan, its link scan and its source-invariant read between the compare-and-set pair, which misaligned every positional row queue. Both defects sit in the doubles, not in the stages or the claim tokens: a double given a session and keyed answers passes the confirmation the brief asked for on the eighteen test_review_docs_stages.py ids unchanged.

One double, one statement log

tests/standard_names/graph_transaction_doubles.py adds transaction_double(rows=None, *, by_statement=None). It extends the existing RecordingGraphClient; query is a MagicMock, and the session transaction's run forwards to the same query, so double.query.call_args_list carries every statement the code sent, in order, whichever surface it used. by_statement maps a marker substring to the rows that statement answers, so a test locates the statement it asserts on by shape rather than by call index, which is the difference between a suite that survives a new statement in the transaction and one that reads the neighbouring answer.
