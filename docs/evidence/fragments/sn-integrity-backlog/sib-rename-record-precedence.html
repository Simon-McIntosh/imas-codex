The DD's own rename annotation outranks the packaged path map

collect_renamed_to_mappings assembles the RENAMED_TO record from three sources, and the packaged path map was inserted first and then never overwritten, because the two later sources used dict.setdefault. The docstring states the opposite order (packaged map lowest, the current DD's change_nbc_previous_name annotation highest), so a stale target in the packaged snapshot shadowed the DD's own annotation and a container rename. The record was assembled with the wrong successor, and a removed path's name would be rebound onto the stale path instead of the annotated one.

Reproduction at base

A probe at 2c9ea5cb passed a packaged entry mapping one path to a stale target, and a DD annotation mapping the same path to the current target: 

UV_PROJECT_ENVIRONMENT=/home/ITER/mcintos/Code/imas-codex/.venv PYTHONPATH="$PWD" \
  uv run --no-sync python -c "<probe: packaged=stale, dd=annotated>"

AssertionError: DD annotation shadowed by packaged/container map: packaged/stale — the packaged target won. A second probe with only a container rename and a DD annotation on the same path returned container/a, so the DD annotation lost at both levels.

What changed

  • imas_codex/graph/build_dd.py: the container-rename and DD annotation loops now assign over the packaged map instead of setdefault-ing into it, so precedence runs packaged < container < DD annotation, as the docstring already stated.
  • tests/graph/test_dd_rename_precedence.py: five tests — a stale packaged entry no longer shadows the DD annotation; the DD annotation outranks a container rename; a container rename outranks the packaged map; a packaged entry still survives where no other source names that path; and all three sources contribute their own paths.
