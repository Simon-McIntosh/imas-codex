In Cypher, x.status <> 'v' is null, not true, when x.status is null, so a row carrying no status silently drops out of any guard written that way. Eight such comparisons remain in provenance_lifecycle.py (2), graph_store/graph_parent_lifecycle.py (2), graph_store/graph_source_bindings.py, attachment_audit.py, review/holds.py and discovery/code/workers.py. Each now decides the case in the query text and states why in a comment, so a future reader can see which reading the guard intends.

The eight sites and what a null status means

SiteReading of a null statusWhy
provenance_lifecycle.py source-migration apply, source.status <> 'stale' not the excluded value — the source migrates with its cohort The clause excludes a proven stale tombstone only, and the same source already counts as a live producer in the source invariant (coalesce(source.status, '') <> 'stale'). Excluding it here made the invariant's producer count and the migration's cohort disagree, and the moved-set size check then failed the whole migration anonymously.
provenance_lifecycle.py exact-source reset apply, source.status <> 'stale' unknown, so excluded — and the exclusion is stated twice The manifest declares the exact expected_status it is resetting, and the equality on the line above already drops a source without one. The coalesce states that the stale clause adds no second route in. Behaviour is unchanged, so this site is pinned rather than fixed: its test asserts the refusal names the source.
graph_store/graph_parent_lifecycle.py candidate finder, structural_source.status <> 'stale' not the excluded value — the parent is a reconstruction candidate The guard admits a parent whose structural source is absent or not a tombstone. A source with no status is not a proven tombstone, so leaving the comparison null excluded the parent from reconstruction forever.
graph_store/graph_parent_lifecycle.py structural seeding, existing_source.status <> 'stale' not the excluded value — seeding proceeds Same reading as the candidate finder, on the write that follows it; the MERGE then adopts the row with coalesce(sns.status, 'composed').
graph_store/graph_source_bindings.py compose-hint decision, CASE WHEN sns.status <> 'extracted' unknown, so excluded — source_not_extracted Only a source proven to sit at extracted may take a compose steer. A null CASE fell through to the later branches, so a status-less source was reported eligible and would accept steering it never earned.
attachment_audit.py live producer count, live_producer.status <> 'stale' not the excluded value — the producer is live This is a positive selection of producers. Null excluded a real producer, so a name backed only by status-less sources read as sourceless — the same defect the source invariant carried.
review/holds.py hold dismissal, hold.status <> 'dismissed' not the excluded value — the hold is dismissible Only an already dismissed hold refuses a second dismissal. A hold with no status has not been dismissed, so null silently made it undismissable and dismiss_hold returned False.
discovery/code/workers.py ingested mark, sf.status <> 'failed' not the excluded value — the file is marked ingested Only a recorded failure withholds the ingested mark. A file with no status was never recorded as failed, and null left it unmarked so the batch reported zero updates.
