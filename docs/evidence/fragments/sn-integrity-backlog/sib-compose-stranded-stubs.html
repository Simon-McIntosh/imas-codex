sib-compose-stranded-stubs — composing the seven pending stubs that stranded their DD sources

Outcome: blocked — two of the seven landed; the remaining five are refused by a binding collision, and a second scoped attempt landed nothing because every claim aborted in the transactional finalize. Composition now adopts an unowned pending projection stub on the path that actually writes a composed name, so two sources bound their own stub and reached accepted (radial_coordinate_of_reflector, vertical_coordinate_of_reflector). The sourceless draft population fell from seven roster names to five — not the export gate's blocking set, which listed none of them before or after; see the correction below. The remaining five still refuse with candidate "…" has non-bindable name_stage "pending", and every one of them is a DD path whose own IMAS node projects onto that pending stub — so the refusal is not a projection it cannot see, and the condition that still fails is answered by neither the graph state nor the recorded message. A second scoped attempt, after unparking the six again, landed nothing at all: every generate_name batch died in the transactional finalize (RuntimeError('source claim changed during transactional name persistence'), nine of nine). Both are recorded below rather than guessed at; neither is a doubled read.

The cause, at its file and line

A composition candidate could not bind a pending target unless the claim that created it owned it, so each attempt generated a name, collided with the projection stub, released the claim, and counted the attempt against the cap. The chain, at the revision this node read (base b6bd5682b):

  • imas_codex/standard_names/graph_store/graph_foundation.py:98 — _STABLE_BINDING_NAME_STAGES is {drafted, reviewed, accepted, approved}; pending is not among them.
  • imas_codex/standard_names/graph_store/graph_source_bindings.py:1026-1036 (base revision) — lifecycle_bindable admitted a pending target only through an own provisional reservation, which a projection stub does not carry.
  • imas_codex/standard_names/graph_store/graph_source_bindings.py:1237-1266 (current revision) — the refusal releases the claim, retains attempt_count, and writes standard-name binding collision: candidate "…" has non-bindable name_stage "…" at composition attempt N.
  • imas_codex/standard_names/graph_store/graph_cost_and_claims.py:213 — _MAX_COMPOSE_CLAIM_ATTEMPTS = 5. At the cap, imas_codex/standard_names/orphan_sweep.py:118-120 parks the source failed. Until this node's merge that statement overwrote last_error with the bare cap message; it now appends ; last refusal: …, which is why the refusal text below survives parking.

The sourceless-name generator. Those three lines compose one loop: a generated candidate that lands on its own pending projection stub is refused by the binding lock (graph_source_bindings.py:1237-1266), the attempt is charged against the cap (graph_cost_and_claims.py:213), and at the cap the source is parked (orphan_sweep.py:118-120) — while the stub it collided with keeps no PRODUCED_NAME edge and stays a sourceless live name, listed in the draft population the export reports. Every trip round that loop manufactures one more live name with no source. The repair belongs to sib-adopt-pending-projection-stubs, which this node merged and measured; the loop is named here as a finding, not fixed here.

The recorded state also carried a trap: attempt_count read 0 on all nine sources while claim_seq was 5–6, so the cap read as unused beside a parked classification.

Correction: the instrument, not the outcome

The census in this runner first selected a blocking set with row.get("name_stage") != "exhausted". That is not the export gate. The gate blocks only on source_losses — imas_codex/standard_names/export.py:3085-3090:

source_losses = [
    row
    for row in sourceless
    if row["name_stage"] in _SHIPPING_NAME_STAGES
    and row["id"] not in _RELEASE_IDENTITY_HOLDS
]

with _SHIPPING_NAME_STAGES = {accepted, approved}, and the failure raised only if source_losses: (export.py:3108-3119). A non-shipping name is collected into draft_sourceless_names (export.py:3099-3106) and reported on the export; an exhausted name is dormant (export.py:3091-3098). The seven were all pending — a draft stage — so none of them could sit in the gate's blocking set at all, and the earlier headline gate_blocking 7 → 5 on this page measured the draft population under the gate's name.

What remains, and why

Five stubs stay pending with no producer, so the export still reports them, and they stay in the draft population. The refused claim emits non-bindable name_stage "pending" — the message that means the adoption predicate was false — yet every condition that predicate tests reads as satisfied in the graph: the claimed source is source_type='dd', the stub carries no reservation and no claim token, no PRODUCED_NAME edge reaches it, and the source's own FROM_DD_PATH node holds a HAS_STANDARD_NAME edge to exactly that stub. Two sources passed the same predicate in the same run. That contradiction is the open question: the refusal message names the one condition the graph says is met, so either the predicate reads a property the census does not, or the exception is not granted on the branch that composes those five. Resolving it needs the claim's own batch record, not another run.

A second defect surfaced in run 2 and then stopped run 3 completely: RuntimeError('source claim changed during transactional name persistence') — raised at imas_codex/standard_names/graph_store/graph_catalog.py:2510-2513, where the batch finalize asserts that the set of sources it just finalized equals the set it intended. In run 2 it fired ten times against twenty-five generation calls; in run 3 it fired nine times and every generate_name batch aborted, so processed was 0 and the run exited 1. It is the reason the second attempt landed nothing new, and it is independent of the collision above: the sources reach the persistence write and are then lost by the finalize, which is also what the five pending stubs' absent producing edges look like from the graph side.
