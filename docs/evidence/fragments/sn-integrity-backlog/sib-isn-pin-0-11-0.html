imas-codex pinned to ISN 0.11.0 and the graph grammar snapshot synced to it

Both imas-standard-names pins in pyproject.toml moved from ==0.10.1 to ==0.11.0 (lines 18 and 186, the core dependency set and the catalog-preview extra). The editable sibling-checkout override in [tool.uv.sources] is unchanged, so the lock continues to resolve the package from ../imas-standard-names. The graph's grammar snapshot was then synced to 0.11.0 through the repository's own grammar-sync path, sync_isn_grammar_to_graph() in imas_codex/standard_names/grammar_sync.py — the same helper that sn run's startup auto-sync, sn clear's re-seed and the hatch build hook call. No Cypher was written by hand.

Lock

uv lock re-resolves the tree at the new pins and exits 0 with no change to uv.lock. That is the correct result and not a missed refresh: an editable path source records neither the requirement specifier nor a resolved version in the lock, so the lock's only imas-standard-names entries are the three references already present — the root project's dependency list, the editable source record, and the package block whose source = { editable = "../imas-standard-names" } stays as it was. The resolution was re-run from a scratch copy of the bumped pyproject.toml placed beside a symlink to the sibling checkout, because this worktree has no ../imas-standard-names of its own; the relative source text in the result is identical, which is why the diff is empty.

Why argmax_with_respect_to is not a GrammarToken

argmax_with_respect_to is an operator, not a vocabulary token. In the 0.11.0 artifact it is declared in imas_standard_names/grammar/vocabularies/operators.yml as an indexed unary-prefix operator, and it is exposed through get_grammar_context()["grammar"]["vocabularies"]["operators"] (52 operators in 0.11.0, this one present with kind: unary_prefix, precedence: 20, indexed: true).

The grammar snapshot's graph spec does not carry the operator registry. Its keys are exactly version, segment_order, segments, templates; _grammar_context_token_rows() flattens only vocabulary_sections, and vocabulary_sections has no operator section (its 22 segments are the closed-vocabulary segments). The graph confirms this is a standing property rather than a 0.11.0 regression: no operator token has ever been a GrammarToken in any synced version — queries for derivative_with_respect_to, time_derivative, maximum and flux_surface_averaged return zero rows across every version. Codex reads operators from the in-process grammar context (imas_codex/standard_names/audits.py), never from the graph.

Making an operator a graph token therefore needs a channel that does not exist: either a GrammarSegment the closed-vocabulary order does not define, or a new node label and sync statement in grammar_sync.py. Both are product-source changes outside this node's write scope, so this read-back is reported here rather than forced. The token is a token of 0.11.0 and reads back as such through the package's own operator registry; it is not a GrammarToken of any release.

Environment follow-up. The shared project environment's editable install still carries 0.10.1 dist metadata, because it was built at the 0.10.1 cut and a worktree must not re-sync an environment shared with peer sessions. That does not undo this sync — the startup auto-sync compares the active content digest, and the installed checkout's grammar files hash to the same sha256:5eac6bca… written here, so it no-ops. It does mean the next deliberate re-sync from that environment would label the same content as 0.10.1. Run uv sync from the main checkout once this pin lands, so the runtime package version reads 0.11.0.

Controls

  • Positive control. The same read-back query that returns the negative-control token empty returns power_convertor with two rows at 0.11.0, so the instrument is shown to see what is present before an absence is reported.
  • Negative control. sourced — a spelling the lead accepted for a later release — returns no row as a 0.11.0 GrammarToken, and no sourced: entry exists in the 0.11.0 vocabularies (its only occurrence in the artifact is inside a comment in qualifiers.yml).
