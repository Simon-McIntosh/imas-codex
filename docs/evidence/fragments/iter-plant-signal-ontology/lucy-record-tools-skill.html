A skill that routes record finding through Lucy's direct tools

The project skill .claude/skills/lucy-records/SKILL.md tells an agent to answer with icp_search_records, icp_get_records, the version, relationship and folder tools before reaching for the chat tool, and confines the chat tool to a question that needs documents read and an answer written. It carries the traps each tool states about itself and four worked searches: signal lists, self-description documents, documents naming one PBS node, and one document's versions. It documents the relation to the repository's own read-only client, whose guarded session refuses any method outside the sign-in exchange except GET and HEAD (iter_codex/discovery/icp/client.py:33). It changes no source and no test.

The wrong field name, and the refusals that make the traps demonstrable

The declared check was run against the wrong field name the skill most plausibly tempts an author into: "version" reads like the document's version but is not a declared property. The live call returns a refusal that proves the field name matters, and the live answer below is the primary evidence — not a claim that a draft contained it. The stored result is:

{"status": "error", "items": [],
 "error": {"code": "invalid_projection", "retryable": false, "details":
   {"code": "unknown_properties", "record_type": "Document",
    "unknown_properties": ["version"],
    "declared_properties": [..., "current_version", ..., "last_version",
      "last_version_state", "version_state", ...],
    "source_read_attempted": false}}}

Two facts come out of that one refusal: the declared name is current_version, and source_read_attempted: false means the call read nothing before rejecting the request. The corrected recipe, with current_version, returned status: "success" with two rows carrying current_version, version_state and file_type.

The second trap was measured the same way. pbs is readable on Document and is not a query field, so a predicate on it is refused rather than silently ignored:

{"status": "error", "items": [],
 "error": {"code": "invalid_query", "retryable": false, "details":
   {"reason": "Unsupported field/operator: pbs/eq; this kind declares no query
    field named 'pbs'. It takes: uid, folder, title, description,
    document_number, file_type, creation_date, ..."}}}

That is why the skill's PBS recipe resolves the node by code, finds candidates by the text fields, and confirms the link by reading pbs back — the only route the schema leaves open.

The mechanical check, and the negative control that found its own blind spot

A gate script compares the skill against the saved live responses: every cited tool name must be in the live tool list, every projected property must be a declared read_properties name of the kind its recipe names, every predicate's field and operator must be declared on that kind's query_fields, and no identity-shaped literal beyond the two invented ones may appear. On the committed skill it reports tools cited: 13, all in live list: True, all declared: True, PBS predicates: [('code', 'eq')], and PASS.

The negative control is a scratch copy of the skill with current_version replaced by version in the signal-list recipe. The first run of that control passed: the gate was reading projections only from prose, so a field name inside a recipe's JSON block was never inspected. That is a defect in the instrument, not a property of the skill, and mutating the input is what exposed it — a green result over an unmutated input had looked like coverage. After the check was repaired to read each recipe's whole JSON object, the same mutation fails:

doc recipe properties: [..., 'version', ...]
all declared: False
FAIL
 - undeclared projection properties: ['version']
EXIT=1

The refusal the server itself returns for the same wrong name is recorded above, so the skill's instruction and the platform's behaviour were each demonstrated rather than asserted.

No real identity in the tracked tree

The skill's examples use the invented UID AB12CD, the invented PBS code 00.AA.BB, and no host, person or document title. Checks run over the file before commit:

grep -Eon '\b[A-Z0-9]{5,}\b' SKILL.md   -> AB12CD only
grep -Ein 'iter\.org|@[a-z]|Dr\.|Mr\.' SKILL.md  -> none
grep -En '[0-9]{2}\.[A-Z0-9]{2}|LC[0-9]|SSEN' SKILL.md -> 00.AA.BB only

Live calls made while writing the skill returned real identities, titles and codes. Those responses were kept under the run directory, outside the repository, and none of their values was carried into the skill or into this fragment.
