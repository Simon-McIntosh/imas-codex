SN Benchmark Evolution Strategy

This HTML migration keeps plan 33 in design / research state. The implementation fraction remains 0.05: the problem statement, phases, and acceptance criteria are explicit, but the code and benchmark integration work were still queued.

§1 — Why the plan exists

The benchmark had converged into a narrow score band and still suffered from single-reviewer bias, sparse and biased anchors, coarse grammar docking, and isolation from the production workflow. Plan 33 exists to make the benchmark discriminate better, mirror production review policy, and become operationally useful.

§3 — Current blockers

  • Reviewer bias persists. Single-model scoring still tilts the benchmark away from real disagreement patterns.
  • Anchor sparsity persists. Most physics domains remain unrepresented in calibration anchors.
  • Workflow integration is absent. The benchmark still lacks graph persistence, status visibility, grammar-sync hooks, and the planned regression gate.

§4 — Plan 34 dependency

Plan 33 directly informs and partially blocks the benchmark-v1 build-out, especially where the eval set wants multi-reviewer consensus, grammar-equivalence scoring, and expanded anchor coverage.

§ Decisions

What should the default benchmark reviewer panel size be?

Use the existing three-seat hosted reference panel for bounded benchmark adjudication. DSv4 itself remains one advisory model and never self-authorizes acceptance.

Should semantic-equivalence consensus lift apply within a batch or across an entire run?

Keep equivalence evaluation within each frozen batch so prompt and cohort instability stays visible rather than being masked by run-wide aggregation.

How often should calibration anchors refresh?

Refresh and version the gold corpus when the grammar/public semantic contract changes; otherwise comparisons lose longitudinal meaning.

Where should the regression baseline live?

Commit the frozen benchmark inputs, expected semantic labels, and thresholds for reproducibility; write measured run results to the established benchmark artifact store.

How broadly may DSv4 review the existing graph after benchmarking?

The local model is effectively free at point of use and can triage thousands of names, but it must not bootstrap its own authority.

Locked by the lead as 6A. After benchmark gates, run the full graph-wide DSv4 advisory census. Outputs are flags and ranked exact manifests only; hosted quorum and governed graph APIs retain authority.
