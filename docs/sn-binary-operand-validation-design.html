ISN's grammar accepts binary-operator forms whose operands are never checked against the closed vocabulary. Closing that by making the operand parse strict turns nine ISN tests red. This record explains the mechanics, measures four options against the real pinned tests and the real stored catalog, and recommends a layered oracle plus the order its pieces land in.

ISN working tree at 937ea94 (the commit imas-codex pins), catalog export of 2026-07-21 (2223 published names)

1 — The hole, reproduced

A binary form is <op>_of_<A>_<sep>_<B>, where the separator comes from the operator's own registry entry (to for ratio, and for product and difference). Operand A may be any snake_case string at all:

>>> from imas_standard_names.grammar import parse_standard_name
>>> parse_standard_name("ratio_of_wibble_frobnicator_to_square_major_radius")
{"physical_base": "wibble_frobnicator",
 "binary_operator": "ratio_of",
 "secondary_base": "square_major_radius", ...}

wibble_frobnicator is the deliberate nonsense control the convergence gates use, and it passes the single validity oracle. Standing alone it is refused, with a good message:

>>> parse("wibble_frobnicator")
ParseError: residue 'wibble_frobnicator' does not match any physical_base
            or geometry_carrier; nearest candidates: (none)

The escape is a literal fallback that only exists inside the binary peel. parser._try_parse_or_literal tries a full recursive parse of the operand and, on ParseError, returns a synthetic QuantityOrCarrier(token=<the whole string>, kind=QUANTITY) as long as the string is snake_case. Its docstring names the motivating case: binary operands with unregistered compound bases such as magnetic_pressure. The fallback is silent — no Diagnostic is emitted, so nothing downstream can tell a resolved operand from a fabricated one. There is a second, independent fallback of the same shape on the compose side, model._parse_simple_base.

The IR makes the structure explicit. Note that the outer IR carries a synthetic placeholder base — the binary application occupies the operator stack, and the operands are full nested StandardNameIR objects, so the recursion this design needs already exists in the data model:

ratio_of_wibble_frobnicator_to_square_major_radius
  operators: [ binary ratio, separator "to", args:
      [ { qualifiers: [],                        base: wibble_frobnicator }   <-- fabricated
        { qualifiers: [square, major(geometry)], base: radius            } ] ]
  base: placeholder

What must keep parsing

The forms below are legitimate and every one of them resolves its operands strictly, so none of them needs the fallback. They are the acceptance floor any gate has to clear.

FormWhy it is load-bearing
ratio_of_electron_temperature_to_ion_temperature The ordinary case. Both operands resolve as qualifier + base (electron + temperature).
flux_surface_averaged_ratio_of_square_toroidal_flux_radius_gradient_magnitude_to_square_major_radius The equilibrium metric coefficient <|grad rho|2/R2> — a flux-surface average of a ratio, which is a different quantity from the ratio of averages. Landed as 331ef7a.
flux_surface_averaged_ratio_of_square_toroidal_flux_radius_gradient_magnitude_to_square_magnetic_field_magnitude Its <|grad rho|2/B2> twin. Both operands carry a postfix magnitude and still resolve.
ratio_of_electron_to_ion_temperature Base elision. Operand A is the bare qualifier electron; it has no base of its own and borrows operand B's. This is the form the naive gate destroys — see §2.

How much of the stored catalog is exposed

Of the 2223 published names in the catalog export, 23 carry a binary operator. Walking each one's operand IRs and asking whether the operand's base token is a registered physical_base or geometry_carrier, 22 of 23 resolve cleanly and exactly one does not:

product_of_poloidal_current_function
  _and_derivative_with_respect_to_poloidal_magnetic_flux_coordinate
  _of_poloidal_current_function

  operand B -> 'derivative_with_respect_to_poloidal_magnetic_flux_coordinate
                _of_poloidal_current_function'   (fabricated by the fallback)

That single exposure is a genuine parser defect rather than a bad name. The operand is an indexed-derivative application, and it fails to parse standalone because the coordinate index universe (parser._coordinate_universe = geometry carriers ∪ coordinate axes) does not contain poloidal_magnetic_flux_coordinate. It holds normalized_poloidal_flux_coordinate, toroidal_flux_coordinate, normalized_toroidal_flux_coordinate and toroidal_flux_radius — but not the un-normalized poloidal one. The consequence is that a stored, exported, published name reaches the catalog with a fabricated operand, and no layer notices. That is the concrete cost of the silent fallback, independent of any gate.

2 — Why the naive gate fails

The naive gate is one edit: make the operand parse strict. Measured by monkeypatching parser._try_parse_or_literal to return None on ParseError and running the full ISN suite.

RunResult
Baseline, unpatched 1 failed, 1855 passed, 28 skipped, 83 xfailed
Gate at the parse-side fallback only 6 failed, 1850 passed — 5 gate-induced, plus the baseline one
Gate at both fallbacks (parse and compose side) 9 failed, 1847 passed — 8 gate-induced, plus the baseline one

The "10 pinned tests" figure recorded in the robustness plan reconciles as the whole red suite of the both-fallbacks variant (9) plus one more from a slightly different patch point; the gate-attributable count is 8 at both layers and 5 at one. The baseline failure is tests/test_json_schema_contract.py::test_write_entry_schema_to_custom_path, caused by an uncommitted imas_standard_names/schemas/entry_schema.json in the ISN working tree — unrelated to operands, and not touched here.

The failures fall into three mechanically distinct classes, and only the first is about vocabulary at all.

Class 1 — the operand is a fragment, not a name

tests/grammar/test_nested_operator_round_trip.py::test_already_working_names_still_round_trip[ratio_of_electron_to_ion_temperature]

This is the mechanic the plan flagged. The IR is:

ratio_of_electron_to_ion_temperature
  operators: [ binary ratio, separator "to", args:
      [ { qualifiers: [],     base: electron          }
        { qualifiers: [ion],  base: temperature       } ] ]

Operand A is the single token electron, which is a registered qualifier (one of 333) and is not a base at all — it is not in the 160 physical_bases nor the 34 geometry_carriers. Parsing it as a standalone name is correctly an error:

>>> parse("electron")
ParseError: residue 'electron' does not match any physical_base or
            geometry_carrier; nearest candidates: (none)

So "operands must parse as names" is a category error, not a strictness dial. An operand of an elided binary form is a fragment by construction: the base is written once and shared. The test pins the full model round-trip, i.e. that compose_standard_name(parse_standard_name(name)) == name — the elision is part of the canonical spelling, not an accident of it. Under the gate the failure surfaces as UnknownBaseTokenError: Unknown physical_base token 'ratio_of_electron_to_ion_temperature' raised out of parse_standard_name itself: the whole name collapses to an unrecognised base, because with the operand parse refused there is no binary peel and the residue is the entire string.

Class 2 — the operand names a quantity the vocabulary lacks

Four tests, all in test_nested_operator_round_trip.py::TestUnaryOverBinary: test_ir_round_trip_preserves_outer_operator, test_validate_round_trip, test_postfix_over_binary_ir_round_trip, test_flat_model_raises_explicit_error. All four are built on gradient_of_ratio_of_electron_pressure_to_magnetic_pressure and its postfix sibling. electron_pressure resolves; magnetic_pressure does not:

ParseError: residue 'magnetic_pressure' does not match any physical_base or
            geometry_carrier; nearest candidates:
            ['magnetic_shear', 'magnetic_flux', 'magnetic_field']

What these tests protect has nothing to do with the operand. They pin the parser path that terminates operator peeling at a binary: a prefix operator peeled before the binary terminator must stay on the IR operator stack rather than being silently discarded, and the postfix magnitude must bind to operand B rather than to the whole ratio (the trap where postfix operators peel at two sites). They use an unregistered operand incidentally, as a convenient two-word compound. So these four are not evidence against a gate — they are evidence that the fixture must change, or magnetic_pressure must be registered, before a gate can land.

Class 3 — the pinned artifact is an error message, not an acceptance

tests/test_binary_operators.py::TestBinaryOperatorEdgeCases::test_compound_base_with_and_in_name asserts that product_of_supply_and_demand_and_output raises with a message matching "reserved connector word". The rightmost separator split yields physical_base='supply_and_demand', and the model validator refuses it because an operand may not contain the operator's own connector word — a genuine ambiguity rule. Under the gate the name is still rejected, but earlier and with a different message (ParseError on the unresolvable operand), so the regex misses. test_flat_model_raises_explicit_error (match "not representable") breaks the same way. Both are error-contract tests: the verdict is unchanged, the diagnosis regresses from specific to generic.

Adding the compose-side gate to model._parse_simple_base breaks three more — TestBinaryOperatorConnectors::test_product_uses_and, test_ratio_uses_to, test_difference_uses_and — which compose from placeholder operands "a" and "b" purely to assert which connector word the renderer emits. Same class: a fixture convenience, not a semantic claim.

The conclusion that shapes every option below: of the eight gate-attributable failures, exactly one (class 1) describes a form the gate must not reject. The other seven are fixture and error-message contracts. The design problem is therefore narrow — admit the elided-operand shape, and decide where the check lives so that a rejection arrives with a usable message.

3 — Where the validation surface can sit

Four candidate placements in the parse → validate → compose → persist flow. The diagram marks each option's surface; the shaded band is the ISN package boundary.

(a) Recursive operand grammar — operands are full names

Make the operand a recursive non-terminal validated by construction, and delete both literal fallbacks.

  • Pinned tests: worst of the four. It is the naive gate plus a grammar change — 8 gate-attributable failures, and class 1 cannot be fixed by relaxing the gate because the elided operand is not a full name and never will be. Admitting it means the operand non-terminal is not "a name" after all, which is exactly the premise this option rests on.
  • Stored names: 1 of 23 binary catalog names invalidated until the coordinate-universe defect is repaired.
  • Reduction over binary: compatible. Both metric coefficients resolve their operands strictly already.
  • Prompts: largest change. The elision form would have to be removed from guidance and the ~15 ratio-class compose paths retaught to spell both bases in full, which lengthens names for no semantic gain.
  • Verdict: rejected. It buys correctness-by-construction at the price of a spelling the grammar deliberately supports.

(b) Parse-then-validate — permissive parser, fragment-aware oracle

Leave the parser's structural job alone; move the vocabulary question to the layer that already owns it. Two parts:

  1. The parse-side fallback stops being silent. When _try_parse_or_literal fabricates an operand base it emits a Diagnostic(category="vocab_gap", layer="parser", severity="warning") naming the operand token. The mechanism exists and is already used for _at_-locus gaps; ParseResult.diagnostics is the channel. Acceptance is unchanged, so this part is provably zero-blast-radius.
  2. parse_standard_name — the single validity oracle — walks binary operand IRs and admits exactly two shapes, RESOLVED and ELIDED as defined in the diagram legend, rejecting everything else with UnknownBaseTokenError(token=<the operand>).

The ELIDED rule is mechanically checkable and needs no new vocabulary: the operand carries no operators, every underscore-delimited word of its base token is in the 333-token qualifier set, and the sibling operand is itself RESOLVED. A prototype of exactly this rule, run over the real populations, gives:

PopulationOracle verdict
2223 catalog names 1 rejected — the poloidal_magnetic_flux_coordinate operand from §1. Every other name clean.
ratio_of_electron_to_ion_temperature accepted — the class-1 failure does not occur
Both metric coefficients (<|grad rho|2/R2>, <|grad rho|2/B2>) accepted
ratio_of_wibble_frobnicator_to_square_major_radius rejected, naming wibble_frobnicator
ratio_of_substrate_to_electron_density rejected, naming substrate
class-2 fixtures (…_to_magnetic_pressure) rejected, naming magnetic_pressure — the four tests still need their fixture decided (§4)
class-3 fixture (product_of_supply_and_demand_and_output) rejected, naming supply_and_demand — but from the oracle, so the connector-word message can be kept ahead of it
  • Pinned tests: class 1 eliminated by the ELIDED rule. Class 3 preserved by ordering: the connector-word check already lives in the model validator and can run before the operand walk, so its message stays first. The three TestBinaryOperatorConnectors tests are untouched because they exercise compose, and the compose-side fallback is not the gate. Residual: the four class-2 tests.
  • Stored names: 1, and it is a bug the gate should surface.
  • Reduction over binary: unaffected. The walk descends the operator stack, so a reduction wrapping a binary is transparent to it.
  • Prompts: no guidance change required. The rejection reaches the composer through machinery that already exists — see below.
  • Consumer wiring: free. codex's workers._grammar_round_trip_failures already calls parse_standard_name on every composed candidate, catches UnknownBaseTokenError, and routes exc.segment/exc.token into describe_gap(...).guidance. An operand rejection raised as that exception type flows into retry guidance with no codex change at all.

(c) Consumer-side gate only — validate at mint/accept in codex

Leave ISN entirely alone; add the operand walk to codex and call it before a name is minted or accepted.

  • Pinned tests: zero. Nothing in ISN changes.
  • Stored names: the one exposure is caught at the codex boundary, but only for names minted after the gate lands; the already-stored one needs a separate audit pass.
  • Reduction over binary / prompts: unaffected.
  • Cost: it reintroduces the failure mode the attachment guard was built to avoid — a vocabulary rule hardcoded in codex, drifting from ISN. It also leaves ISN's stated single validity oracle wrong: a name the oracle accepts would be refused by a consumer, so "valid" would mean two different things depending on who asks. Any other consumer (the SPA grammar composer, a direct ISN user) keeps the hole.
  • Verdict: viable only as a stopgap if the ISN coordination window is long, and then only with a drift test asserting the codex rule matches the ISN vocabulary.

(d) No gate — strengthen the classifier verdicts only

Accept the permissive parser as correct and invest entirely in making the composer not want to write a bad operand. Codex's _ratio_composition already refuses to guess: a division whose operands do not both cover completely stays absent rather than emitting confident wrong guidance, on the explicit reasoning that a wrong composition costs more than an honest gap.

  • Everything: zero blast radius, by construction.
  • Cost: it treats a soft signal as a hard one. Guidance biases a model; it does not stop one. The single stored catalog exposure was produced with this machinery in place, which is the direct counter-evidence — and nothing here would have flagged it, because the composer never saw a gap: the name parsed.
  • Verdict: necessary, not sufficient. Keep the classifier work; it is what makes a rejection actionable rather than merely blocking. But it is the complement of a gate, not a substitute.

4 — Recommendation and migration order

Option (b), staged, with (d) retained as the guidance half. The parser stays the liberal structural layer it is documented to be, the oracle becomes the single place where "is this name valid" is answered completely, and the rejection reaches the composer through wiring that is already in place. The staging matters more than the choice: two of the four steps are prerequisites, and landing the gate before them is what turns the suite red.

StepWhereWhat landsWhat pins it
1 — make the hole observable ISN grammar/parser.py The literal fallback emits a vocab_gap Diagnostic naming the fabricated operand token. Acceptance unchanged. A test asserting the diagnostic appears for ratio_of_wibble_frobnicator_to_… and is absent for ratio_of_electron_temperature_to_ion_temperature and both metric coefficients. Full ISN suite stays at its baseline.
2 — repair the coordinate universe ISN vocabularies Admit the un-normalized poloidal flux coordinate as an indexed operator's coordinate index, so the one exposed catalog name's operand resolves. This is a vocabulary rotation, not a code change. A test that derivative_with_respect_to_poloidal_magnetic_flux_coordinate_of_poloidal_current_function parses standalone, and that the stored product_of_… name's operands are both RESOLVED.
3 — decide the class-2 fixture ISN tests, or ISN vocabularies Either register magnetic_pressure as a physical_base (it is an ordinary plasma quantity and the parser's own nearest-candidate list has no equivalent), or rewrite the four TestUnaryOverBinary cases onto a registered operand. Rewriting is cheaper and keeps the tests about what they actually pin — peel order and postfix binding — but registering is the better answer if the quantity is wanted. The four TestUnaryOverBinary cases, unchanged in intent: outer operator preserved on the IR stack, postfix bound to operand B, flat model raising "not representable".
4 — the gate ISN grammar/model.py (parse_standard_name) The operand walk: admit RESOLVED and ELIDED, reject otherwise with UnknownBaseTokenError. Runs after the connector-word check so the class-3 message ordering is preserved. Positive: the four §1 must-parse forms plus all 23 binary catalog names. Negative: wibble_frobnicator and substrate controls rejected, each naming its own operand token. Contract: product_of_supply_and_demand_and_output still raises "reserved connector word".
5 — pin and reconcile imas-codex Bump the ISN pin. No gate code: workers._grammar_round_trip_failures already routes UnknownBaseTokenError into describe_gap. Add the binary-operand case to describe_gap's guidance so the message names the operand slot, and run a catalog reconcile so any stored name the new oracle refuses is quarantined rather than re-exported. A codex test that a composed candidate with an unregistered operand produces non-empty retry guidance naming the operand; the export pre-validation pass over the full catalog.

Steps 1 and 2 are independently valuable and carry no acceptance change, so they can land immediately and in either order. Step 4 must not land before 2 and 3. Nothing here is unilateral: steps 1–4 are all ISN-side and go through the coordinated rotation (verify, add, grammar suite, RC, pin bump).

5 — The other grammar-stability holes

Inventory only. Each is a coordinated ISN-side item; none is fixed here.

Unsegmented registry tokens

A token in a vocabulary but in no segment cannot be emitted by any enumerator, so no prompt gallery or composer surface ever offers it. Measured against SEGMENT_TOKEN_MAP (653 tokens across 20 keys) the list is shorter than previously recorded and worth restating precisely. Of the 169 registered loci, exactly two appear in no segment: active_wall_point and beam_path, both type: geometry entries in locus_registry.yml whose geometry/position/path segment keys all resolve to the Position enum, which does not contain them. Of the six locus_qualifiers, upper, lower, inner and outer are reachable through other segments but primary and secondary are in no segment at all — there is no locus_qualifier key in the map. Two corrections to the earlier note: gyrocenter is now segmented (as a subject), and the 36 qualifier tokens that appear in no SEGMENT_TOKEN_MAP key are all bare-prefix operators (square, volume_averaged, time_derivative, …) that live in v.qualifiers by the known IR-qualifier convention and are correctly segmented as operator through the operator registry — not a hole. Recommended fix: add the two geometry loci to the Position enum and add a locus_qualifier segment key, with a drift test asserting that every token in every ISN vocabulary appears in at least one segment or the operator registry — the test is what stops the class recurring.

The qualifier category ordering the prompts cannot see

vocab_loaders.load_qualifier_categories() reads qualifier_categories.yml, which assigns every one of the 333 qualifier tokens to exactly one of 12 categories in file order, and model.py uses that file order to decide canonical qualifier placement. get_grammar_context() — the single context surface the compose prompts are built from — exposes grammar.vocabularies with exactly five keys: coordinate_axes, geometry_carriers, locus_registry, operators, physical_bases. There is no qualifiers key and no qualifier_categories key. So the prompts ask a model to honour a canonical qualifier ordering whose defining structure is absent from the context it is given; the model can only infer the order from the scored examples. This is the same information the canonical-qualifier-order decomposition depends on, so exposing it is a prerequisite for that work rather than a parallel nicety. Recommended fix: add the category→ordered-token-list structure to get_grammar_context() preserving file order, and pin it with a test asserting the exposed order matches the order model.py applies — the two must not be allowed to drift, or the prompt will teach a stacking the validator rejects.

The rho_tor twin carriers

toroidal_flux_coordinate and toroidal_flux_radius are both registered geometry_carriers, both flagged constant_on_flux_surface: true, and both describe rho_tor — the second's own comment says so (toroidal flux radius coordinate (rho_tor)). Both are live in the catalog with overlapping derivatives, which is the concrete cost: toroidal_flux_radius_of_magnetic_axis sits beside normalized_toroidal_flux_coordinate_at_magnetic_axis, and toroidal_flux_coordinate_of_neoclassical_tearing_mode_center beside toroidal_flux_radius_at_pedestal_top — the same physical coordinate, two carriers, and an inconsistent _of_ versus _at_ relation on top. Because each carrier accretes its own derivative family, the duplication compounds rather than staying at two. toroidal_flux_radius is the one the equilibrium metric coefficients are built on, via the toroidal_flux_radius_gradient base. Recommended fix: pick one carrier as canonical — the metric coefficient dependency argues for toroidal_flux_radius — retire the other to an alias, and let the existing deprecation-stub mechanism carry the stored names across. The retirement must be a single rotation covering the normalized variants too, or the twin simply reappears one level up.

6 — Reproducing the measurements

Every number above comes from the ISN checkout at 937ea94 with the catalog export of 2026-07-21. The blast-radius runs patch the fallback from a pytest plugin rather than editing the parser, so the ISN working tree stays clean:

  • Baseline and gated suite runs: uv run pytest tests/ -q, and the same with a plugin that rebinds parser._try_parse_or_literal (and, for the both-layers variant, model._parse_simple_base) to a strict parse.
  • Catalog exposure and oracle prototype: walk every standard_names/*.yml entry through grammar.parser.parse, descend the operator stack for OperatorKind.BINARY applications, and test each operand's base token against v.bases | v.carriers, then against the ELIDED rule (all(word in v.qualifiers) and no operators, with a RESOLVED sibling).
  • Segment coverage: union SEGMENT_TOKEN_MAP.values() and difference it against v.loci, v.locus_qualifiers and v.qualifiers.

No timing figures are quoted. ISN measurements on a login node are dominated by filesystem latency and would be meaningless; nothing in this design turns on performance.
