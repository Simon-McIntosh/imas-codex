Review · ITER plant data

The ITER archive signal structure in the shared ontology

The archive added its signal classes one pass at a time. This reviews them against the shared schema, measures what the live graph holds, and proposes the structure the plant-wide work will write into. It changes no graph node and no relationship.

Method, and what this record rests on

The schema was read from iter_codex/schemas/facility.yaml after the source and generated description separation landed: description now carries the source text, and generated_description with generated_description_source carries a model’s reading of it. That change is commit c92bd8642, present in this review’s base history.

Counts are read from the live graph in one facility-scoped pass per label, with every result bounded by an explicit facility_id and, where a traversal was unavoidable, a finite depth. The read was read-only: no node and no relationship was written, merged or deleted. The measure jobs ran on a compute partition, not on the login node or the fleet node. The base revision is 730b85cd8e937b36a5adec071dc2b74f505125de.

Three deliberate limits. A count is a count of relationships unless the row says signals, and rows that count distinct signals say so. Classes with no ITER population are listed rather than omitted, because their absence is itself a fact the plant-wide work depends on. And the documentation measure in the documentation section is a lower bound against a sample census, not a census of what exists; section 4 of the plan recounts the same population against a fuller one.

The plant-network section is the one part of this record that is not a measurement. This node read no ICP record, so the pipe and cable populations it cites are the coordinator’s reading and the live graph holds no connection nodes; whether the records client can reach those records by GET is left open. The sibling-relation attempt is quoted from the committed evidence at the ref this record names, read with git show and not merged, and none of its counts were re-measured here.

The six problems, each with its resolution

1. Two role vocabularies with no stated precedence

Resolution: keep both axes, state the precedence in the slot descriptions, and give the query filters one combined predicate.

The source-assigned axis (vocabulary_role, five members, with vocabulary_role_source and vocabulary_role_state) is authoritative. It is decided only where a source’s own text names one member of the closed role vocabulary, and a source naming two members leaves the axis undecided rather than choosing. The judged axis (signal_role, six members) is a reader’s hypothesis from the signal’s name, description and glossary, written at enrichment and reset whenever the signal is re-described by reprocessing. The precedence is therefore: where vocabulary_role_state is decided, that member is the signal’s role; otherwise signal_role is used, and it is never presented as though a source had said it.

FacilitySignal is shared, so the resolution is not a rename. What changes is additive: both slot descriptions state their own provenance and the precedence (today they state provenance only), and signal_vector_search_block in iter_codex/graph/domain_queries.py gains an optional effective_role predicate that compiles to the precedence rule, leaving the existing role and vocabulary_role arguments unchanged. The plant search tool and the LLM search tools keep their own filters and gain the same combined filter where they already expose both.

What it makes redundant: nothing. It removes an ambiguity, not a definition. signal_role has no ITER population, so no ITER node changes.

2. Component and control membership each exist twice

Resolution: retire CANDIDATE_PLANT_COMPONENT and IN_ARCHIVE_CONTROL_NODE, with their two scalar mirrors.

The measured identity above is the evidence: the targets agree for every signal carrying both, so this is a no-loss change rather than a judgement about which source is better. The parse-time candidate link and its candidate_plant_component slot retire; the archive-component link and its archive_component slot remain the single component membership. The archive grouping’s function-level control link and its archive_control_node slot retire; AT_CONTROL_NODE and the control_node slot remain the single control membership. The grouping writer stops writing either duplicate.

Both classes are ITER-only, so this is a removal, not an additive change. It makes redundant the four definitions named: one relationship type and one slot per membership axis. The write order it assumes is stated in the migration: the archive grouping must run before any reader relies on a component membership, because the parse alone will no longer establish one.

3. The field-code table is not in the graph

Resolution: add one ITER-only class, ArchiveFieldCode, link signals to it, and retire the private configuration entries.

The table already exists as a value object — FieldCodeEntry(code, component_kind, role, meaning, source, support) — built from graph sources by build_from_graph and written to a private receipt by python -m iter_codex.remote.field_code_table. Its role comes from what a source states, in the order signal-list rows, controls metadata, functional specification; its meaning is a one-line reading declared by hand in the facility’s private configuration under field_code_meanings (69 entries), because a meaning is a human reading of a source’s wording and cannot be derived, and a code whose sources disagree has no entry.

The class reuses no existing shared class: no shared class holds a code and its reading, and reusing StandardName or PlantFunctionCategory would assert a meaning those classes do not establish. It is ITER-only and additive. It carries the entry’s own fields: code, component_kind (optional), role, meaning, meaning_source, support, and a state of established or conflicting, with the conflicting roles and sources recorded on the node rather than dropped. A signal reaches it by the code on its name and the category of its archive component; the entry reaches the row that established its meaning, and through that row the document. The 259 distinct codes (30,031 signals) become at most 259 nodes, and the 69 private meanings move onto them.

New relationships: HAS_FIELD_CODE from FacilitySignal, or through its PlantComponent where the component kind is known, and FIELD_CODE_SOURCE_ROW from ArchiveFieldCode to PlantSignalRow.

What it makes redundant: the 69 field_code_meanings entries in iter_private.yaml and the two MEANINGS_KEY readers in iter_codex/remote/field_code_table.py and iter_codex/remote/signal_vocabulary.py. The private table stops being the only store of a code’s meaning; the graph holds it, with the row it came from.

4. The plant breakdown is linked only through pilot rows

Resolution: bind each first-level control node to its plant node in the graph, and resolve deeper nodes by descent.

Today a control node has no plant link: the only path from a control node to a plant node is through an imported signal-list row, and rows exist for one pilot system (343 rows, of which 334 carry a plant link). The proposal adds an optional plant_structure slot to ControlNode (range PlantBreakdownNode, relationship CONTROL_NODE_PLANT_STRUCTURE), populated for the eleven first-level nodes only, from curated bindings each recorded with the document that states the binding. Deeper nodes inherit the binding by walking PARENT_CONTROL_NODE upward to level one; no deeper node carries its own edge, so the 539 parent links already in the graph are the whole of the inheritance mechanism.

The binding cannot be a rule. The control-path spelling of a first-level node and the top segment of a plant-breakdown code are different vocabularies maintained by different organisations, and the one system whose members are visible in the graph already shows a code whose top segment is shared by unrelated members. The migration therefore reads the curated binding, not the spelling.

What it makes redundant: the pilot row only, as the route to a plant node. The rows keep their own link. No class is reused away; PlantBreakdownNode is reused.

5. Two document classes, and neither holds a catalogued document

Resolution: one shared Document class with optional cataloguing slots; PlantContextDocument is removed and its seven nodes migrate into it.

A signal list that has been found but not read fits neither class today. The shared Document begins its workflow at discovered, which fits a catalogued document, but it holds no version, version state, digest, title or plant reference, and it requires a filename and a file-format document_type that a catalogued document may not have. The plant-context class holds version and plant reference but requires the fetched file’s sha256, so a document cannot exist in it before it is fetched. The two constraints are the defect: one class describes a file, the other a record.

The merged class adds, all optional, so nothing another facility’s node carries is disturbed:

  • source_uid — the native record identity; title — the record’s own title;
  • version and version_state, a new enum of the declared version state including superseded and obsolete, so a stale version is recorded as stale rather than dropped;
  • sha256 — present only once the bytes were read;
  • content_role, a new enum holding signal list, functional specification and supporting reference. This is not document_type, which is the file format and stays;
  • context_system_code, source_system_codes and source_binding_note — the curation slots; and text — extracted body text for an imported spreadsheet;
  • pbs_codes — the plant-breakdown codes the record itself states, whether or not each resolves; and a multivalued plant_structure link to PlantBreakdownNode for those that do.

Two existing constraints relax for every facility harmlessly: filename and document_type become optional, because a catalogued record has neither until it is fetched, and every existing document node already sets both. PlantSignalRow.source_document retargets from PlantContextDocument to Document, so FROM_PLANT_DOCUMENT keeps its name and its 343 relationships. CONTEXT_FOR_PLANT becomes DOCUMENT_PLANT_STRUCTURE, still 7 links.

What it makes redundant: the whole PlantContextDocument class — one class removed and ten slots absorbed — so no second document store remains. What none fits: the extension is to a shared class precisely because a second document class is the problem, so the resolution reuses rather than introduces.

6. Source and generated description share a single slot

Resolution: keep the landed separation; no further change.

FacilitySignal now has description (source), generated_description and generated_description_source, with generated_description_updated_at. The graph confirms the separation is in use and uneven, as expected on an unenriched catalogue: 2,898 signals carry description_source, 190 carry a generated description, and 190 are enriched. The plant-wide enrichment runs will fill both; nothing about the slot is undecided, and the review adds no change to it.

Are the plant-structure class and the PBS one concept?

Yes. The class is the official plant breakdown record, and it should be named for what it is: PlantBreakdownNode.

The live data settles the identity. All 18 nodes carry an official plant-breakdown code, an official record title, a native record identity and the guarded records endpoint that produced them; 16 carry a parent established by the source record rather than inferred from spelling. The topology is a real breakdown tree, from two top-level systems through a handful of children, one branch three deep. No node is derived from a signal name and none is guessed. The class’s own description already says “official plant breakdown record read through the guarded records client”: the identifier and the concept were one all along, and only the name lagged.

What the class is not is the control hierarchy. ControlNode is a five-level parsed structure read from signal and control names, with 550 nodes and 539 parent links; it is parsed, repeatable and spelled, while the plant breakdown is curated, official and titled. Keeping the two apart is correct, and the proposal links them at level one rather than merging them.

The rename is safe because the class is ITER-only, but it is a rename, so it is one atomic change: class PlantStructure to PlantBreakdownNode, its parent relationship PARENT_PLANT_STRUCTURE to PARENT_PLANT_NODE, and the three slots that range over it. No other facility holds a node of the class, so no other facility’s data is touched. If the lead prefers not to churn the name, the alternative is to keep the class name and state the identity in its description, which the description already partially does; the review recommends the rename because the name is the only place a reader will look.

Plant networks: the typed connection

Proposal: add one ITER-only class, PlantConnection, a reified edge between two PlantComponent nodes that carries the medium and the source record stating the connection.

No shared class fits. Nothing in the shared schema is a connection or a network: the classes that reify an edge do so because the edge carries facts of its own, and SignalContextLink is the precedent in this very proposal. Reusing PlantComponent would fold an edge into a node and leave a component that is also a pipe; reusing FacilitySignal or Document would assert a meaning neither has. So the design reuses no shared class, and instead follows the schema’s reified-edge pattern and the existing PlantContextProvenance mixin, which supplies facility ownership and a stable import cohort. Every one of the class’s changes is therefore confined to ITER data.

The class is minimal in what it interprets and complete in what it retains. Every source field the piping and cabling records carry is either on the connection or reachable through source_uid, so the import the pipeline plan owns needs no further schema change for the families the lead named. Nothing on the class is a required set an existing facility could fail; the two relationship slots are optional because a connection whose endpoints cannot be identified is still a real connection (see below).

The medium is recorded with its provenance. The pipe records sampled carried an empty fluid, so an empty medium is not water and not “unknown medium”: it is undecided, exactly as an undecided role is not a role. A cable record’s kind decides electrical; a pipe decides its medium only where fluid states one; an importer may fill medium only with medium_state decided, and every decided medium names the field that decided it. This is the same precedence discipline the review applies to the two role axes, used for the same reason: a later reader must be able to tell a fact the source stated from a gap the source left empty.

What it makes redundant: nothing. It retires no existing definition: no class, slot or relationship in the graph is replaced by it. What it rules out is two alternatives that would each need a further change. It rules out a connected_to list on PlantComponent, which cannot carry a medium, a direction or a source record without becoming a list of strings. And it rules out a class per network, which would need a new class and a new import every time the plant’s media vocabulary grows. One class with a medium enum accommodates the electrical, hydraulic and cryogenic networks in the same store.

Source populations are the coordinator’s ICP4 reading — about 122,500 pipe records and about 253,600 cable records — not this review’s own measurement: this node did not probe ICP, and the live graph holds 0 connections because nothing has imported them yet. A cable record set of that size is also the sensor-to-cubicle trace the plan wants, since the signal cables are among the 253,600.

Identifying a source component with an archive component

The two sides are recognised by the grammar the brief names, and the recognition is a rule rather than a curation. An archive component is the parser’s triple: a control path, a component category letter code, and a component sequence with its leading zeroes. A source component is the record’s functional reference, read the same way: a plant-system code, a function-category code and a sequence — the invented example 00AA00-BJ-1234 splits that way. Both are normalised by the parser’s existing rules and compared segment by segment, and the identity holds only when all three segments agree exactly.

A match links the connection’s end to the existing PlantComponent. Nothing is merged, renamed or rewritten: the component keeps its identity, its signals and its group, and the connection points at it. identity_state records resolved when both ends matched and partial when one did.

No match is the expected case for part of the population, and the design keeps the connection through it. The end’s PlantComponent link is left unset, the raw functional reference and the source’s own component identity stay on the connection, and identity_state records partial or unresolved. Three rules make that safe. A component is never fabricated from a functional reference, because a fabricated PlantComponent becomes a plant group under the sibling rules while every signal-group consumer assumes the parser established it, so an invented group would be an empty group wearing the same label as a real one; a source-only reference also has a source identity of its own, maintained by another organisation, and no attribute of a connection is a claim that the archive holds that component. A reference that matches more than one archive component is not resolved by picking one: it is recorded unresolved with the number of candidates, because choosing would turn a duplicate in the archive into a decided fact. And an unresolved end keeps its port and its raw reference, so a later pass that widens the grammar resolves it in place rather than re-reading the source.

The distinction from the plant-breakdown binding is the reason this one can be a rule. There a control-path spelling is compared with a curated plant-breakdown code, two vocabularies maintained by different organisations, so the binding is curated; here both sides are the functional-reference grammar, so exact triple agreement is evidence the source itself states. The curated part stays: the level-one binding is unaffected, and nothing in this design infers a PlantBreakdownNode from a functional reference.

How the sibling-relation attempt relates

The sibling-relation attempt pinned at refs/keep/relate-sibling-signals relates signals to signals within one plant group, by rule, from the decided vocabulary role and the field codes: six ordered role pairs mapped to three kinds of typed edge (MEASURED_AGAINST, COMMANDS, FLAGS) and two keys, a shared field-code stem of at least two characters or a sole decided quantity candidate. It was delivered as failed for a missing prerequisite, not a defective rule: the stored vocabulary decides 202 roles over 97,525 signals, with no setpoint among them, so the rules establish zero relations; a plant-scope pass in memory decides 1,575 roles including 7 setpoints and is the widening the vocabulary section owns. The relation surface itself was proven on a disposable graph: planned, written, walked from a server, removed, and walked again, with two negative controls failing as they must.

The connection design and that attempt are different edge families and neither subsumes the other. A connection is a component-to-component physical route with a medium and a source record; a sibling relation is a signal-to-signal functional pairing with a rule and a matched key; neither is derivable from the other. They meet at one point, the group: both take the archive PlantComponent as the plant group, which is why the identity rule above matters to both. Importing the networks hardens the sibling grouping rather than competing with it, because one physical component with an archive spelling and a source spelling would otherwise become two groups, and two groups silently suppress every relation across them.

Two constraints follow. A relation stays inside one group: a signal on the neighbouring component is reachable through a connection, and it is not a sibling, so the walk from a component to a connected component must not become an input to the relation rules. And the connection supplies no role: it neither fixes nor depends on the missing prerequisite, and the two can land in either order. The sibling attempt’s decisive finding for this portion of the review is therefore a scope boundary, not a design input — its typed edges are signal-to-signal, and this class adds no signal edge at all.

The documentation behind the proposal

Measure: 11 of 11 first-level control-breakdown nodes that hold at least one catalogued ITER archive signal have at least one signal-list or self-description document found for them — a lower bound of 1.00.

The population is the eleven level-one nodes; each holds at least one signal, so none is excluded by the denominator. The census is the sample at ~/.cache/imas-codex-codac-uda/document-census/signal-lists-sample.tsv: 168 rows found on 2026-11-22 by direct record search — 154 signal-list rows, 9 self-description rows, and five rows of other kinds. The two signal-list pages read were both incomplete, and 23 and 19 rows respectively were withheld by permissions, so the census is a sample of a search that was still running, and the number is a lower bound in two distinct ways: the search was not finished, and the rows it could not read are not in the count.

Of the 168 rows, 97 carry at least one plant-breakdown code (84 distinct codes) and 71 carry none. A row with no code is attributed to a root only where its own title names the system; a row that neither carries a code nor names a system is not attributed, and is one reason the bound is low rather than exact. Attributing a row to a root by code and by title is a support measure, not a claim: section 4 recounts the same population against its fuller census and resolves each document’s own plant reference.

Negative controls

Control A — the class kept unchanged. ArchiveEndpoint keeps all three nodes, and every ITER signal reaches one: all 97,525 signals carry a metadata-archive link, none is unattached, and the relationship types that reach an endpoint are exactly METADATA_ARCHIVE, LISTED_BY_ARCHIVE and DATA_ARCHIVE, all three of which the proposal retains. No ITER node or relationship is left unrepresented by the kept form: the control passes with zero unattached signals and zero unretained relationship types.

Control B — the class it removes. PlantContextDocument is named in eight source files. Every one is assigned a replacement reader in the declared migration map: the bundle builder, the enrichment reader, the generated model, the generated schema context, the schema class definition, and three test modules. The run reports unassigned: []; the control passes. The positive control for this kind of check is in the same run: the grep that finds the nine sites is the one executed, not a list written by hand, so the check reports the sites that exist rather than the sites remembered.

Both controls are read-only, log to the run directory, and are reproduced by negative_control.py. Neither writes a node or a relationship.

What this review does not settle

  • The exact curated binding of each first-level root, and the plant node for each: the migration records it with the document that states it, per root. The census carries a plant-breakdown code for 97 of its rows, covering six of the eleven roots; the other five roots’ documents are attributed by title.
  • Whether the extracted text on a catalogued document should instead go through the shared chunk path. The merged class keeps it as one optional slot so the row importer keeps working; the alternative would move the pilot rows’ source text into chunks, which is larger than this review’s mandate.
  • The per-kind resolution of a field-code entry where two component kinds genuinely disagree. The class records the conflict and the migration decides whether such a code links from signals at all; it is a data question the 259 codes answer.
  • The full census and its hand checks, which are the plan’s section 4.
  • Whether the project’s records client can read the piping and cabling records by GET. This node did not probe ICP, so the record proposes a class the plan’s import will read by a route that is not yet proven; the class does not depend on the route, because it holds the source’s own identity and every stated property rather than an endpoint-specific handle.
  • The complete medium vocabulary. The pipe records sampled carried an empty fluid, so the enum’s members beyond electrical are proposed and not yet measured; adding a member later is additive, and medium_state keeps an empty field from being read as a member.
  • Whether a port ever needs its own class. The connection records the port identities the source states and interprets none of them, because a port node with no other attribute would duplicate a string already on the connection. A port record kind imported later, with facts of its own, is an additive class rather than a change to this one.
