3 - Proposed surface for imas-codex discover FACILITY

One command, imas-codex discover FACILITY (the bare group the lead chose, which host.py's _HostGroup routes to a hidden sequence subcommand when the first token is not a known subcommand). Its options are the settled spellings below. The per-domain commands remain, narrowed to the stage-specific options the sequence does not redeclare.

optionmeaningreplaces
--only STAGE[,STAGE]run only these stages (repeatable or comma-separated)none on discover; matches sn run --only
--skip STAGE[,STAGE]run every stage except thesenew; --skip is not on sn run
--flushdrain pending work in every stage without seeding new workthe discovered absence of a drain mode

Stage names are the nine the registry orders: paths, code, documents, wiki, signals-scan, signals-enrich, signals-check, candidates, mapping. The names are the command's own stage nouns, so --only signals-enrich reads the same whether it selects a sequence stage or, later, a sn run phase.

  • The five per-domain --*-only flag families retire in favour of --only / --skip over stage names: --scan-only becomes --only paths --scan-only on the per-domain command only if the half remains, and less usefully --skip the rest at the sequence level.
  • The sequence reuses --cost-limit and --time with their existing meaning over a longer invocation, so they add no new concept.
  • Path-or-topic scoping keeps its two distinct spellings on purpose: --focus is a topic and --path-prefix is a path. Merging them would recreate the very one-spelling-two-meanings defect section 2.1 records at sn run.

4 - Evidence for a --flush drain mode in discover

The question is whether discover's stages separate seeding new work from draining pending work, which is what a --flush mode would key on. They do, and the separation is already in the code as a stage's pending-work predicate: a seed stage's predicate asks whether there are source nodes to enumerate; a drain stage's predicate asks whether there are nodes at a given status awaiting the next stage.

Every drain predicate is a status-plus-claim query (status = $X AND claimed_at IS NULL), and the corresponding seed step is the one that creates nodes at status X. So --flush has a clean definition in discover: run the drain half of every stage and skip its seed half. On the sequence's nine stages that means skipping paths scan, code scan, documents scan, wiki scan and signals scan, and running everything downstream.

Two caveats, both visible in the code. First, has_pending_enrich_work and has_pending_check_work swallow a query exception and return False (signals/parallel.py:747, :777); a graph fault therefore reads as nothing to do, so a --flush pass must not treat an empty result as proof of an empty queue without a graph-health check first. Second, the seed half of a stage is not always a separate flag: documents has --scan-only but no --enrich-only, so the drain/seed split for documents exists in the pipeline, not yet in its CLI.

Verdict. --flush has a real definition in discover and should be adopted at the sequence level. It is the same concept as sn run --flush (sn.py:1729) with the same definition: skip seeding, drain what the graph already holds. Discover gains the spelling it lacks rather than a new concept.
